# vigia — Specification

Status: **v0, 2026-07-30.** Source of truth. Code is written against this document; see `CLAUDE.md` § Method for the drift rule.

---

## 1. Problem

Running a full git TUI in a pane beside an AI coding agent, to watch changes as they land, is the wrong tool. A multi-panel git client spends the pane on branches, commits, stashes and status. In a pane already halved against the agent, every panel is a few lines tall and names truncate.

What is wanted: **the live diff, fullscreen, auto-updating, scrollable, mouse-driven, and beautiful.** Nothing else.

## 2. Product class — the load-bearing decision

`vigia` is a **monitor**, not a reviewer. That single distinction generates every budget below, and the budgets are the product.

| | Reviewer | **Monitor (`vigia`)** |
|---|---|---|
| How it starts | Launched per review | Already open |
| Interaction | The point | Rare or never |
| Correct when untouched | No | **Required** |
| Runtime | Minutes | **Days** |
| Latency budget | Seconds | **A frame** |

`btop` is the reference for what monitor-class feels like: you read state from shape and colour, glance away, glance back, and never configure anything.

Design rationale beyond this section is recorded outside the codebase; call `recall` when a decision needs it.

## 3. Invariants

Numbered because tests reference them. Each must have a test that fails on violation. **An invariant without a failing test is a wish.**

Budgets are **absolute** and chosen to be defensible on their own terms, not relative to any other tool.

| # | Invariant | Budget | How it is proven |
|---|---|---|---|
| **I1** | Redraw is **event-driven**, never a fixed timer. No filesystem event and no git index change means no work. | **0 wakeups** while idle | CPU sampled over a 60s idle window; assert no render calls |
| **I2a** | **Re-diffing is incremental** — the frame path never re-diffs a file that did not change. | re-diff cost ∝ what changed, **not** worktree size | Assert the re-diff count and byte count for a single-line edit, across **two** fixtures differing only in changed-file count. One fixture cannot prove it: see §7 |
| **I2b** | **Re-highlighting is incremental** — only changed hunks are re-parsed. | re-parse ∝ edit size, **not** file size | Assert the re-parse count and byte count for a single-line edit, across **two** fixtures differing only in file size. One fixture cannot prove it, for the reason I2a's row gives: see §7 |
| **I3** | **Flat resources over days.** No unbounded growth in RSS, file handles, or temp files. | **RSS drift < 5%** over 24h; **zero** temp files retained | Soak: synthetic edits driven through the whole pipeline, RSS sampled at a fixed count across the window. Scheduled rather than per-commit, and the scheduled window is shorter than 24h for a reason that is not ours: see [`RULINGS.md`](RULINGS.md) and §7 |
| **I4** | **Streams, never buffers.** A frame **builds** only what it draws: diffs, highlighting and reads of file *content* follow the window, never the worktree. The one exception is the diff's **height**, which is counted for every changed file once per tick, without materialising any of it. | **first paint < 100ms** on a 100k-line diff; **counting the height < 16ms** on the same fixture | `criterion`, gated in CI; the counting bound in `crates/vigia/tests/reads.rs`, and `what_a_row_exact_scrollbar_would_cost` records what it was admitted on |
| **I5** | **Correct with zero interaction.** Auto-follows the newest change and scrolls to it, untouched. | — | Scripted edit sequence, snapshot the frame, no input given |
| **I6** | **Legible at 40 columns.** No horizontal overflow, no truncated-to-useless labels. | — | Snapshots at 40 / 80 / 120 columns, plus structural gates in `crates/vigia/tests/legibility.rs` sweeping every width from 1 to 120: no row over-occupies, no hint is cut in half, and every label that lost characters says so |
| **I7** | Startup to first paint is imperceptible. **The first frame draws the diff without colour**, because a grammar's patterns compile on first use at 74-362ms and the frame after it is where that belongs; the reader gets content rather than a blank alternate screen. | **< 50ms** | `crates/vigia/tests/first_paint.rs`, over the **shell's** first paint rather than the core's, asserting the body is full and that nothing was parsed before it asserts the clock. `criterion` does **not** track this shape: `benches/engine.rs`'s `open_and_first_paint` builds no `Highlighter`, which is the core-only measurement §10 corrects |
| **I8** | Terminal restored on **every exit the process can observe**: the quit key (Ctrl-C included), an error return, a panic under `panic = "abort"`, and an externally delivered termination — `SIGINT`, `SIGTERM` or `SIGHUP` on Unix, a `CTRL_C`, `CTRL_BREAK` or `CTRL_CLOSE` console event on Windows. **`SIGKILL` and `TerminateProcess` (`taskkill /F`) are outside it on both**, because neither runs any code the process owns, and they are the whole of what *no design* can reach. Four further cases are excluded by **choice** rather than by the platform, and the difference matters to anyone reading this row as a promise: `SIGQUIT`, whose default dump is the thing whoever sent it asked for; `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT`, which reach a service rather than a console application; and **the second ask**, which takes the default disposition and restores nothing, because a process that has been told once and is still here has to remain killable. The **first** ask leaves the way the quit key does, exit **0** and no message. §11.1 carries both halves. | — | Takeover order and its exact inverse; the partial-failure unwinding; a panic-hook test; escape sequences against DEC's own numbers; and a two-process gate that signals a child and reads back what its guard wrote |
| **I9** | Steady-state frame time holds 60fps under continuous edits. | **< 16ms** p99 | Gated over the **frame path**, not the primitives: a settled frame, one line rewritten before each frame, every file materialised. The caller-side gate **paints as well as collects**, for the reason §7 gives. `criterion` tracks the same shape |
| **I10** | **Glanceability history is bounded.** Churn history is bounded by a fixed window and a fixed cap on tracked paths, independent of how many files the session changed. A path that ages out of the window is dropped entirely. | **≤ 256 paths**, **≤ 120s**, whatever the session changed | Structural, in `crates/vigia-core/tests/history.rs`: a fixture recording **10,000** distinct paths asserts the store sits *at* the cap and that eviction actually ran, and a window of silence empties it. The soak asserts the same over the real process, and **refuses to assert** in a window that reached neither rule. Not in `tests/budgets.rs`: every gate there is a ratio or a duration, and this is a count |

A regression past any budget **fails the build.**

## 4. Scope

**In:** working-tree diff (unstaged by default), event-driven refresh, follow mode, scroll (keyboard + mouse wheel), syntax highlighting, per-file churn visualisation, a pinned file list above the diff (§11.1), responsive layout, theming.

**Out of v1, deliberately:** staging, committing, rebasing, branch or commit browsing, annotations, comment threading, AI features, remote operations. Each is reviewer-class and each would cost an invariant.

**Deferred, not rejected:** multi-worktree view (several agent sessions at once — the strongest differentiator after glanceability, and the most btop-shaped); Jujutsu and Sapling support.

## 5. The differentiator: glanceability

`btop`'s real achievement is that state is readable from **shape and colour** without reading text. `vigia`'s translation:

- per-file **churn sparkline** — change density over time
- a **heat strip** locating change within the file
- live **+/− counters**
- a **visual pulse** on what just changed

This is what makes it a monitor rather than a narrow diff view, and it is where design effort goes once the invariants hold.

### 5.1 What the README mockup commits to

`assets/preview.svg` is the most detailed design artifact in the project, it is **public**, and until now it was specified by a three-sentence caption. A picture in a README is a promise; these are the promises in it, and what each one costs.

Elements the four bullets above do **not** cover are marked **(unspecified)** — they are in the picture, so they are committed, and they had nowhere to be described.

| Element in the mockup | What it needs |
|---|---|
| Header: `vigia · 3 changed` … `watching` | A **mode word**, so there is a set of modes. The changed-**line** total is the §10 header question, and the file count drawn here is not it: a per-file count is free where a repository-wide one is not. **Ruled 2026-07-31: there is no line total** ([#49](https://github.com/breferrari/vigia/issues/49)), so this row is now fully specified rather than partly and the header's facts are exactly three. A repository-wide `+`/`-` is a reviewer's summary of a changeset rather than a monitor's account of what is happening, it puts first paint back in proportion to the size of the diff against I4, and the only way round that is the wake I1 forbids. §10 carries the argument. **Ruled 2026-07-31 and implemented: the set is two**, `watching` and `not watching`. This cell used to say that `watching` "implies at least a settling state and an idle one", and it implies neither: both are durations, and a duration cannot be drawn honestly by a shell that only wakes when a file changes. That is the same wall the pulse hit one row below, and the two words left are the only two states the shell can actually tell apart. The header also draws the **worktree** name on the left where the picture draws `vigia`, which is the first of two deliberate departures from the mockup, the second being §5.1's element split. See §11.1 for both. **Reopened 2026-08-01 on the phrasing rather than the facts** ([#67](https://github.com/breferrari/vigia/issues/67)): the three facts are right and `watching · 3 files` reads as *"watching 3 files"*, a verb with an object, naming a curated set that does not exist and that B6's no-flags ruling puts out of scope. The ladder is the proof they were meant to be independent — the count drops first and the word survives alone — and at the full rung they fuse anyway. The count is also not about the watched thing: this watches the whole worktree, and `3` is what changed inside it. **Ruled 2026-08-02 and implemented: the count moves to the left, with the worktree, and reads `3 changed`; the mode word takes the right alone.** The fix is *adjacency* rather than vocabulary, which is what makes it a layout ruling and not a rewording: §11.1 already lays the footer out by subject, the header has the same three subjects available, and it was seating a tree-fact next to a self-fact. Separated, the count has nothing beside it that a participle could govern. **`changed` rather than `files` is the load-bearing half**, because `vigia · 3 files` on the left would be a *worse* claim than the one being replaced: this repository has more than three files in it, so the count has to name the change rather than the things. Two cheaper alternatives were rejected and are recorded so the ruling is a choice: `watching · 3 files changed` stops parsing as a sentence, since a clause cannot be a participle's object, and costs eight columns on a row this section forbids from taking a second line; `live · 3 files` stops parsing for the same reason and spends the `watching` / `not watching` negation pair ruled one sentence above, which exists so that a reader who has learned one word has learned both. See §11.1 for the ladder, which keeps its order and changes only which side each rung is dropped from |
| Per-file **sparkline** | A **retained time series per file** — samples of churn over a window, bucketed. This is the only unbounded state in the design and it is the one I3 forbids growing: the window and the sample rate are part of the invariant, not a rendering detail. **Ruled 2026-07-31 and implemented: a 120-second window in 8 buckets of 15 seconds, capped at 256 paths, evicted by window and by least-recently-changed.** That is I10, which now has a row above rather than a warning below. One sample per path per coalesced tick, and heights are scaled against the **busiest bucket on screen** rather than per row, because the question a reader asks down a file list is which file is busiest. **Reopened 2026-08-03 on what an *empty* bucket draws** ([#78](https://github.com/breferrari/vigia/issues/78)): the store is fed from the watch, so a file already modified when `vigia` started has no tick behind it, and a reader who opens the pane beside an agent that has written twenty files saw twenty rows and no sparklines. That is the *ordinary* first frame rather than an edge, because the pane is opened precisely when work is in progress, and it left the element §5 names as one of four differentiators absent exactly where it is worth most. **Ruled 2026-08-03 and implemented: a bucket with no writes draws a track, so a file with no history is the all-empty case and draws a full one.** One rule rather than a special case for the cold row, and it is the rule the heat strip's cell below in this table and `Theme::bar_track` already state: this table read the picture that way for the heat strip and never for the sparkline, and `Theme::bar_track` reached the same rule a third time for the scrollbar, which is not a glance element and so is not in this table at all. **It costs nothing, and that is what changed rather than the argument**: [#77](https://github.com/breferrari/vigia/issues/77) reserves the slot at every width whether or not a row can fill it, so the column is spent either way and the only question left is whether it says anything. Nothing is invented by saying it: the track's claim is "no churn in the window", which is true, where backfilling from git would put a fabricated number in the one element whose job is to be trusted at a glance. **The track is `_`, deliberately not the ramp's `▁`.** The heat strip may draw a live slice and its track from the same `█` because colour is its only channel; a sparkline's channel is **height**, so spending the ramp's floor on "no data" would make one write and no writes the same shape and leave colour alone carrying the distinction the lowest block exists to protect. `·` was rejected for sitting mid-cell, which would draw an empty bucket *above* a bucket holding one write. **And the picture was corrected on one row**, which the issue asked for conditionally and which turned out to be unconditional: the dimmed `Cargo.toml` drew eight buckets, seven of them at the ramp's floor height in the ramp's own floor colour `#1f6f3f` and one taller, and dim is the recency ladder's `cold` rung, whose meaning is *nothing is tracked for this path* rather than *this path is old*. A cold row carrying a bucket is therefore a state the tool cannot produce **at all**, not merely at launch, so that row's eight bars are now uniform track. **The picture had no sparkline track in it to read**, which is why `Theme::dark`'s `spark_track` is the one value in that palette chosen rather than read off the file: before this correction every quiet bucket in the picture was drawn in a *bucket* colour. The correction then put one there, and it is drawn in the chosen `#30363d` rather than in the `#21262d` the heat strip on that same row uses, so the artifact and the shell agree. **The two tracks differ on purpose and that is the ruling this cell adds to the one above**: a sparkline track is one stroke where a heat slice is a solid block, and the same value behind a twelfth of the ink reads as absence, which is the state this element exists to stop looking like. Rows 1 and 2 are left alone deliberately and every bucket in them is a written one, so nothing there is the shape this rules against. See §11.1 |
| Per-file **heat strip** | Hunk line-ranges projected onto a fixed number of buckets across the file's length, so it needs the file's **total line count**, not only its diff. Colour rule when one bucket holds both additions and deletions. **Ruled 2026-07-31 and implemented.** Bucket count is **12**, from the picture, which draws exactly twelve; the picture also draws an empty bucket as a **dark track** rather than as a gap, so a drawn strip is always its full width and a reader can see how much of the file is untouched. The one exception is a file with no line diff *at all*, which draws no strip rather than a strip of pure track: §11.1 carries that ruling and why it is the opposite of the sparkline's. A mixed bucket is **yellow**: every alternative paints it as pure, and separating addition from removal by position is the strip's whole job. **Intensity is three steps, matching the picture** ([#11](https://github.com/breferrari/vigia/issues/11)). This cell said two for a phase, because sixteen foreground-only colours hold a normal and a bright of each hue and no third stop, so the ramp was as wide as the palette could draw rather than as wide as the picture asked for. A wider palette closed it. At sixteen colours it is still two, and `ansi` spells that out in its own fields rather than leaving the depth ladder to collapse them by accident. The line count it needs is **free**: see §5.2 |
| Per-file `+42 −7` | Covered. Per-file counters are free — a file must be diffed to be drawn (§10). |
| A **dimmed row** (`Cargo.toml` in the mockup renders fainter than the rows above it) | A **recency gradient**: rows fade as their last change ages. **Ruled 2026-07-31 and implemented as three rungs of one ladder** — pulse, live, cold — read from I10's store; see §11.1. Sixteen foreground-only colours have three intensities to spend, so the gradient is a ramp of three rather than a fade. **Corrected 2026-07-31: the fourth rung is not [#11](https://github.com/breferrari/vigia/issues/11)'s to bring**, and this cell used to say it was. The rung count belongs to `Recency` in `vigia-core`, which has exactly three variants and whose `cold` means *untracked* rather than *old*, so a wider palette draws the same three rungs in better colours and cannot draw a fourth. A real fade needs the store to emit an age fraction, which is a core change with an I10 budget on it. See §11.1 |
| `●` on the diff header | The pulse, but drawn as a **persisting mark**, not a flash. So it has a **decay**. **Ruled 2026-07-31 and implemented: it persists for exactly one tick and cuts rather than fades.** It is the top rung of the recency ladder above, not a second mechanism, and the rung is deliberately *not* a duration: see §11.1 for why a wall-clock decay cannot be drawn without the timer I1 forbids. It marks **every** path in the newest tick, which is what §11.2 B2 said the pulse was for. **Ruled 2026-08-03 and implemented: the dot carries it alone and the `just changed` label is gone**, from the picture as well as the shell, which is the first change made *to* `assets/preview.svg` rather than to the code beneath it. The label was the row's second statement of one fact. The dot is already unique on the screen, it is already the pulse colour, and the row it sits on is already the brightest rung of the gradient one row above, so a reader who has seen the mark once has nothing left to learn from the words beside it: the label read as a caption on a signal that had already been read. **A label is not free on a monitor**, which is what makes this a ruling rather than taste. Text has to be *read*, and §5 puts the whole differentiator in what can be taken from shape and colour without reading; fourteen columns of it sat in the widest rung of the row ladder, so at every width below sixty-five the picture and the shell disagreed about what the pulse even was. The one thing the words did carry that the dot does not is the *name* of the state for a first-time reader, and that is what the README is for. See §11.1 for the rung the ladder loses with it |

Ruled 2026-07-30 and implemented; the engine emits meanings and the shell colours them, which is what leaves the palette to #11. See §11.1 |
| A **tinted row** with a coloured left bar on every added and removed line | A per-row **background**. It is what separates a changed line from a context line in the picture, because the text itself is highlighted identically on both, and it is doing the same work the dimmed row above does: it is how the eye finds what moved without reading. Not drawable at sixteen foreground-only colours, where an ANSI background is a solid block rather than a tint. **Ruled 2026-07-31 and implemented** ([#11](https://github.com/breferrari/vigia/issues/11)): the wash is painted across the whole row, gutter and trailing blanks included, so it reads as a band rather than as a highlight behind some text. **The left bar is the sigil cell, inverted** — the diff hue behind, the row's own wash in front. | Status bar `0.8ms frame` | Instrumenting the render path and drawing the result. Self-referential: measuring and painting the number costs frame time that I9 gates. **Ruled 2026-07-31 and implemented: the p99 of the last 128 completed frames, nearest-rank, sampled every frame** ([#41](https://github.com/breferrari/vigia/issues/41)). The **statistic is p99 because I9 is**, and a readout reporting a median would be silent about exactly the frames the budget exists to bound. **128 because §7 already says why not 30**: at 30 samples a nearest-rank p99 is just the maximum, and at 128 it is rank 127, so one cold outlier is excluded and two are not. That is the behaviour a monitor wants, since the 60.97ms first-touch parse two rows down is a real frame that should not sit on the readout for two minutes. **A frame is the whole turn of the loop** — the wake, the drain, every `Frame::advance` in the batch, `View::collect`, and the paint — which is §7's rule that a gate is written against the caller's whole frame, applied to a readout instead. The number drawn is necessarily the **previous** frames', because a frame cannot include its own paint in what that paint draws; that is honest rather than stale, since it describes completed frames and stays true while nothing happens |
| Status bar `11MB` | A live RSS readout. I3 samples RSS in a **soak test**, never on screen; reading it per frame is a syscall on some platforms. **Ruled 2026-07-31 and implemented: it is read once per painted frame, on all three tier-1 targets, and drawn in `MiB`** ([#41](https://github.com/breferrari/vigia/issues/41)). Three things had to be settled and only one of them was cost. **The read is a syscall everywhere it ships**, which is not what the soak's own helper suggested: `soak.rs` spawns `ps` on macOS and `tasklist` on Windows, and the latter is **42.8ms median** on the reference machine against the 16ms I9 budget, 2.7x it for the read alone. What makes it affordable on screen is that both platforms have an in-process answer through a crate `gix` **already** puts in the graph, so neither costs a new crate: `libc::proc_pidinfo` on macOS and `windows-sys`' `GetProcessMemoryInfo` on Windows, against `/proc/self/status` on Linux, which needs nothing. The soak keeps its subprocess readers where the shipped one has none and is sampled 288 times across a window rather than per frame, which is what that 42.8ms is the reason for. **`MiB` rather than the mockup's `MB`**, because I3's soak is the only other place this quantity is quoted and it is in MiB throughout; two units for one number is two dialects, and a reader comparing the screen against a soak report would read the 4.9% difference as drift. `assets/preview.svg` was corrected to match. **And the number is "as of the last change", not "now"** — the trade that had to be accepted rather than solved: this shell wakes only on a filesystem event, so a pane left open on an idle tree shows the RSS from whenever the last write landed. Refreshing it needs a wake I1 forbids inventing, and the pulse's escape from the same wall does not transfer, because an event names paths and never bytes. It is consistent rather than broken: the diff on screen is *also* as of the last change, and this readout now carries the same contract as everything beside it |

| Key hints `q quit · f follow · ↑↓ scroll` | A hint bar, and it **constrains I6**: roughly thirty columns of it must degrade legibly at forty. **Ruled 2026-07-30: it does not degrade by shortening.** The footer takes a second line instead, and only below the width where a whole line holds the bar does it drop hints, `JK files` first and then `jk scroll`. See §11.1 for why the first of those is a bonus rung that never decides the footer's height. See §11.1. |

Three of these are corrections rather than gaps:

1. **`f` toggles follow.** The mockup shows a dedicated key and a state indicator. That is the answer to §11.2 B1, and it was published before the question was asked. Ruled and implemented 2026-07-30; `f` is in `input.rs` and the rule is §11.1.
2. **The dimmed row and the pulse are one mechanism**, not two: both are recency rendered as intensity. Specifying them separately would produce two decay clocks that disagree on screen. This said "the `just changed` label" until 2026-08-03, and the label going does not weaken it: the correction was always about the two being one ladder rather than about which glyphs the top rung spends.
3. **The table above is a list of elements and was silent about the container**, which is what let B4 sit `(proposed)` for two phases while the picture and the code drew different screens. Ruled 2026-08-01 ([#66](https://github.com/breferrari/vigia/issues/66)): the file list is a **region**, pinned above the diff, and §11.1 carries it. Every row in this table is unchanged by that; what changed is where three of them are drawn and for how long they stay there.

**A fifth departure, and it was in the diff body where the first four were in the chrome and the glance row: the mockup stands its sigil off the line and the shell drew it flush.** Found 2026-08-15 by a reader watching the pane, and settled by the picture's own coordinates rather than by argument: the sigil sits at `x=72`, one cell of `~8.1px` ends it at `80.1`, and every content origin is `x=88`. Ruled towards the picture and implemented the same day ([#164](https://github.com/breferrari/vigia/issues/164)); §11.1 carries the rule, why it does not ladder, and what the column costs at forty.

**And the picture's split of elements across the two regions is not kept**, which is the second deliberate departure from `assets/preview.svg` after the header's worktree name. It gives the summary rows no kind letter and the diff heading no counters, so each region draws a different subset. That is coherent only while the region shows every changed file, and an automatic unbounded changed set means it cannot: a file scrolled out of a capped region would take its counters with it and leave nowhere to read them. Both regions draw the same row through the same `Painter::file_row`, which also leaves one degradation ladder to gate rather than two.

**A third departure, older than either and recorded here because auditing the picture against the code hits it first: the mockup orders a row's right-hand side differently from the renderer.** The picture places sparkline, then counters, then heat strip, left to right, with the counters coloured green and red. `Painter::file_row` allocates right to left by priority — counters first because they are the row's content, then the pulse, then the heat strip, then the sparkline — so the drawn order is pulse, heat, sparkline, counters, and the counters are one dim string rather than two coloured ones. The renderer's order is the one that survives a narrow pane, because allocating by priority is what lets the ladder drop the least valuable element first; the picture's is the one that reads well at a width nothing degrades at. This is a departure in the **picture**, not a gap in the code, and it is left standing rather than redrawn: the mockup is a design artifact and its job here is to promise a layout, which after B4 it does correctly. **The counters became two right-anchored columns on 2026-08-02 and the order did not move** ([#77](https://github.com/breferrari/vigia/issues/77)): that issue is about *alignment*, and this paragraph is about *order*, which is the distinction that kept the two from being confused. The renderer sizes nothing from the row now: a constant table of layouts holds that priority as its survival order, and the drawn order is still pulse, heat, sparkline, counters. **The colour half closed on 2026-08-15 and the order half is what is left of this departure** ([#157](https://github.com/breferrari/vigia/issues/157)): the counters were one dim grey where the picture draws them green and red, and nothing defended the grey — §5.3 had already lent them the two colours in the same sentence that lends the footer's follow marker, and the shell had shipped only the marker half. So this paragraph is now about *order* alone, which is the distinction the sentence above already drew for alignment and which turns out to be the same one twice.

**And the picture said something about those colours nobody had read off it**, which is the half of #157 that was not compliance. The mockup draws `+42` in `.grn` and `-7` in `.red` on its first two rows and `-0` in **`.faint`** on its third, so the rule it states is *value-dependent*: a half takes its diff colour where it has something to say, and the row's dim grey where it does not. §5.3 derives the same answer without the picture — green and red are lent "only where they restate the same fact", and a `-0` restates none — and the reason it matters is the reading the element exists for. On a worktree an agent is only adding to, an unconditional red would put red on every row, and *is anything being removed* would have no answer left on screen. What is deliberately **not** settled is which grey: the picture's `.faint` is `#6e7681` where `Theme::chrome_dim` is `#8b949e` on `dark`, and that is a question inside one role rather than about it. It is left open here beside the same question for the gutter, which draws `.dim` where the picture draws `.faint`. The two halves are still drawn or dropped **together**, because `+42` with no `-7` beside it reads as a total rather than as half a pair; it is only their ink that is per half.

**And the picture promised one more thing than this table listed: the row is columnar.** Every file row in `assets/preview.svg` puts the same element at the same `x`, so three sparklines read as one small-multiples chart and three heat strips as a comparison, which is the whole of what a file *list* is for. `Painter::file_row` right-packed instead, taking each element out of a budget that had already lost the elements outside it, so every element's position was a function of the widths of the ones to its right and no two rows agreed. Ruled 2026-08-02 towards the picture; §11.1 carries the rule and what it costs.

**A picture in a public README is a specification whether or not it is written down.** This one implied a retained time series, a recency gradient, two status readouts and a keybinding, none of which appeared in the spec, the roadmap, or any issue — while [#10](https://github.com/breferrari/vigia/issues/10) carried four of them in a single line. That is the same failure as §11: behaviour that exists somewhere real, with no line claiming it.

### 5.2 Where the mockup pulls against the invariants

§5 says design effort goes here "once the invariants hold", and [#10](https://github.com/breferrari/vigia/issues/10) repeats it: *"depends on the invariants holding first."* **That framing is wrong, and correcting it is the most consequential thing in this section.** At least two elements need retained state the frame path does not produce, in `vigia-core` rather than in the shell. They do not sit on top of the invariants. They **move** them.

**The sparkline needs precisely what eviction throws away.** `FrameStats.evicted` exists so the cached-diff map stays "bounded by the current diff rather than by everything ever edited" — that is how I3 is argued today. A churn sparkline is change density *over time*, so it has to survive a file settling: one that empties the moment a file stops changing shows nothing worth glancing at, and *"what was hot thirty seconds ago"* is the entire question it answers. Glanceability history therefore cannot live in the evicting map — and must not be unbounded either.

> **I10 earned its row on 2026-07-31**
>
> It was written here as a **proposal**, deliberately kept out of the §3 table,

> now has a budget (256 paths, 120 seconds), a fixture that drives ten thousand

> Two things it cost that this section did not predict. The store had to be fed

>

**The heat strip needs a whole-file property.** Locating change within a file requires that file's **total line count**, and the frame path is built to avoid exactly that: pure revalidation reads **0 bytes** (§10), the number I2a is written against. Measured naively — every changed file, every frame — it reintroduces the read I2a removed. It is cacheable per `(path, blob id)`, since a file's length cannot change without its content changing, so it is payable once per version rather than once per frame. **That caching is not an optimisation; without it the heat strip breaks I2a.**

**Two status readouts measure the thing they run inside.** `0.8ms frame` means instrumenting the render path and drawing the result — a readout whose own cost falls inside the budget it reports, gated by I9 at 16ms p99. `11MB` is a live RSS number, and I3 samples RSS in a **soak test** precisely because reading it is a syscall on some platforms rather than free per frame. Both are honest to show; neither is free to show; the spec said nothing about either.

**Consequence for sequencing:** Phase 3 is not a rendering phase. Its two headline elements each need a core-side change with an invariant attached, so they belong in the same conversation as I2a and I3 rather than strictly after them.

**Confirmed by building the first one.** [#38](https://github.com/breferrari/vigia/issues/38) landed the sparkline, the recency gradient and the pulse, and the diff was mostly `vigia-core`: a new bounded store, a change to what a `Tick` carries, a new invariant with its own budget, and a soak assertion. The drawing was a bucket ladder and a three-step ramp. This section predicted that split and it was right, which is worth recording because the alternative reading — that Phase 3 is where the shell gets prettier — was the one both §5 and [#10](https://github.com/breferrari/vigia/issues/10) originally invited.

### 5.3 The design language

The principles the individual rulings keep deriving, stated once so a new question starts here instead of re-arguing an old answer. Each names where it already bit; the laws themselves live where they always did (§5.1 for the picture, §11.1 for behaviour) and are not restated.

**The picture binds the elements; the snapshots are what ships; the distance between them is the work.** One canonical mockup, corrected in the same pass as any ruling that changes what it draws — never redrawn ahead of a ruling, because a picture answering an open question *is* the answer and must not arrive by ambush (B4), and never left behind one, because that is drift (§5.1's departure table is the complete list of licensed disagreements). But the mockup is rendered in pixels, and a cell grid can only approximate it: what it specifies is the **element set and each element's promises** (§5.1's table), never glyph-for-glyph fidelity. The first live wide-pane run made the difference unmistakable — every promised element present, and the pane still reading far from the picture. When that happens, the gap is not a defect in either artifact; it is the design backlog, itemised: spacing, colour weight, composition, density. The snapshot suite carries the rendered truth at every width and state, which one picture cannot.

**Furniture runs full-bleed; text is inset.** The mockup draws washes and rules to the pane edge and glyphs one to three cells in, and the two roles must not swap: a wash that stops short reads as a misaligned highlight, text at column 0 reads as squeezed. **Ruled and implemented 2026-08-10** ([#119](https://github.com/breferrari/vigia/issues/119)); §11.1 carries the ladder, the floor that keeps it clear of I6's forty columns, and the reason a region pays it on one side. What the build added to the principle is that a margin has to be laddered as a **total** rather than per side, because stepping both sides on one column hands a widening pane a narrower row, which is the layout table's own rule reaching a place nobody had looked for it. Chrome is the third role and never grows for a transient thing (§11.1's notice rule).

**Snap, never ease.** A monitor's premium feel is the state change that lands whole in one frame. Animation needs a clock, a clock needs the timer I1 forbids, and the refusal is not a sacrifice: easing tells a reader the tool is doing something, and this tool's whole claim is that it already did it. The same reasoning retired the pulse decay (§11.1) and the frozen-clock header words (§5.1) — anything drawn as *elapsing* lies the moment nothing wakes.

**Acknowledgment before action, priced honestly.** Every act the shell accepts answers on the same frame — a click lands, a drag tracks, a digit teleports. Extending that to *intent* (hover) was ruled on rather than accreted ([#123](https://github.com/breferrari/vigia/issues/123), §11.2 B10, declined 2026-08-15), and **the price this paragraph quoted for it was wrong**, which is worth keeping rather than quietly editing out. It said hover *"costs a wake class I1 currently never pays"*. I1 pays it now, and pays more than a wake: `crossterm`'s `EnableMouseCapture` sets DEC mode `?1003h`, any-event tracking, so pointer motion over the pane already arrives, and `run` draws once per drained batch whether or not any wake in it produced an action — so a batch of nothing but motion already performs a memory read, a whole-frame paint and a recorded frame ([#154](https://github.com/breferrari/vigia/issues/154), `RULINGS.md`'s I1 section). None of that can be given back portably. So hover was declined on what it *shows* instead, and on a mechanism rather than a preference: **nothing would ever tell it to turn off.** No mouse protocol reports a pointer *leaving*, the takeover does not enable focus reporting, and on an idle tree nothing repaints, so the last-hovered row would stay lit as a claim about where a pointer used to be.

**The pattern still generalises, and it is what survives that correction**: a feel improvement that costs an invariant a sentence gets a decision issue; one that costs nothing (inset, half-page keys, file-granular jumps) gets a row. What B10 adds is that **the sentence has to be true when it is written**. A decision issue opened against a cost nobody measured spends a ruling's worth of attention on the wrong question, and this one very nearly did.

**Colour is spent by role, and the diff's is inviolable.** Green and red mean added and removed, may never collapse at any rung that has colour (the depth ladder's one absolute), and are loaned out only where they restate the same fact (the footer's follow marker, the counters). **A loan is per statement rather than per element**, which is what "the same fact" means when read strictly and which nothing had had to apply until [#157](https://github.com/breferrari/vigia/issues/157): a `-0` on a file row is the counters' element and is not the fact, so it keeps the dim grey while the `+2` beside it takes green. Cyan marks structure and instrument. Intensity is the recency ladder and nothing else — dim is a *meaning*, not a style. A new element gets a colour only by taking a role, never by being distinct.

**Shape carries signal; words are read.** The four glance elements are shape-and-colour precisely so the eye takes them without reading (§5), which is why the pulse lost its label and why a hint is dropped whole rather than abbreviated — half a word is a *reading* task on a surface built to avoid one. Text on screen is either content, a name, or advice, and each has its own degradation law (§11.1).

**Richness is the reward of space.** The invariants price wakes, writes and clocks — they price **ink at zero**: borders, dense graphs and colour ramps are all drawing on frames that already happen, so a monitor can be the best-looking thing in the terminal while staying the cheapest. The ladder therefore runs in both directions. Below I6's floor the pane is spartan because every cell is contested; upward, each rung *earns* more of the cockpit — the inset, then the colour the mockup already promises, then borders that speak ([#124](https://github.com/breferrari/vigia/issues/124)), higher-resolution detail, the worktree churn graph, a list deeper than six on a pane tall enough to hold it ([#125](https://github.com/breferrari/vigia/issues/125)). What stays refused is only what the invariants actually name: easing (a clock), decoration that must be configured (B6), and any element whose information is not already retained. An earlier draft of this paragraph refused borders and meters on taste; that was the author's dial, not the spec's, and the correction is recorded so the next reader knows which kind of rule this is.

## 6. Architecture

Cargo workspace, two crates:

- **`vigia-core`** — library. Git (`gix`), diff modelling, incremental highlighting (`syntect`), filesystem events (`notify`), the watch and coalesce engine, the frame path. **No terminal I/O, no ratatui.** Every invariant except I6 and I8 is testable here, headlessly.
- **`vigia`** — the `ratatui` + `crossterm` shell: input, layout, theming. Thin by design, so the TUI stays swappable and the engine stays provable. A library with a five-line binary on top rather than a binary alone, because §7 makes the snapshot suite the proof for I5 and I6 and a test cannot import a `main.rs`.

The split is a dependency decision, not a hedge: the TUI renders whatever the core produces, so the core has to work first or the TUI is being built on sand.

`notify` is named here because I1 requires filesystem events rather than a timer, and each platform delivers them differently: `inotify` on Linux, `FSEvents` on macOS, `ReadDirectoryChangesW` on Windows. `notify` is the standard Rust abstraction over those three, and it keeps the binary pure Rust. Verified 2026-07-30 against `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-musl` and `aarch64-apple-darwin`: no `cc`, `cmake` or `bindgen` in any of the three graphs. The `-sys` crates it pulls (`inotify-sys`, `fsevent-sys`, `windows-sys`) are FFI declarations against facilities the OS already ships, so they compile no C.

**`libc` on macOS and `windows-sys` on Windows** are named here for §5.1's memory readout, and they are named rather than merely used because CLAUDE.md's rule is that a dependency reaches the spec before it reaches a manifest. Both are **target-conditional dependencies of `vigia` alone**, both are `unsafe` FFI declarations against facilities the OS already ships, and **neither adds a crate to any graph**: `gix` already puts `libc` into the Apple graph through `gix-hash` to `sha1-checked` to `cpufeatures`, and `windows-sys` 0.61 into the Windows graph through `gix-sec`. What each one buys is one syscall in place of a **subprocess**. `soak.rs` reached the same numbers by spawning `ps` and `tasklist`, which is affordable 288 times across an hour and not sixty times a second: `tasklist` alone is 42.8ms median on the reference machine against a 16ms frame. Linux needs neither, since `/proc/self/status` is a file read.

> [!WARNING]
> **Check the lock file, do not recall what a dependency costs**
>
> The paragraph above was nearly two platforms instead of three. `libc` was
> confirmed already-present with `cargo tree` and `windows-sys` was assessed from
> memory as *"a new crate in the graph"*, in the same hour, by reasoning that
> should have applied to both — and the Windows readout was filed as deferred work
> ([#56](https://github.com/breferrari/vigia/issues/56)) on the strength of it. The
> sentence directly above this one had said otherwise since Phase 1. **A
> dependency's cost is a fact about the lock file and is one command away, so an
> assessment of it that was not run is a guess** wearing a measurement's clothes.

**`signal-hook` on Unix and `windows-sys`'s `Win32_System_Console` on Windows** are named here for I8's externally delivered signal, and they are one decision rather than two: `std` has no signal API, the mechanism differs by platform, and the alternative to naming both is the platform-asymmetric guarantee [#16](https://github.com/breferrari/vigia/issues/16) already rejected as worse than one stated uniformly. Both are **target-conditional dependencies of `vigia` alone**, and — the paragraph above being what this one was checked against rather than recalled from — **neither adds a crate to any graph**: `cargo tree -i signal-hook` reports it already present at 0.3.18 on Linux and on Apple, pulled by `crossterm` through `ratatui`, and `Win32_System_Console` is a feature of a crate `vigia` already declares. Measured 2026-08-08, unique crates before and after: 183 Linux, 181 Apple, 185 Windows, unchanged on all three.

**It stays pure Rust, and `signal-hook` is the one dependency here where that had to be read rather than assumed.** It ships a `build.rs`, which is the shape §6 exists to catch: the file is `fn main() {}` for every feature but `extended-siginfo-raw`, `cc` is an *optional* build-dependency behind that one feature, and nothing enables it. The `no C toolchain` CI job is what keeps that true rather than this sentence.

**`regex-fancy` is what keeps `syntect` pure Rust, and its price is a compile deferred to first use.** `syntect`'s default engine is `regex-onig`, which is oniguruma, which is C: taking the defaults would put `cc` in the graph on its own and cost musl-static and Windows tier-1. That choice stands. What was never priced is *when* the pure-Rust engine does its work. `syntect` holds each pattern in a `once_cell::sync::OnceCell` and hands it to `fancy_regex` on first use, so the **first parse under a grammar** costs **74-362ms** where loading all seventy-five costs 318µs: Rust 93.11ms, Python 89.05ms, JavaScript 103.27ms, Go 74.14ms, Markdown 361.74ms, measured in release on the reference machine.

**And it is per pattern rather than per grammar**, which is the part that decides what can be done about it. Warming on one file leaves a *different* file of the same language still paying: 41.41ms residual on `.rs`, 95.04ms on `.md`, 201.20ms on `.html`. A synthetic sample is worse than a real sibling, and a bare newline worse again. So "this grammar is warm" is not a property that exists, anything built on one would be acting on a false claim, and the two honest moves are to keep the cost off the frame a reader is waiting on (I7, [#51](https://github.com/breferrari/vigia/issues/51)) and to run ahead of them where losing the race costs nothing. Everything else is the cold path §7 already excludes from I9 by definition.

**Coalescing stays ours.** `notify` has a companion debouncer crate, and taking it would move coalesce policy out of `vigia-core`, which is the one place I1 is testable. `notify` supplies raw events and nothing else.

**There are two coalescings, and only the first is that one.** `vigia-core` coalesces **events**: which filesystem writes count as one change. That is I1's, and it stays in the core for the reason just given. The shell coalesces **paints**: how many frames one burst of wakes is worth. That is I9's, it cannot live in the core because a paint is the shell's and because one of the three wake sources is the terminal, which §6 puts outside `vigia-core` entirely, and it decides nothing about which events are real. It costs I1 nothing, because draining a queue that is already there is a `try_recv` and never a wait: an idle shell still blocks on one `recv` and still does no work. [#45](https://github.com/breferrari/vigia/issues/45).

A coalesced tick also **names the file whose write landed last in it**, which is what I5 follows and what §11.1 specifies. The path is a by-product of the gitignore filter, which already resolves every event against the worktree root, so carrying it costs no syscall. This is the second thing the debouncer crate would have taken away.

**The frame path keeps its diffs between frames.** I2a forbids re-diffing a file that did not change, so the core holds the previous frame's diff per path and revalidates instead of recomputing. Validity is decided from three things that cost no file read: the index blob the change names, the kind of change, and a `stat` of the working-tree file. Content is never hashed to decide this, because hashing is the read I2a exists to avoid.

A `stat` on its own is not proof, and the gap is the one git calls *racily clean*: two writes of the same length inside a single modification-time granule are indistinguishable by `stat`.

The rule that closes it has to account for **flooring**. A filesystem stamps a modification time by truncating the current time to its own granularity, so a write landing *after* a read can record a time *before* it. "Older than the read" therefore proves nothing, because the granule may still be open: measured on NTFS, that mistake serves a stale diff on about one same-length rewrite in four hundred, and on a 1s-granule volume it would be most of them. So a fingerprint is trusted only once a **full granule has passed** between the stamp and the read, and anything else is re-diffed. The margin is a constant that must be an upper bound on real granularity: **2 seconds**, since FAT and exFAT quantise to 2s and HFS+ to 1s, where NTFS, ext4 and APFS are milliseconds or finer. That trades redundant diffs of files written in the last two seconds, which are files that just changed, for never showing a stale one. **It is a table lookup rather than a measurement because measuring the right filesystem would need a probe write**, and §11.1 now carries "the monitor writes nothing" as a rule rather than as an accident of what this code happens to do: the margin's whole case rests on that, so the two have to be one decision.

**What it still cannot see** is a writer that restores a modification time it did not advance: `cp -p`, `rsync -t`, `unzip`, `touch -r`. Git carries the inode change time to catch those, and `std` exposes no equivalent on Windows, so closing it is a dependency decision rather than an implementation detail. Tracked on the deferral shelf rather than assumed away.

**And it assumes the modification time is stamped by the local clock.** The margin compares a filesystem timestamp against this process's clock, so on a network filesystem the server's skew subtracts directly from it: a server two seconds behind consumes the whole margin and the flooring problem returns. Local worktrees, which is what a monitor beside an agent watches, are unaffected.

## 7. Testing

- **Snapshot tests over `ratatui::backend::TestBackend` with `insta`** — render frames into an in-memory buffer, snapshot as text. This is what makes I5 and I6 assertable at all: the UI becomes diffable text.
- **`criterion`** for I4, I7 and I9, **tracking rather than gating.** Criterion compares a run against a saved baseline, and the budgets in §3 are absolute, so it is the right instrument for "this got 20% slower" and the wrong one for a pass/fail line. Compiled in CI so the benchmarks cannot rot; not timed there, because a shared runner cannot produce a number worth comparing.
- **Budget gates** in `crates/vigia-core/tests/budgets.rs`, in **two tiers**, because an absolute wall-clock threshold is a strong instrument on a known machine and a weak one on a hosted runner:
  - *Structural* gates compare the engine against itself across fixtures that differ only in how much changed. They are ratios and exact byte counts, so they are hardware-independent, take **no slack**, and are what actually catches a regression. Making the frame path re-read every changed file is a 5x wall-clock change that a generous threshold waves through, and a 100x byte-count change that these cannot.
  - *Absolute* gates hold the wall clock to §3. Release only, since the budgets were set against optimised code, and with a slack multiplier (`VIGIA_BUDGET_SLACK`, default 1) so a shared runner's variance does not read as a code regression.
- **A budget measured on one target is a budget about that target, and until 2026-08-08 the shipped Linux binary was not the one measured.** Every absolute gate ran on `ubuntu-latest`, which is glibc, while §9 makes `x86_64-unknown-linux-musl` the **only** Linux artifact a release produces. A different allocator under a frame's allocation pattern is not a hypothetical difference, so the artifact a Linux reader receives had never been held to I7 or I9 at all. The `musl` job in `ci.yml` now runs the absolute gates against that target, which costs no runner change because a static musl test binary executes natively on a glibc host. The same axis as the four bullets below it, one dimension over: those ask whether the gate measured the right *moment*, and this asks whether it measured the right *binary*. [#12](https://github.com/breferrari/vigia/issues/12).

  **It runs `-p vigia`, and the reason is a constraint worth knowing rather than a convenience.** The unscoped form does not compile for a cross target: `criterion` is a dev-dependency of `vigia-core`, it pulls `alloca`, `alloca`'s build script is `cc`, and `cc` then looks for `x86_64-linux-musl-gcc`, which a hosted runner does not have. **So the pure-Rust property `CLAUDE.md` protects holds for the shipped graph and does not hold for the dev graph on a cross target**, which is a real asymmetry and is recorded here rather than papered over by installing a C cross-compiler in CI. The scope is also right on its own merits: `vigia`'s only dev-dependency is `insta`, which is pure Rust, and `vigia-core`'s budgets are engine primitives measured on glibc in the same run rather than anything "the artifact Linux ships" was about.

  **Measured 2026-08-08, and the concern that motivated it was unfounded.** On `ubuntu-latest`, release, `x86_64-unknown-linux-musl`, `VIGIA_BUDGET_SLACK=3`: **first paint 14.49ms** against I7's 50ms budget (150ms effective at that slack), the frame that compiles the grammar 57.92ms behind it; a bulk rewrite of 100 undrawn files inside the settle margin **p50 11.96ms, p99 12.46ms, max 12.69ms** over 270 in-margin frames against I9's 16ms budget (48ms effective); one memory read 26.6µs. Every gate green, and first paint holds even against the unslacked 50ms.

  The worry was musl's allocator under a frame's allocation pattern, and at this workload it does not show. **The only comparable reference figure is the 105.03ms** the bullet three below records: that is the shipped first paint, measured through the shell over a hundred-file fixture, and it is what [#51](https://github.com/breferrari/vigia/issues/51) then fixed. §10's 20.37ms is *not* comparable and is the trap that bullet exists to name, since it comes from the core's frame path and builds no `Highlighter`. Two different machines and two different code states, so this settles no comparison; what it settles is the question actually asked, which is whether the artifact Linux receives holds the budgets, and it does with room.

  **The numbers are in the log because the step passes `--nocapture`**: every gate prints what it measured and libtest discards a passing test's output, so without it this job would prove the budgets hold and record nothing about by how much.

  **The gate covers I9, and the first version of this bullet claimed I7 as well, which was false.** I9's gates are in `crates/vigia/tests/budgets.rs` and I7's are not: a first-paint cost is invisible to any gate that warms up, which is the bullet three below this one, so I7 has a file of its own in `crates/vigia/tests/first_paint.rs`. Naming `--test budgets` therefore measured one of the two. **Worse, and pre-existing: `first_paint.rs`'s absolute gate is release-only through `absolute_gates_apply`, and no CI job selected it in release at all**, so I7's absolute gate reported itself skipped in the debug run and was never reached in the release one. It ran nowhere, on any target, for as long as it has existed. Both the `test` job and the `musl` job now run it, **in a step of its own rather than as a second `--test` on the budget step**: cargo runs test binaries one at a time but chooses the order, and sharing one invocation put `first_paint`'s three cold starts over a 100 x 500 fixture *between* the two `budgets` binaries, so the shell's absolute gates began measuring immediately after a burst of exactly the disk and allocator work they are most sensitive to. Two flakes landed in the two runs that shared the invocation, on gates that had been green, and none in the run after the split ([#36](https://github.com/breferrari/vigia/issues/36) tracks the underlying sensitivity). This is §7's own recurring shape reached through the test **selector** rather than through the gate's contents, which is a fifth axis: the gate was correct, warm, positioned and non-vacuous, and nothing ran it.
- **An invariant the engine can only make possible gets a second gate over the caller**, in `crates/vigia/tests/`. I4 is the case: the core fetches content per file, so painting the top of a large diff without reading the bottom is *available*, and nothing in the core stops a renderer from asking for every file anyway. Asking is the natural way to write one. So what one screenful costs is gated where the screen is, against two fixtures differing only in changed-file count, for the reason the tier above gives. **Either tier can be the one that has to move there**, and I2b needed both: `reads.rs` holds the structural half, and `crates/vigia/tests/budgets.rs` holds an *absolute* one, because highlighting follows the viewport and so happens in the shell — a frame timed in the core is a frame with the syntax parser missing.
- **A budget measured at one position is measured at its cheapest one.** A caller starts at the top, so a gate that never scrolls tests the corner of the space where the least work is possible. I2b's frame gate ran at row zero and passed while a frame four screenfuls down cost 53ms against a 16ms budget, sustained and with no input; its own assertion was right and could not fire. Any gate over a windowed view is parameterised by where the window is.
- **A gate that warms up cannot see a first-paint cost, and a first-paint budget therefore needs a gate that never warms.** The third along the same axis as the two above, and the cheapest to state: a steady-state gate is *right* to discard its warmup, so the discarding is not a flaw to fix but a blind spot to cover elsewhere. Every steady-state wall-clock gate in `crates/vigia/tests/` drops fifty frames, and I7 — a budget about exactly one frame, the first — had its only gate in `crates/vigia-core/tests/budgets.rs`, where that gate builds no `Highlighter` and so measured open-plus-diff-one-file. The shipped first paint was **105.03ms** against a 50ms budget, 2.1x over, for two phases, and what made it invisible was two correct decisions meeting: the steady-state gates warmed past it and the startup gate was one crate short of the stage that cost. **A budget over the first N of anything needs a gate whose window starts at zero.** [#51](https://github.com/breferrari/vigia/issues/51), `crates/vigia/tests/first_paint.rs`.
- **A gate for a *deferred* cost asserts the work was deferred, not merely that the clock is small.** The corollary, and it is where this one could have gone wrong: the fix for a slow first paint is to do less on it, so the gate's own subject is now something that could quietly become *drawing less*. `first_paint.rs` asserts the body is full and that the frame parsed zero lines **before** it asserts the clock, and that a later frame parses more than zero, or the whole gate is satisfied by a build whose highlighter never runs. It also compares the plain frame's rows against the coloured one's, so a deferral that changed *what* was drawn rather than only its colour goes red — at the `Row` level, which is one level short of the cell a reader sees, and [#106](https://github.com/breferrari/vigia/issues/106) is that gap named rather than left implied.
- **A frame-time gate that never paints has timed half a frame.** The third along the same axis as the two above, and it went unnoticed longest because the omission is invisible from inside the gate: every budget gate in this repo timed `Frame::advance` plus `App::view` and stopped, so `render` was outside both tiers on both crates. That is where a row's *width* is decided, so the cost of drawing was measured by nothing at all. A row carrying **7.2x more line than pane** then passed a 16ms gate for two phases, and what found it was a reader scrolling a Japanese README rather than any test. The rule generalises past this instance: **a gate is written against the caller's whole frame, and any stage left outside it is a stage nothing can regress you on.** `crates/vigia/tests/paint.rs` holds the structural half, against a counter the renderer returns. [#45](https://github.com/breferrari/vigia/issues/45).

- **A structural gate bounds a counter, not a resource, so a cost added outside that counter's population is invisible to it.** The line above one axis over, and the difference is what makes it worth its own entry: there the omission was a *stage* left outside the timer, here every stage was inside and the gate was still blind, because the new syscall landed in `Worktree` while `FrameStats::probes` counts the frame path. [#15](https://github.com/breferrari/vigia/issues/15) needed a file's type before reading it, and the obvious `lstat` put a **second `stat` per file** on exactly the path `crates/vigia/tests/reads.rs::a_tick_inside_the_settle_margin_stats_each_file_once` exists to hold at one, asserting `probes <= FILES` and saying so in its own failure message. It stayed green. The clock could not cover for it either: `budgets.rs::what_a_bulk_rewrite_of_undrawn_files_costs` **deliberately refuses to assert a wall clock** on this fixture, for the reasons recorded there, so the count was the only tier that could have caught this and it was the tier that could not see it. Measured by hand instead, at **+1.18ms p50** over a hundred undrawn files inside the settle margin, 13.45ms against 14.63ms with p50 stable to 0.03ms across three runs on each side. The cost went, by carrying the answer forward from the status walk that had already paid for it (`FileChange::maybe_symlink`), which returns the p50 to **13.40-13.47ms** against `main`'s 13.44-13.45ms: level, which is the claim, rather than faster, which it is not. An earlier pair of runs read 13.28-13.30 and a wider sample did not hold it, so the range here is the one to quote.

  **And removing the cost was not the end of it, which is the half worth keeping.** With the syscall merely made *conditional* and still counted nowhere, the fix was as invisible as the regression had been: deleting the hint and restoring the unconditional `lstat` left **every test in the repository green**. An optimisation whose whole justification is a syscall count, sitting in the one repository whose method is *"an invariant without a failing test is a wish"*, had no failing test. So the probe is now drained across the layer into `probes` (`Worktree::take_type_probes`), and `a_tick_inside_the_settle_margin_stats_each_file_once` fails with its own unchanged message, **"the tick took 200 stat calls over 100 files"**. **Completing a counter's population is not the same act as widening a gate to admit a regression**, and the difference is which direction it makes the gate fire in: one lets a regression through, the other catches one that was previously invisible. The tell generalises past the instance: **when a change adds work near a counter, ask which population the counter has, not whether its gate is green** — and ask it again after the fix, because a saving the instrument cannot see is a saving the next reader can delete.
- **A fixture over ASCII cannot tell a column bound from a character bound**, because over ASCII they are the same number. The budget fixtures are generated source, 34 columns of it a line, so *"a row costs the pane"* and *"a row costs the whole line"* produced identical counts across every gate in the suite. Anything measured in **rendered width** needs a fixture where width and length disagree: `Scratch::wide_lines` is 531 columns over 412 characters of Japanese, emoji and Latin. Same shape as the row-budget gate's hundred-file fixture, one axis over.
- **A fixture population sitting on its tooling's default configuration cannot observe the code that exists for the non-default.** The same family as the line above, one axis further out: there the fixtures were uniform in their *content*, here they are uniform in how they were *built*. Every fixture in this repository is created by `Scratch`, which shells out to `git init` and sets `core.autocrlf false`, so both sides of every diff were always LF, git's clean filter never had anything to convert, and the code path that skipped it produced byte-identical output to the code path that runs it. Not one test was wrong and not one of them could have failed: [#65](https://github.com/breferrari/vigia/issues/65) drew a file `git diff` called unchanged as a 1,790-line rewrite while the suite was green, and what found it was pointing the tool at a real repository. **The tell is checkable and is the one to reach for: delete a normalisation, filter or conversion step and see whether anything goes red.** That is a mutation test with a specific target, "does any fixture make this branch's presence observable" rather than "is this branch covered". The answer is to **span** the axis rather than move along it, so `Scratch::crlf_worktree` stands beside `Scratch::new` instead of replacing it. Git alone offers `autocrlf`, `.gitattributes` filters, `core.symlinks`, `core.ignorecase` and sparse checkout; a fixture built by `mkdir` and `write` has silently taken the same position on all of them.

  **`core.symlinks` was the next one along and it was holding two defects, which is the strongest evidence this rule has produced.** Named above as an unspanned axis before anyone had looked; [#15](https://github.com/breferrari/vigia/issues/15) spanned it and found that a symlink was diffed as its *target's contents* where git stores the target **path**, so a link pointing at a 4 KiB binary rendered as a binary change costing 4 KiB. That one was known and filed. The second was not: `frame::fingerprint` used `fs::metadata`, and **Windows refuses to resolve a symlink whose stored target uses forward slashes**, which is exactly what git stores. So the fingerprint was `None` on every checked-out link, nothing was ever reusable, and every symlink in a Windows worktree was re-diffed on **every frame, indefinitely**, against I2a. No gate could have caught it and none did, because the axis had no fixture on it. The tell this section already gives is what found it: `crates/vigia-core/tests/frame.rs::a_repointed_symlink_is_not_reused_from_the_targets_fingerprint` is where to restore the following `stat`, and `settle` then reports *"still re-reading after 8 idle frames"*, which is the never-reusable defect stated by a test rather than argued for. **An axis named as unspanned is a prediction, and this is the one that paid.**
- **A gate whose setup materialises every unit has measured the cheapest cache population.** The fourth along the same axis as the three above, and the one that hid longest because the helper responsible is *named* for the other thing it does. `settle()` exists to wait out the staleness margin, and the way it proves the wait worked is `materialise()`, which diffs **every** file. A frame holding a `FileDiff` for every changed file rebuilds every height from memory and reads nothing, so the walk I4's narrowing admits cost exactly zero in every gate that opened with `settle`, on both tiers, in both crates. The bug it hid was not small: the height walk re-read the whole undrawn changed set on **every tick**, 94 files and 3.7 MiB over the hundred-file fixture, 18.36ms p99 against 16ms, with eleven read-bounding gates green over it. The tell is that the setup and the subject share a resource: **if a gate's fixture setup populates the cache the gate is about, it has measured the case where that cache is full.** `settle_spans` is the same wait without the materialisation, and the two now stand beside each other rather than one replacing the other, which is the same "span the axis rather than move along it" answer the `crlf_worktree` rule above reaches. [#101](https://github.com/breferrari/vigia/issues/101), `crates/vigia/tests/reads.rs::a_tick_re_measures_only_what_changed` and `crates/vigia/tests/budgets.rs::ticking_over_an_undrawn_worktree_holds_the_frame_budget`.
- **A gate that settles before it measures has measured the cheapest state.** The same mistake as the line above, along a different axis: time rather than position. `settle()` exists so a fixture written moments ago can be *proved* unchanged, and every structural gate in `crates/vigia/tests/reads.rs` calls it first, so the settle margin — the one window in which the frame path deliberately recomputes instead of reusing — was the one window nothing measured. §10's claim that the margin breaches I9 under a bulk rewrite therefore went two phases with no gate on either tier, in either direction: nothing would have caught the breach if it were real, and nothing showed that it was not. An invariant that governs a window needs a gate that runs *inside* it. [#32](https://github.com/breferrari/vigia/issues/32).
- **A gate can assert the defect it was named against, and the tell is an exact small count where the rule is a bound.** `crates/vigia/tests/scroll.rs::the_bottom_of_the_diff_is_content_rather_than_blank` was written against a blank pane, said so in its name, said so again in its comment — *"an empty pane, which in a monitor is indistinguishable from a broken one"* — and then asserted `view.rows.len() == 1` against a twenty-two row body. Every word around it was right and the one line that runs pinned the failure in place. That is worse than the absent gate §7 already warns about, because a defect with a green gate over it is one nobody goes looking for: [#57](https://github.com/breferrari/vigia/issues/57) was found by a reader watching an agent run `git reset --hard`, two phases after the gate shipped. The signature is a **specific small number where the rule is about a bound** — "the screen is full" is `== height`, never `== 1` — and it is legible by reading the assertion against the test's own name, which is the cheapest review there is and was never done here.
- **An invariant whose two failure modes are not symmetrical gets a gate for each.** I2a is the case that made this a rule. Reusing too *little* is slow and loud, and the budget gate catches it. Reusing too *much* is fast, passes every budget, and shows a diff that no longer exists, so `crates/vigia-core/tests/frame.rs` compares every reused frame against one computed with no memory at all. A budget gate alone would have called the second failure a success.
- **A rule covering a window too small to race is extracted as a pure function and tested directly.** The racily-clean guard in §6 cannot be reached on demand from a filesystem: dropping it leaves the whole integration suite green and only a unit test over the decision function goes red. Where a correctness rule has no reachable integration path, the pure-function test *is* the gate, and that is worth stating rather than discovering.
- **Gates are mutation tested before they are trusted.** Break the code deliberately, confirm the gate goes red, restore. Two of the flaws found this way were invisible to reading: a structural gate comparing one call against the sum of its own calls, and a p99 over too few cold samples.
- **Steady-state budgets are sampled after a warmup**, and over enough frames for a percentile to be one. I9 is a claim about steady state, so the cold path is outside its scope by definition; measured cold frames run ~40ms against a warm p99 of ~3ms, and at 30 samples a nearest-rank p99 is just the maximum.
- **A CI guard fails the build if `cc`, `cmake` or `bindgen` enters the dependency graph** on any tier-1 target, plus a musl build asserting the binary links no shared libraries. The pure-Rust constraint is what makes musl-static and Windows cheap, so it is enforced rather than trusted.
- **The soak drives the whole pipeline, not the engine.** I3 is a claim about the process a reader leaves open, so measuring `vigia-core` alone would prove it about a program nobody runs. The harness is `vigia::run` with the terminal removed: a real `notify` watch thread, real coalescing, `Frame::advance` per tick, follow and scroll through `App`, `View::collect` driving the `Highlighter`, and `render` into a `ratatui` buffer. What it leaves out is named rather than discovered later: the terminal takeover, which needs a tty and is I8's; the input thread; the signal handler, which is process-global and would arm the harness rather than a shell; and index writes, because the loop reaches the same mass-eviction state by reverting files and keeping `git` out of the measured window is what makes the temp-file gate exact.
- **The soak is two tiers, like every other budget here.** *Structural* gates — the retained caches bounded by the current diff and by the viewport, eviction actually happening, and **zero temp files retained** — are counters and directory entries, so they are hardware-independent, take no slack, and run in every `cargo test`. The *absolute* gate is RSS drift, and it is the one that has to be scheduled.
- **A drift gate over a window shorter than its own warmup is measuring warmup.** RSS climbs to an allocator plateau in the first minutes of any process and only then goes flat, so a short window reads that climb as a leak and a generous threshold would then wave a real leak through. The gate therefore discards a warmup prefix, compares the median of the first quarter of what remains against the median of the last quarter, and **refuses to assert at all** below a window where that leaves two ends worth comparing. Refusing is the point: a gate that cannot say "no drift" has not been tested, and one that says it from four samples is worse than absent.
- **The gate's warmup prefix is workload-dependent, the report says so, and that is a ruling rather than an omission.** The prefix is a **fraction** of the window, 10%, which is window-independent and is what it was chosen for. It is not *workload*-independent: RSS reaches its plateau in about **thirty seconds** over the default 20 x 200 fixture and in about **eight hours** over the 100 x 500 one, where allocator arenas and four retained caches accrete toward their bounds for a third of the day. A tenth of a 24-hour run therefore discards 2.4 hours of a climb that takes eight, the first quarter's median sits on the ramp, and the ends-ratio measures climb-to-plateau. The first full window did exactly that: **13.26% against the 5% budget**, on a process that moved 0.33 MiB across the sixteen hours past its plateau, which is 0.02 MiB/h against the +81.3 MiB/h a deliberate 1 KiB-per-frame leak calibrates at. That reading is a **known instrument artifact** rather than a leak, and it is the case §10 anticipated as "crosses on variation rather than on a leak".

  **The answer is a measured number printed beside the verdict, not a moved baseline.** The report carries where the series settled and what the same ends-ratio says from there: over the recorded day, `settled at sample 97 of 288 (8.08h in), drift from there 1.85%` beside the gate's own 13.26%. A reader of a red day-long run has both figures and can tell a baseline on a warmup ramp from a leak, which is what the fraction alone could not say. The walk is the obvious one: the settled **level** is the median of the last quarter, and a rolling window of that same quarter width steps back from the end while its median stays within **1%** of the level. Nothing is gated on it, so the band moves a printed number rather than a verdict.

  **A measured baseline was built three times and does not ship, which is worth recording so a fourth is not attempted in good faith.** Each formulation fell to a real adversarial shape and each defect lived inside the previous fix: a leak between two plateaus absorbed as warmup (**4.24%** against a 20.00% window); one 4 KiB page prepended to a flat head defeating the clause added to stop that (**4.77%** against 29.50%); a warmup followed by a flat stretch followed by a leak passing through the same clause again (**4.99%** against 25.00%). The shared root is that a walk finds a plateau's *end* while a gate would need its whole *shape*, which is change-point detection and is a discipline rather than a patch. It is out of proportion here, because the gate's real leak-catching duty is already discharged twice: by the calibrated-leak fixture, which is caught from the fraction unchanged, and by the structural tier. **The gate keeps its one honest property, which is that it can be wrong only in the loud direction.** A red the printed plateau explains is an annotation; a green produced by an unsound detector is a laundering, and a suite stays green while that happens.
  `crates/vigia/tests/soak.rs::statistic` holds every clause of this, the recorded 288-sample series included as a fixture, because a run this long cannot be waited for and a number recovered by hand off a printed series cannot be checked again. The three detector designs and the shapes that defeated each are on [#127](https://github.com/breferrari/vigia/pull/127), which is the record of why this question is closed rather than deferred.
- **The same report carries the shape the gate rounds off, and the gradient through it, neither of them gated.** A ratio between two ends cannot tell a process that stepped once and went flat from one that is climbing, and that difference is the whole of §10's open question about I3. So the report also prints the medians of a quarter's worth of samples at **four** positions and a least-squares gradient in **MiB per hour**, fitted against elapsed time rather than sample index so it survives a run whose loop fell behind. The gradient is **signed** where the gate's ratio is deliberately clamped: a gate must not pass for the wrong reason, and a diagnostic whose job is a sign must not hide one. The **middle pair and the gradient** are reported and never gated; the outer two reach the gate only through the drift ratio, which is the assertion it always was. **Where the series settled, and the same ends-ratio taken from there** go on the same page for the same reason and are equally ungated: the bullet above is why. Nothing new is asserted on, and that is deliberate — a threshold on the gradient or on the shape would be a budget this document does not name, and §10's rule for drift that crosses on variation rather than on a leak is a measured warmup or a measured budget, never a wider one. **A gradient is printed with the span it was fitted over**, because for one fixed amount of RSS wander the reported MiB/h goes as the reciprocal of the window. Reference machine, by window and with the provenance each figure actually has: **+364.71 MiB/h** at 15s and **+7.89** then **+2.74** at 600s, all from the instrument over the default 20 x 200 fixture; **+1.94** at 900s from the instrument over 100 x 500; and **−0.70** at 900s and **+0.92** at 3600s over 100 x 500, both computed by hand off the printed series before the instrument existed. Those are the windows rather than the fitted spans. A span is about nine tenths of its window at 288 samples, and **three quarters** at the fifteen-second default, where `MIN_SAMPLES` rather than the warmup fraction sets it: 11.2s of 15. The 15s figure is the one a reader is most likely to convert, and it is the one the nine tenths does not fit. Nothing is wrong with any of them, and without the span beside it none is comparable to another, which is the comparison this section asks a reader to make. The instrument becomes readable somewhere around the window I3's budget names, which is an argument for running that window rather than against the instrument. The outer two are the gate's own numbers, unchanged, which `crates/vigia/tests/soak.rs::statistic::the_gated_ends_are_the_first_and_last_quarter_medians` holds in place, over two fixtures because each hides what the other catches.
- **A bound is only evidence when something reached it, so a gate over one asserts that eviction happened as well as that the bound held.** I10 is the case that made this a rule and the numbers say why: the per-commit soak window touches about eighty distinct paths against a cap of 256 and never turns the 120-second window over once, so the per-sample bound `tracked <= 256` is satisfied there the way an empty room satisfies a fire code. The soak therefore **refuses to assert** when the run reached neither eviction rule and prints why, exactly as the drift gate does; the deterministic proof is a fixture that drives ten thousand paths in every `cargo test`. Verified by running the soak at 300 files, where it reports 256 tracked at the cap with 207 evicted, so the gate can say yes and not only "not applicable".
- **Every instrument above measures a fixture, so one of them measures a worktree instead, and it gates nothing.** `crates/vigia/tests/observe.rs` is `vigia::run` with the terminal taken out and with **no writer of its own**: it is pointed at an existing checkout and the agent in the other pane is the workload. That is [#72](https://github.com/breferrari/vigia/issues/72), and the reason it asserts nothing is that its window is whatever a working session happened to be and its workload is whatever somebody happened to do, so a threshold over either would be a budget this document does not name. The soak stays where a resource claim is gated. Three things about its shape are rules rather than choices, and each is one of this section's own turned on itself. **The oracle runs in a separate process**, because answering "does this diff agree with `git`" diffs every changed file, which is the setup-materialises-every-unit trap four bullets up, aimed this time at the very caches whose cost is the measurement. **A budget is a bucket edge**: "was a frame ever over 16ms" has to be a *count*, so 16000µs is a declared boundary and the accessor **refuses** any threshold that is not one, which is the same refusal the drift gate makes and is gated the same way. **Nothing unbounded is retained**, because the process holding the samples is the process whose RSS is one of the readings, so a `Vec` of every frame cost would have the instrument reporting its own growth as the product's; the worst eight frames are kept with their context and everything else is a bucket. What it cannot reach is #72's item 5, *"what was reached for and not found"*, which needs a person and is the half §11.2 B7 declined an observation log over.

  **And a harness that claims to be the caller's whole frame has to be it, which this one was not on its first attempt.** The rule three bullets up is that a gate is written against the caller's whole frame and any stage left outside it is a stage nothing can regress you on. An instrument is one step further along the same line: a number is comparable to the product's only if it was taken over the product's frame. `drive` left three stages out and each understated a real cost. `branch_for` reads `.git/HEAD` on exactly the frames that draw the empty state, which over the recorded sessions was about half of them. The `chrome` is built **twice** per paint, so a notice raised during the collect reaches that frame rather than the next. And `Shell::draw` settles I7's repaint debt **inside the same tick**, so the first frame a reader sees is painted twice and a harness that painted once timed the plain half of it and displaced the colour onto the frame after. Measured on a scratch fixture before and after: a first frame of **5.52ms** became **558.83ms**, which is where the grammar compile actually lands. That last one is the mechanism this section already records the product nearly losing (*"deleting the second statement left the whole suite green"*), lost in a second hand-copy of the same sequence, which is the argument for the gate rather than for the reading: `crates/vigia/tests/observe.rs::wiring` drives one `draw` over a real worktree and asserts the debt is settled and the frame is coloured, over **two** fixtures because a dirty tree never reaches the branch read at all.
- **`proptest`** over diff parsing and hunk-boundary logic.

## 8. Phases

Live status, issue-linked, is in [`ROADMAP.md`](ROADMAP.md). This section is the shape; that file is the state. Work is taken one task at a time via `.claude/skills/take-next/`.

**Phase 1 — core engine.** `vigia-core` plus a `main` that prints frame timings. Prove `gix` gives working-tree-vs-index diffs at the fidelity and speed needed — it is the least-precedented dependency in the stack and everything sits on it. Land **I1, I2a, I4, I7, I9**, each gated. No TUI.

**Phase 2 — minimum monitor.** ratatui + crossterm shell. Follow mode (I5), scroll, mouse, exit safety (I8), 40-column layout (I6). Plus **I2b** (needs `syntect`) and **I3** (soak). Snapshot suite.

**Phase 3 — glanceability.** Section 5, plus theming.

**Phase 4 — the artifacts tell the truth.** The public surfaces — README, mockup, spec, tracker — agree with the code and with each other.

**Phase 6 — measured, not assumed.** Claims that outran their evidence get their measurement: the workload the thesis is about, the window I3's budget names, the default-view ruling a week of use decides. **Closed 2026-08-07, with the two rows that need a *duration* moved to the Shelf rather than finished** — the workload's own window accrues one session at a time and the default-view ruling waits on it, and a milestone that cannot close until somebody has used the tool for a week is a calendar rather than a queue. The measurement each was blocking has been taken; what neither has is repetition.

**Phase 7 — distribution.** `cargo-dist`, crates.io publish, personal Homebrew tap, prebuilt binaries on GitHub releases.

**Phase 8 — look and feel.** Layout, colour, keys and chrome, taken after distribution on purpose: the minimal real thing ships first, and polish lands as post-release momentum guided by the real-use evidence rather than ahead of it. **Missing from this list until 2026-08-09**, when [#12](https://github.com/breferrari/vigia/issues/12) corrected the README's phase table and found the same gap here. ## 9. Distribution

- **crates.io** — `cargo install vigia`. A name **cannot be reserved; it must be published**, and a publish is **permanent** (`cargo yank` hides a version from new dependents, it does not delete it, and the name stays taken). So the first publish should be a crate that does the minimal real thing. Verified free 2026-07-30, **and again 2026-08-08 against `index.crates.io` rather than the web API**, which is the file `cargo` itself resolves against and therefore the only answer that binds. `vigia-core` is free too, and that is not a courtesy check: see the publish-order bullet below.
- **Homebrew** — `homebrew-core` **cannot be reserved** and requires notability: ≥30 forks **or** ≥30 watchers **or** ≥75 stars, plus a stable versioned release. Until then a **personal tap** (`breferrari/homebrew-tap`) gives `brew install breferrari/tap/vigia` immediately, is fully under our control, and is what `cargo-dist` generates. Tap repository created 2026-08-08.
- **GitHub releases** — prebuilt binaries per platform via `cargo-dist`.
- No domain. Not needed for a CLI.
- **Two names are claimed, not one, and the order between them is forced.** `crates/vigia/Cargo.toml` declares `vigia-core` by `path` *and* `version`, and a registry will not accept a package whose dependency it cannot resolve, so `cargo publish -p vigia` fails outright with `no matching package named vigia-core found` until `vigia-core` exists on crates.io. The §6 crate split therefore spends a second permanent name, which is a cost of that split nobody priced at the time and which is worth stating rather than discovering at the release. **The pipeline runs `cargo publish --workspace`**, one command rather than two, because cargo resolves the dependency order and waits for the index itself; the two-call form needs a sleep between them whose right length nobody knows.
- **The release is one dispatch from the Actions tab, and every irreversible thing hangs off it.** `cargo-dist` 0.32 (the binary is named `dist`) builds the four target artifacts, creates the GitHub release, publishes the Homebrew formula to the tap, and runs a custom publish job that sends both crates to crates.io. `dist` has no built-in crates.io publisher: `publish-jobs` accepts `homebrew`, `npm` and custom reusable workflows, and the registry one is ours, in `.github/workflows/publish-crates-io.yml`. **That is what makes the tag the gate**: `RELEASE-SMOKE.md` runs against `dist build` output *before* the tag, not against a published artifact after it.

  **Started by `bump.yml`, not by a tag push, and that is a mechanism rather than a preference.** `[workspace.metadata.dist] dispatch-releases = true` makes `release.yml` run on `workflow_dispatch` and **removes its tag-push trigger entirely**, so `git tag v0.1.2 && git push --tags` no longer produces a release. The reason is that the alternative needs a second permanent secret: a tag pushed by a workflow holding `GITHUB_TOKEN` triggers no further workflow, because GitHub suppresses that to prevent recursion, and `workflow_dispatch` is one of the two documented exceptions. So a bump job can start the release with the token it already has, where pushing a tag would need a PAT with write access to this repository. `bump.yml` takes *patch*, *minor* or *major* from a dropdown, works out the next version, moves **both** version strings, proves the manifests still agree and that the built binary reports the new number, and only then commits and dispatches. Its `rehearse` option runs all of that and dispatches the tag `dry-run`, which is dist's own word for build everything and publish nothing, so the whole path can be exercised without spending a version. `crates/vigia/tests/package.rs::the_release_button_reaches_the_release` holds the three files together, because the failure when they drift is a release that silently never happens after the version has already moved.

  **Starting the release needs no PAT. Committing the bump does, and the two were conflated until 2026-08-11.** The paragraph above is about the *trigger*, and it says nothing about the write: `main` is protected by seven required status checks, and a commit pushed with `GITHUB_TOKEN` triggers no workflow by the same suppression rule, so those checks can never arrive on it. The push is rejected with "7 of 7 required status checks are expected" however long anyone waits, and the bot holds write rather than admin and so cannot bypass them either. That is run 31435812487, the button's first real run, and it cost nothing because the ordering above verifies the version before committing it: `main` stayed at 0.1.0, no tag existed, nothing was published. So the commit is pushed with a fine-grained token whose owner is an admin of this repository, and the pre-flight checks two things before the version moves. **One token fills two roles**, and it is the `HOMEBREW_TAP_TOKEN` secret: it carries Contents read and write on the tap and on this repository, so it publishes the formula and moves the version. `bump.yml` reads it into a variable named for the second role, since that is what the step reasons about, and `RELEASE-SMOKE.md` §0 records the sharing along with how to separate the two whenever that is wanted. They are different claims and neither implies the other: a real write to this repository, created and then deleted, covers the token's own grant, while `.permissions.admin` covers the standing of the account behind it, since bypassing a protected branch is a property of a role rather than of a token. The second is a rule check rather than a probe and is labelled as one in the workflow, because the only true probe of moving a protected branch is moving it, which is the irreversible act the whole step runs before.

  **What the pre-flight deliberately does not check is whether `main` still lets admins bypass at all.** Reading branch protection needs admin rights on the API: `administration` is not a scope a workflow may request under `permissions:`, so the job's own token cannot be granted it, and granting it to the release token would widen a long-lived secret past `Contents` to buy a better error message. A better message is all it would buy. What the step exists to prevent is an irreversible half-step, a version moved or a crate published against a token that cannot finish, and a protection setting that refuses the push is not one: the push is the last thing before the release is dispatched, so it fails with `main` unmoved, no tag and nothing published, which is exactly what run 31435812487 did. **And one premise stays unproven until a real push lands**, namely that a fine-grained token inherits its owner's bypass; `RELEASE-SMOKE.md` §0 records it as unproven rather than letting the guard imply otherwise. **Naming the token in the push URL is necessary and was not sufficient.** `actions/checkout` persists the workflow's own token into `.git/config` as an `Authorization` header, and git prefers a configured header over any userinfo in the remote URL, so the push went out as the bot whatever the URL said: every check above passed and the push was rejected exactly as before. The checkout therefore runs with `persist-credentials: false`, and that is the load-bearing half of the mechanism rather than a hardening detail. `crates/vigia/tests/package.rs::the_push_that_moves_main_is_authorised_before_the_version_does` is the gate that holds the shape, and it asserts three things that each looked sufficient alone: that the checkout persists no credentials, that the remote the push names carries the token, and that the refspec is `HEAD` at the default branch.

  **The registry publish runs last, and it is not atomic with the rest.** dist places every custom publish job `needs: [plan, host]`, and `host` is where `gh release create` runs, with no `--draft`, so the GitHub release and its binaries are public before the registry is touched; `announce` afterwards is a checkout. This bullet claimed the opposite when it was written, that `announce` waiting on the publish job stopped a release half-shipping, and that was wrong on the mechanism as well as the conclusion. **The order is right for the reverse reason**: crates.io is the only step that cannot be undone, where a GitHub release can be deleted, a tap commit reverted and a tag moved, so the permanent action goes after everything reversible has already worked. The cost is stated rather than designed away: a failure there leaves public binaries and an unclaimed name, recoverable by re-running the job, and §5 of the checklist verifies the registry directly instead of inferring it from a green workflow.
- **Four targets in v0.1, and Linux is musl alone.** `x86_64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`. One static Linux binary that runs on any distribution beats two that need selection logic, and `CLAUDE.md` already names musl as this project's static-binary story. **`aarch64-unknown-linux-musl` and `aarch64-pc-windows-msvc` are deferred**, not rejected: both need a cross linker on the release runner, which is the component most likely to fail first on a release nobody has cut before, and neither is reachable by a user who cannot already use one of the four.
- **A published `.crate` does not carry `.github/`, and thirteen of `vigia`'s test files read outside the package.** Counted by **file** rather than by read, because a file is the unit that gets excluded and a read is not. Twelve reach `vigia-core/tests/support/mod.rs` by `#[path = "../../…"]`: `budgets.rs`, `first_paint.rs`, `follow.rs`, `list.rs`, `observe.rs`, `paint.rs`, `reads.rs`, `rows.rs`, `scroll.rs`, `soak.rs`, `viewport.rs`, `writes.rs`. Two read repository documents through `CARGO_MANIFEST_DIR`: `soak.rs`, which is in both groups and reads `../../.github/workflows/soak.yml`, and `package.rs`, which reads this file and three workflows. So `cargo test` inside an unpacked or vendored copy fails where it passes in a checkout. All thirteen are deliberate and none is a reason to weaken a gate. **The fix, applied 2026-08-08 by [#12](https://github.com/breferrari/vigia/issues/12), is `exclude = ["tests/**"]` in `crates/vigia/Cargo.toml`**: the package ships no test suite rather than shipping one that cannot compile, which is excluding the tests rather than stopping testing the repository. `vigia-core` is not excluded and does not need to be, because its `tests/support/mod.rs` is inside its own package and `benches/engine.rs` reaches it without leaving.

  **This bullet said "three escapes" across two files until 2026-08-08, and the count was the part that was checkable.** It was prose, so nothing could contradict it, and it was wrong by a factor of four in a section whose own last sentence says a count is what a later reader can check. It also described `observe.rs`'s escape as being "for the fixture its wiring gate needs" when it is the same support-module `#[path]` as the other eleven. A number only prose holds is a number that drifts silently every time a test is added, which is what happened ten times. `crates/vigia/tests/package.rs::the_spec_names_every_test_that_escapes_the_package` is the replacement, and it earned its place on its first run by failing against **`package.rs` itself**: the file was written to enforce this bullet, escapes the package in order to read this bullet, and was not named in it. A gate that catches its own author on the first run is the strongest evidence available that it is not decorative.

## 11. Behaviour

§3 says how well `vigia` does things. Every number in it is defensible and every one has a test. Nothing above says **what happens when you press a key, or when nothing has changed** — and that gap is why the product reads as a screenshot with budgets attached.

### 11.1 What the shell does today

Most of this was back-filled from the implementation on 2026-07-30 rather than newly decided. **Follow mode is the exception**: it was ruled on 2026-07-30, as B1 and B2 below, and written here *before* the code existed — which is the order the README claims for everything and which §11's warning exists because this file did not keep. Where this disagrees with the code, the code is the bug.

**What the diff contains.** Working tree against the index. **Untracked files are included** and diff as all-additions — load-bearing rather than incidental, since creating new files is among the most common things an agent does, and a tool blind to them would miss its own use case. Rename tracking is **on by default**: showing a move as an unrelated delete plus add misdescribes what the agent did. Its streaming cost is the open question in §10, not a settled trade.

**The working-tree side is normalised the way git's clean filter would normalise it**, and the diff is taken against that rather than against the bytes on disk. Git does not compare raw bytes either: it runs the working-tree side through the clean filter first, so on a checkout with `core.autocrlf=true` — what the Windows installer writes — the CRLF on disk is turned back into the LF the blob holds before anything is compared. Skipping that made every line of every such file differ from its stored form, which is [#65](https://github.com/breferrari/vigia/issues/65): a 21-line edit drawn as **+905 −885**, and a file `git diff` calls unchanged drawn as a whole-file rewrite, on the installed default of one of three tier-1 targets. Two shapes, and the smaller is the one that was reported: with `* text=auto eol=lf` only an editor writing CRLF creates the discrepancy, while with no `.gitattributes` at all the checkout itself does, so *every* edit to *any* text file read as a rewrite.

**A file whose only difference is its line endings reports no change, and stays listed while doing so.** The second half is a ruling rather than a leftover. Dropping it from the list needs its content during `Frame::advance`, which is a read per changed file on the path I4 governs and is exactly what that invariant forbids; and a header count disagreeing with the body under it is the contradiction B3's empty state exists to remove. Both halves are also what git does, which is the tie-breaker rather than a coincidence: `git status` lists such a file and `git diff` reports nothing for it.

**The rules the filter applies are re-read once a frame, not once a process.** `.gitattributes` and `core.autocrlf` decide what a diff normalises, and both are things the agent in the other pane is free to write: a monitor that resolved them at startup would go on drawing the old answer indefinitely while a restart drew a different one, which is I5 failing silently over a window I3 measures in days. So `Frame::advance` drops the filter and the next working-tree read rebuilds it, which bounds staleness to one frame without giving up the laziness: a frame whose diffs are all reused reads nothing and so rebuilds nothing, and only a frame already going to disk pays. `gix` rebuilds its own attributes stack on every status walk, so this matches the freshness of the walk it is paired with rather than inventing a policy. `crates/vigia-core/tests/normalise.rs` gates it **through `Frame::advance`** rather than through two bare calls to `Worktree::diff`, because nothing in the latter marks a frame boundary and a gate written that way passes whatever the filter's lifetime is.

**`core.safecrlf` is not consulted, because it guards writing.** It makes `git add` refuse a file whose conversion would not round-trip, so that history cannot be corrupted by one; `git diff` ignores it entirely, which is checkable and is checked, since the same mixed-terminator file git **refuses to add** is one it reports as unchanged. `vigia` never writes, so the guard covers an operation it does not perform, and inheriting it meant failing the frame over one file with mixed line endings, on that frame and every frame after it, because the file stays mixed. One such file anywhere in the tree stopped the pane working. Found by auditing rather than by using it, which is the only reason it is not a third row in the table above.

**External filter drivers are not run, and that is §6 rather than an omission.** `gitattributes` can point the clean filter at an external program, and Git LFS is the common one: a repository using it sets `filter.lfs.clean` to a command. Running those would mean spawning a process per file per frame, which is precisely the shape §6 rules out when it takes an in-process diff over a `git diff` subprocess per tick. `eol`, `working-tree-encoding` and `ident` are pure Rust and do apply. What the ruling costs is recorded rather than hidden: under LFS the worktree holds real content while the blob holds a pointer, so an LFS-tracked *text* file diffs as a rewrite. That is not a regression, since it is what happened before any filter ran at all, and it is [#69](https://github.com/breferrari/vigia/issues/69). What decides that a file is **binary** is a separate question this file does not yet answer, and is [#68](https://github.com/breferrari/vigia/issues/68): the engine sniffs content for NUL bytes, which is git's fallback and not its rule, so a path the attributes declare `binary` is diffed as text anyway.

**The body is two regions: a pinned file list, a rule, and the scrolling diff.** This is B4, ruled 2026-08-01 as a **layout** question rather than the navigation one it was written as ([#66](https://github.com/breferrari/vigia/issues/66)). The proposal that stood here for two phases — *"one continuous scroll, list as map"* — answered *navigable?* and settled *is it a region at all?* underneath it, in the direction the code happened to have taken. `assets/preview.svg` draws the other answer and has since before the question was asked: `src/engine/watch.rs` appears **twice** in it, once at `y=92` in a block of three summary rows and once at `y=202` as the diff heading, with a rule at `y=178` between them, which one stream never does. §5.1's rule that a published artifact answering an open question **is** the answer applies to layout exactly as it applied to `f`. **The rule between them stays bare, ruled 2026-08-15 as §11.2 B11** ([#124](https://github.com/breferrari/vigia/issues/124)), and on what a heading *is* rather than on where the reader has scrolled: it is a `Painter::file_row` carrying the glance elements through the drawer both regions share, so folding it into a border line either strips those elements or puts a whole glance row in a rule. B4's own reason settles the rest, since the pinned list is already this repository's answer to a heading scrolling out of sight, and `Body::split`'s `rule: list > 0` makes the two coextensive so that answer is never absent.

**What it buys is the thing §5 calls the differentiator actually staying on screen.** Three of the four glance elements — sparkline, heat strip, counters — ride a `Row::File` heading, so in one stream they are visible only while that heading is, and scrolling two hundred lines into a file takes every file's glance signal off the screen at once. That is the inverse of what a monitor is for: §2 buys *readable at a glance*, and a glance surface that survives only at scroll position zero is a glance surface that is absent whenever anyone is actually reading.

**The list stays not navigable, which is the half B4 proposed and which stands.** There is no selection, no focus and no second mode: `▸` marks the file the diff is inside and is not a cursor, and no key changes meaning depending on where anything is. B4's own rationale is the reason — *selection implies focus, focus implies a second mode, and modes are reviewer-class* — and it is honoured here rather than overridden. The region is a **map**, which is what "list as map" wanted and what a stream of headings could not supply, because §11.2's phrasing presupposed a list to be a map *of* and there was none, there were headings.

**Its height is the changed-file count, capped at six, plus the rule.** Three changed files draws three rows, which is the picture exactly; a formatter touching two hundred draws the cap and scrolls. Six is the largest block that still reads as a glance rather than as a list to be searched, and on the 24-row pane this tool is built for it leaves fourteen rows of diff after the header, the rule and a one-line footer.

The height is a function of **pane geometry, follow state and changed-file count**, which is exactly the set `Footer::plan` takes, because the list divides whatever the footer leaves. None of those is transient, and that is the property being bought: the region cannot jog a reader's diff the way a notice or a passing failure would. It does move when the footer does — `f` on a forty-column pane takes a second footer line and the list gives up a row for it — and that is a reader's own keypress changing the shape of the screen, which is the same thing pressing `f` already did before this region existed. It gives way on a short pane the way the footer gives up its second line, and the diff keeps `MIN_BODY` rows before the list gets any.

**The list is ordered the way the stream is**, which is `Frame::files()`, which is status order. That is what makes it a map rather than a second opinion: the caret's place in the list and the thumb's place on the diff's scrollbar then describe the same position. Ordering by diff size was rejected on I4 — it needs every changed file's diff, which is [#49](https://github.com/breferrari/vigia/issues/49)'s argument against a repository-wide total arriving in a second place, landing here identically. Ordering by recency from `History` is genuinely free and was rejected for a different reason: it decouples the list from the stream, so the caret stops corresponding to the scroll position and the map stops being one.

**A list row draws exactly what a heading in the stream draws**, through the same `Painter::file_row` and the same degradation ladder. This is the **second deliberate departure from `assets/preview.svg`**, beside the header's worktree name, and it is recorded rather than absorbed: the picture splits the elements across the two regions, giving the summary rows no kind letter and the diff heading no counters. That split stops being defensible the moment the list scrolls, because a file scrolled out of the region would lose its counters altogether and there would be nowhere left to read them.

**A region's file rows draw their glance elements in columns**, which is [#77](https://github.com/breferrari/vigia/issues/77) and which the picture had promised since before anything was built. Every element used to come out of a budget that had already lost the elements outside it, so its position was a function of *their* widths on *that* row, and the counts cell is the widest variable thing there. Three sparklines then failed to read as one small-multiples chart, which is the reading a list exists to give. So the ladder runs **once for a region** and every row draws into the slots it produced. Its order is unchanged: counts, then the pulse, then heat, then sparkline.

**A row that has no such fact keeps the column rather than closing it.** This is the half that makes it universal rather than occasional: a file with no line diff has no heat strip, and until [#78](https://github.com/breferrari/vigia/issues/78) a file that had not been written since launch had no sparkline either, which at launch is every file. Under right-packing each absence let that row's remaining elements slide into the space and pulled it out of line with its neighbours. The sparkline's half of that is now a **track** rather than a blank; the heat strip's is still a blank, and the paragraph below on the two strips' empty states says why the difference is a ruling rather than an inconsistency.

**The counts cell is two columns and not one field**, `+N` right-anchored in its own and `-M` in its own, one space apart, which is what the picture draws. A single field aligns whichever end it is anchored to and leaves the other ragged, so an eye running down three files' additions gets the same non-comparison this ruling exists to remove.

**Each half is drawn in its own diff colour, and a half with nothing to say is drawn in the row's dim grey.** `+42` green, `-7` red, `-0` grey ([#157](https://github.com/breferrari/vigia/issues/157)). It is §5.3's rule rather than the picture's, though the picture draws it too: green and red are lent out only where they restate the same fact, and a zero restates none. Drawing it red anyway would cost the element its whole reading, because a worktree an agent is only adding to would then carry red on every row and answer nothing. **Presence is shared and ink is per half**, which is the one place these two rules pull apart: the pair is drawn or dropped together for the reason the width paragraph below gives, and a renderer that greyed a whole cell because one half was zero would be applying the wrong one of the two.

**The slots come from the pane and never from the rows**, and that is the ruling the first attempt got wrong. Sizing the counts field to the widest count among the rows a region was about to draw holds *within* a window and moves *between* windows: scrolling a list until a file with `+1500 -1500` enters it widens the field by six columns and slides every heat strip and sparkline on every row. Reported from use within an hour of the branch running, which is the sixth time a defect on this surface has been. Intermittent movement is worse than a layout that is simply wrong, because there is nothing on screen to argue with. So every slot is a constant or a rung of the pane's width, and nothing a reader scrolls past can move anything. Measuring over every changed file instead would also be stable, and is forbidden for [#49](https://github.com/breferrari/vigia/issues/49)'s reason exactly: it needs every changed file's diff, which puts the frame back in proportion to the size of the diff against I4.

**Each region plans its own**, because the two are different widths: the list insets by the caret, and that is now the only difference, since both pay the scrollbar column whether or not one is drawn. Neither reads a row, so a heading scrolling past cannot move the pinned region above it.

**Every slot is reserved whether or not anything can fill it**, including the sparkline in a region where no file has a history yet, which at launch is every file ([#78](https://github.com/breferrari/vigia/issues/78)). The alternative was tried: reserving only what some drawn row could fill moves every column on the tick the first file is written, which is precisely the moment a reader is looking at the screen. What it cost when this was written was a row that is mostly blank until the first write, and at forty columns that was most of the row. **That price was paid twice and is now refunded once**: [#78](https://github.com/breferrari/vigia/issues/78) fills the reserved sparkline slot with a track instead of leaving it blank, so the slot a reader could not see the point of is the one that now says *no churn in the window*. Reserving the column was the decision that made saying so free.

**And a region is planned against the pane less a scrollbar column, drawn or not.** A bar appears when `scrollable` finds the region cannot show all it holds, so its presence is a fact about the **contents**: a seventh changed file, or a diff one row taller than the screen, narrowed the region by two columns and re-planned every row in it. At some widths that slid the elements sideways and at others it crossed a rung and took the counts cell off every row of the list. That is the same defect this section rules out one axis over, and it survived the first fix because a scrollbar does not look like content. §11.1's own `CARET_FLOOR` had already ruled the identical hazard the same way, counting the bar's columns on a screen with no bar so the caret cannot appear and vanish with the file count.

**What it costs is the sparkline between 40 and 41 columns**, on top of the 36 to 39 the counts cell took, so the sparkline now needs 42. That is the second time this ruling has been paid for in the same element, and it is worth stating plainly rather than burying: at exactly the width I6 is named for, a pane shows the heat strip and the counts and no sparkline. The alternative is not "a sparkline at forty" but "a sparkline at forty until a seventh file changes", which is the intermittent layout this whole section exists to refuse, and an intermittent view is worse than a smaller one because there is nothing on screen to argue with. The two blank columns on a pane with nothing to scroll are the visible price, and they are the same price the reserved-slot ruling above pays for the slots a row can still fail to fill, which since #78 are the heat strip's, the pulse's and the counts cell's: the sparkline's is the one that stopped being among them.

**And the pane stands back from its own edge, on a ladder of its own.** `assets/preview.svg` draws its furniture to the window edge and its glyphs one to three cells inside it: the row washes span `x=8 width=884` and the region rule runs `x1=8` to `x2=892`, which is the window exactly, while the nearest glyph is the caret at `x=16` and the text proper begins at `x=32`. The shell drew everything from column 0, and by §5.1's own law that made it a fourth undocumented departure from the picture rather than a choice. Ruled 2026-08-10 towards the picture ([#119](https://github.com/breferrari/vigia/issues/119)): **one cell a side from 44 columns, two from 80, and nothing at all below 43.** The floor is I6's, not a rounding, since the sparkline has been bought and sold twice in the paragraphs above over two columns at exactly forty. **Forty-three rather than forty-four is the odd rung and not a slip:** the total climbs one column at a time for the reason the next paragraph gives, so the first of the pair lands a width before the second. What the floor protects is the forty-column pane, three columns clear either way. `crates/vigia/tests/legibility.rs::the_pane_insets_its_text_at_every_rung` sweeps the drawn column at every width, and `the_inset_never_reaches_the_forty_column_pane` is the floor.

**The margin is a ladder of the *total*, split between the two sides, and that is a ruling rather than arithmetic.** A per-side ladder steps both sides on the same column, so it spends two columns for the one a widening pane just gained, and the content width goes *down* where it should go up. That is what the layout table above is written out to refuse, one element further out, and it is not a hypothetical: taking both sides at once grew the footer to two rows at 44 and at 80, spending a body row on a **wider** pane, and walked the header's worktree name from marked back to whole as the pane *narrowed* across 80. Both were caught by gates that already existed. So the total climbs by one per rung and is split with the odd column going left, which leaves the pane square at every width except 43 and 79. The left is the side that goes first because a reader registers it as the edge of the page, and because the regions already take their left from this ladder while their right is the scrollbar's.

**The inset is charged to a region on its left alone**, and that is what makes it affordable. A glance row already stops two columns short of the pane's right edge for the bar, drawn or not, so the columns a right-hand margin would want are standing there; `planning_width` spends them once. A row therefore loses its rung's width in path and never twice it, and at 80 columns the pane's two margins come out equal. This holds only while no rung's **right half** exceeds the bar's reserve (the rungs count the whole margin across both sides, so the widest is four and its half is two), and `the_inset_never_outgrows_the_scrollbars_reserve` is what fails if one ever does, because a wider half would reinstate the trailing reserve the paragraph below refuses and needs that ruling re-decided rather than silently worked around.

**The diff's content rows are the one class this does not describe, and they get their own rule.** A hunk header, a note and a content line keep the *region's* right edge rather than the pane's, which is older than the margin and is why they move by two columns when a diff outgrows its pane and takes a scrollbar. The margin does not compound with that: a content row stops at whichever of the region's own edge and the pane-less-margin is already further in, so wherever a bar is drawn it lands exactly where the heading above it lands, and where none is drawn it stands back by the margin like the chrome. Charging both put a content line two columns left of its own heading on precisely the screens where the diff was long, which is the contents deciding the layout that this section refuses everywhere else. `a_diff_outgrowing_its_pane_does_not_move_the_content_rows_edge` gates the agreement, and `the_pane_keeps_its_trailing_margin_with_nothing_to_scroll` gates the other screen, because the first draws only barred panes and the margin term is unreachable from it. Giving these rows the bar's reserve unconditionally would make them agree at every width and is deliberately **not** done here: it costs every content line two columns at forty, which is I6's question and not this one's.

**So a residual survives, and it is stated rather than left to be rediscovered.** The movement is the scrollbar's reserve less the trailing margin: two columns below forty-four, one from forty-four to seventy-nine, and none from eighty up. Forty-three is not in the improved band, because its rung is the odd one and spends its single column on the left, so its trailing margin is zero and it behaves as before. Reduced and bounded is what this issue buys; removing it outright is the I6 trade above.

**The counts cell is two fixed halves of five columns**, `+9999` and `-9999`, with magnitude giving way to a shorter form past that rather than to more digits: `+10k`, `+999k`, `+1M`, `+4G`. Five is the narrowest width at which that abbreviation is **total**: a narrower rung was tried and drew `+0k` for a 250-line change, because two characters have no truthful form for it and the search fell through to the thousands unit. It cost the sparkline between 36 and 39 columns to fix, which is the honest trade against a number that says none when it means two hundred and fifty. That is the rule the status bar's frame and memory cells already follow with `>1s` and `>1GiB`. A field wide enough for `+4294967295` would spend eleven columns a row forever on a number no file reaches. **The halves do not narrow**, and they are the only thing on the row that does not: a narrower cell is what drew `+0k`, so the width is the correctness rather than a preference. They go together or not at all, because `+42` with no `-7` beside it reads as a total rather than as half a pair, and below the width that holds the pair the row draws its path alone.

**A rename's label is a rung, not a token to be cut.** A row draws `new ← old` whole or it draws the new path alone; it never elides the pair. Every other label on screen loses its *head* when it does not fit, because a path's tail is what identifies the file, and that premise is false of a pair: cutting the head of `new ← old` leaves a tail belonging to `old`, so the row names the file the rename came **from** and never the one it is about. That is worse than a truncation, because nothing on screen says it happened. The rule was latent while the row right-packed and left the path more room, and ordinary once the columns above took it.

**The layouts are written out as a table rather than allocated element by element**, and that is what makes narrowing monotone. Allocating greedily in priority order is what the rest of this document's ladders do, and for a *shared* layout it oscillates: measured across every width, the row lost its sparkline at 37 columns, got it back at 40 and lost both glance elements at 41, because each element took the widest rung it could afford and starved whatever came after. Those three widths were measured while the counts cell still had a narrow rung, so they do not reproduce against today's table; they are kept as the evidence that retired greedy allocation, not as a claim about the current one. Widening a pane must never take something away. Each row of the table gives up exactly one thing against the row above it and gains nothing, so the whole ladder is monotone by construction rather than by argument. The drop order, narrowing: the sparkline's resolution, then the strip's, then the sparkline, then the strip, then the pulse, and the counts last, because they are the row's content rather than a signal drawn beside it and because the cell no longer has a narrow rung to give up first. `crates/vigia/tests/legibility.rs::the_glance_columns_collapse_in_one_order` asserts the monotonicity as a rule and pins the walk with the width each state begins at, because a rule alone cannot see a boundary that moved.

**The ladder lost its top rung on 2026-08-03 and no boundary moved with it.** It used to open by dropping the pulse **label**, which is the rung §5.1 has now retired everywhere; the pulse is one column at every width it is drawn at all, so the table is six steps rather than seven and the widest layout is the one that used to be second. Every boundary below it is unchanged, because a layout's width is the sum of its own slots and none of the surviving six changed: what went is a fourteen-column rung that only existed above sixty-five columns, and the walk `the_glance_columns_collapse_in_one_order` pins is identical. That is the check worth stating rather than the arithmetic. **A rung removed from the top of a monotone ladder can only be free**, and a rung removed from anywhere else cannot be, so this is the one edit to that table that does not have to re-derive every width under it.

**There is no trailing reserve beyond the scrollbar column ruled above.** The picture leaves about a sixth of the row blank on its right, and *that* is an artifact of a fixed canvas at a width where nothing degrades rather than a promise; spending it at forty columns is what I6 forbids. The two columns a row does stop short of the pane's edge are the bar's, paid whether or not a bar is drawn, and they are the price of the ruling above rather than a margin. **#119 does not change this and is the reason it is worth re-reading:** the pane's inset is a *leading* margin, and the reason it costs a glance row one column per rung instead of two is precisely that this ruling stands and the trailing columns stay the bar's. A reader who takes the two blank columns on the right of a wide pane for the inset's other half has the arithmetic backwards, and a future rung wide enough to need columns of its own would be reinstating the reserve this sentence refuses. The claim that *is* load bearing is the other one, and it holds: the columns are decided before the path is drawn and the path takes what is left, so scrolling a long path into view cannot move them.

**A visible list row costs one `Frame::diff` and no more**, which is what keeps the region inside I4 rather than beside it. The bound is the region's own height, never the changed-file count, so the cost follows the window exactly as the body's does. That is an I4 claim rather than a new invariant, and `crates/vigia/tests/reads.rs` is where it is gated, alongside the ones that already bound the body.

**What that row costs depends on which side of the settle margin the file is on, and both halves are worth saying.** Settled, it is a `stat` and a cache hit reading **zero bytes**, which is I2a doing its job and is the state a monitor sits in for almost all of its life. *Inside* the margin it is a real read, because `Frame::diff` cannot prove a file written in the last two seconds unchanged and re-reads it by design. So a six-row region on a tree being actively written costs six reads a frame rather than six `stat`s, and the earlier claim here that the region's doubled ask was "a count that doubles and not work that does" was true only of the settled half.

**The two regions therefore hand entries to each other rather than asking twice.** The file an agent has just written is the one file the margin is certain to cover, it is always the file the diff is inside, and it is always in the window while the list follows, so asking the frame for it a second time read and diffed it again on **every frame this tool exists for**: 258,790 bytes where 36,970 will do, measured over twenty files of five hundred lines. `View::collect`'s walk now records the entries it builds and `take_list` draws from those, which is the same one-pass rule that section of the code already followed for the diff. `a_screen_a_single_file_fills_reads_that_single_file` gates it as a relation, that the region computes one fewer diff than it asks for, so it survives a change to the region's height.

**The list follows the diff, and `J`/`K` move it without moving anything else.** It slides on its own to keep the caret visible, so the region is correct untouched the way I5 requires of everything else. Shift is the modifier because `Ctrl-J` is LF and `Ctrl-C`/`Ctrl-D` already quit, Alt is intercepted by terminal emulators and by macOS Option, and `G` has already taught a reader that case is load bearing here. A plain letter also reaches terminals that never report a modified arrow, so neither binding is the only way in.

**`J` takes the window over, and anything that moves the diff hands it back.** That is the list's own version of follow mode, and it is a mirror rather than an analogy: a manual scroll takes the *diff* away from following and gives the *list* back to it, in the same line of the same function. It was ruled the other way first, as *snap back when the diff lands outside the window*, and that rule is wrong in a way only building it showed: the window can never be away from the current file in the first place, because the frame after `J` drags it straight back, so the keys do nothing. The two halves are both load bearing. Without the takeover `J` is inert; without the handback a reader who browsed once has a map that never agrees with the diff again. **The caret marks the current file whenever the window still shows it, and is simply absent once a browsed window has moved off it.** It is not suppressed by the takeover, and that distinction is worth stating because the opposite reads as the tidier rule: the caret says *the diff is in this file*, which stays true while a reader browses, and hiding it on a window that is showing that file would withhold a fact the reader can act on. What the takeover changes is where the window looks, not what the mark means.

**Scrolling the list does not disengage follow mode**, and that is a ruling rather than an omission. Follow is a claim about the **diff** viewport, and moving a window over a map expresses no intent about what the diff should show — the same reasoning that already exempts a terminal resize one paragraph down. Browsing the changed set while the diff goes on following what an agent is writing is the monitor behaviour, and the two would fight if one disengaged the other. `Action::is_manual_scroll` is an exhaustive match precisely so that a new action has to answer this rather than inheriting a default.

**Both regions carry a scrollbar, and both are exact.** The list's thumb spans the visible window over the changed-file count, both of which are free. The diff's spans the screen's rows over the diff's **total** rows and sits at the rows above it, which is what every other scrollbar means.

**The diff's was ruled coarse first, and that ruling was wrong.** It read that a total needs every changed file diffed, which I4 forbids, so the bar approximated the whole from the current file's height. Reported from use within the hour: it vanished on a short file, ballooned on a long one, and never reached the bottom, because the trailing files are rarely the height of the one being read. The argument was right that *diffing* every file is unaffordable and wrong that a total needs it. A height is hunk boundaries and line counts; a `FileDiff` is those plus an owned `String` per drawn line. Counting instead of building took the reference fixture from **442.71ms to 8.76ms**, against `git diff --numstat`'s 46ms for the same work, and §3's I4 now carries the narrowing that admits the walk.

**The half page is `d` and `u`, and it keeps no overlap row where a whole page does.** They are `less`'s own bindings and the follow-mode paragraph below already claims `less +F` semantics, so the precedent is internal as well as cultural; both letters were free. A page steps `height - 1` so that one row survives the seam and a reader does not lose their place; a half page already leaves half the screen standing, so taking a row off it as well would pay twice for one anchor and leave `d` and `u` out of step with each other. Both directions floor, which is what makes the pair an exact inverse on an odd body as well as an even one. **`Ctrl-D` and `Ctrl-U` are refused rather than overlooked**: `Ctrl-D` is one of four ways out, and rebinding a way out to a scroll is the surprise this map has avoided everywhere else. `D` and `U` are unbound for the reason `F` is, one row above a pair where case is what tells the two apart. [#121](https://github.com/breferrari/vigia/issues/121).

**And the half page is not hinted, because at eighty columns the footer is exactly full.** [#121](https://github.com/breferrari/vigia/issues/121) proposed `du half` as a bonus rung above the ladder below, on the argument that it would ride at widths with room. There is no such width where it matters: with follow engaged, a position and both readouts, the row is 40 columns of hints, 2, 19 of readouts, 2 and 13 of state, which is the 76 that eighty columns leave after the inset, to the column. A fifth hint is therefore paid for out of the readouts — the frame time would first arrive at 81 columns instead of 69, and the pair at 89 instead of 77 — and `render__the_status_bar_carries_what_a_frame_cost.snap`, the picture whose job is to show this layout is *good* at one width rather than merely legal at every width, would have lost both cells. Refusing it costs little: `Space`, `PgDn` and `PgUp` have never been hinted either, and the bar's four hints are the way out, the state whose absence is invisible, and the two vi-dialect keys for the rows and the region. A half page is a pager reflex of exactly that unhinted family. `crates/vigia/tests/legibility.rs::a_wider_hint_bar_cannot_quietly_push_the_readouts_out` pins the two boundaries so the next hint added above the baseline has to argue for what it spends rather than take it quietly. **What stays open is the ruling underneath, and it is not this one**: whether a bonus rung is exempt from the drop order below, which puts advice above instrumentation at every width, or whether being unowed makes it the one thing that yields to a readout. [#147](https://github.com/breferrari/vigia/issues/147).

**The file is a granularity, and until [#122](https://github.com/breferrari/vigia/issues/122) the map had every other one.** Rows are `j`/`k`, screens are `Space` and `d`, the two ends are `g` and `G`, and not one of them is the unit the pinned list draws, the header counts and the reader thinks in: reaching the next file meant holding `j` through the rest of this one or reaching for the mouse, which already had the gesture. `n` and `p` step one changed file. `1` to `6` put the diff at the Nth row the list is drawing. All of them land on the file's **heading**, which is the resolution a click on a listed file and a follow jump already use, and none of them costs a diff: a heading is row zero, so nothing here asks how tall anything is and I4 never sees it. **B4 is untouched.** All three move the *diff*, exactly as a click does, and nothing is remembered: no row becomes special, no focus appears, and the event after one means what it would have meant.

**`p` from inside a file goes to the previous file, never to the top of the current one**, and at either end of the changed set the step moves nothing at all. The pager reflex of "this section first" is refused because it would make one key mean two things depending on where the viewport happened to be, which is the rule this whole map is built on, and because `g` is already the key that reaches a top. Clamping the file index rather than refusing the step is refused for a neighbouring reason: it would give `n` at the last file a *backwards* jump to that file's heading and `p` at the first a forwards one, a key undoing what its own letter says. **Follow mode is still disengaged at both ends**, where nothing moved, because on this map follow yields to a reader's intent rather than to whether the arithmetic landed somewhere new. `g` at the top and `G` at the last file already behave that way, and the alternative reading is the one `J` at the last window takes: that one is right there because the state it protects, the map having quietly stopped following, has nothing on screen to announce it, where `follow ▶` leaving the footer is visible.

**The digits address the window, not the changed set.** `3` means the third row the list is drawing, so after browsing with `J` it names a different file than it did before: what you can see is what you can name. Two bounds make that true, and **which one does the work was settled by mutation rather than by argument.** A digit past the **drawn rows** is the ordinary case and is one only a keystroke can reach, because a pointer is bounded by the region and a keyboard is not: a nine-row pane gives the region four rows while `5` and `6` stay under the reader's hand. The **file count** bound then looks redundant, and reading says it is: with the window bound in place, no digit on a freshly drawn screen can name a file past the end, because the window is never taller than what is left below it. What it actually guards is the screen being **out of date**. The row count is what the last frame drew, so between a paint and the keystroke that follows it the changed set can get shorter, which is `git reset --hard`, a branch switch, or the agent in the other pane reverting its own work: six rows were on screen, two files are left, and `6` still passes the window bound because the window is remembered from the frame that drew six. **A click on a listed file puts the diff at it.** The gesture a reader tries without being told, next to a region that draws the names of the things it is a map of. **And the pointer is acknowledged only when it acts, never when it merely arrives: there is no hover state, ruled 2026-08-15 as §11.2 B10** ([#123](https://github.com/breferrari/vigia/issues/123)). **The wheel reads where the pointer is, and it is the only thing in this shell that does.** A reader hovering the map and turning the wheel means the map. §2 makes `btop` the reference and that is what `btop` does. **A drawn thumb is a published affordance, so both are draggable**, and a press anywhere on a track jumps to it. The scrollbar column is tested before the region containing it, or every drag would read as a wheel.

**A track maps onto travel, not onto the whole.** The list's travel is its file count less its own height; the diff's is its total rows less a screenful. **Scroll position is `(file, offset within that file)`, never a row index.** A frame that changes something above the viewport therefore does not teleport the view. This is a correctness property, not an implementation detail: with a row index, an agent writing to a file earlier in the list would yank the reader's position on every keystroke it makes.

**A position past the end of the diff resolves to the last screenful, not the last row.** The two are not the same place, and taking the second for the first draws one line of content over a blank screen while the header goes on truthfully saying how many files changed: one thing on screen contradicting the other two, which is the ambiguity B3's empty state exists to remove. Reachable two ways, and **only one of them is scrolling**. Backing off from an end already in hand still costs a screenful.

**Follow mode**, which is I5. `less +F` semantics, and the toggle the README mockup already published: follow is **on at startup**, **any manual scroll disengages it**, and **`f` re-engages it and jumps straight to the newest change** rather than waiting for the next one. The footer shows `follow ▶` while it is engaged.

Two boundaries are load bearing, because each is a way for the mode to be quietly wrong rather than visibly broken. A **terminal resize does not disengage**: it moves no viewport and expresses no intent, and a monitor beside an agent is resized constantly. And **`G` disengages rather than re-engaging**, because "jump to the last changed file" and "resume following" are different intents that would otherwise be the same key, leaving a reader unable to look at the newest file without also re-arming the view.

**The newest change is the file whose write landed last in the settled batch**, and the batch is the coalesced tick. A monitor cannot find that file by looking: `stat`-ing every changed file is the cost [#19](https://github.com/breferrari/vigia/issues/19) already records as breaching I9 at scale, and I4 forbids reading files the frame does not draw. It does not have to look, because the filesystem event already carries the path. `Tick` reports it, so following costs no read, no `stat` and no diff. When the named path is not in the diff — an index write, or an edit reverted before the tick landed — the view stays where it is, because there is no newest *change* to follow.

**How the chrome fits**, which is I6. One rule, and the layout follows from it: **a thing made of items breaks, a thing made of characters marks its edge, and content is neither.**

The **hint bar is a list**, so when the footer cannot hold both halves on one line it takes a **second line** rather than shortening anything. The state moves to the upper of the two and the hints keep the bottom row, so narrowing a pane never moves the hints out from under a reader's eye. It grows only while at least two body rows survive — a monitor with no diff left in it has stopped being one — and only when there is a state worth moving. A notice, which replaces the hints, inherits that whole line when there is one, but **never causes it**: a notice is transient, and a footer that grew for one would jog the reader's diff down a row and back every time a file vanished between being named and being read. The height is a function of width, follow state and changed-file count, all of which change only when the diff does.

Below the width where even a full line holds the bar, it drops **whole hints** and never part of one: `JK files` first, then `jk scroll`, then `q quit`, leaving `f follow` last.

**And `JK files` is a bonus rung, which is a rule rather than a position in that list.** The footer's height is decided by the widest bar a reader is owed at forty columns, not by the widest bar that exists; rungs above that are drawn where there happens to be room and are never worth a row. **Neither readout can change how many rows the footer takes**, and that is a rule rather than a consequence. `Footer::plan` decides its height from the state ladder alone, exactly as it did before these existed, and the diagnostics take only what is left after the hints have their widest fitting rung. Two things would otherwise jog a reader's diff down a row and back for no reason they could see: the frame cell **does not exist on the first paint**, because no frame has completed to have a p99 of, and the memory cell does not exist on a platform with no cheap read. **The footer's right-hand side carries three colours, and they are the picture's.** `assets/preview.svg` draws `0.8ms` and `24MiB` in its cyan, the word `frame` beside them in the same grey as the hints, and the follow marker in green. Both styles are **reused rather than named anew**, which keeps this a reading of the picture rather than a palette decision: the cyan is the same one every other structural mark uses and the green is the diff's own added colour, each matching the picture to the byte on the dark palette. That is the reuse `not watching` already makes of the alert.

Drawn as a **second pass over the cells**, not as separate placements, and that is load bearing rather than an implementation note. Each readout is part of a token a ladder picks whole: `0.8ms frame   19MiB` is one rung and `follow ▶  N/M` is another. Placing each colour separately would take the choice of what to draw away from the ladders and would oblige the footer's width arithmetic to know about colour. Tinting afterwards cannot move a column.

**The pass must terminate and must not reach past the diagnostics**, and both are rulings rather than implementation notes because both were got wrong. A walk that asks whether a cell *opens* a measurement and whether it *carries* one has to consume the opening cell whatever it says: `>` answers yes and no, so on `>1s` the two questions spun against each other and the pane froze mid-frame. And the marker is found within the state's own columns, never the whole row, because a notice is an error string carrying a path and `▶` is a legal filename character: scanning the row let a file name fabricate the one glyph that says the view is live.

**Both cells are a constant width whatever they say.** `0.8ms frame`, ` 12ms frame` and `999ms frame` are all eleven columns, and the number is right-aligned inside them, so a value changing between frames never shuffles what is beside it. Past the field, magnitude gives way to a sigil rather than to precision: `>1s` for a frame and `>1GiB` for memory, because the exact value at those magnitudes tells a reader nothing the sigil does not, and a number that grew a column would move the footer under their eye.

The **header never grows**, and after the ruling above that has to be said of both sides rather than of one token. A worktree name is not a list and has nowhere to break, so it marks its edge like every other single token; the clause it now leads *is* a thing made of items, and it breaks the way the rule says by dropping a whole rung rather than by taking a line. A second line could not guarantee a fit either way, and it would spend a body row on a maybe.

**The header is laid out by subject, the way the footer is.** Two facts about the **tree** on the left, the worktree name and then how much of that tree has changed, and the one fact about **`vigia` itself** on the right, which is whether the watch is still live. That is the three-subject rule the footer runs on further up — advice, then what the tree is doing, then what `vigia` is doing — applied to the row at the other end of the screen. **The grouping is borrowed and the priority is not**, and the difference is worth stating because the two rows rank the same subject oppositely: on the footer, what `vigia` is doing is the least a narrow pane owes anyone and the diagnostics drop first, while on the header the self-fact is the last thing standing. Neither is inconsistent, because the priority was never the subject in the first place. It is **recoverability**: the footer's readouts describe a budget and a number that barely moves, and both are recomputed on the next frame, where a header that has stopped saying it is live leaves a reader with no way to find out. It is a ruling rather than an arrangement, and [#67](https://github.com/breferrari/vigia/issues/67) is what it costs to get wrong: the header used to seat the count beside the mode word, where `watching · 3 files` read as *"watching 3 files"*, a participle with an object naming a curated watch set that does not exist and that B6's no-flags ruling puts out of scope. The count reads `changed` rather than `files` for a reason that only appears once it has moved: `vigia · 3 files` would be a **worse** claim than the one it replaced, since the repository has more than three files in it. It is also one rule where there were two, because `changed` is a participle with no plural to inflect.

**The ladder keeps its order and changes only which side each rung is dropped from.** Widest first: `{worktree} · {N} changed` with the mode word, then the worktree name with the mode word, then the worktree name alone. **The left-hand side leads with the worktree, not the program**, and this is the first of the two places the layout departs from `assets/preview.svg` on purpose, the other being §5.1's element split. The picture puts `vigia` there. Written here 2026-07-31 rather than left in a code comment, because §5.1's own rule is that a published artifact answering a question is the answer, so a deliberate departure from one is exactly the thing that has to be argued in the open or it reads as drift.

And it is the worktree's own name **even when the path it was given does not contain one**. `vigia .` hands `gix` a workdir of `.`, which has no final component, so the header drew `.` — the single thing it exists to say, and the one thing it could not. The path is resolved for **display** before its last component is taken. Display only: the value the watch compares event paths against is left alone, because resolving it there would introduce `\\?\C:\` on Windows and `/private/var` on macOS, and [#30](https://github.com/breferrari/vigia/issues/30) is the record of what a root that matches no event path costs.

**The mode word, and the set it implies.** It sits on the right, alone. The mockup drew it there with the count beside it; `assets/preview.svg` was corrected with the ruling above rather than departed from, so the picture and the shell agree on this row and the deliberate departures stay at two.

| Mode | What it means |
|---|---|
| `watching` | the watch is live, so the screen follows the tree |
| `not watching` | the watch never armed, or it ended, so this is a still picture |

**Two, and I1 is the reason rather than minimalism.** §5.1 read `watching` as implying at least a settling state and an idle one. It implies neither, because both are *durations* and this shell wakes only when something changes. `Watcher::next_tick` blocks until a burst has settled, so the shell is never awake **during** settling and could not draw it without a redraw nothing schedules; and "idle" needs a wake that says nothing happened, which is the timer I1 forbids. Either word could come into existence and then never leave, which is precisely the frozen clock the recency ladder above rejected for the pulse. A header that lies about the present until the next file is written is worse than one with fewer words in it.

**The word starts at `watching`, before the watch is armed.** Arming happens after first paint on purpose, so the watch does not observe the shell's own setup reads. A third word for those microseconds would flicker on every single launch to describe a state that always resolves the same way within one wake, and when arming genuinely fails the failure arrives as its own wake and corrects the word.

**`not watching`, not `stalled` and not `still`.** It is the mockup's word negated, so a reader who has learned one has learned both. `stalled` reads as temporary when this is not, and `still` means both "motionless" and "continuing".

**The mode is state, so the reason for it is not.** A watch that ends puts `not watching` on the header **and** its error on the footer as a notice. The header carries what is durable — this diff has stopped being live — and the notice carries which failure did it, which is not. Before this the durable half rode the notice alone, and survived only because the tick that clears a notice can never arrive again once the watch is gone.

**And a dead watch is drawn loud while a live one stays quiet.** `watching` takes the header's dim grey, the one the footer's own secondary tokens are drawn in; `not watching` takes the footer's alert. The changed-file count left that class with [#67](https://github.com/breferrari/vigia/issues/67) and now takes the worktree name's weight, which is the ruling one paragraph up rather than an exception to this one. A state nobody can catch at a glance has not been reported, and §5 makes colour half the differentiator, so a header whose failure looks exactly like its working state fails twice. It is the **footer's own** alert rather than a colour of its own, because the notice carrying which failure already uses it and the two halves of one event should not arrive in two different reds. That is a reuse of an existing style rather than a palette decision, which stays [#11](https://github.com/breferrari/vigia/issues/11)'s.

**The mode word outranks everything else wherever it fits at all**, which is why it holds the side that is placed first: the count summarises a body that is on screen and can be recovered by counting it, and whether the pane is still live is recoverable from nowhere. That is the footer's own rule further up, and it matters most at exactly the widths where the body has nothing in it to count.

**It is not, however, the last thing standing on the row, and the difference is measurable rather than pedantic.** The two sides have independent budgets: the word is all-or-nothing at its own width, while the name marks its edge at any width above zero. So on a live watch the name has the row alone from 5 to 7 columns, the word takes it alone from 8, a marked fragment of the name rejoins it at 10, and both are drawn whole from 14; with `not watching`, four columns wider, those are 5 to 11, 12, 14 and 18. Widening a pane from 7 to 8 columns therefore *removes* the worktree name. That is unchanged behaviour and it is what placing the right first has always meant; it is recorded because the tidier claim — one total order over three facts — is false, and this file's own rule is that an invariant with no failing test is a wish. There is no test for the tidier claim because there is nothing true to gate.

They were wrong here first: this said both facts appear from 13, where 13 draws `vig› watching` and only 14 draws the name whole. A measurement quoted in prose and nowhere else drifts from the thing it measured, silently, because no document fails.

**The count is nothing at all when it is zero**, the same way a position is nothing when there is no diff to be positioned within. `0 changed` spends columns restating what the empty state says below in words.

**And there is no fourth fact.** The header carries the worktree, the changed-file count and the mode word, and it does not carry a repository-wide `+`/`-` total. That is a ruling rather than an omission, and it is [#49](https://github.com/breferrari/vigia/issues/49): a total needs every changed file's diff, which puts first paint back in proportion to the size of the diff and is exactly what I4 forbids, and computing it behind the frame to dodge that needs a wake no filesystem event caused, which is I1's. §10 carries the argument and §5.1 records what it settles about the mockup. `crates/vigia/tests/render.rs` gates it over the drawn row rather than over what a frame cost, because a total computed on a handle of its own would never reach the stats `tests/reads.rs` reads.

**And the mode word is never cut.** It is drawn whole or dropped, which is stricter than the marking rule the rest of the header follows: `wat›` is a state a reader cannot read, and unlike a path it has no half that identifies it. **What delivers that is `put_right`, which draws its token whole or not at all**, rather than a ladder of the word's own. It had one until [#67](https://github.com/breferrari/vigia/issues/67), because this side carried the count too and so had a real choice to make; moving the count left left a ladder of one rung wrapped around a mechanism that was already doing the work, and two mechanisms guaranteeing one rule is a rule nobody can locate.

**The empty state**, which is B3. This is the screen the tool sits on most of the time, and the first thing anyone sees when they open it beside an agent that has not written yet, where a blank pane and a hang look identical.

Four facts, two of which the header already carries, so the body spends one line rather than four:

| Fact | Where it is drawn |
|---|---|
| which repository | the header's left-hand side |
| that it is watching | the header's mode word |
| which branch | the body line |
| that there is nothing to show | the body line |

The line reads `no unstaged changes · main`, and `no unstaged changes` alone when HEAD names no branch.

**It no longer reads `working tree clean`, and that phrase was wrong rather than merely plain.** It is git's, and git means index-against-HEAD as well as tree-against-index. This diff is the working tree against the index, so a worktree with every change staged draws zero files and was being told it was clean while `git status` said the opposite. `no unstaged changes` is exactly what zero files means here, untracked files included, since an untracked file is unstaged too.

**The branch is orientation, not the comparison.** Nothing about it changes what is diffed, and it is named anyway because two agents on two worktrees of one repository are otherwise identical on screen, which is the multi-worktree case §4 defers rather than rejects. A detached HEAD names no branch and the line drops it rather than inventing one: `HEAD@abc123` would put a commit id in a monitor that shows no commits.

**It costs one `.git/HEAD` read, taken only on frames that draw no diff.** I4 holds because the thing read is the thing drawn, and the frame that draws it is the cheapest one there is: nothing to diff, and nothing else to read.

And a token that had to lose characters says so, in the direction it lost them. `…` on the **left** means the beginning is gone, and only a file path uses it, because the end of a path is what names the file. `›` on the **right** means it continues past the edge: the worktree name, a notice, a hunk header, a note, the empty-state line. A hunk header silently cut to `@@ -258,7 +25` reads as a different line number, which is the failure this closes.

**A blank row closes every file's block but the last.** Ruled 2026-08-15 ([#165](https://github.com/breferrari/vigia/issues/165)), and it is the one boundary on this screen the picture could not settle: `assets/preview.svg` draws a single file's diff, so §5.1's law that a published artifact answering an open question *is* the answer does not reach a question the picture never poses. The stream has one boundary per changed file and drew none of them, while the boundary between the two **regions** one level up gets a rule of its own. A heading is a `Painter::file_row` carrying the kind letter, the path, the pulse, the heat strip, the sparkline and the counters, so without the blank a dense row lands directly under a dense row and the only thing marking the seam is content.

**Trailing rather than leading, and that is what keeps the map's promises.** Every jump here resolves to `Position { file, row: 0 }` — `n`, `p`, the digits, `g`, `G`, a click on a listed file, a follow jump — so row zero of a file has to be its heading. A leading blank would put one above every heading a reader jumped to, or force the jump to resolve to heading-minus-one, which is the off-by-one this row model has already been bitten by. `crates/vigia/tests/scroll.rs::every_jump_lands_on_a_heading_and_never_on_a_gap` asserts the drawn row rather than the position, because the two designs produce identical `Position`s and only the row tells them apart.

**And not after the last file, which is the exception rather than the tidy rule.** The first draft of this ruling was uniform, on the argument that a per-file conditional costs more than one blank at the bottom of the stream. It does not, and the reason is not arithmetic: the paragraph above about resting on the last **screenful** rules the bottom of the diff to be content, `crates/vigia/tests/scroll.rs::the_bottom_of_the_diff_is_content_rather_than_blank` is the gate over it, and that gate carries its own warning about having once been weakened into asserting the defect it was named against. A blank there would separate the diff from nothing, since the footer is chrome with a row of its own, and it would spend the row a reader who scrolled to the end asked for.

**A blank row and not a rule**, because §11.2 B11 has just ruled the rule between the regions stays bare, so a second rule inside the stream would mean something different on the same screen, and §5.3's furniture law would run it full-bleed. Space is the quietest thing that is still a boundary.

**It is counted, which is the half that had no gate.** `view::rows_of` and `view::span_of` are the counting twins the row-exact scrollbar is scaled against, and the blank belongs to neither: whether a file is followed by one is a fact about its **position**, where both are handed a file. `view::gap_rows` is that fact written once and `view::diff_rows` is the total, because five expressions sum file heights and every one of them has to agree. Nothing checked that agreement before, since every other gate on this surface reads a *position* and a drifting total moves no position at all — it moves the thumb, silently, on a bar this project already had to make row-exact once. `crates/vigia/tests/scroll.rs::the_counting_twins_agree_with_the_rows_drawn` is that gate.

**A clipped diff line is marked too, and is not a truncated label.** Content cannot wrap, because a wrapped line moves every line below it and the shape of the screen stops meaning anything. Nor can it elide, because unlike a label no part of it is the identifying part. So it is clipped and marked `›`, and I6's "truncated-to-useless labels" is read as being about labels rather than about content. That is a ruling, not an omission: the alternative was a horizontal pan, which is a key and a mode this spec does not name.

**A clear column stands between the sigil and the line, and it does not ladder.** Ruled 2026-08-15 ([#164](https://github.com/breferrari/vigia/issues/164)), towards the picture, and it is the **fifth** departure from `assets/preview.svg` this document has had to record rather than a preference argued from taste. The mockup states its own grid in a comment, one cell at `13.5px` being about `8.1px`, and in the diff body it places the line number end-anchored at `x=60`, the sigil at `x=72` and every content origin at `x=88`. The sigil is one cell, `72` to `80.1`, so `7.9px` of clear column has stood after it since before any of this was built, and the origin is uniform down the block: the unsigilled context rows take their content from `x=88` too, and every indent is `88` plus a whole number of cells, which the file's own comment calls out at `120.4` for four spaces. The shell drew none, so a removal's red `-` ran into the first token a reader scans for. §5.3 calls §5.1's departure list the complete set of licensed disagreements and this was not on it, which makes it an omission rather than a decision. (The list's own arithmetic is separately wrong and [#156](https://github.com/breferrari/vigia/issues/156) owns that; this paragraph adds a member to it without settling the count.)

**Why it does not degrade, where every other spacing decision here does.** #119's margin is a ladder and the row's glance elements are a ladder, so a rung was the obvious shape. The sigil column **is the diff signal** at any depth or on any palette that cannot wash the row, which the tinted-row cell of §5.1 states and `crates/vigia/tests/colour.rs` gates, so a column that keeps that signal legible is part of the signal rather than decoration beside it and I6's "every cell is contested" does not reach it. A gap that vanished at 43 columns would take the signal's legibility away exactly where the pane is most crowded.

**And it is uniform rather than conditional on the line, which is the part worth stating because the cheaper rule is so nearly right.** The gap earns its column only where a line has no leading whitespace of its own; an indented line already stands off its sigil by its own indentation. Drawing it only for unindented lines would make a content row's origin a function of its *contents*, which is the intermittent layout this section has already refused twice, for the counts cell and for the scrollbar's reserved column. So every content row pays it, and the ones that did not need it are the price of the ones that did.

**What it costs, measured rather than waved at.** One column of every content row, and it lands hardest at the forty I6 is named for: on the reference fixture the eighty-column pane clips nothing before or after, and the forty-column pane goes from **one** clipped line to **three**. `crates/vigia/tests/paint.rs`'s row-cost gates are bounds on characters examined rather than exact counts, so they gain slack rather than moving. The hunk header, the file heading and both regions' chrome are untouched: the column comes out of content and nothing else. **The gutter is untouched in what it draws and moved in when it is affordable**, which is the correction this ruling nearly shipped without: the column comes out of content, so the rule deciding *how much content is enough* is the one thing that had to be recharged, and it was not. `gutter_width` measured a pane against a prefix that no longer existed, so at the narrowest width keeping the line numbers it enforced `MIN_TEXT_WIDTH`'s floor at 23 rather than 24, on a pane with a scrollbar and therefore in the ordinary case for a diff taller than its region. One width per digit count, all below 43. **Nothing reddened, because that floor had no test**: it was a threshold two expressions held by hand, which is the wish `CLAUDE.md` names, and the two gutter gates that exist sample away from the boundary and assert the gutter does not *vanish* rather than that what survives clears the floor. `crates/vigia/tests/legibility.rs::a_drawn_gutter_leaves_the_text_its_floor` is what fails now, and the drop boundary moves out one column per digit count as the floor's own ruling is finally paid. **Rejected: moving the gutter's existing trailing space to the far side of the sigil**, which is free and wrong twice, because the picture puts a gap on *both* sides of the sigil and because `260-` reads as arithmetic rather than as a line number beside a removal.

**How a diff line is coloured**, which is what I2b pays for. Content is syntax highlighted, and the mockup had already ruled how: added, removed and context lines all carry the same classes, the sigil is green or red, and the line number stays faint. **Ruled 2026-07-30: follow the picture literally**, per §5.1's rule that a published artifact answering an open question is the answer. Only content is highlighted. A file heading, a hunk header and a note are chrome, and chrome that changed colour by what it happened to name would stop being readable as chrome.

Three things follow, and each is a constraint rather than a preference.

**The engine emits meanings, not colours.** `vigia-core` maps a syntax scope onto one of nine classes and stops. Which colour a class gets is the shell's, and therefore [#11](https://github.com/breferrari/vigia/issues/11)'s. A core that emitted truecolour would have settled the palette question in the one place §6 says has no terminal in it, and it would have pre-empted the 256-colour degradation path before anyone wrote it.

**The diff signal degrades to the sigil column, and that is a loss rather than a simplification.** What separates an added line from a context line in the mockup is the row tint and the left bar of §5.1, and sixteen foreground-only colours can draw neither. So until #11 lands a background, `+` and `−` carry it alone. Recorded out loud because §5 makes shape and colour the whole differentiator, and this is the one place where following the picture spends some of it. The alternative considered and rejected was to keep unclassified text green on an added line and red on a removed one: it preserves the wash, it contradicts the picture, and it would have made the shell's colours mean two different things at once.

**A file type nothing recognises is not an error.** The syntax is resolved from the path, by extension and then by whole file name, and anything unresolved draws exactly as it did before there was highlighting at all. A monitor that refused a file because it could not colour it would have inverted its own job.

**How recency is drawn**, which is I10 and which §5.1 asked for as two separate things. It is **one ladder with three rungs**, read from one store through one lookup, and each rung is an intensity on the file's own heading:

| Rung | What it means | How it draws |
|---|---|---|
| **pulse** | named by the **most recent tick** | brightest, plus a `●` in the pulse colour |
| **live** | has a sample inside the 120-second window | plain |
| **cold** | nothing in the window, so nothing is tracked for it | faintest |

Three rulings are inside that table and none is cosmetic.

**The top rung is not a duration, and I1 is the reason.** §5.1 reads the mockup's persisting mark as a decay, and a decay measured against a wall clock has to be *seen* decaying, which needs a redraw nothing schedules. Inventing a timer to get one is exactly what I1 forbids, and it is the same wall §10's highlight-tail bullet already hit. So the window stays real time and the **sampling** is event-driven: the store advances once per coalesced tick, on the wake that was already going to redraw. Nothing on screen changes without something changing on disk, which is what a monitor is for. Defining the pulse as *newest tick* rather than *last three seconds* is what stops that from being a lie: a tree that has gone quiet keeps the mark on the file that really is the newest change, indefinitely and correctly, instead of freezing a clock mid-count.

**Cold is not a fourth rule.** A path with nothing left in the window is dropped from the store entirely, per I10, so "cold" and "untracked" are the same state. That is also what the **first** frame of a session looks like: a worktree that was already dirty draws every row cold, because a monitor has no way to know what happened before it was looking and inventing a recency for it would light up rows nothing has touched.

**Three is a property of the store, not of the palette, and this file said otherwise for a phase.** §5.1 and `theme.rs` both promised that the *real* gradient arrives with [#11](https://github.com/breferrari/vigia/issues/11)'s truecolour, on the reasoning that sixteen foreground-only colours have only bold, plain and dim to spend. The arithmetic is right and the conclusion does not follow. What #11 widens is how many distinct colours a rung may be drawn *in*; what decides how many rungs there **are** is `Recency`, and it has three variants because the store can answer exactly three questions about a path: is it in the newest tick, is it anywhere in the window, or is it not tracked at all. A fourth rung would have to mean *how far through the window*, which nothing currently computes and which the row above makes expensive to add honestly: the window is real time, the sampling is event-driven, and a fraction of it read on a quiet tree is a number that ages without being redrawn. So #11 replaced bold, plain and dim with three chosen luminances, and stopped there. Widening the ladder is an I10 change with a budget attached, not a theme.

The general shape, and it is the second time this file has recorded it: **a limit blamed on the rendering layer was a limit of the data behind it.** §5.2 caught the mirror image, an expensive-looking property that turned out to be a by-product already computed. Before assigning a limitation to the thing that draws, check what the thing that supplies can actually distinguish.

**The sparkline is a thing made of items**, so under the layout rule above it **breaks**: it drops whole buckets, oldest first, and never draws a partial one or a squeezed strip.

**The heat strip is a fourth kind of thing, and the rule needed a third clause to say so.** *A thing made of items breaks, a thing made of characters marks its edge, and content is neither* covers a list, a token and a line. A heat strip is made of items and is **not a list**: its items are slices of one file, in order, and the set of them *is* the claim. Dropping the last six would draw the first half of a file as though it were the whole of it, and a reader would conclude the tail is untouched. Less detail is honest; a prefix presented as a whole is not.

So **a projection re-projects rather than dropping items**: a narrower rung sums adjacent slices and classifies the sums, which at halves is exact. Twelve slices, then six, then none. `crates/vigia/tests/legibility.rs` gates it with a file changed at both ends and quiet in the middle, which is the one shape where truncation and re-projection differ, and it reads **cell colours** rather than symbols because every slice draws the same block.

**And the two strips scale against different things, deliberately.** A sparkline's height is measured against the busiest bucket **on screen**, because the question a reader asks down a file list is which file is busiest, and a row scaled against itself draws every file at full height the moment it is the busiest thing it has ever been. A heat slice's intensity is measured against the busiest slice **of its own file**, because the question is where in *this* file the work is, and the neighbouring rows have nothing to do with it. One is a comparison down the list, the other across a row. Its heights are scaled against the busiest bucket **on screen** rather than against each row's own maximum, because scaling per row draws every file at full height the moment it is the busiest thing it has ever been, which answers a question nobody asked while destroying the one comparison a file list is for.

**A sparkline bucket with no writes draws a track, and a file with no churn is the all-empty case.** This paragraph used to end *"a file with no churn draws no strip at all rather than an empty one, **so it spends none of its row**"*, and the clause after the comma is what made it wrong: the reserved-slot ruling earlier in this section takes the slot from the pane whether or not a row can fill it, so the row is spent either way and "nothing" bought exactly what "a track" costs. Replaced 2026-08-03 ([#78](https://github.com/breferrari/vigia/issues/78)). §5.1 carries the ruling and why the track is `_` rather than the ramp's floor.

**The heat strip's empty case is not the same case, and its opposite ruling stands.** `heat_at` draws nothing for a file with no line diff at all, because a strip of pure track there would say *"this file is in the diff and I cannot tell you where"*. That is an **epistemic gap**: the row asserts the file changed, and the strip cannot place it. A sparkline's empty state is a **fact** the store actually holds, that nothing has been written since the watch opened, so the two elements draw opposite conclusions from the same-looking input and both are honest. The distinction is what keeps #78 from being an argument for changing the strip too.

**And no glance element may take a heading below twelve columns of path.** The counters, the pulse, the strip and the sparkline are all placed from the right, against a floor the path keeps; which of them survives a given width is the layout table's business rather than a per-row allocation, and the order is the one recorded above. A row reduced to `M …` would have stopped naming its own file, which is the truncated-to-useless shape I6 forbids, arrived at by decoration rather than by narrowing.

**CLI.** One optional positional path, defaulting to the working directory. **One flag, `--version` (and `-V`), which prints `vigia <version>` and exits successfully**, and every other argument beginning with `-` is refused with one line naming that fact rather than being taken as a path, so `vigia --colour=never` is told what the surface is instead of being told `--colour=never` is not a repository. **A second argument is refused too**, which this line said implicitly and nothing enforced until [#12](https://github.com/breferrari/vigia/issues/12): the classifier saw only the first argument, so `vigia . --colour=never` watched `.` and dropped the flag in silence, which is a worse answer than the refusal a flag gets alone because the tool starts and draws and so appears to have accepted it. Arity is part of the surface, so the classifier takes the whole argument list rather than one of it. That is not `--help` implemented; B6 leaves the question of whether it should be, and rules everything else about this line, including why the version query is not the thing it forbids. The version is `CARGO_PKG_VERSION`, so the string cannot drift from the manifest the release was cut from, and the classification lives in the library rather than in `main.rs` because §7 makes the test suite the proof and a test cannot import a `main.rs`.

**Configuration is a theme file and one environment variable**, which is B6 ruled 2026-07-31 and amended the same day. The CLI gains nothing either way.

**A palette is a preference, so it lives in a file.** `~/.config/vigia/theme` is read when nothing overrides it, resolved from `HOME` or `USERPROFILE`, which is **one** rule rather than one per platform: no XDG matrix, no `%APPDATA%` special case, no discovery crate. `VIGIA_THEME` still names a built-in or points at a file, and still wins, because a variable is how you say "not this time" without editing anything.

**A colour depth is not a preference, it is a property of the terminal you are in right now.** One machine, one user, one afternoon: this pane is truecolour, that one is an `ssh` into something ancient, the third is CI. A file gives all three the same answer and is wrong for two of them. So `VIGIA_COLOR` stays a variable, which is the same reasoning that makes `NO_COLOR` one.

The amendment costs less than B6 assumed because **the format and the parser already existed**: `VIGIA_THEME` has always been able to point at a theme file. What was added is a place to look, not a surface. And it removes a step rather than adding one, since a preference set once now survives a new shell.

**And the monitor writes nothing** — not into the worktree, not into a state directory, not into `.git`.

B7 ruled 2026-08-05, and it is stated here because it was load-bearing in two places before it was a rule in any: §6 makes the settle margin a table lookup rather than a measurement on the grounds that measuring would need a probe write, and §10's settle-margin bullet rests the whole 2-second constant on *"a monitor never writes, so it only ever sees the gaps its user's tools happened to leave"*. Both arguments were true because `vigia` happens to open no file for writing, which is nobody's decision. A cache, a lock file or a crash dump added in good faith would have made two recorded rulings quietly wrong, and nothing would have said so.

**It is a rule about the filesystem, and deliberately not about what the process emits.** Bytes going to the terminal this program draws into are a different surface with different costs, and reading this rule as covering them would foreclose questions it has no business deciding: [#120](https://github.com/breferrari/vigia/issues/120) asks about OSC 8 links on paths and a yank key over OSC 52, both pure emission, and it is right to treat those as outside this line rather than settled by it. Where the two meet is that neither may become a *reason* to write: a clipboard fallback needing a temp file, or a link needing a resolved path cached to disk, is this rule's business again. **Both were ruled 2026-08-15 and both were declined, as §11.2 B8 and B9** — which is where a reader following this pointer should go, and neither decline rests on this rule, exactly as this paragraph required.

**The mechanism a reader revisiting B7 needs, because it is the part that is not obvious.** A log inside the worktree is not untidy, it is a **self-sustaining wake loop**: the write is a filesystem event, the event is a tick, the tick is a frame, and the frame writes again, at frame rate, for as long as the process lives. `vigia-core`'s event filter decides how visible that is, and of the four places a write can land it hides three. A path *outside* the worktree fails `strip_prefix` and is dropped. A path inside it and **gitignored** is dropped by the exclude rules. A path inside `.git` is dropped unless its file name is `index`, which is the one file there that changes a diff. A path inside the worktree and **not** ignored is accepted. So the guard a writing monitor would need is not a convention about where the file goes; it is the worktree root resolved before the file is opened, and a refusal — which is a behaviour, not a detail, and is one of the five B7 counts.

**Where an instrument goes instead, since declining one is not the same as having none.** The harness, which is where every other measurement of this product already lives: the soak is `vigia::run` with the terminal removed (§7), and `VIGIA_BUDGET_SLACK` is the standing precedent for a variable the tests read and the binary does not, so a measurement switch can cost the product surface nothing. What the *reader* gets is the footer's own readouts, which is the other half of the same split and is §5.1's business rather than this paragraph's.

Gated by `crates/vigia/tests/writes.rs`, over every entry under a fixture root with `.git` included and the root itself stamped, across a first paint, six reader actions, a second tick and the grammar warmer **joined** rather than detached, because a write that lands after the comparison is a gate that passed by racing. One thing a reading could have got wrong was checked rather than assumed: `gix`'s status walk is never asked to write the index — `write_index` is called nowhere in `crates/` — and the gate confirms it empirically, so a monitor that reads a working tree many times a second leaves it byte for byte as it found it. Both directions are tested, per §7: a sibling gate writes a file and asserts the comparison **reports** it, because a comparator that cannot say "something moved" has not been tested.

### How colour degrades

`SPEC.md` §5 makes shape and colour the whole differentiator, so a palette that assumed 24-bit colour would be a product that silently stops working on the terminals that do not have it. §10 named that and left it open. This is the answer, and it is **two axes rather than a fallback chain**.

**The palette decides what may be drawn. The depth decides how finely it can be expressed.** Both have to allow an element before it appears, and they genuinely disagree: `ansi` refuses a row wash at *every* depth, because a wash has to assume a background and that palette's entire contract is that it assumes none, while `dark` draws one wherever the depth can express it.

Three palettes ship. **`ansi` is the default**, unchanged from what shipped before there was a choice: every colour in it is one of the sixteen *names*, so it resolves to whatever the reader's own terminal scheme says and `vigia` matches the pane beside it instead of fighting it. It is the only palette that is correct on a background nothing has detected, and detecting one needs a tty round-trip this shell does not make. `dark` is `assets/preview.svg` read out of the file rather than approximated. `light` is the same design re-picked at light-background luminance, with every ramp reversed, because on white it is the dark end that has contrast to spend.

The depth ladder, and what each rung loses:

| Rung | Foreground | Background |
|---|---|---|
| truecolour | 24-bit, as authored | as authored |
| 256 | quantised to the xterm palette | **dropped** |
| 16 | nearest of the sixteen names | dropped |
| none | dropped | dropped |

**A background needs 24-bit and a foreground does not**, and that asymmetry is the one thing here worth arguing with. §5.1 already records that a quantised background is a solid block rather than a tint: the darkest available green behind a line of code is a slab, and a slab destroys the syntax colours sitting on it. Worse than no tint. So the row wash needs the top rung while the text goes all the way down to sixteen, and below it the diff signal narrows back to the sigil column exactly as §11.1 recorded before #11.

**That boundary sat at 256 for a phase and it took a screen to move.** The cube has six levels per axis and its darkest two are 0 and 95, so a *subtle* colour has nowhere to land: `#1b3d29` quantises to `#005f00` and `#45222a` to `#5f0000`, saturated primaries at roughly two and a half times the authored luminance. Over a hunk that reads as a strong tint and the report would have been "the colour looks wrong". Over a **newly added file, where every row is an addition**, it is a screenful of flat green, and §5's whole claim is that colour carries signal. Reported 2026-08-03 with two photographs of it. The argument was already written here as the reason Windows detects 24-bit rather than 256; what was missing was applying it to the rung itself.

**The grey ramp is not the escape**, and it is worth naming because it is the obvious next idea. It is far nearer in distance than the cube, and it is where the quantiser would send a desaturated wash if its chroma gate did not stop it. But `#1b3d29` and `#45222a` average to the *same* grey, so an added row and a removed row would be one colour, which is the one thing §5 says may never happen at any rung that has colour at all. There is no honest wash below 24-bit. A reader whose terminal draws more than detection can prove says so with `VIGIA_COLOR`, and inside `tmux` that also needs the multiplexer to pass 24-bit through rather than approximate it.

Detection is a precedence chain, first answer wins: `VIGIA_COLOR`, then `NO_COLOR`, then `TERM=dumb`, then `COLORTERM` claiming 24-bit, then **`TERM_PROGRAM`**, then **Windows with `WT_SESSION`**, then `TERM` promising 24-bit, then `TERM` containing `256color`, then **Windows**, then sixteen.

**A terminal that names itself sits above `TERM`, and that ordering was learned rather than designed.** Git Bash and MSYS export `TERM=xterm-256color`, so a chain that read `TERM` first sent the most common shell for this repo to 256, where a subtle colour has nowhere to land: the xterm cube's darkest axis levels are 0 and 95 with nothing between, so a row wash of `#1b3d29` quantises to `#005f00`, a saturated primary rather than a tint. A terminal that names itself is better evidence than a variable describing a terminfo entry.

**That ruling was written for `WT_SESSION` and it generalises, which is what `TERM_PROGRAM` is doing here.** The chain used to have exactly two positive signals on a Unix, and both of them fail in the arrangement §1 describes as the whole point of the tool. `COLORTERM` is the only convention for claiming 24-bit and **nothing propagates it**: `ssh` forwards `TERM` alone, and a multiplexer replaces `TERM` with an entry of its own. `tmux` at its default `default-terminal screen` is the ordinary case, and `screen` contains neither `256color` nor anything else the chain read, so a reader running an agent in one pane and `vigia` in the pane beside it landed on sixteen. Sixteen drops backgrounds by the rule above it, so `dark` coloured every foreground and washed no row, and from the outside that is a palette being ignored rather than a rung being wrong. Reported from a real macOS pane 2026-08-03, where the giveaway was the `@@` header: at sixteen `#58a6ff` resolves to `LightCyan`, and it was cyan.

`TERM_PROGRAM` survives all of it, because it names the process that owns the screen rather than the entry the innermost layer chose to advertise. **`Apple_Terminal` is the one entry in that table that is not truecolour**, and it is why the table answers with a rung rather than a yes: Terminal.app has never drawn 24-bit, it rounds the sequences to its own palette, and claiming truecolour there is the over-claim this ladder's floor exists to avoid. An under-claim only looks flatter than it had to.

**`TERM` reads two more promises than it did, both terminfo's own vocabulary.** The `-direct` suffix is what the database calls direct colour, and a handful of terminals ship an entry naming themselves (`xterm-kitty`, `xterm-ghostty`, `alacritty`, `wezterm`, `foot`, `contour`, `rio`), none of which spells `256color` and none of which has ever had a 16-colour era. A terminal that merely *usually* has truecolour is not in that list: it belongs behind `COLORTERM` or `VIGIA_COLOR`, because the list is evidence about terminals someone checked rather than a claim about the ones nobody has.

**Windows detects truecolour, and 256 was not a safe default but a different wrong one.** What it was protecting against is consoles older than Windows 10 1703, which has not been a supported target for years. A reader on something genuinely older says so with `VIGIA_COLOR`, which is what the override is for.

**`TERM` only ever promotes.** On a Unix it is the last signal rather than the whole one; on Windows it describes a world where sixteen was the floor, so reading it as a demotion would take colours away from consoles that have them. An entry that promises neither rung yields nothing and leaves the floor where it is. The floor is sixteen because it is the one answer that is never actively wrong.

**Modifiers survive every rung, including none.** `NO_COLOR` asks for no *colour*, and bold is not colour. On a monochrome terminal it is the only distinction left.

**Quantising happens once, at startup.** The palette is walked a single time and the result stored, so the frame path draws with values that already mean what this terminal can show and I9 never sees any of it.

**What a wider palette does not buy is a wider ramp.** Mapping a 24-bit colour onto sixteen entries cannot keep nine syntax classes distinct: `#ffa657` and `#e3b341` are both yellow, and that is arithmetic rather than a choice. `ansi` is the answer for a sixteen-colour terminal and hand-picks all nine. What may **never** collapse at any rung that has colour at all is the diff signal, because §5 spends it on colour, and that has its own gate.

**A theme that does not parse is reported before the screen is taken**, which is the rule B5 already states for a path that is not a repository and holds here for the same reason: an error painted inside a TUI that then hands the terminal back is an error nobody sees. An unknown key is **refused rather than ignored**, with the line it was found on, because a silently dropped key is a theme that does nothing and "it was discarded" is the one explanation a reader cannot arrive at by looking at their screen.

**A path that is not a repository exits before the screen is taken.** That is the first half of B5, and it shipped with the shell rather than being ruled first: `Worktree::discover` and the opening walk both run ahead of `Session::enter`, so the failure reaches a terminal the reader can still read. An error painted inside a TUI that then hands the terminal back is an error nobody sees. Recorded 2026-07-31, when [#40](https://github.com/breferrari/vigia/issues/40) found §11.2 still calling it proposed, which is this section's warning box in miniature.

**The first signal from outside leaves the way the quit key does: the terminal goes back, nothing is printed, and the exit status is 0.** Ruled 2026-08-08 with [#24](https://github.com/breferrari/vigia/issues/24) rather than left to fall out of the code, because it is the part of that work a reader can observe from outside the process. Nothing failed, so there is nothing to report, and a message printed after the terminal has already come back would arrive on a shell prompt the sender was not looking at. **The first ask deliberately does not re-raise** so that a parent's `wait` reports *killed by SIGTERM*: it reports *exited 0*, because from this program's point of view it was asked to stop and it stopped. If a script ever needs to tell "quit" from "killed" on the first ask, this is the line that has to change.

**The second signal takes the default disposition, so it kills the process and restores nothing.** Also ruled 2026-08-08, and it is the half that keeps the first half safe. Arming a handler takes away the guarantee the sender had before it: an unarmed `vigia` died on one `kill`, where an armed one turns that `kill` into a wake for a loop, and a loop wedged for any reason would swallow every further one. That process is unkillable short of `SIGKILL`, and reaching for `SIGKILL` produces exactly the wrecked terminal this invariant exists to prevent, so the graceful path has to have a floor under it. A reader whose first ask appears to do nothing gets, on the second, precisely what they would have got if none of this existed. The consequence is stated rather than buried: **on the second ask the terminal is not restored**, `wait` reports killed by that signal, and the I8 row names it as a by-choice exclusion.

**No dependency was needed for that, which corrects the reason this section carried for a day.** The first version of this ruling said re-raising would need `libc` on every Unix target to restore a default disposition and raise again. It does not: `signal-hook`'s `low_level::emulate_default_handler` is exactly that call, it is in the crate §6 already names, and the unique-crate count on all three tier-1 targets is unchanged by using it. The exit-0 choice for the first ask is therefore a choice about what leaving politely means, not a concession to a dependency, and saying so is the difference between a ruling and an excuse.

**B8 — OSC 8 hyperlinks on drawn paths. Ruled 2026-08-15: no, and the ground is what it costs the instruments rather than what it costs the reader.** It costs the reader nothing, which is the honest half of the proposal: the sequence is emittable under `ratatui` (`ratatui-core`'s own `merge_diff_link` and `merge_diff_split_link` are exactly this shape, the bytes going into a cell's *symbol* with `CellDiffOption::ForcedWidth` carrying the real display width and a long link split so the opener and closer sit in the first and last cell), it changes no drawn cell, and a reader who never discovers it loses nothing. **It is deliberately not declined on discoverability**, which is the tempting wrong reason and the one the issue itself reached for: an undrawn link is not the same shape as an undrawn *instruction*, so §11.1's ruling against drawing the digits' rank ([#149](https://github.com/breferrari/vigia/issues/149)) does not reach it and must not be cited as though it did.

What it costs is measured, and it lands on the gates. **A linked path measures 46 columns instead of 1**, because `unicode-width` gives every character in the sequence a width — the two `ESC`s included, at one column each — rather than recognising any of it as a control sequence, and `Span::raw` is how `occupied`, `rows_at` and `legibility.rs`'s whole 1..=120 sweep all measure a row. Worse, `TestBackend`'s `Display` **is** every snapshot in this repository, and a linked cell renders there as `]8;;file:///…/src/main.rs\M]8;;\`, so adopting would commit raw escape sequences and the path with them into `.snap` files.

**Both costs were priced by building it rather than by predicting it, and the number depends on the URI, which is itself a finding.** Wrapping the path in `Painter::file_row` with a **repository-relative** URI and running the workspace fails **29 tests across four binaries**: 19 in `render.rs`, 8 in `legibility.rs`, and one each in `follow.rs` and `rows.rs`, with the linked cell measuring 46. With the **absolute** URI a `file://` link actually needs, it is **35 across five binaries** and the cell measures 53, `palette.rs` joining because the absolute path reaches a fixture assertion. So the honest figure for an adoption is the larger one, and the smaller one is what a session reproducing this from a relative path will see. Neither set is about hyperlinks: they are the width ladder, the collapse order, the sparkline and heat gates and the snapshot suite, every one reading a cell that now claims a width it does not have. **The absolute form is also what puts a machine path into a committed `.snap` file**, which `CLAUDE.md`'s house rules forbid outright, so the shape that is cheapest to gate is the one that does not work.

**And the painter cannot emit it at all, which is the cost nobody had priced.** `ratatui`'s `set_stringn` filters graphemes with `!symbol.contains(char::is_control)`, so every escape written through `Painter::put` is **silently dropped** and what reaches the screen is the payload as visible text: the first attempt at the mutation above drew `]8;;file:///crates/…` into the row and reddened 23 tests across five binaries, two of them in `legibility.rs`, for a reason that had nothing to do with hyperlinks. A link therefore has to be written onto the cell with `set_symbol`, after `put` has run, which is a **second drawing route for path cells that bypasses the width ladder, the elision rule and the edge marking** every other drawn label goes through. What that route costs is the property `crates/vigia/src/render.rs`'s `Painter::list` states as *"one drawer, one degradation ladder, one set of gates, and no way for the two regions to disagree"*, and which §11.1 carries as its own rule that a list row draws exactly what a heading draws.

Against all of that, the benefit cannot be measured from here at all: a `file://` URI hands the path to the reader's **system handler**, so whether a Ctrl-click opens anything they want is a fact about their machine, and B6 forecloses the configuration key that would let them aim it. A measured cost to the instruments against an unmeasured benefit is the trade §7 exists to refuse, and refusing it here is that section applied to its own gates rather than to the product.

**Reopen it on `ratatui` carrying a hyperlink as cell *metadata* rather than as bytes inside the symbol**, which would delete both measurements above and with them this entire ruling; or on [#72](https://github.com/breferrari/vigia/issues/72) reporting readers reaching for files and finding no route. The terminal survey the issue asks for is a cost of **adopting** rather than of declining, which is why declining did not need it: a decline is safe under every possible survey result, and only an adoption depends on which one it is.

**B9 — a yank key over OSC 52. Ruled 2026-08-15: no, and the ground is that it would be the first key on this map to destroy something the reader owns.** Not the first *irreversible* one, and the distinction is worth keeping rather than smoothing: `q`, `Esc`, `Ctrl-C` and `Ctrl-D` quit, which no keypress undoes either. What separates them is whose state they spend. Quitting ends this program and touches nothing else; every remaining binding moves a viewport or toggles drawn state and is undone by pressing something else. The system clipboard is **shared mutable state other programs read**, so `y` would overwrite whatever the reader had there, on one unmodified keystroke, with no undo and no warning, and the thing destroyed is not `vigia`'s to spend.

**And `vigia` could not tell them it had worked.** OSC 52 has no reply, so the only mechanism that could confirm the write is OSC 52's own query form, which reads the reader's clipboard back — a privacy escalation far past the affordance. So the program can neither report success honestly nor fail visibly. A `copied` notice would be a claim it cannot support, and it would also **outstay its subject**: a notice is cleared by the next `Wake::Tick` and by nothing else, and a keypress produces no tick, so a notice raised by `y` would sit on the footer until the worktree next changed, which on an idle tree is never. That is a sharper objection than a clock, and it is the one that holds: I1 is not needed to refuse this. The dependency is the smallest of the reasons and is recorded because the issue claimed the opposite: `crossterm` does ship this, as `clipboard::CopyToClipboard`, but behind an `osc52` feature that is `dep:base64`, and `base64` is not in the graph today.

**The case for it is stronger than the issue made and is recorded here rather than dropped, because it is what this will come back on.** The proposal argued convenience. The real argument is that **`vigia` has already taken the ordinary route away and truncated the replacement**: `Session::enter` takes `EnableMouseCapture` unconditionally, so a native drag-select depends on whatever bypass modifier the reader's terminal happens to offer, and at the forty columns I6 is named for the path on screen is *elided* — `render__the_glance_elements_at_forty_columns.snap` draws `M …ngine/watch.rs` through the same `Painter::file_row` the list uses, so even a successful selection yields a string that is not the path. On the pane this tool is built for there is no route to the real path at all, and that is a gap this program created. It loses today because no reader has reported it ([#72](https://github.com/breferrari/vigia/issues/72) has one recorded session) and because a first irreversible key is a poor instrument for discovering whether a gap bites. **Reopen it on [#72](https://github.com/breferrari/vigia/issues/72) showing that it does** — and if it does, OSC 52 is not the only shape worth considering, so this ruling deliberately does not pre-commit the answer to the question it is inviting.

**Each has its own gate, and one gate could not have held both.** `crates/vigia/tests/legibility.rs::a_drawn_path_carries_no_escape_sequence_of_its_own` holds B8. It does not try to name a hyperlink, which is not nameable from drawn output, since a correctly rendered link looks exactly like a path; it forbids the **mechanism**, an escape smuggled into a cell, which is B8's only workable route. `crates/vigia/tests/input.rs::the_yank_key_is_refused_rather_than_unbound` holds B9, and it exists because the first one cannot: **an OSC 52 write draws nothing.** It touches no cell and leaves every buffer identical, so the entire rendering suite stays green while B9 is violated, and a ruling whose only tripwire is a drawing gate would report that nothing had happened. The keymap is where B9 is decidable, because a clipboard write needs a key to arrive on. That the two rulings needed two gates for the same reason they needed two numbers — their effects land in different places — is the clearest evidence available that splitting them was right.

**B10 — a hover highlight on what the pointer is over. Ruled 2026-08-15: no, and the invariant argument this question was built on turns out to be void.** ([#123](https://github.com/breferrari/vigia/issues/123).) The issue framed it as a trade against I1: *"'the loop wakes on pointer motion' is a sentence §3 currently does not have to say, and adopting this means saying it"*, and §5.3 stated the same thing as settled. **§3 already has to say it.** `crossterm`'s `EnableMouseCapture` writes `?1000h ?1002h ?1003h ?1015h ?1006h` as one bundle, and `?1003h` is *any-event tracking*: every pointer movement, button held or not. Those events arrive as `Wake::Input` today, the loop calls `regions()` and `action_for`, gets nothing, and continues — under a comment in `crates/vigia/src/lib.rs` that names this exact concern. **And the cost is larger than a wake, which the first draft of this ruling got wrong**: `continue` leaves that wake and not the batch, and `sample_memory`, `shell.draw` and `record_frame` all run unconditionally once the batch loop closes, so a batch of nothing but pointer motion already performs a memory read, a whole-frame collect and paint, and a frame recorded into the p99 the status bar draws. That is a gap in I1's letter, it is unmeasured, and it is [#154](https://github.com/breferrari/vigia/issues/154) rather than this ruling. What it means here is that **the cost is wholly sunk**: declining saves none of it, and adopting adds no wake, no paint and no frame — only an `Option` of a target and a style on rows that were being redrawn anyway.

**Nor can it be given back, which closes the branch nobody had named.** If the wake buys nothing, the obvious move is to stop asking: `1000` and `1002` and `1006` give click and drag without any-motion. That is not portably available. On Windows `EnableMouseCapture::is_ansi_code_supported()` is `false` and `execute!` routes the whole bundle through the console API, writing **zero bytes**, so hand-written DEC modes would work on Unix and be a no-op on Windows — the mouse lost on a tier-1 target, or two mechanisms where there is one. `RULINGS.md`'s I1 section carries the measurement and the reason I1 is not breached by it.

**So this is decided on what hover shows, and it loses on a mechanism rather than on a preference: nothing would ever tell it to turn off.** No mouse protocol reports a pointer *leaving* a region or a window; reports simply stop. `TAKEOVER` does not enable focus reporting either — it is `RawMode`, `AlternateScreen`, `MouseCapture`, `Cursor`, and `Event::FocusLost` is handled in the keymap but never asked for — so nothing announces that the reader has tabbed away. And on an idle tree nothing repaints, because a paint needs a wake. So the last row the pointer crossed on its way out stays lit, indefinitely, as a claim about where a pointer **used to be**. That is the same shape B9 refused one paragraph up, where a notice is cleared by the next `Wake::Tick` and by nothing else: a mark that cannot be cleared by the thing that raised it is a mark that outstays its subject.

**The behavioural version of that objection is weaker and is not what this rests on**, but it is worth recording because it is what a reader will reach for first: in the arrangement §1 describes, a reader typing in the agent's pane leaves the mouse wherever it was, frequently over this one, so a pointer at rest is usually abandoned rather than aiming. That is an unevidenced claim about people and the spec has none to offer either way — §2 says interaction is *"rare or never"* and says nothing about where a resting pointer sits, and every mouse defect §11.1 records as reported from use describes somebody **aiming**. The mechanical version above needs none of it.

**And the affordances it would confirm are already drawn**: the caret, the thumb, and a row that draws the name of what it maps. What is *not* claimed here is the tempting generalisation, that every drawn mark in the pane is a fact about the worktree — §11.1 falsifies that in its own words, since the frame and memory cells *"describe `vigia` itself"*, the mode word is *"the one fact about `vigia` itself"*, and the footer's `N/M` is *"a place rather than a measurement"*. The true form is narrower and survives all of them: **facts about `vigia` itself are confined to the chrome, and hover would be the first mark inside a body region that is about an input device.** [#149](https://github.com/breferrari/vigia/issues/149)'s taxonomy is deliberately not borrowed for this: under it a hover mark is *location* rather than *instruction*, so that ruling does not reach hover, exactly as B8 above warns against citing it where it does not.

**The case for it is real and is now far cheaper than the issue believed, which is the part worth handing forward.** Acknowledgment before action is most of what "snappy" means with a pointer, and the issue reports that two of six defect reports on the interaction surface came from readers *aiming* at things — which is the only evidence anywhere on this question and it points the other way from the decline's behavioural half. Anyone reopening should know they are buying **an `Option` and a style**, not a wake class and not a repaint: the wake, the paint and the recorded frame all already happen. The version of this question that was priced against I1 was priced against nothing. **Reopen it on [#72](https://github.com/breferrari/vigia/issues/72) showing readers aiming and missing**, and answer the clearing mechanism first, because that is what the decline actually rests on: a hover that cannot be turned off is refused however cheap it is.

**A narrower shape is named rather than pre-committed, so a reopening is not forced through the widest form: the scrollbar thumb alone.** It is the one target a reader must genuinely aim at and the only one with no drawn confirmation of its own mid-approach. Note where it sits against each ground rather than only the flattering one: it is the *best* case on clearing, since a stale highlight on a one-column bar is nearly invisible and the thumb is redrawn on every scroll anyway, and the *worst* case on the body-region rule above, since a thumb highlight is entirely about the input device. Whoever takes it should say which of the two they are answering.

**The gates, and one of them had to be written after all.** `crates/vigia/src/terminal.rs::every_command_is_the_escape_sequence_it_is_named_for` asserts the mouse bundle byte for byte, `?1003h` included, so the sunk cost stops being true loudly rather than silently if anyone changes it. For the ruling itself the first draft pointed at `nothing_a_reader_did_not_ask_for_becomes_an_action` and claimed it *"reddens the moment hover is built"*, **and that was false in the way that matters**: it hands `action_for` a `Regions::default()`, a screen with no list, no diff and no bar, so every region-gated arm returns `None` against it whatever it does in production. `Down(Left)` sits in that same list and is emphatically not inert on a real screen. A hover written the way the click arm is written, `Moved if regions.over_list(row)`, would have left it green. `crates/vigia/tests/input.rs::pointer_motion_over_a_laid_out_screen_is_still_no_action` is the gate that catches the shape anyone would build, over a laid-out screen with the pointer on the list, the diff and the bar in turn; the region-gated mutation reddens it and nothing else in the workspace.

**And the gate #123 actually asked for is not here, because it would assert something untrue.** Its exit criterion was *"a structural gate asserts zero paints for motion over a non-target"*, and the honest count today is **one** paint per motion batch rather than zero, for the reason two paragraphs up. Saying so is the finding; writing the gate the criterion names would require fixing [#154](https://github.com/breferrari/vigia/issues/154) first, and that is a change to the event loop rather than a ruling.

**B11 — a speaking rule: the diff's heading embedded in the border line between the regions. Ruled 2026-08-15: no, and on what the heading *is* rather than on when it is there.** ([#124](https://github.com/breferrari/vigia/issues/124).) The proposal is the terminal's oldest space-saver, `─ src/engine/watch.rs ● ────`, costed as a relocation: the diff *"draws its heading as a full row"* below the rule, so folding it into the line *"gains one body row"*. **A heading here is not a line of text.** It is a `Painter::file_row`, drawing the kind letter, the path, the pulse, the heat strip, the sparkline and the counts through the one drawer §11.1 rules for both regions, on the one degradation ladder. Folding that into a border line has two branches and each spends something already ruled: **drop the glance elements**, and the pinned occurrence stops being what a list row is, which is the property B8 states as *"one drawer, one degradation ladder, one set of gates, and no way for the two regions to disagree"*; or **keep them**, and the rule is a full glance row with dashes at the ends, which is not a rule. Neither branch is a relocation, and neither depends on where the reader has scrolled to.

**The row it would reclaim is real, and more often than the first draft of this ruling said**, which is worth recording because the correction cuts against the decline rather than for it. That draft said the heading is under the rule *only at scroll zero*. `App::jump_to` lands **every** jump on the file's heading — its own words are *"the one resolution every jump on this map shares: follow, `g`, `G`, a click on a listed file, a digit, and `n`/`p`"* — and follow is on before anything is touched, which is I5. So the row is there at startup, on every followed tick, and after every jump, and it is absent only after a *relative* scroll: `j`/`k`, `d`/`u`, a page, a wheel, a drag. §2 prices those as the rare interactions. **On a monitor being watched rather than read, the saving is available most of the time**, and that is the strongest form of the case for adopting. What is true of the frames in between is only that the row under the rule is then content, a hunk header or a note, so a rule that spoke would be pinning a heading no longer otherwise on screen: a sticky heading, which is new state rather than a moved row.

**And B4 already answered stickiness the other way, by construction rather than by preference.** *The heading scrolls away, so you lose track of which file you are in* is the reason recorded above for building the pinned list at all, since three of the four glance elements ride a `Row::File` heading and are visible in one stream only while that heading is. What makes that airtight rather than merely usual is `Body::split`, which sets `rule: list > 0`: **the rule and the list are coextensive**, so there is no state anywhere with a rule and no list to answer the question the rule would be answering. (Below `CARET_FLOOR`'s eighteen columns the list draws without a caret, which is far under I6's forty.) **What this ruling deliberately does not rest on is counting carriers.** An earlier draft argued that the caret and the footer's `N/M` already carry the current file so a rule would be a third, and that proves too much: §11.1 rules restatement *in* where it makes a map rather than a second opinion, a stream heading is already a second full-row carrier of what a list row carries, and the three carry three different facts — a path, a row, an ordinal. The footer's index is also not unconditional, since `state_rungs` drops `N/M` a rung before the follow marker on narrow panes, and §11.1 calls it *"the half a reader can reconstruct"*.

**What reopens it is not #125, and saying so is the correction that matters most for whoever reads this next.** An earlier draft named #125 on the ground that a speaking rule *"earns where many regions compete for identity"*. #125 proposes no such thing: its widest rung turns the list from a strip above the diff into a **left rail**, which is the same two regions rearranged, and it says outright *"Not the borders — #124 owns the chrome question … Ruled apart they still stand alone."* A left rail has no horizontal rule at all, so #125 does not reopen B11, it **dissolves** it: the subject stops existing and the question becomes a different one. What would genuinely reopen this is [#72](https://github.com/breferrari/vigia/issues/72) measuring the quantity the ruling turns on — how much of a real session is spent at a file boundary against scrolled inside one — because that is what decides whether the row is usually there, and the structural objection in the first paragraph is what a reopening has to answer first.

**Declining costs the picture nothing, which the issue made a deliverable of the other branch.** `assets/preview.svg` draws the rule at `y=178` and the heading at `y=202`, two separate rows, so the artifact and the shell already agree and no departure is created. The count of standing departures is left alone here rather than asserted, because §5.1 records a first, a second, a third and a fourth while two other sentences still say the total is two, and reconciling that is its own question ([#156](https://github.com/breferrari/vigia/issues/156)). `crates/vigia/tests/render.rs::the_rule_separates_the_regions_and_spans_the_pane` is what fails if the rule ever speaks: it asserts the rule row **equals** the rule glyph repeated across the pane at 40, 64 and 120 columns, and asserts the rows above and below do not contain that glyph, so a title in the line reddens it on the first character.
