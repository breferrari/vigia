# vigia — Specification

Status: **v0, 2026-07-30.** Source of truth. Code is written against this document; see `CLAUDE.md` § Method for the drift rule.

## 0. How to read this document

Source of truth means: **what must hold now**. It does not mean every sentence is beyond question, and the difference has cost real features more than once, so it is written down here where every reader passes.

- **A ruling is its reason plus a date.** The reason, not the sentence, is the authority. Before citing a ruling to refuse or constrain something, re-read the reason and check it is still a fact; a citation without that check is a mood wearing a reference.
- **A refusal that names an absence expires fastest.** *"No API reports that"*, *"the takeover does not enable X"*, *"no font carries it"*: dependencies add things, terminals add things, and nobody re-reads a refusal when they do. Two features here were declined for a year on absences that had stopped being true (§11.2 B10 is one), and one on a fact about fonts quoted as a fact about rendering (§5.3, corrected by [#318](https://github.com/breferrari/vigia/issues/318)). Check the world, not the memory of it: the dependency's source in the registry cache, and the web.
- **An invariant is load-bearing, and whether it reaches the case in front of you is a fresh question every time.** Quote the row's own words. I1's budget is *0 wakeups while idle*; nothing a reader's hand is doing is idle.
- **A budget cited as a reason arrives with its current headroom** or it is not an argument. "This costs a wake" means nothing beside "2.4ms of a 16ms frame".
- **Research rows start from the world and then diff against this file**, not the other way round. Reading the rulings first anchors the survey to what was already decided, which is how a document that records yesterday's ceiling becomes tomorrow's.
- **When a reason collapses, the question reopens.** It does not get a fresh reason for the same conclusion ([#123](https://github.com/breferrari/vigia/issues/123) is the case that taught this).
- **A ruling can be withdrawn, and `REVOCATIONS.md` is where that is said.** Deleting one silently leaves the next reader unable to tell a reversal from an accident, so a withdrawal keeps the old text verbatim and names who ended it.

## 1. Problem

Running a full git TUI in a pane beside an AI coding agent, to watch changes as they land, is the wrong tool. A multi-panel git client spends the pane on branches, commits, stashes and status. In a pane already halved against the agent, every panel is a few lines tall and names truncate.

What is wanted: **the live diff, fullscreen, auto-updating, scrollable, mouse-driven, and beautiful.** Nothing else.

## 2. Product class — the load-bearing decision

`vigia` is a **monitor**, not a reviewer. That single distinction generates every budget below, and the budgets are the product.

| | Reviewer | **Monitor (`vigia`)** |
|---|---|---|
| How it starts | Launched per review | Already open |
| Interaction | The point | Rare or never |
| Correct when untouched | No | **Required** |
| Runtime | Minutes | **Days** |
| Latency budget | Seconds | **A frame** |

`btop` is the reference for what monitor-class feels like: you read state from shape and colour, glance away, glance back, and never configure anything.

Design rationale beyond this section is recorded outside the codebase; call `recall` when a decision needs it.

## 3. Invariants

Numbered because tests reference them. Each must have a test that fails on violation. **An invariant without a failing test is a wish.**

Budgets are **absolute** and chosen to be defensible on their own terms, not relative to any other tool.

| # | Invariant | Budget | How it is proven |
|---|---|---|---|
| **I1** | Redraw is **event-driven**, never a timer that runs unbidden. No filesystem event and no git index change means no work. **A clock is permitted only while the thing that armed it is still on screen and still changing**, and the three conditions are the whole of the licence: it may not start on its own, it may not outlive that thing, and the idle path must be untimed *by construction* rather than by care. Hold-to-repeat on the scrollbar's step buttons (§11.1) is the first clock to meet them and is an **instance of this rule rather than an exception to it**: anything else bounded the same way is already licensed and needs no further ruling. **A sample inside the history window is such a thing**, ruled 2026-08-22 by [#243](https://github.com/breferrari/vigia/issues/243): the window ages, it empties `HISTORY_WINDOW` after the last write, and the clock stops with it. | **0 wakeups** with an empty window, which is the state a monitor left open overnight is in. While the window holds a sample: **at most one wake per `HISTORY_SAMPLE`**, and at most `HISTORY_SAMPLES` of them after any burst, because the window drains. While a print that moved is inside the settle margin: **one wake**, at the margin's end after the last of them | CPU sampled over a 60s idle window **entered with the window already empty**; assert no render calls. | **I7** | Startup to first paint is imperceptible. **The first frame draws the diff without colour**, because a grammar's patterns compile on first use at 74-362ms per grammar, which is **124 to 695ms for a cold screenful** at the scale a frame pays it (Windows figures taken under `codegen-units = 1`, which §6 now records as overstating what ships by roughly 6x on that target and by nothing at all on Linux), and the frame after it is where that belongs; the reader gets content rather than a blank alternate screen. **And no frame parses under a grammar nothing has compiled**, whenever it arrives: a file whose language this process has not met draws plain, the warmer compiles it off the frame, and the wake that ends the warm is the redraw that colours it. Not in `tests/budgets.rs`: every gate there is a ratio or a duration, and this is a count |

A regression past any budget **fails the build.**

## 4. Scope

**In:** working-tree diff (unstaged by default), event-driven refresh, follow mode, scroll (keyboard + mouse wheel), syntax highlighting, per-file churn visualisation, a pinned file list above the diff (§11.1), responsive layout, theming.

**Out of v1, deliberately:** staging, committing, rebasing, branch or commit browsing, AI features, remote operations. Each is reviewer-class and each would cost an invariant.

**Deferred, not rejected:** multi-worktree view (several agent sessions at once — the strongest differentiator after glanceability, and the most btop-shaped); Jujutsu and Sapling support.

## 5. The differentiator: glanceability

`btop`'s real achievement is that state is readable from **shape and colour** without reading text. `vigia`'s translation:

- per-file **churn sparkline** — change density over time
- a **heat strip** locating change within the file
- live **+/− counters**
- a **visual pulse** on what just changed

This is what makes it a monitor rather than a narrow diff view, and it is where design effort goes once the invariants hold.

### 5.1 What the README mockup commits to

`assets/preview.svg` is the most detailed design artifact in the project, it is **public**, and until now it was specified nowhere. **A picture in a public README is a specification whether or not it is written down.** This one implied a retained time series, a recency gradient, two status readouts and a keybinding, none of which appeared in the spec, the roadmap, or any issue.

Elements the four bullets above do **not** cover are marked **(unspecified)** — they are in the picture, so they are commitments. Every row below is now ruled and implemented; §11.1 carries what the shell does and this table carries what the picture asked for.

| Element in the mockup | What it needs |
|---|---|
| Header: `vigia · 3 changed` … `watching` | A **mode word**, so there is a set of modes, and a count. **Ruled: the header's facts are exactly three, the mode set is two** (`watching` and `not watching`), **and there is no changed-line total** ([#49](https://github.com/breferrari/vigia/issues/49)). A repository-wide `+`/`-` is a reviewer's summary rather than a monitor's account, it puts first paint back in proportion to the size of the diff against I4, and the only way round that is the wake I1 forbids. The two words are the only two states a shell that wakes on writes can tell apart: anything finer is a duration. **The count sits on the left with the worktree name and reads `3 changed`; the mode word takes the right alone** ([#67](https://github.com/breferrari/vigia/issues/67)). That is a layout ruling rather than a rewording — `watching · 3 files` reads as a verb with an object, naming a curated set that does not exist, and the fix is *adjacency*: separated, the count has nothing beside it a participle could govern. **`changed` rather than `files` is the load-bearing half**, because this repository has more than three files in it, so the count has to name the change rather than the things. See §11.1 for the ladder. |
| Per-file **sparkline** | A **retained time series per file** — samples of churn over a window, bucketed. This is the only unbounded state in the design and the one I3 forbids growing, so the **window** and the **path cap** are part of the invariant: that is I10, a 120-second window capped at 256 paths, evicted by window and by least-recently-changed. **How finely the window is divided sits underneath I10 rather than inside it**, and it has moved three times: the store keeps 120 one-second samples per path, and the drawn bucket count is a **width rung** of 24, 12 or 6 ([#234](https://github.com/breferrari/vigia/issues/234)), so a drawn bucket is ten seconds on every pane the picture is measured at and a wider pane buys more of them. What that measurement found is that a finer *period* buys nothing and a finer *column count* buys the shape: twelve buckets of five seconds draws fewer distinct heights than twelve of ten, while twenty-four of five draws more than either. **An empty bucket draws a track** ([#78](https://github.com/breferrari/vigia/issues/78)), so a file with no history draws a full one — the store is fed from the watch, so a file already modified when `vigia` started has no tick behind it, and that is the *ordinary* first frame rather than an edge. The track is `_`, deliberately not the ramp's `▁`: a sparkline's channel is **height**, so spending the ramp's floor on "no data" would make one write and no writes the same shape. **A sample weighs the bytes a write moved, and a height is measured against `scale_of`** ([#232](https://github.com/breferrari/vigia/issues/232)); counting files instead let a worktree where one file is saved repeatedly make itself the peak and draw every active column at full height. **The ramp is cyan, three stops** ([#196](https://github.com/breferrari/vigia/issues/196)) — the picture ramps across five greens and is right about the ramp and wrong about the hue, because green already means addition two rows down. See §11.1. |
| Per-file **heat strip** | Hunk line-ranges projected onto buckets across the file's length, so it needs the file's **total line count**, not only its diff — which is free, see §5.2. **Twelve buckets at the picture's own width, from a source resolution of twenty-four** ([#161](https://github.com/breferrari/vigia/issues/161)); §11.1 carries the rung ladder. An empty bucket is a **dark track** rather than a gap, so a drawn strip is always its full width and a reader can see how much of the file is untouched; the one exception is a file with no line diff at all, which draws no strip, and §11.1 carries why that is the opposite of the sparkline's rule. **A mixed bucket is yellow**, because every alternative paints it as pure and separating addition from removal by position is the strip's whole job. **Intensity is three steps at a wide palette and two at sixteen colours**, which `ansi` spells out in its own fields rather than leaving the depth ladder to collapse by accident. **The twelve are drawn as twelve** ([#196](https://github.com/breferrari/vigia/issues/196)): the picture draws separate rects and the shell drew `█` twelve times, which on a cell grid is one continuous bar, so two adjacent slices in one band read as a single wide one and *where in this file the work is* is exactly the question that needs counting. |
| Per-file `+42 −7` | Covered. Per-file counters are free — a file must be diffed to be drawn (§10). |
| A **dimmed row** (`Cargo.toml` renders fainter than the rows above it) | A **recency gradient**: rows fade as their last change ages. **Ruled, session; three rungs of one ladder** — pulse, live, cold — read from I10's store. Sixteen foreground-only colours have three intensities to spend, so the gradient is a ramp of three rather than a fade, and **a wider palette does not bring a fourth**: the rung count belongs to `Recency` in `vigia-core`, whose `cold` means *untracked* rather than *old*, so a better palette draws the same three rungs in better colours. A real fade needs the store to emit an age fraction, which is a core change with an I10 budget on it. See §11.1. |
| `●` on the diff header | The pulse, drawn as a **persisting mark**, not a flash. **What it persists for was corrected 2026-08-26** ([#345](https://github.com/breferrari/vigia/issues/345)), reported from the pane: it stays on the file the newest burst named until another write arrives, or until I10's own bound retires the track. It had a decay for four days and nobody chose one — ageing the churn window gave the recency a second term on a complaint about a settled row's *brightness*, and the mark went with the ink because one value answered both questions. It is a second predicate over the same store now: the ladder answers *how brightly* and this answers *which file last*, and it is deliberately **not** a duration, because a wall-clock decay cannot be drawn without the timer I1 forbids. It marks every path in the newest tick, which is what §11.2 B2 said the pulse was for. **The `just changed` label is gone, from the picture as well as the shell** — the first change made *to* `assets/preview.svg` rather than to the code beneath it. **A label is not free on a monitor**: text has to be *read*, §5 puts the whole differentiator in what can be taken from shape and colour without reading, and fourteen columns of it sat in the widest rung, so below sixty-five columns the picture and the shell disagreed about what the pulse even was. |
| Diff body: **syntax highlighted content**, five classes deep (`kw`, `fnn`, `typ`, `var`, `con`) over a default foreground | I2b, and a **class set** rather than a palette: what the picture commits to is which distinctions are worth a colour, not which colour each one gets. The engine emits meanings and the shell colours them. See §11.1. |
| A **tinted row** with a coloured left bar on every added and removed line | A per-row **background**. It is what separates a changed line from a context line in the picture, because the text is highlighted identically on both, and it does the same work the dimmed row does: it is how the eye finds what moved without reading. The wash is painted across the whole row, gutter and trailing blanks included, so it reads as a band rather than as a highlight behind some text, and it is **not drawable below 24-bit**, where a quantised background is a solid block and a block behind highlighted code destroys the colours on it. **The left bar is the pane's leading cell, background only, and it costs no column** ([#218](https://github.com/breferrari/vigia/issues/218)). It is one cell of the blank margin [#119](https://github.com/breferrari/vigia/issues/119)'s ladder keeps, so it is a **width rung**: drawn from forty-three columns up, absent below. **It reaches `ansi` and every depth, where the wash reaches neither**, and that asymmetry is the ruling: a wash must be a **tint**, which cannot be chosen without knowing the background, where a bar is a **saturated block on a blank column**, which needs no such knowledge. It was refused before on *the bar has no terminal equivalent that does not spend a whole column* — true while the pane drew from column zero, false once #119 gave it a margin, and nobody re-read it. |
| Status bar `0.8ms frame` | Instrumenting the render path and drawing the result. Self-referential: measuring and painting the number costs frame time that I9 gates. **Ruled, session; the p99 of the last 128 completed frames, nearest-rank, sampled every frame** ([#41](https://github.com/breferrari/vigia/issues/41)). The **statistic is p99 because I9 is**, and a readout reporting a median would be silent about exactly the frames the budget exists to bound. **128 because §7 already says why not 30**: at 30 a nearest-rank p99 is just the maximum, and at 128 it is rank 127, so one cold outlier is excluded and two are not. **A frame is the whole turn of the loop** — the wake, the drain, every `Frame::advance` in the batch, `View::collect` and the paint — which is §7's whole-frame rule applied to a readout. The number drawn is necessarily the previous frames', because a frame cannot include its own paint in what that paint draws. |
| Status bar `11MB` | A live RSS readout. I3 samples RSS in a **soak test**, never on screen; reading it per frame is a syscall on some platforms. **Ruled, session; once per painted frame, on all three tier-1 targets, drawn in `MiB`** ([#41](https://github.com/breferrari/vigia/issues/41)). **The read is a syscall everywhere it ships**, which is not what the soak's own helper suggested: `soak.rs` spawns `tasklist` on Windows, which is **42.8ms median** against the 16ms I9 budget. What makes it affordable on screen is that both platforms have an in-process answer through a crate `gix` **already** puts in the graph — `libc::proc_pidinfo` on macOS and `windows-sys`' `GetProcessMemoryInfo` on Windows, against `/proc/self/status` on Linux. **`MiB` rather than the mockup's `MB`**, because I3's soak quotes this quantity in MiB throughout and a reader comparing screen against soak would read the 4.9% difference as drift; `assets/preview.svg` was corrected to match. **And the number is "as of the last change", not "now"** — this shell wakes only on a filesystem event, so a pane left open on an idle tree shows the RSS from whenever the last write landed. That is consistent rather than broken: the diff on screen is *also* as of the last change. |
| Status bar `follow ▶` | A follow-state indicator, which presumes the mode exists. **Landed with I5**, on the footer rather than a third chrome line. I6 later gives it a line of its own, above the hints, at the widths where one line cannot hold both. See §11.1. |
| Key hints `q quit · f follow · ↑↓ scroll` | A hint bar, and it **constrains I6**: roughly thirty columns of it must degrade legibly at forty. **Ruled 2026-07-30, session: it does not degrade by shortening.** The footer takes a second line instead, and only below the width where a whole line holds the bar does it drop hints, `JK files` first and then `jk scroll`. See §11.1 for why the first of those is a bonus rung that never decides the footer's height. |

Three of these are corrections rather than gaps:

1. **`f` toggles follow.** The mockup shows a dedicated key and a state indicator. That is the answer to §11.2 B1, published before the question was asked.
2. **The dimmed row and the pulse are one mechanism**, not two: both are recency rendered as intensity. Specifying them separately would produce two decay clocks that disagree on screen.
3. **The table above is a list of elements and was silent about the container**, which is what let B4 sit `(proposed)` for two phases while the picture and the code drew different screens. The file list is a **region**, pinned above the diff ([#66](https://github.com/breferrari/vigia/issues/66)). Every row in this table is unchanged by that; what changed is where three of them are drawn and for how long they stay there.

#### The departure ledger

A departure is a decision somebody made for the shell against the picture. **One is open: the header draws the worktree name where the picture draws `vigia`.** The rest are closed, and how each closed is the record worth keeping, because §5.3's law is that a published artifact answering an open question *is* the answer and does not outrank a decision made against an invariant.

- **The element split across the two regions** — closed 2026-08-17 by correcting the **picture**. It gave the diff's heading no kind letter, no counters, no heat strip and no sparkline, so each region drew a different subset. That is coherent only while the pinned region shows every changed file, and an automatic unbounded changed set means it cannot: a file scrolled out of a capped region would take its counters with it and leave nowhere to read them. Both regions draw the same row through the same `Painter::file_row`, which also leaves one degradation ladder to gate rather than two.
- **The right-hand order** — closed 2026-08-17 by redrawing the **picture**. It placed sparkline, counters, heat strip, with the pulse at the right edge; `Painter::file_row` allocates right to left by priority, so the drawn order is pulse, heat strip, sparkline, counters. The renderer's order is the one that survives a narrow pane, because allocating by priority is what lets the ladder drop the least valuable element first. **Reported from the picture and ruled the other way** after standing for three phases on the argument that a mockup promises a layout rather than places it: a reader comparing the two could not line up a single element, which is what a specification is for. **What this cost is the argument that lost**: a picture that places every element where the binary places it is harder to redraw when the layout moves, and §5.3's rule that the mockup is corrected in the same pass as any ruling that changes what it draws is now doing more work. Taken on the ground that a specification nobody can check against the thing it specifies is not one.
- **The columnar row** — closed 2026-08-02 towards the **picture**. Every file row in `assets/preview.svg` puts the same element at the same `x`, so three sparklines read as one small-multiples chart and three heat strips as a comparison, which is the whole of what a file *list* is for. `Painter::file_row` right-packed instead, so every element's position was a function of the widths of the ones to its right and no two rows agreed. §11.1 carries the rule and what it costs.
- **The sigil's standoff** — closed 2026-08-15 towards the **picture**, by its own coordinates rather than by argument: the sigil sits at `x=72`, one cell of `~8.1px` ends it at `80.1`, and every content origin is `x=88` ([#164](https://github.com/breferrari/vigia/issues/164)). Found by a reader watching the pane.

Three things that look like departures and are not:

- **The staged run and its mark** ([#313](https://github.com/breferrari/vigia/issues/313)). The toggle is off by default, so the mockup and the shipped default pane are the same screen. What would be a departure is the picture drawing one thing while an unpressed pane draws another.
- **The left rail** ([#252](https://github.com/breferrari/vigia/issues/252), [#295](https://github.com/breferrari/vigia/issues/295)). `assets/preview.svg` is a **109-column** render, below the rail's 134, and since B14 made the rail a gesture the stacked layout is what ships at every width until a reader asks otherwise. `tests/rail.rs::the_rail_grows_with_the_pane_and_keeps_the_pictured_complement` asserts the glance complement against a rung read off that render rather than restated.
- **A picture that is simply behind.** Two were found in one pass: the status bar drew a hint bar [#80](https://github.com/breferrari/vigia/issues/80) had already replaced, and the state cell drew the follow marker without the `N/M` position `state_rungs` has drawn since the pinned region existed. **A departure is a decision somebody made; this is a picture nobody had opened since the ruling that changed what it should say.** §5.3's *"corrected in the same pass as any ruling that changes what it draws"* is the rule that was missed, and missing it is silent, which is why the audit that found these was of the artifact rather than of any gate.

**Two claims about the picture in this section have themselves been wrong, both found by opening the file** ([#156](https://github.com/breferrari/vigia/issues/156) is that gap, open). One said the mockup gives the summary rows no kind letter; it has drawn `M` at `x=32` since it was first committed. Nothing downstream could tell, because a claim about a picture is checked by opening the picture and the sentence read like a description of one.

**And the picture states one colour rule nobody had read off it** ([#157](https://github.com/breferrari/vigia/issues/157)): it draws `+42` in `.grn` and `-7` in `.red` on its first two rows and `-0` in **`.faint`** on its third, so the rule is *value-dependent* — a half takes its diff colour where it has something to say, and the row's dim grey where it does not. §5.3 derives the same answer without the picture, since green and red are lent only where they restate the same fact and a `-0` restates none. The reading it protects is the point: on a worktree an agent is only adding to, an unconditional red would put red on every row and *is anything being removed* would have no answer left on screen. The two halves are still drawn or dropped **together**, because `+42` with no `-7` beside it reads as a total rather than as half a pair; only their ink is per half. What is deliberately not settled is which grey.

### 5.2 Where the mockup pulls against the invariants

§5 says design effort goes here "once the invariants hold", and [#10](https://github.com/breferrari/vigia/issues/10) repeats it: *"depends on the invariants holding first."* **That framing is wrong, and correcting it is the most consequential thing in this section.** At least two elements need retained state the frame path does not produce, in `vigia-core` rather than in the shell. They do not sit on top of the invariants. They **move** them.

**The sparkline needs precisely what eviction throws away.** `FrameStats.evicted` exists so the cached-diff map stays "bounded by the current diff rather than by everything ever edited" — that is how I3 is argued today. A churn sparkline is change density *over time*, so it has to survive a file settling: one that empties the moment a file stops changing shows nothing worth glancing at, and *"what was hot thirty seconds ago"* is the entire question it answers. Glanceability history therefore cannot live in the evicting map — and must not be unbounded either.

> [!NOTE]
> **I10 earned its row on 2026-07-31**
>
> It was written here as a **proposal**, deliberately kept out of the §3 table, because that table is for invariants with a failing test and this had none. It now has a budget (256 paths, 120 seconds), a fixture that drives ten thousand paths through it, and a soak assertion over the real process, so it has moved up. [#38](https://github.com/breferrari/vigia/issues/38).
>
> Two things it cost that this section did not predict. The store had to be fed from the **watch** rather than from the frame path, so `Tick` now carries every file a burst wrote instead of only the last, capped at the same 256 so a bulk operation cannot make a tick expensive before the store gets a chance to bound it. And the decay the mockup asks for turned out to be an I1 question rather than a rendering one: see §11.1.
>
> What it got right is the sentence everything else followed from. **The data structure was the decision and the drawing was the easy part.**

**The heat strip needs a whole-file property.** Locating change within a file requires that file's **total line count**, and the frame path is built to avoid exactly that: pure revalidation reads **0 bytes** (§10), the number I2a is written against. Measured naively — every changed file, every frame — it reintroduces the read I2a removed. It is cacheable per `(path, blob id)`, since a file's length cannot change without its content changing, so it is payable once per version rather than once per frame. **That caching is not an optimisation; without it the heat strip breaks I2a.**

> [!NOTE]
> **The cache above was never needed, and the reason is worth more than the prediction**
>
> **Corrected 2026-07-31 by building it.** [#39](https://github.com/breferrari/vigia/issues/39). The paragraph above is right that a whole-file read would break I2a and wrong that a new cache is what avoids it. `hunk::compute` interns **both sides** to diff them at all, so the working-tree side's line count is already computed on every diff and was being thrown away. It is now a field of `FileDiff`, which means it is cached and invalidated with the diff itself.
>
> That is **stricter** than the `(path, blob id)` key proposed here, not merely cheaper: a blob id names the index side, and a working-tree edit does not touch it, so a cache keyed that way would have served a stale length for exactly the file a reader is watching being written. `tests/frame.rs` gates the difference with an edit that keeps a file's byte length and changes its line count.
>
> The general shape, and it is the third time this project has hit it: **the expensive-looking property was a by-product of work already being done.** I5 found the follow target already resolved by the gitignore filter; I10 found the burst's paths already resolved by the same filter; this found the line count already interned by the differ. Look for the by-product before designing the cache.

**Two status readouts measure the thing they run inside.** `0.8ms frame` means instrumenting the render path and drawing the result — a readout whose own cost falls inside the budget it reports, gated by I9 at 16ms p99. `11MB` is a live RSS number, and I3 samples RSS in a **soak test** precisely because reading it is a syscall on some platforms rather than free per frame. Both are honest to show; neither is free to show; the spec said nothing about either.

**Consequence for sequencing:** Phase 3 is not a rendering phase. Its two headline elements each need a core-side change with an invariant attached, so they belong in the same conversation as I2a and I3 rather than strictly after them.

**Confirmed by building the first one.** [#38](https://github.com/breferrari/vigia/issues/38) landed the sparkline, the recency gradient and the pulse, and the diff was mostly `vigia-core`: a new bounded store, a change to what a `Tick` carries, a new invariant with its own budget, and a soak assertion. The drawing was a bucket ladder and a three-step ramp. This section predicted that split and it was right, which is worth recording because the alternative reading — that Phase 3 is where the shell gets prettier — was the one both §5 and [#10](https://github.com/breferrari/vigia/issues/10) originally invited.

### 5.3 The design language


The principles the individual rulings keep deriving, stated once so a new question starts here instead of re-arguing an old answer. Each names where it already bit; the laws themselves live where they always did (§5.1 for the picture, §11.1 for behaviour) and are not restated.


**The picture binds the elements; the snapshots are what ships; the distance between them is the work.** One canonical mockup, corrected in the same pass as any ruling that changes what it draws — never redrawn ahead of a ruling, because a picture answering an open question *is* the answer and must not arrive by ambush (B4), and never left behind one, because that is drift. But the mockup is rendered in pixels and a cell grid can only approximate it: what it specifies is the **element set and each element's promises**, never glyph-for-glyph fidelity. When every promised element is present and the pane still reads far from the picture, the gap is not a defect in either artifact; it is the design backlog, itemised — spacing, colour weight, composition, density. The snapshot suite carries the rendered truth at every width and state, which one picture cannot.


**Furniture runs full-bleed; text is inset.** The mockup draws washes and rules to the pane edge and glyphs one to three cells in, and the two roles must not swap: a wash that stops short reads as a misaligned highlight, text at column 0 reads as squeezed. *Ruled 2026-08-10, session* ([#119](https://github.com/breferrari/vigia/issues/119)); §11.1 carries the ladder and the floor that keeps it clear of I6's forty columns. What the build added is that a margin has to be laddered as a **total** rather than per side, because stepping both sides on one column hands a widening pane a narrower row. Chrome is the third role and never grows for a transient thing.


**Furniture spans the region that drew it, not the screen.** The law above says a wash runs full-bleed; this says *full-bleed to what*. Until 2026-08-23 the two readings were the same sentence, because every region spanned the pane. [#252](https://github.com/breferrari/vigia/issues/252) put the list beside the diff, and the reading that had never had to be chosen became the only one that draws: a wash reaching the pane's edge from a region two thirds of the way across it would paint over the rail. `render` kept the seam open for three phases on purpose rather than collapsing two numbers that happened to be equal.


**An act answers in one frame; a change may be drawn arriving.** *Ruled 2026-08-27, reader, reversing "snap, never ease".* Two questions the old ruling collapsed. **Anything the reader does lands whole, immediately** — a click, a drag, a digit, a toggle — because easing a response tells a reader the tool is still working, and this tool's claim is that it already finished. **A change the reader did not ask for may be drawn arriving**, because there the motion is the signal rather than a report on the tool's progress. **The footer's own line is outside this**, *ruled 2026-09-04, reader*: every message on it arrives and leaves, a receipt for the reader's own act included, and each of the three does so in its own way. The line is chrome rather than content, and a message that appeared between two frames was reported from the pane as reading like a glitch.

**What licenses it is I1's clock rule, not an exception to it.** The old ruling argued that animation needs a clock and a clock is the timer I1 forbids — the reasoning `RULINGS.md` had already corrected for the step-button repeat and not carried across: I1's measure is **0 wakeups while idle**, and a clock that cannot start on its own does not touch it. So an effect is permitted exactly on the three conditions I1 already states — **it is armed by an event that had already woken the loop, it may not outlive what armed it, and it may not re-arm itself** — and it holds I9's 16ms like any other frame. A quiet tree still costs nothing, which is the whole of what I1 protects. The same reasoning retired the pulse decay and the frozen-clock header words — **anything drawn as *elapsing* lies the moment nothing wakes.**


**Acknowledgment before action, priced honestly.** Every act the shell accepts answers on the same frame — a click lands, a drag tracks, a digit teleports. Extending that to *intent* (hover) was ruled on rather than accreted ([#123](https://github.com/breferrari/vigia/issues/123), §11.2 B10), declined, and reversed 2026-08-16; §11.1 carries the behaviour and the clearing ladder.


**Both reasons for the decline were false in the same way, and that is the durable lesson.** The first said hover *"costs a wake class I1 currently never pays"*: I1 pays it, because `EnableMouseCapture` sets `?1003h` and pointer motion already arrives. The second said *nothing would ever tell it to turn off*, naming as the mechanism that *"the takeover does not enable focus reporting"* — **a line this repository had not written, phrased as a fact about the world.** Each was an absolute about the outside that was never checked, and each was the clause that had already done its work. **A conclusion that outlives the reason it was given is the thing to be suspicious of**: when a stated basis collapses the question reopens, it does not acquire a new basis for the same answer.


**And prefer the claim that has no tense.** *"`TAKEOVER` does not request focus reporting today"* was true when written and false when the build merged; the correction to *"requests it today"* was the same shape pointed the other way. *"`?1004h` is one step `TAKEOVER` can take"* was true before the build and after it. A sentence about what the code does **now** belongs in §11.1, which a build already has to update.


**The principle the reversal produced**: a mark about an **input device** is licensed inside a body region on a surface the reader's pointer can act on, and it must be the quietest thing still visible in that region. The quietness is not decoration, it is what pays for a mark that can go stale: a glance has to reach the worktree first and the pointer never.


**The general shape**: a feel improvement that costs an invariant a sentence gets a decision issue; one that costs nothing gets a row.


**Colour is spent by role, and the diff's is inviolable.** Green and red mean added and removed, may never collapse at any rung that has colour (the depth ladder's one absolute), and are loaned out only where they restate the same fact — the footer's follow marker, the counters. **A loan is per statement rather than per element**, which is what "the same fact" means read strictly: a `-0` on a file row is the counters' element and is not the fact, so it keeps the dim grey while the `+2` beside it takes green ([#157](https://github.com/breferrari/vigia/issues/157)). Cyan marks structure and instrument. Intensity is the recency ladder and nothing else — dim is a *meaning*, not a style. **A new element gets a colour only by taking a role, never by being distinct.**


**A pointer mark is the one case that is not durable** ([#189](https://github.com/breferrari/vigia/issues/189)), so it may take a weight of its own: it is not a claim about the worktree and it is gone the moment the pointer moves. **It takes the pointer's own colour**, `Theme::bar_hover`'s, so one reading means *the pointer is here* on a step button, a thumb and a listed path alike, and **it underlines**, which nothing else in these palettes does. That modifier was always the load-bearing channel and the brightness was never doing the work: on `ansi` a hovered path's foreground equals `Theme::path_cold`'s outright, because sixteen names hold nothing between colour 8 and `Gray`. An earlier draft put the mark **above** all three recency weights, which contradicted the quietness rule in the same breath ([#193](https://github.com/breferrari/vigia/issues/193)); quietness wins, because a hover can go stale and a recency cannot, so a mark that outranks every claim about the worktree is read first and is the one most likely to be wrong. `crates/vigia/tests/render.rs::a_hovered_row_reads_as_the_pointer_and_never_as_recency` and `::the_pointer_reads_the_same_colour_wherever_it_rests` are what fail if either stops being true. **The rule this replaced would have refused the feature**, which is the second time in two days a rule here was read as a wall when it was a description: *there is no rung* was a reason to build one rather than to decline.


**And a second bounded exception, the durable one**: the row the caret marks draws its **path bold**, on top of whatever recency gave it. That is not a third meaning for intensity but the caret's second channel — `▸` and the weight are one statement said twice, resolved from one predicate in `Painter::list`, so they name the same row or neither is drawn. The tie is `affords_caret`: below seventeen columns the caret is dropped and the weight goes with it, and a bold row with nothing pointing at it would be a weight a reader cannot attribute. It shares `BOLD` with the pulse rung, which is not a collision because both readings carry a glyph of their own, and glyphs are what survives `NO_COLOR`. **Why the region needed it**: every other durable distinction there is carried by weight, and the one row a reader most needs to find carried a glyph alone. The two exceptions are orthogonal rather than ranked, so a hovered current row reads as both — colour and underline are the pointer, weight is the file the diff is inside — and ranking them would take one of those facts off the screen.


**Green is loaned a third time, to the staged mark** ([#313](https://github.com/breferrari/vigia/issues/313)). *Staged* is a different fact from *added*, so this is not the same-fact loan above. It is taken on evidence rather than on room: **`git status` paints a staged path green and an unstaged one red**, so a reader who has used git has already learned this mark and any other colour would be a second vocabulary for a distinction git already spells. Inheriting one beats inventing one, which is why `SHEET_CLOSE` and the scrollbar's glyphs are what they are.


**What keeps the diff's own green unambiguous is *where* the mark is drawn, and that is the bound on the loan.** It inks the kind letter, on file rows only, so it is never on a content row and never beside a `+` sigil or a `+42` counter. A reader who has not asked for the staged run sees no green in the list at all. **The ladder is untouched and so is the pointer's channel**: the mark takes no intensity, so recency still owns weight, and it underlines nothing, so hover still owns that. **What it does not do is survive `NO_COLOR`** ([#316](https://github.com/breferrari/vigia/issues/316)), where the run separators carry the fact alone — the price of the column, paid only by a reader who has both asked for the staged run and turned colour off. `render.rs::the_mark_takes_the_staged_colour_and_never_the_diffs_green` is what fails if the two greens are collapsed into one theme key: they are the same hue today and they are different roles.


**The column is what a glyph cost.** The mark was a `│` in a gutter column of its own until 2026-08-25, and it had to be taken on *every* row of *both* runs, because a mark appearing per row would slide the paths beside it one cell sideways at each run boundary. So the pane spent a column of the filename, its most contested element, everywhere at once, to mark the rows of one run. Colour says the same thing for nothing. **A background block is refused by the depth ladder**: §5.1's quantiser drops `bg` at every rung below `Truecolor` and `Ansi16` is the default, so the mark would be invisible for most readers rather than merely plainer. Foreground survives every rung that has colour at all.


**An overlay was asked for first and was checked before it was refused.** `U+20D2 COMBINING LONG VERTICAL LINE OVERLAY` composes correctly: `ratatui` segments by extended grapheme cluster, a `Cell` holds a string rather than a `char`, and `"M\u{20d2}"` measures one grapheme of width one, so no row arithmetic would move. `Cell::merge_symbol` is not a route either — it is box drawing only, and `MergeStrategy::Exact` falls back to `Replace` on a non-box base, which would eat the letter. It was refused on **font coverage**, and **that half of the refusal was corrected on 2026-08-25** ([#318](https://github.com/breferrari/vigia/issues/318)): `fc-list` measures one font and the refusal quoted it as if it measured rendering. Every Linux and Windows terminal in the 2026 matrix resolves a glyph its configured font lacks from the system's other fonts **by default**, and this project's own probes draw `M` + `U+20D2` correctly under the stock `JetBrainsMono Nerd Font` that carries none of the block. So *"vanishes with nothing to fall back to"* was false on every terminal this machine has, and *"cannot be probed from inside a terminal"*, which is true, was never the operative fact — the same per-terminal table that decides `Depth`'s and `Glyphs`' rungs can decide this one. **What that does not reopen is the shipped mark**: ink needs no vocabulary at all and costs nothing anywhere. What it reopens is the vocabulary itself ([#324](https://github.com/breferrari/vigia/issues/324)): overlays, sextants and octants are per-terminal capabilities now rather than per-font gambles.


**A union is what makes any of this necessary, and a swap would have needed none of it.** Showing one comparison at a time spends no channel at all, because every row on screen is the same kind and the header can say which; it was the shape this was first planned as and the reader ruled against it, on the ground that neither view alone answers *what has the agent done*. The second run costs a column of every path and one accent, and what it buys is a pane that never goes blank while there is uncommitted work in the tree.


**Shape carries signal; words are read.** The four glance elements are shape-and-colour precisely so the eye takes them without reading (§5), which is why the pulse lost its label and why a hint is dropped whole rather than abbreviated — half a word is a *reading* task on a surface built to avoid one. Text on screen is either content, a name, or advice, and each has its own degradation law.


**Richness is the reward of space.** The invariants price wakes, writes and clocks — they price **ink at zero**: borders, dense graphs and colour ramps all draw on frames that already happen, so a monitor can be the best-looking thing in the terminal while staying the cheapest. The ladder therefore runs in both directions. Below I6's floor the pane is spartan because every cell is contested; upward, each rung *earns* more of the cockpit. What stays refused is only what the invariants actually name: easing (a clock), decoration that must be configured (B6), and any element whose information is not already retained. **An earlier draft refused borders and meters on taste; that was the author's dial, not the spec's**, and the correction is recorded so the next reader knows which kind of rule this is.

## 6. Architecture

Cargo workspace, two crates:

- **`vigia-core`** — library. Git (`gix`), diff modelling, incremental highlighting (`syntect`), filesystem events (`notify`), the watch and coalesce engine, the frame path. **No terminal I/O, no ratatui.** Every invariant except I6 and I8 is testable here, headlessly.
- **`vigia`** — the `ratatui` + `crossterm` shell: input, layout, theming. Thin by design, so the TUI stays swappable and the engine stays provable. A library with a five-line binary on top rather than a binary alone, because §7 makes the snapshot suite the proof for I5 and I6 and a test cannot import a `main.rs`.

The split is a dependency decision, not a hedge: the TUI renders whatever the core produces, so the core has to work first or the TUI is being built on sand.

### Dependencies, and what each one costs

**`CLAUDE.md`'s rule is that a dependency reaches the spec before it reaches a manifest**, so every direct one is named below with what it buys and what it adds to the graph. **A dependency's cost is a fact about the lock file and is one command away, so an assessment of it that was not run is a guess wearing a measurement's clothes** — that is not hypothetical: `windows-sys` was assessed from memory as *"a new crate in the graph"* and the Windows memory readout was filed as deferred work ([#56](https://github.com/breferrari/vigia/issues/56)) on the strength of it, while a sentence in this section had said otherwise since Phase 1.

**`notify`** is named because I1 requires filesystem events rather than a timer, and each platform delivers them differently: `inotify` on Linux, `FSEvents` on macOS, `ReadDirectoryChangesW` on Windows. It is the standard Rust abstraction over those three and it keeps the binary pure Rust. Verified against all three tier-1 targets: no `cc`, `cmake` or `bindgen` in any graph. The `-sys` crates it pulls are FFI declarations against facilities the OS already ships, so they compile no C.

**`tinyvec`** buys nothing and is declared for a version bound alone, which is the one shape this section's rule did not anticipate. `tinyvec 1.13.0` does not compile, `unicode-normalization` asks for `^1` beneath `gix-utils`, and a fresh resolve therefore took the broken one and broke `cargo install` while every check here, which resolves through the lock, stayed green ([#396](https://github.com/breferrari/vigia/issues/396)). It adds no crate to the graph, and it is deleted rather than maintained the moment a compiling release exists ([#397](https://github.com/breferrari/vigia/issues/397)).

**`tachyonfx`** is named for §5.3's *a change may be drawn arriving*, and it sits under the `ratatui` organisation rather than beside it, which is the provenance this stack already accepts for the shell itself. **It schedules nothing**, which is the whole of why I1 is untouched: `Shader::process` takes the elapsed duration as an argument and `done` reports completion, so the clock stays this program's and bounded by the tick that armed it. Measured rather than assessed, on this section's own rule: it adds **`bon` and `micromath`**, plus `bon-macros` and `prettyplease` as build-time proc macros, because `compact_str` and `unicode-width` are already in the graph beneath `ratatui-core` and `thiserror` beneath `gix`; `default-features = false` drops the DSL and `anpa` with it. No `cc` and no `-sys`, MIT. **Its MSRV is unstated**, which nothing here gates and which is recorded rather than found later.

**`rustix`** is named for exactly one act: the startup background query ([#325](https://github.com/breferrari/vigia/issues/325), §11.2 B18). Before the event reader exists, the shell asks the terminal its background colour (OSC 11) and waits at most a breath for the answer, and waiting on a tty without burning a thread needs one `poll`. It was already in this workspace's graph beneath `crossterm` and `notify`; the alternative was hand-rolled `libc` FFI, which is the same dependency with less checking. Unix only; Windows answers no query and keeps its posture.

**`ureq`, `rustls-graviola` and `serde_json`** are named for the startup update check (§11.1), the only request this program makes, one per process. `ureq` blocks, so the check is a thread rather than a runtime; `serde_json` reads one field out of the answer, and `serde` and `memchr` are already here beneath `syntect`, so it costs two crates. Measured, not assessed, and over the **build graph** rather than the lock: **190 unique crates to 208 on musl and 191 to 209 on Windows**, with no `cc`, `cmake` or `bindgen` on any of §9's four targets. `Cargo.lock` carries `ring` and `cc` once each, behind an optional `rustls-webpki` feature nothing enables, and `cargo tree -i ring` reaches neither. `gzip` adds no crate, since `flate2` and `miniz_oxide` arrive with the grammar dump, and takes the transfer from 71,166 bytes to 10,002.

**The provider is where the pure-Rust rule bites, and one combination survives it.** `rustls` defaults to `aws-lc-rs`, which is `cmake`; `ureq`'s own `rustls` feature is `ring`, which is `cc`. `rustls-no-provider` with [`rustls-graviola`](https://github.com/ctz/graviola/) compiles nothing but Rust, and it is written by the author of `rustls` under the same repository as `graviola`, which is the provenance this stack already accepts for `tachyonfx`. The alternative, `rustls-rustcrypto`, is alpha and carries an advisory. **Two of `ureq`'s defaults are wrong for one fixed endpoint** and are set rather than inherited: it follows ten redirects with `https_only` off, so a redirect could carry the check to cleartext, and its body cap counts *compressed* bytes, so a small gzip answer can decompress without bound.

**And it costs two guards, both about a crash rather than a feature.** `graviola` **asserts** on six x86_64 CPU features (`aes`, `pclmulqdq`, `bmi1`, `adx`, `avx`, `avx2`) and four on aarch64, which its own source puts at processors after roughly 2013. Under `panic = "abort"` that assert kills the monitor rather than the request, so the same features are tested through `std::arch` first. And it is a `compile_error!` elsewhere, so both crates are **target-conditional**: an armv7 or riscv64 `cargo install` still compiles, and the check is not in it. **Its MSRV is 1.89**, which is why this workspace's is.

**`libc` on macOS and `windows-sys` on Windows** are named for §5.1's memory readout. Both are **target-conditional dependencies of `vigia` alone**, both are `unsafe` FFI declarations against facilities the OS already ships, and **neither adds a crate to any graph**: `gix` already puts `libc` into the Apple graph through `gix-hash` → `sha1-checked` → `cpufeatures`, and `windows-sys` 0.61 into the Windows graph through `gix-sec`. What each buys is one syscall in place of a **subprocess**: `soak.rs` reaches the same numbers by spawning `ps` and `tasklist`, which is affordable 288 times across an hour and not sixty times a second, since `tasklist` alone is 42.8ms median against a 16ms frame. Linux needs neither, since `/proc/self/status` is a file read.

**Both are `dev-dependencies` of both crates as well, for the budget gates' CPU clock** ([#212](https://github.com/breferrari/vigia/issues/212)). §7's absolute tier attributes a wall-clock overshoot to the host or to us by reading thread CPU time beside it, `std` exposes no CPU clock on any platform, and this time Linux needs one too: `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` on every unix, `GetThreadTimes` on Windows. **The distinction that keeps it cheap is `dev`**: a dev-dependency is absent from the published crate's graph and from the shipped binary, and the purity gate walks `-e normal,build`, so §6's no-C-toolchain rule is not even in play.

**`signal-hook` on Unix and `windows-sys`'s `Win32_System_Console` on Windows** are named for I8's externally delivered signal, and they are one decision rather than two: `std` has no signal API, the mechanism differs by platform, and the alternative to naming both is the platform-asymmetric guarantee [#16](https://github.com/breferrari/vigia/issues/16) already rejected as worse than one stated uniformly. Both are target-conditional dependencies of `vigia` alone, and **neither adds a crate to any graph**: `signal-hook` is already present at 0.3.18 on Linux and Apple, pulled by `crossterm` through `ratatui`, and `Win32_System_Console` is a feature of a crate `vigia` already declares. Measured 2026-08-08, unique crates before and after: 183 Linux, 181 Apple, 185 Windows, unchanged.

**`signal-hook` is the one dependency here where pure Rust had to be read rather than assumed.** It ships a `build.rs`, which is the shape §6 exists to catch: the file is `fn main() {}` for every feature but `extended-siginfo-raw`, `cc` is an *optional* build-dependency behind that one feature, and nothing enables it. The `no C toolchain` CI job is what keeps that true rather than this sentence.

### Highlighting: the engine choice and what it defers

**`syntect` is fast enough incrementally to hold I2b, so tree-sitter stays out on speed as well as on toolchain.** One screenful of Rust highlights in **1.53ms** against I9's 16ms and a real shell frame under continuous edits in **10.52ms p99**, against **6.97ms** for the core path before highlighting existed. What is not affordable is parsing a hunk *whole*: the 1006-line hunk that fixture produces costs **60.97ms**, 3.8x over budget and paid on every frame under I9's own shape, which is why parsing forward only as far as the screen has asked is load-bearing rather than an optimisation.

**`regex-fancy` is what keeps `syntect` pure Rust, and its price is a compile deferred to first use.** `syntect`'s default engine is `regex-onig`, which is oniguruma, which is C: taking the defaults would put `cc` in the graph on its own and cost musl-static and Windows tier-1. What was never priced is *when* the pure-Rust engine does its work. `syntect` holds each pattern in a `once_cell::sync::OnceCell` and hands it to `fancy_regex` on first use, so the **first parse under a grammar** costs **74–362ms** where loading all seventy-five costs 318µs.

**And it is per pattern rather than per grammar**, which is the part that decides what can be done about it. Warming on a small sample leaves a *different* file of the same language still paying: over a 2.5KB synthetic sibling, `.js` is 80.49ms above floor, `.html` 40.10ms and `.cpp` 37.55ms. So **"this grammar is warm" is not a property that exists** and anything built on one would be acting on a false claim ([#51](https://github.com/breferrari/vigia/issues/51)).

**The cliff is a compile rather than a parse, which is what the flatness in content size says.** Measured at screenful scale, twenty-four lines, a fresh `SyntaxSet` per case:

| | cold | after the warmer read one real 64KB sibling | floor |
|---|---|---|---|
| `.rs` | 123.98ms | **2.40ms** | 2.40ms |
| `.md` | 694.75ms | 89.77ms | 90.65ms |
| `.toml` | 15.26ms | 0.43ms | 0.40ms |

A 594-byte Markdown screenful costs **631.46ms cold and 0.97ms warm**, a 650x penalty on half a kilobyte, while a 16.8KB one costs 439.26ms and 117.00ms.

> **Every figure in this table was measured on Windows under `codegen-units = 1`, and it overstates what ships.** [#261](https://github.com/breferrari/vigia/issues/261) found that at that setting the MSVC target compiles `fancy-regex` roughly 6x slower than at any other, so these costs are inflated by a factor this repository chose and did not know it was paying. The profile now sets 2, and the same worst screenful parses in **8.81ms on Linux**. The penalty is also **Windows-specific**: on Linux, `codegen-units` 1, 2 and 16 sit within 3% of each other on every fixture, so the cliff is a property of one target's codegen rather than of the engine or the profile. macOS has never been measured. **A reader taking a number from this section should ask which of §9's four targets it came from.** The figures are left rather than rewritten because re-measuring them honestly needs the platform they were taken on, and a number retyped across platforms is worse than a number with its provenance attached.

**So the exact claim is the negative one, and that is what the frame path acts on** ([#129](https://github.com/breferrari/vigia/issues/129)). A grammar nothing has ever built a `ParseState` for has every pattern uncompiled, which is knowable rather than estimated: `syntect` exposes no way to fill a `OnceCell` but a parse, so the two places in `vigia-core` that parse are the whole population. **A frame therefore never parses under a grammar the warmer has not run over. It draws that file plain, says which grammar it wanted, and the warm that follows wakes the loop to colour it.** Reaching every pattern directly was checked and is **not available**: `SyntaxReference::contexts` is private, `ContextId`'s fields are private, and `Regex::try_compile` compiles a throwaway rather than filling the set's own cell. Parsing a real file is the only way in, which is why the warmer reads `WARM_BYTES` of one rather than a fixture.

**Warming past what the reader is about to meet is refused on memory.** Compiling ten grammars moves RSS from **6.73 MiB to 64.73 MiB**, Rust alone +12.43 MiB and Markdown +19 to +35 MiB. I3's budget is drift rather than a plateau, so that is a bad trade rather than a breach: a monitor left open for days would carry the compiled form of languages the session never opens. The exception is the **three** grammars the repository itself leads with, counted from the index, because the agent in the other pane is near-certain to write the language the repository is mostly made of. **Counted per grammar rather than per extension**, and the difference is not cosmetic: the index can only be tallied by extension, since §6 puts `syntect` on the other side of `worktree.rs`, and a language spelled two ways (`.yml` and `.yaml`, `.md` and `.markdown`) is then counted twice at exactly the point where the counts decide who wins.

### The grammar set

**Which languages the dump covers is a decision, and until 2026-08-19 it was an inheritance.** `Highlighter::new` loaded `syntect`'s bundled dump: 75 syntaxes, a Sublime Text 3 era snapshot chosen by nobody. Probed against what a 2026 reader opens, 36 formats drew plain — TypeScript first among them, and `Cargo.toml` drew plain in a tool written in Rust. *Ruled 2026-08-18, reader* ([#235](https://github.com/breferrari/vigia/issues/235)): **`vigia` covers every modern language, with no tiering.** The bar for a format is that a grammar exists that this stack can carry.

**The mechanism is a curated dump embedded in `vigia-core`, not per-grammar submodules.** [`two-face`](https://codeberg.org/CosmicHarper/two-face) (MIT OR Apache-2.0) packages `bat`'s curated grammar set as a `syntect`-ready dump with a **`fancy`-vetted variant**: every definition it ships compiles under `fancy-regex`, this crate's engine. That vetting is load-bearing rather than a convenience. `syntect` compiles each pattern lazily behind an `expect` and the workspace builds with `panic = "abort"`, so **a grammar carrying a pattern the shipped engine cannot compile is a process kill on the first file that reaches it** — a single `.ps1` in the diff would take the monitor down, and `bat` never meets this because its default engine is oniguruma. Grammars `bat` does not carry are vendored as pinned `.sublime-syntax` files under `assets/syntaxes/` with provenance headers, **and each upstream's licence text is committed beside them** at `assets/syntaxes/licences/<repo>.LICENSE`, because MIT and Apache-2.0 both ask for the notice in every copy of a substantial portion and the dump is a copy: a header naming a licence is not the licence.

**No shipped grammar may carry a pattern that fails to compile**, for the abort just named. `two-face`'s `fancy` build guarantees it for `bat`'s set by excluding what cannot comply; every locally vendored grammar is gated by `crates/vigia-core/tests/coverage.rs`, which force-compiles its patterns **and its `first_line_match`** under the shipped engine, because a lazy compile is a gate that green-lights whatever nothing happened to reach. Three more gates live beside it: one compiles every first-line regex in the **whole** dump, since `two-face`'s vetting covers match patterns and a first-line regex is exactly the kind nothing reaches until an extensionless file turns up; one ties the committed sources to `NOTICE.md`'s hash table and to the dump's own roster, because the two were otherwise checked separately and a source edited without rerunning `xtask` passed both; and one parses a snippet per covered format and asserts the spread of classes it reaches, because a grammar that loads and draws plain is what #235's second half was about.

**An ambiguous extension resolves by a written rule, not by registration accident.**

| Extension | Resolves to | Why |
|---|---|---|
| `.h` | Objective-C | ObjC's grammar is a C superset, so C headers colour fully and only C++-only constructs draw plain; and it is the dialect of the reader who filed #235. `bat` rules the other way (`*.h` → C++, their #877), recorded here so flipping this row is one edit and an informed one |
| `.m` | Objective-C | Same population argument over MATLAB, and the same one-row flip if it proves wrong |
| `.v` | V | Verilog is in the dump too, so the collision is real; the ruling's whole subject is the modern-language set, and V is the one it covers |
| `.sass` | Sass | It resolved to **Ruby Haml**, which is simply wrong. The pin gate in `tests/coverage.rs` is what makes a quiet return to Haml a red build |
| `.jsx` | the TSX grammar | TSX is a superset of JSX, and the Babel grammar is `fancy`-excluded |
| `.ts` | TypeScript, unless the first line opens `<?xml` — then XML | A `.ts` whose first line is an XML declaration is a Qt translation file |

**Resolution has five steps rather than two**: the table above, then whole file name with a leading-dot retry (so `.gitignore` can match a grammar registering `gitignore`), then extension, then the nearest-grammar approximations below, then `find_syntax_by_first_line` when the file's first line is known — which is what gives an extensionless shebang script a language at all. Whole name **before** extension because it is the more specific claim: `CMakeLists.txt` is registered whole by the CMake grammar, and the old extension-first order handed it to Plain Text, so it drew plain for as long as highlighting has existed. The first line travels on `FileDiff`, captured from bytes the diff already holds, so no read is added anywhere (I4). The warmer does not use it, deliberately: its per-grammar cap is checked before the read, and reordering that to sniff content would spend the I/O the cap exists to save.

**What the ruling costs, measured 2026-08-19, release.** The release binary moves from **5,492,224 to 6,102,528 bytes** (+11%) carrying 217 syntaxes against 75; the embedded dump is 970,915 bytes. Loading it at startup is **0.674ms** best of 20 (318µs before), and the dump is **uncompressed by measurement rather than by default**: the compressed form of the same set loads at **9.67ms**, a 14x, against 90KB saved in a binary whose size budget has an order of magnitude more room than its startup budget. First paint over the 100-file, 100k-line fixture is **15.15ms against I7's 50ms**. RSS is untouched by the count, because it follows the grammars that *compile*, and a grammar nobody opens costs its bytes in the dump and nothing else.

**Four ruled formats have no grammar this stack can carry, and each is a recorded gap with a nearest-grammar approximation rather than a silent plain.** **Astro** and **Bicep** ship ST4 `version: 2` grammars built on `extends:` inheritance, which `syntect` does not implement, so `.astro` draws as HTML and `.bicep` as JavaScript, the grammars their upstreams extend; **Mojo** has no `.sublime-syntax` anywhere and is a Python superset, so `.mojo` and `.🔥` draw as Python; **MDX**'s only real grammar carries no licence to vendor under and is a Markdown superset, so `.mdx` draws as Markdown. **Carbon** has no grammar in any format and gets nothing. The approximation step runs **after** ordinary resolution fails, so the day a real grammar lands in the dump it wins without the table changing. **PowerShell is covered, not a gap**: `two-face` excludes it under `fancy` for one subroutine-call regex, and the vendored copy patches that one pattern structurally, the capture having been unused.

### Coalescing, and the frame path's memory

**Coalescing stays ours.** `notify` has a companion debouncer crate, and taking it would move coalesce policy out of `vigia-core`, which is the one place I1 is testable. `notify` supplies raw events and nothing else.

**There are two coalescings, and only the first is that one.** `vigia-core` coalesces **events**: which filesystem writes count as one change. That is I1's. The shell coalesces **paints**: how many frames one burst of wakes is worth. That is I9's, it cannot live in the core because a paint is the shell's and because one of the four wake sources is the terminal, and it decides nothing about which events are real. It costs I1 nothing, because draining a queue that is already there is a `try_recv` and never a wait: an idle shell still blocks on one `recv` and still does no work ([#45](https://github.com/breferrari/vigia/issues/45)).

A coalesced tick also **names the file whose write landed last in it**, which is what I5 follows. The path is a by-product of the gitignore filter, which already resolves every event against the worktree root, so carrying it costs no syscall. This is the second thing the debouncer crate would have taken away.

**The frame path keeps its diffs between frames.** I2a forbids re-diffing a file that did not change, so the core holds the previous frame's diff per path and revalidates instead of recomputing. Validity is decided from three things that cost no file read: the index blob the change names, the kind of change, and a `stat` of the working-tree file. Content is never hashed to decide this, because hashing is the read I2a exists to avoid.

A `stat` on its own is not proof, and the gap is the one git calls *racily clean*: two writes of the same length inside a single modification-time granule are indistinguishable by `stat`.

**The rule that closes it has to account for flooring.** A filesystem stamps a modification time by truncating the current time to its own granularity, so a write landing *after* a read can record a time *before* it. "Older than the read" therefore proves nothing, because the granule may still be open: measured on NTFS, that mistake serves a stale diff on about one same-length rewrite in four hundred, and on a 1s-granule volume it would be most of them. So a fingerprint is trusted only once a **full granule has passed** between the stamp and the read. The margin is a constant that must be an upper bound on real granularity: **2 seconds**, since FAT and exFAT quantise to 2s and HFS+ to 1s, where NTFS, ext4 and APFS are milliseconds or finer. That trades redundant diffs of files written in the last two seconds, which are files that just changed, for never showing a stale one. **It is a table lookup rather than a measurement because measuring the right filesystem would need a probe write**, and §11.1 carries "the monitor writes nothing" as a rule rather than as an accident of what this code happens to do: the margin's whole case rests on that, so the two have to be one decision.

**What it still cannot see** is a writer that restores a modification time it did not advance: `cp -p`, `rsync -t`, `unzip`, `touch -r`. Git carries the inode change time to catch those, and `std` exposes no equivalent on Windows, so closing it is a dependency decision rather than an implementation detail. Tracked on the deferral shelf rather than assumed away.

**And it assumes the modification time is stamped by the local clock.** The margin compares a filesystem timestamp against this process's clock, so on a network filesystem the server's skew subtracts directly from it: a server two seconds behind consumes the whole margin and the flooring problem returns. Local worktrees, which is what a monitor beside an agent watches, are unaffected.

## 7. Testing


- **Snapshot tests over `ratatui::backend::TestBackend` with `insta`** — render frames into an in-memory buffer, snapshot as text. This is what makes I5 and I6 assertable at all: the UI becomes diffable text.

- **`criterion`** for I4, I7 and I9, **tracking rather than gating.** Criterion compares a run against a saved baseline, and the budgets in §3 are absolute, so it is the right instrument for "this got 20% slower" and the wrong one for a pass/fail line. Compiled in CI so the benchmarks cannot rot; not timed there, because a shared runner cannot produce a number worth comparing.

- **Budget gates** in `crates/vigia-core/tests/budgets.rs`, in **two tiers**, because an absolute wall-clock threshold is a strong instrument on a known machine and a weak one on a hosted runner:

  - *Structural* gates compare the engine against itself across fixtures that differ only in how much changed. They are ratios and exact byte counts, so they are hardware-independent, take **no slack**, and are what actually catches a regression. Making the frame path re-read every changed file is a 5x wall-clock change that a generous threshold waves through, and a 100x byte-count change that these cannot.

  - *Absolute* gates hold the wall clock to §3. Release only, since the budgets were set against optimised code, and with a slack multiplier (`VIGIA_BUDGET_SLACK`, default 1) so a shared runner's variance does not read as a code regression.


**A breached p99 is re-measured once, and only a second breach fails.** *Ruled 2026-08-17, session* ([#178](https://github.com/breferrari/vigia/issues/178)), after a third gate failed with its median comfortably inside budget and its tail an order of magnitude out. Wall clock includes time the process was not running, so on a two-vCPU hosted runner one descheduling quantum puts two samples of two hundred and fifty outside the budget, which **is** the ninety-ninth percentile. Two rounds fix that without weakening anything, because interference is independent between rounds while a regression recurs by construction. **What is deliberately not done**: raising the slack, which hides a regression exactly as well as a stall, and trimming the percentile, which weakens the tail claim the budget *is*.


**And what a second breach means is decided by thread CPU time rather than by the shape of the distribution** ([#212](https://github.com/breferrari/vigia/issues/212)). A median inside budget with a tail outside it is *consistent with* a stall and does not establish one; CPU time establishes it, because no amount of host contention inflates work done. The comparison is a round's **off-CPU time against the time that round spent above budget** (`Samples::excess_over`): if the time the process spent not running covers the round's total excess, the host is a sufficient explanation, so the breach is reported and not failed. **Both sides are sums over the round** ([#269](https://github.com/breferrari/vigia/issues/269)) — compared against the p99's own overshoot instead, ordinary per-frame scheduling noise out-accumulates a per-frame overshoot and the test drifts toward acquittal as the sample count rises. **Reporting a covered breach rather than failing it is the only weakening in this ruling.** Totals rather than a CPU percentile, because `GetThreadTimes` is quantized to the scheduler tick and a 3ms frame reports zero CPU on Windows. Where a platform has no thread clock an unattributable breach is **ours**, which is the only safe direction. **What CPU time cannot separate is preemption from our own blocking**: a frame that started waiting on the disk reads here as a busy host, and what covers that is the structural tier.


- **A budget measured on one target is a budget about that target, and until 2026-08-08 the shipped Linux binary was not the one measured.** Every absolute gate ran on `ubuntu-latest`, which is glibc, while §9 makes `x86_64-unknown-linux-musl` the **only** Linux artifact a release produces, so the artifact a Linux reader receives had never been held to I7 or I9 at all. The `musl` job in `ci.yml` now runs the absolute gates against that target, which costs no runner change because a static musl test binary executes natively on a glibc host. [#12](https://github.com/breferrari/vigia/issues/12).


**It runs `-p vigia`, and the reason is a constraint worth knowing.** The unscoped form does not compile for a cross target: `criterion` is a dev-dependency of `vigia-core`, it pulls `alloca`, `alloca`'s build script is `cc`, and `cc` then looks for `x86_64-linux-musl-gcc`, which a hosted runner does not have. **So the pure-Rust property `CLAUDE.md` protects holds for the shipped graph and does not hold for the dev graph on a cross target**, recorded here rather than papered over by installing a C cross-compiler in CI.


**The concern that motivated it was unfounded.** On `ubuntu-latest`, release, musl, `VIGIA_BUDGET_SLACK=3`: **first paint 14.49ms** against I7's 50ms; a bulk rewrite of 100 undrawn files inside the settle margin **p50 11.96ms, p99 12.46ms** over 270 in-margin frames against I9's 16ms. Every gate green, and first paint holds even unslacked. The numbers are in the log because the step passes `--nocapture`: libtest discards a passing test's output, so without it this job would prove the budgets hold and record nothing about by how much.


**The first version of this bullet claimed I7 as well, which was false, and the pre-existing half is worse.** `first_paint.rs`'s absolute gate is release-only through `absolute_gates_apply`, and no CI job selected it in release at all, so it reported itself skipped in the debug run and was never reached in the release one. **It ran nowhere, on any target, for as long as it had existed.** Both the `test` and `musl` jobs now run it **in a step of its own**: cargo runs test binaries one at a time but chooses the order, and sharing one invocation put `first_paint`'s three cold starts over a 100 x 500 fixture *between* the two `budgets` binaries, so the shell's absolute gates began measuring immediately after a burst of exactly the disk and allocator work they are most sensitive to ([#36](https://github.com/breferrari/vigia/issues/36)). That is this section's own recurring shape reached through the test **selector**: the gate was correct, warm, positioned and non-vacuous, and nothing ran it.


- **An invariant the engine can only make possible gets a second gate over the caller**, in `crates/vigia/tests/`. I4 is the case: the core fetches content per file, so painting the top of a large diff without reading the bottom is *available*, and nothing in the core stops a renderer from asking for every file anyway. Asking is the natural way to write one. **Either tier can be the one that has to move there**, and I2b needed both: `reads.rs` holds the structural half and `crates/vigia/tests/budgets.rs` an *absolute* one, because highlighting follows the viewport and so happens in the shell — a frame timed in the core is a frame with the syntax parser missing.


**Seven rules below are one family: a gate can be correct and still measure the cheapest corner of the space it is about.** Each was found by a real defect passing a green suite, and each names a different corner.


- **A budget measured at one position is measured at its cheapest one.** A caller starts at the top, so a gate that never scrolls tests the corner where the least work is possible. I2b's frame gate ran at row zero and passed while a frame four screenfuls down cost 53ms against a 16ms budget, sustained and with no input; its own assertion was right and could not fire. Any gate over a windowed view is parameterised by where the window is.

- **A gate that warms up cannot see a first-paint cost, and a first-paint budget therefore needs a gate that never warms.** A steady-state gate is *right* to discard its warmup, so the discarding is a blind spot to cover elsewhere rather than a flaw to fix. Every steady-state wall-clock gate drops fifty frames, and I7 — a budget about exactly one frame — had its only gate in `vigia-core`, where that gate builds no `Highlighter`. The shipped first paint was **105.03ms** against a 50ms budget, 2.1x over, for two phases, invisible because two correct decisions met. **A budget over the first N of anything needs a gate whose window starts at zero.** [#51](https://github.com/breferrari/vigia/issues/51), `crates/vigia/tests/first_paint.rs`.

- **A gate for a *deferred* cost asserts the work was deferred, not merely that the clock is small.** The fix for a slow first paint is to do less on it, so the gate's own subject could quietly become *drawing less*. `first_paint.rs` asserts the body is full and that the frame parsed zero lines **before** it asserts the clock, and that a later frame parses more than zero, or the whole gate is satisfied by a build whose highlighter never runs. It also compares the plain frame's rows against the coloured one's — at the `Row` level, which is one level short of the cell a reader sees, and [#106](https://github.com/breferrari/vigia/issues/106) is that gap named rather than left implied. [#129](https://github.com/breferrari/vigia/issues/129) needed the same pairing for a second deferral: `warm.rs` asserts a grammar nothing has compiled parses **zero** lines and draws every span plain, and, in the same file because a gate for an absence alone is satisfied by a build that never highlights anything, that the same hunk colours once the warm lands.

- **A frame-time gate that never paints has timed half a frame.** It went unnoticed longest because the omission is invisible from inside the gate: every budget gate in this repo timed `Frame::advance` plus `App::view` and stopped, so `render` — where a row's *width* is decided — was outside both tiers on both crates. A row carrying **7.2x more line than pane** passed a 16ms gate for two phases, and what found it was a reader scrolling a Japanese README. **A gate is written against the caller's whole frame, and any stage left outside it is a stage nothing can regress you on.** `crates/vigia/tests/paint.rs`, [#45](https://github.com/breferrari/vigia/issues/45).

- **A structural gate bounds a counter, not a resource, so a cost added outside that counter's population is invisible to it.** The line above one axis over: there a *stage* was left outside the timer, here every stage was inside and the gate was still blind, because the new syscall landed in `Worktree` while `FrameStats::probes` counts the frame path. [#15](https://github.com/breferrari/vigia/issues/15) needed a file's type before reading it, and the obvious `lstat` put a **second `stat` per file** on exactly the path `reads.rs::a_tick_inside_the_settle_margin_stats_each_file_once` exists to hold at one. It stayed green, and the clock could not cover for it either, because that fixture's gate deliberately refuses to assert a wall clock.


**And removing the cost was not the end of it, which is the half worth keeping.** With the syscall merely made *conditional* and still counted nowhere, deleting the fix and restoring the unconditional `lstat` left **every test in the repository green** — an optimisation whose whole justification is a syscall count, in the one repository whose method is *"an invariant without a failing test is a wish"*, had no failing test. The probe is counted across the layer now — `Worktree::diff_counted` threads a `&mut u64` that `FrameStats::probes` accumulates, so a `stat` taken anywhere under it lands in the frame's own count — and the gate fails with its own unchanged message, **"the tick took 200 stat calls over 100 files"**. **Completing a counter's population is not the same act as widening a gate to admit a regression**: one lets a regression through, the other catches one that was previously invisible. **When a change adds work near a counter, ask which population the counter has, not whether its gate is green** — and ask again after the fix, because a saving the instrument cannot see is a saving the next reader can delete.


- **A fixture over ASCII cannot tell a column bound from a character bound**, because over ASCII they are the same number. The budget fixtures are generated source, 34 columns a line, so *"a row costs the pane"* and *"a row costs the whole line"* produced identical counts across every gate in the suite. Anything measured in **rendered width** needs a fixture where width and length disagree: `Scratch::wide_lines` is 531 columns over 412 characters of Japanese, emoji and Latin.

- **A fixture population sitting on its tooling's default configuration cannot observe the code that exists for the non-default.** The same family one axis further out: there the fixtures were uniform in their *content*, here in how they were *built*. Every fixture is created by `Scratch`, which shells out to `git init` and sets `core.autocrlf false`, so both sides of every diff were always LF and the code path that skipped the clean filter produced byte-identical output to the one that runs it. Not one test was wrong and not one could have failed: [#65](https://github.com/breferrari/vigia/issues/65) drew a file `git diff` called unchanged as a 1,790-line rewrite while the suite was green, and what found it was pointing the tool at a real repository. **The tell is checkable: delete a normalisation, filter or conversion step and see whether anything goes red.** That is a mutation test with a specific target — "does any fixture make this branch's presence observable" rather than "is this branch covered". The answer is to **span** the axis rather than move along it, so `Scratch::crlf_worktree` stands beside `Scratch::new` instead of replacing it. Git alone offers `autocrlf`, `.gitattributes` filters, `core.symlinks`, `core.ignorecase` and sparse checkout; a fixture built by `mkdir` and `write` has silently taken the same position on all of them.


**`core.symlinks` was the next one along and it was holding two defects, which is the strongest evidence this rule has produced.** Named above as an unspanned axis before anyone had looked. [#15](https://github.com/breferrari/vigia/issues/15) spanned it and found a symlink diffed as its *target's contents* where git stores the target **path** — known and filed. The second was not: `frame::fingerprint` used `fs::metadata`, and **Windows refuses to resolve a symlink whose stored target uses forward slashes**, which is exactly what git stores. So the fingerprint was `None` on every checked-out link and every symlink in a Windows worktree was re-diffed on **every frame, indefinitely**, against I2a. No gate could have caught it, because the axis had no fixture on it. `crates/vigia-core/tests/frame.rs::a_repointed_symlink_is_not_reused_from_the_targets_fingerprint` is where to restore the following `stat`, and `settle` then reports *"still re-reading after 8 idle frames"*. **An axis named as unspanned is a prediction, and this is the one that paid.**


- **A gate whose setup materialises every unit has measured the cheapest cache population.** The one that hid longest, because the helper responsible is *named* for the other thing it does: `settle()` exists to wait out the staleness margin, and the way it proves the wait worked is `materialise()`, which diffs **every** file. A frame holding a `FileDiff` for every changed file rebuilds every height from memory and reads nothing, so the walk I4's narrowing admits cost exactly zero in every gate that opened with `settle`, on both tiers, in both crates. The bug it hid was not small: the height walk re-read the whole undrawn changed set on **every tick**, 94 files and 3.7 MiB over the hundred-file fixture, 18.36ms p99 against 16ms, with eleven read-bounding gates green over it. **If a gate's fixture setup populates the cache the gate is about, it has measured the case where that cache is full.** `settle_spans` is the same wait without the materialisation and stands beside `settle` rather than replacing it, which is the same span-the-axis answer as `crlf_worktree`. [#101](https://github.com/breferrari/vigia/issues/101).

- **A gate that settles before it measures has measured the cheapest state.** The same mistake along a different axis, time rather than position. `settle()` exists so a fixture written moments ago can be *proved* unchanged, and every structural gate in `reads.rs` calls it first, so the settle margin — the one window in which the frame path deliberately recomputes instead of reusing — was the one window nothing measured. §10's claim that the margin breaches I9 under a bulk rewrite went two phases with no gate on either tier, in either direction. **An invariant that governs a window needs a gate that runs *inside* it.** [#32](https://github.com/breferrari/vigia/issues/32).

- **A gate can assert the defect it was named against, and the tell is an exact small count where the rule is a bound.** `crates/vigia/tests/scroll.rs::the_bottom_of_the_diff_is_content_rather_than_blank` was written against a blank pane, said so in its name, said so again in its comment, and then asserted `view.rows.len() == 1` against a twenty-two row body. Every word around it was right and the one line that runs pinned the failure in place. That is worse than an absent gate, because a defect with a green gate over it is one nobody goes looking for: [#57](https://github.com/breferrari/vigia/issues/57) was found by a reader watching an agent run `git reset --hard`, two phases after the gate shipped. **The signature is a specific small number where the rule is about a bound** — "the screen is full" is `== height`, never `== 1` — and it is legible by reading the assertion against the test's own name.


- **An invariant whose two failure modes are not symmetrical gets a gate for each.** I2a is the case. Reusing too *little* is slow and loud, and the budget gate catches it. Reusing too *much* is fast, passes every budget, and shows a diff that no longer exists, so `crates/vigia-core/tests/frame.rs` compares every reused frame against one computed with no memory at all. A budget gate alone would have called the second failure a success.

- **A rule covering a window too small to race is extracted as a pure function and tested directly.** The racily-clean guard in §6 cannot be reached on demand from a filesystem: dropping it leaves the whole integration suite green and only a unit test over the decision function goes red. Where a correctness rule has no reachable integration path, the pure-function test *is* the gate.

- **Gates are mutation tested before they are trusted.** Break the code deliberately, confirm the gate goes red, restore. Two of the flaws found this way were invisible to reading: a structural gate comparing one call against the sum of its own calls, and a p99 over too few cold samples.

- **Steady-state budgets are sampled after a warmup**, and over enough frames for a percentile to be one. I9 is a claim about steady state, so the cold path is outside its scope by definition; measured cold frames run ~40ms against a warm p99 of ~3ms, and at 30 samples a nearest-rank p99 is just the maximum.

- **A CI guard fails the build if `cc`, `cmake` or `bindgen` enters the dependency graph** on any tier-1 target, plus a musl build asserting the binary links no shared libraries. The pure-Rust constraint is what makes musl-static and Windows cheap, so it is enforced rather than trusted.

- **`proptest`** over diff parsing and hunk-boundary logic.


### The soak, and the instrument that gates nothing


- **The soak drives the whole pipeline, not the engine.** I3 is a claim about the process a reader leaves open, so measuring `vigia-core` alone would prove it about a program nobody runs. The harness is `vigia::run` with the terminal removed: a real `notify` watch thread, real coalescing, `Frame::advance` per tick, follow and scroll through `App`, `View::collect` driving the `Highlighter`, and `render` into a `ratatui` buffer. What it leaves out is named rather than discovered later: the terminal takeover, which needs a tty and is I8's; the input thread; the signal handler, which is process-global; and index writes, because the loop reaches the same mass-eviction state by reverting files, and keeping `git` out of the measured window is what makes the temp-file gate exact.

- **The soak is two tiers, like every other budget here.** *Structural* gates — the retained caches bounded by the current diff and by the viewport, eviction actually happening, and **zero temp files retained** — are counters and directory entries, so they run in every `cargo test`. The *absolute* gate is RSS drift, and it is the one that has to be scheduled.

- **A drift gate over a window shorter than its own warmup is measuring warmup.** RSS climbs to an allocator plateau in the first minutes of any process and only then goes flat, so a short window reads that climb as a leak and a generous threshold would then wave a real leak through. The gate discards a warmup prefix, compares the median of the first quarter of what remains against the median of the last quarter, and **refuses to assert at all** below a window where that leaves two ends worth comparing. Refusing is the point: a gate that cannot say "no drift" has not been tested, and one that says it from four samples is worse than absent.

- **The gate's warmup prefix is workload-dependent, the report says so, and that is a ruling rather than an omission.** The prefix is a **fraction** of the window, 10%, which is window-independent and is what it was chosen for. It is not *workload*-independent: RSS plateaus in about **thirty seconds** over the default 20 x 200 fixture and in about **eight hours** over 100 x 500. A tenth of a 24-hour run therefore discards 2.4 hours of a climb that takes eight, and the first full window read **13.26% against the 5% budget** on a process that moved 0.33 MiB across the sixteen hours past its plateau. That is a **known instrument artifact**, and it is the case §10 anticipated as "crosses on variation rather than on a leak".


**The answer is a measured number printed beside the verdict, not a moved baseline.** The report carries where the series settled and what the same ends-ratio says from there: `settled at sample 97 of 288 (8.08h in), drift from there 1.85%` beside the gate's own 13.26%. The settled **level** is the median of the last quarter, and a rolling window of that same quarter width steps back from the end while its median stays within **1%** of the level. Nothing is gated on it.


**A measured baseline was built three times and does not ship, which is worth recording so a fourth is not attempted in good faith.** Each formulation fell to a real adversarial shape and each defect lived inside the previous fix: a leak between two plateaus absorbed as warmup (**4.24%** against a 20.00% window); one 4 KiB page prepended to a flat head defeating the clause added to stop that (**4.77%** against 29.50%); a warmup followed by a flat stretch followed by a leak passing through the same clause again (**4.99%** against 25.00%). The shared root is that a walk finds a plateau's *end* while a gate would need its whole *shape*, which is change-point detection and is a discipline rather than a patch. It is out of proportion here, because the leak-catching duty is already discharged twice: by the calibrated-leak fixture, caught from the fraction unchanged, and by the structural tier. **The gate keeps its one honest property, which is that it can be wrong only in the loud direction.** A red the printed plateau explains is an annotation; a green produced by an unsound detector is a laundering, and a suite stays green while that happens. `crates/vigia/tests/soak.rs::statistic` holds every clause, the recorded 288-sample series included as a fixture; the three detector designs and the shapes that defeated each are on [#127](https://github.com/breferrari/vigia/pull/127).


- **The same report carries the shape the gate rounds off, and the gradient through it, neither of them gated.** A ratio between two ends cannot tell a process that stepped once and went flat from one that is climbing, and that difference is the whole of §10's open question about I3. So the report prints the medians of a quarter's worth of samples at **four** positions and a least-squares gradient in **MiB per hour**, fitted against elapsed time rather than sample index so it survives a run whose loop fell behind. The gradient is **signed** where the gate's ratio is deliberately clamped: a gate must not pass for the wrong reason, and a diagnostic whose job is a sign must not hide one. The middle pair and the gradient are reported and never gated. A threshold on either would be a budget this document does not name.


**A gradient is printed with the span it was fitted over**, because for one fixed amount of RSS wander the reported MiB/h goes as the reciprocal of the window. Reference machine, by window: **+364.71 MiB/h** at 15s, **+7.89** then **+2.74** at 600s, **+1.94** and **−0.70** at 900s, **+0.92** at 3600s. A span is about nine tenths of its window at 288 samples and **three quarters** at the fifteen-second default, where `MIN_SAMPLES` rather than the warmup fraction sets it. **Without the span beside it none is comparable to another**, which is the comparison this section asks a reader to make, and the instrument becomes readable somewhere around the window I3's budget names. `soak.rs::statistic::the_gated_ends_are_the_first_and_last_quarter_medians` holds the outer two in place, over two fixtures because each hides what the other catches.


- **A bound is only evidence when something reached it, so a gate over one asserts that eviction happened as well as that the bound held.** I10 is the case: the per-commit soak window touches about eighty distinct paths against a cap of 256 and never turns the 120-second window over once, so `tracked <= 256` is satisfied there the way an empty room satisfies a fire code. The soak **refuses to assert** when the run reached neither eviction rule and prints why, exactly as the drift gate does; the deterministic proof is a fixture that drives ten thousand paths in every `cargo test`. Verified by running the soak at 300 files, where it reports 256 tracked at the cap with 207 evicted.


- **Every instrument above measures a fixture, so one of them measures a worktree instead, and it gates nothing.** `crates/vigia/tests/observe.rs` is `vigia::run` with the terminal taken out and with **no writer of its own**: it is pointed at an existing checkout and the agent in the other pane is the workload ([#72](https://github.com/breferrari/vigia/issues/72)). It asserts nothing because its window is whatever a working session happened to be, so a threshold over either would be a budget this document does not name. Three things about its shape are this section's own rules turned on itself. **The oracle runs in a separate process**, because answering "does this diff agree with `git`" diffs every changed file, which is the setup-materialises-every-unit trap aimed at the very caches whose cost is the measurement. **A budget is a bucket edge**: "was a frame ever over 16ms" has to be a *count*, so 16000µs is a declared boundary and the accessor **refuses** any threshold that is not one. **Nothing unbounded is retained**, because the process holding the samples is the process whose RSS is one of the readings, so the worst eight frames are kept with their context and everything else is a bucket.


**And a harness that claims to be the caller's whole frame has to be it, which this one was not on its first attempt.** `drive` left three stages out and each understated a real cost. `branch_for` reads `.git/HEAD` on exactly the frames that draw the empty state, which over the recorded sessions was about half of them. The `chrome` is built **twice** per paint. And `Shell::draw` settles I7's repaint debt **inside the same tick**, so the first frame a reader sees is painted twice and a harness that painted once timed the plain half and displaced the colour onto the frame after: a first frame of **5.52ms** became **558.83ms**, which is where the grammar compile actually lands. That last one is the mechanism this section already records the product nearly losing, lost again in a second hand-copy of the same sequence, which is the argument for a gate rather than for a reading: `observe.rs::wiring` drives one `draw` over a real worktree and asserts the debt is settled and the frame is coloured, over **two** fixtures because a dirty tree never reaches the branch read at all.

## 9. Distribution

- **crates.io** — `cargo install vigia`. A name **cannot be reserved; it must be published**, and a publish is **permanent** (`cargo yank` hides a version from new dependents, it does not delete it, and the name stays taken). So the first publish should be a crate that does the minimal real thing. Verified free 2026-07-30, **and again 2026-08-08 against `index.crates.io` rather than the web API**, which is the file `cargo` itself resolves against and therefore the only answer that binds. `vigia-core` is free too, and that is not a courtesy check: see the publish-order bullet below.
- **Homebrew** — `homebrew-core` **cannot be reserved** and requires notability: ≥30 forks **or** ≥30 watchers **or** ≥75 stars, plus a stable versioned release. Until then a **personal tap** (`breferrari/homebrew-tap`) gives `brew install breferrari/tap/vigia` immediately, is fully under our control, and is what `cargo-dist` generates. Tap repository created 2026-08-08.
- **GitHub releases** — prebuilt binaries per platform via `cargo-dist`.
- No domain. Not needed for a CLI.
- **Two names are claimed, not one, and the order between them is forced.** `crates/vigia/Cargo.toml` declares `vigia-core` by `path` *and* `version`, and a registry will not accept a package whose dependency it cannot resolve, so `cargo publish -p vigia` fails outright with `no matching package named vigia-core found` until `vigia-core` exists on crates.io. The §6 crate split therefore spends a second permanent name, which is a cost of that split nobody priced at the time and which is worth stating rather than discovering at the release. **The pipeline runs `cargo publish --workspace`**, one command rather than two, because cargo resolves the dependency order and waits for the index itself; the two-call form needs a sleep between them whose right length nobody knows.
- **The release is one dispatch from the Actions tab, and every irreversible thing hangs off it.** `cargo-dist` 0.32 (the binary is named `dist`) builds the four target artifacts, creates the GitHub release, publishes the Homebrew formula to the tap, and runs a custom publish job that sends both crates to crates.io. `dist` has no built-in crates.io publisher: `publish-jobs` accepts `homebrew`, `npm` and custom reusable workflows, and the registry one is ours, in `.github/workflows/publish-crates-io.yml`. **That is what makes the tag the gate**: `RELEASE-SMOKE.md` runs against `dist build` output *before* the tag, not against a published artifact after it.

**Started by `bump.yml`, not by a tag push, and that is a mechanism rather than a preference.** `[workspace.metadata.dist] dispatch-releases = true` makes `release.yml` run on `workflow_dispatch` and **removes its tag-push trigger entirely**, so `git tag v0.1.2 && git push --tags` no longer produces a release. The reason is that the alternative needs a second permanent secret: a tag pushed by a workflow holding `GITHUB_TOKEN` triggers no further workflow, because GitHub suppresses that to prevent recursion, and `workflow_dispatch` is one of the two documented exceptions. So a bump job can start the release with the token it already has, where pushing a tag would need a PAT with write access to this repository. `bump.yml` takes *patch*, *minor* or *major* from a dropdown, works out the next version, moves **both** version strings, proves the manifests still agree and that the built binary reports the new number, and only then commits and dispatches. Its `rehearse` option runs all of that and dispatches the tag `dry-run`, which is dist's own word for build everything and publish nothing, so the whole path can be exercised without spending a version. `crates/vigia/tests/package.rs::the_release_button_reaches_the_release` holds the three files together, because the failure when they drift is a release that silently never happens after the version has already moved.

**Starting the release needs no PAT. Committing the bump does, and the two were conflated until 2026-08-11.** The paragraph above is about the *trigger*, and it says nothing about the write: `main` is protected by seven required status checks, and a commit pushed with `GITHUB_TOKEN` triggers no workflow by the same suppression rule, so those checks can never arrive on it. The push is rejected with "7 of 7 required status checks are expected" however long anyone waits, and the bot holds write rather than admin and so cannot bypass them either. That is run 31435812487, the button's first real run, and it cost nothing because the ordering above verifies the version before committing it: `main` stayed at 0.1.0, no tag existed, nothing was published. So the commit is pushed with a fine-grained token whose owner is an admin of this repository, and the pre-flight checks two things before the version moves. **One token fills two roles**, and it is the `HOMEBREW_TAP_TOKEN` secret: it carries Contents read and write on the tap and on this repository, so it publishes the formula and moves the version. `bump.yml` reads it into a variable named for the second role, since that is what the step reasons about, and `RELEASE-SMOKE.md` §0 records the sharing along with how to separate the two whenever that is wanted. They are different claims and neither implies the other: a real write to this repository, created and then deleted, covers the token's own grant, while `.permissions.admin` covers the standing of the account behind it, since bypassing a protected branch is a property of a role rather than of a token. The second is a rule check rather than a probe and is labelled as one in the workflow, because the only true probe of moving a protected branch is moving it, which is the irreversible act the whole step runs before.

**What the pre-flight deliberately does not check is whether `main` still lets admins bypass at all.** Reading branch protection needs admin rights on the API: `administration` is not a scope a workflow may request under `permissions:`, so the job's own token cannot be granted it, and granting it to the release token would widen a long-lived secret past `Contents` to buy a better error message. A better message is all it would buy. What the step exists to prevent is an irreversible half-step, a version moved or a crate published against a token that cannot finish, and a protection setting that refuses the push is not one: the push is the last thing before the release is dispatched, so it fails with `main` unmoved, no tag and nothing published, which is exactly what run 31435812487 did. **And one premise stays unproven until a real push lands**, namely that a fine-grained token inherits its owner's bypass; `RELEASE-SMOKE.md` §0 records it as unproven rather than letting the guard imply otherwise. **Naming the token in the push URL is necessary and was not sufficient.** `actions/checkout` persists the workflow's own token into `.git/config` as an `Authorization` header, and git prefers a configured header over any userinfo in the remote URL, so the push went out as the bot whatever the URL said: every check above passed and the push was rejected exactly as before. The checkout therefore runs with `persist-credentials: false`, and that is the load-bearing half of the mechanism rather than a hardening detail. `crates/vigia/tests/package.rs::the_push_that_moves_main_is_authorised_before_the_version_does` is the gate that holds the shape, and it asserts three things that each looked sufficient alone: that the checkout persists no credentials, that the remote the push names carries the token, and that the refspec is `HEAD` at the default branch.

**The registry publish runs last, and it is not atomic with the rest.** dist places every custom publish job `needs: [plan, host]`, and `host` is where `gh release create` runs, with no `--draft`, so the GitHub release and its binaries are public before the registry is touched; `announce` afterwards is a checkout. **The order is right for the reverse reason**: crates.io is the only step that cannot be undone, where a GitHub release can be deleted, a tap commit reverted and a tag moved, so the permanent action goes after everything reversible has already worked. A failure there leaves public binaries and an unclaimed name, recoverable by re-running the job; §5 of the checklist verifies the registry directly rather than inferring it from a green workflow.
- **Four targets in v0.1, and Linux is musl alone.** `x86_64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`. One static Linux binary that runs on any distribution beats two that need selection logic, and `CLAUDE.md` already names musl as this project's static-binary story. **`aarch64-unknown-linux-musl` and `aarch64-pc-windows-msvc` are deferred**, not rejected: both need a cross linker on the release runner, which is the component most likely to fail first on a release nobody has cut before, and neither is reachable by a user who cannot already use one of the four.
- **A published `.crate` does not carry `.github/`, and twenty-four of `vigia`'s test files read outside the package.** Counted by **file**, which is the unit that gets excluded; a read is not. Twenty-one reach `vigia-core/tests/support/mod.rs` by `#[path = "../../…"]`: `budgets.rs`, `config.rs`, `first_paint.rs`, `follow.rs`, `list.rs`, `masthead.rs`, `observe.rs`, `paint.rs`, `rail.rs`, `reads.rs`, `rows.rs`, `scroll.rs`, `select.rs`, `sheet.rs`, `single.rs`, `soak.rs`, `unreadable.rs`, `viewport.rs`, `wrap.rs`, `writes.rs`, `send.rs`. A setting or gesture that changes what the walk draws needs a real repository, driven through `App::apply` rather than by setting a field. Five read repository documents through `CARGO_MANIFEST_DIR`, and **two of those five are in both groups**, keeping the total twenty-four rather than twenty-six: `soak.rs` reads `../../.github/workflows/soak.yml` and `sheet.rs` reads `README.md` to hold its gesture table against the sheet's ([#288](https://github.com/breferrari/vigia/issues/288)), and both also reach the fixture module; `package.rs`, which reads this file and three workflows, `theme_docs.rs`, which reads `docs/THEME.md`, and `register.rs`, which reads every `.rs` file under `crates/` to hold the comment ratchets, are in this group alone. `register.rs` climbs **one** level to reach a sibling crate where every other escape climbs two, so a scanner matching only the two-level shape misses it. All twenty-four are deliberate and none is a reason to weaken a gate. **The fix, applied 2026-08-08 by [#12](https://github.com/breferrari/vigia/issues/12), is `exclude = ["tests/**"]` in `crates/vigia/Cargo.toml`**: the package ships no test suite rather than shipping one that cannot compile, which is excluding the tests rather than stopping testing the repository. `vigia-core` is not excluded and does not need to be, because its `tests/support/mod.rs` is inside its own package and `benches/engine.rs` reaches it without leaving.

**This bullet said "three escapes" across two files until 2026-08-08, and the count was the part that was checkable.** It was prose, so nothing could contradict it, and it was wrong by a factor of four in a section whose own last sentence says a count is what a later reader can check. It also described `observe.rs`'s escape as being "for the fixture its wiring gate needs" when it is the same support-module `#[path]` as the other eleven. A number only prose holds is a number that drifts silently every time a test is added, which is what happened ten times. `crates/vigia/tests/package.rs::the_spec_names_every_test_that_escapes_the_package` is the replacement, and it earned its place on its first run by failing against **`package.rs` itself**: the file was written to enforce this bullet, escapes the package in order to read this bullet, and was not named in it. A gate that catches its own author on the first run is the strongest evidence available that it is not decorative.

- [x] ~~The settle margin is a fixed 2 seconds and could be narrowed per worktree from the modification times status already reports.~~ **Closed 2026-07-30: the margin stays at 2 seconds, and both halves of that were wrong.** ([#32](https://github.com/breferrari/vigia/issues/32).) **The estimator is unsound**, because it bounds the *smallest* granule observed while soundness needs the *largest* that occurs, and granularity is not uniform within one volume. Measured on the reference NTFS volume: 10,324 same-length rewrites over 3s produced 1,959 distinct stamps whose positive gaps spanned **502µs to 17,522µs, a 34.8x spread**, and a bulk write of 100 files produced a smallest cross-path gap of **998µs**. Narrowing to 998µs would leave a real 17.5ms granule uncovered and serve exactly the stale diff `settled` prevents. Nothing passive does better: a monitor never writes, so it sees only the gaps its user's tools happened to leave, and those bound the granule from the wrong side. **And the breach was the fixture rather than the product.** Over the same event and 2.5s of frames, the core ran **98 of 182 frames over budget** and the shell ran **0 of 1060**, because I4 already makes the shell diff only what it draws. What is left is the core's own number, which is [#19](https://github.com/breferrari/vigia/issues/19)'s job.

That is a 5.0 GiB `target/` under a running build, and a synthetic worktree has no such thing. For the first **530 seconds** there were **zero frames** while tens of thousands of events arrived and were discarded.

> **What is *not* open here, because it was a breach and is fixed**

>

> A hunk whose content changed used to throw its whole parse away, so the walk above was paid on *every* frame for as long as the file being read was the file being written — 520 lines per frame for a 22-row body, **53ms p99** four screenfuls in, sustained and with no input. A changed hunk now rewinds to the deepest parse position the new content still agrees with, so a frame costs a screenful plus one `CHECKPOINT_STRIDE` at any depth: 40 lines and **11.47ms p99** on the same fixture, against 10.02ms at the top. Two lessons went into §7 rather than staying here: a budget measured at one position is measured at its cheapest one, and the caller-side gate §7 asks for can be the *absolute* tier rather than only the structural one.


- [ ] Rename tracking cannot stream, so with it on the first change arrives at 97% of the walk and time-to-first equals time-to-last. Tracked by [#48](https://github.com/breferrari/vigia/issues/48). It is on by default anyway, because reporting a move as an unrelated delete plus add misdescribes what the agent did. Confirm against a week of real use, or paint without renames and reconcile them on a later frame. **One session has run and the question is nowhere near being asked**: the changed set peaked at **3** files over 3,960 samples, so a walk whose cost is a concern at ten thousand is not one a real session reaches. That is evidence about likelihood rather than about the walk, which is what this bullet is deferred on.


- [ ] The frame path walks status to completion before it reports a file list, so it does not stream the way the raw change iterator does. Tracked by [#48](https://github.com/breferrari/vigia/issues/48). **Two walks since [#313](https://github.com/breferrari/vigia/issues/313)** when the staged run is drawn, and the second cannot stream at all: `gix`'s tree-index status is callback-driven, so the iterator over it is one over a `Vec` already filled. It reads no content and measures 430µs against the other walk's 2.15ms on a 200-file fixture, so it changes the size of this question rather than its shape. Two reasons it costs nothing today: rename tracking cannot stream either and is on by default, and a scrollbar needs the file count regardless of how few files are drawn. What is open is whether both hold at ten thousand changed files, where the walk itself could exceed I4. Revisit with rename tracking, since they stand or fall together.


- [ ] An attributes change is a fourth way a cached artefact goes stale, and two of the three ways it can arrive are still invisible. Tracked by [#111](https://github.com/breferrari/vigia/issues/111). Writing a `.gitattributes` changes what git's clean filter does to files it does not touch, so a `FileDiff` or a `FileSpan` computed under the old rules describes bytes that are no longer the ones a diff would compare, while every term in the reuse rule reports "unchanged". `Frame::advance` drops both caches when a `.gitattributes` is in the changed set, which is what an agent writing one looks like. What that does **not** see is a change to `core.autocrlf` (configuration, not a file the status walk reports) or to `.git/info/attributes` (inside `.git`, which the walk does not enumerate). Both leave a stale diff on screen until something else touches the file, and neither has a gate, because reaching them from a test means changing configuration mid-session rather than writing a file. Measured before the guard existed: a file committed LF and held CRLF reported **80 rows where a cold frame computes 8**, indefinitely. `crates/vigia-core/tests/normalise.rs::a_running_frame_drops_what_it_cached_when_attributes_change` covers the file-shaped case on both caches, and mutation confirms it: clearing neither map, only the spans, or only the diffs each turns it red.


- [ ] The height walk is incremental now, and what remains is a syscall count rather than a read count. Tracked by [#19](https://github.com/breferrari/vigia/issues/19). [#101](https://github.com/breferrari/vigia/issues/101) took a tick over a hundred undrawn changed files from 16.98ms p50 to 9.40ms by replacing a read per file with a stat per file, and the term that is left grows the same way: **500 changed files is 501 stats a tick, 15.01ms p50 and 16.82ms p99**, which is *over* I9 rather than at it, no gate runs at that scale, and 2000 is 26.06ms of stats before anything is drawn. #19 was filed against the *diff* path's revalidation and the fix landed on a different one: the wall is the same wall, it has moved from a hundred files to about a thousand, and it is a property of how many `stat` calls a tick can afford rather than of either caller. The way out is not a faster stat but taking the fingerprints from the walk `advance()` already performs, which means changing what `gix`'s status hands back.


- [ ] Highlighting a hunk is forward-only, so the first frame that draws deep inside a large hunk pays for everything above it there: landing on the last row of a 1006-line hunk costs the whole **60.97ms** parse, once. Tracked by [#51](https://github.com/breferrari/vigia/issues/51). `G`, a follow jump into a large file and scrolling **up** into the bottom of the previous file all land there directly; scrolling down never does, because a screenful at a time is a screenful of parsing. §7 puts the cold path outside I9 by definition, so this is a first-touch cost rather than a breach, but it is a real hitch on one keypress. The fix, if daily use asks, is to bound the parse per frame and leave the tail unclassified until the next.


**A bounded parse is schedulable, and the reason once recorded here for why it was not is corrected rather than deleted, because it was cited to refuse things.** It said the redraw was one the event loop had no reason to schedule and that I1 forbade inventing a timer to get one. There is no timer to invent: [#262](https://github.com/breferrari/vigia/issues/262) added `Wake::Warmed`, a wake the frame path sends itself off a background compile, and #51 closed by having the shell draw a second frame immediately (`App::owes_repaint`). Both are scheduled on **work** rather than on a clock, so I1's *0 wakeups while idle* does not reach either. **But neither is the mechanism a bounded parse would need.** `owes_repaint` is drained by an `if` and capped at exactly one extra frame, structurally: written as a `while` it spun at 100% CPU with the alternate screen held, because `paint` swallows a failed collect and the debt never clears. A parse bounded across N frames still needs a mechanism built. What is open is whether daily use asks for the bound; what is settled is that I1 is not the reason it cannot be had.


**Daily use did ask, and the half that was fixable is fixed.** [#45](https://github.com/breferrari/vigia/issues/45) reported a fast scroll dropping frames. A *first* entry from below still costs the whole walk and is still the cold path: **25.01ms** for a 120-row hunk of wide-character Markdown against 139µs for a frame that reused it. What was not the cold path is a hunk re-entered after leaving the screen, paying 26.39ms for a parse that had been in memory one frame earlier; `RETAINED_HUNKS` keeps four after they scroll off, so reversing direction over ground already read costs **397µs**. Bounded by a constant added to the viewport rather than by the session, so I3 sees a slightly higher plateau rather than drift. **And the per-line cost is a function of line length, not of the script**: 660-byte Markdown parses at **0.32µs a byte** against **1.76µs a byte** for 34-byte Rust lines, so wide content is *cheaper* per byte and expensive only because the lines are nineteen times longer. Attributed by running the identical bytes under an extension `syntect` has no grammar for: **708µs of a 764µs collect** at p99 is the parse.


- [ ] The heat projection is the one drawn thing whose cost follows the file rather than the window. Tracked by [#55](https://github.com/breferrari/vigia/issues/55). Placing a change needs its working-tree line number, and a line number is only known by counting the lines before it, so `heat_of` walks every line of a drawn file's hunks even though the viewport shows a screenful. Everything else in the shell follows the screen. This is not a read, so `reads.rs` does not move and I2a is untouched; it is arithmetic over lines already in memory, and it runs only for rows actually drawn.


**What "actually drawn" means has grown twice with the pane it is measured on**, which is what this bullet has to be re-measured against when it is next picked up. The bound is the pinned list's **drawn height**, plus the headings in the diff, plus the file the viewport is sitting inside. That was a flat six rows, then a share of the pane ([#160](https://github.com/breferrari/vigia/issues/160)) — twelve on a fifty-row pane — and **beside a rail there is no cap at all** ([#252](https://github.com/breferrari/vigia/issues/252)), so a fifty-row pane draws forty-six rows. What the rail did not leave unmeasured is the *frame*: a 200x40 pane drawing thirty-six pinned rows is **0.71ms p50 and 0.79ms p99 against I9's 16ms**, worst of three rounds interleaved with the 80x24 screen every other budget is taken on, which read 0.99ms and 1.36ms. So the worst case grew and the frame it sits in did not. Recorded rather than assumed away, because the shape is the one I4 exists to prevent even where this instance is affordable. Tracked by [#50](https://github.com/breferrari/vigia/issues/50). **Narrowed 2026-08-25 by [#313](https://github.com/breferrari/vigia/issues/313)**: a reader can now draw both comparisons with `a`, so this stopped being *which comparison the tool is about* and became *which way the toggle starts*, which is a view default and therefore [#306](https://github.com/breferrari/vigia/issues/306)'s file. The week of use still decides it, and the cost of getting it wrong is now one keystroke rather than a redefinition of every drawn element.

This is a posture question with no work left in it — whether the README and the release notes say *supported* or *best-effort* — and it belongs with the first release. `ROADMAP.md` has recorded that placement since before the technical halves closed. Tracked by [#11](https://github.com/breferrari/vigia/issues/11).


**The colour half closed 2026-07-31**: degradation is a mechanism with a gate over every rung rather than a hope, so a console that cannot draw 24-bit gets 256 by detection and not by accident.


**The glyph half closed 2026-08-17 by [#159](https://github.com/breferrari/vigia/issues/159), and what made it decidable is that this bullet was wrong about its own mechanism.** *"There is no equivalent for characters"* is true of **probing** and false of **deciding**: no terminal reports which glyphs its font carries, and `Depth` never asked one either — it reads `TERM_PROGRAM` and `TERM` and consults a table of what somebody checked. `Glyphs` picks `block`, `braille` or `octant` the same way. Measured rather than assumed: **Consolas, which the legacy console draws with, carries none of U+2800**, while Cascadia Mono and Cascadia Code carry all of it, so Windows without `WT_SESSION` takes blocks and Windows Terminal takes braille. That is the exact inverse of `Depth`'s Windows rung, and the asymmetry is the finding rather than an inconsistency: **colour aged out on that console and glyphs did not, because the font did not age with it.** Octants are reachable only by `VIGIA_GLYPHS=octant` until [#324](https://github.com/breferrari/vigia/issues/324) teaches `Glyphs::detect` the 2026 matrix, which pins the four engines that self-draw the range natively — ghostty 1.2+, foot 1.20+, kitty 0.40+ and VTE 0.78+ — the same way this bullet already argued for braille.


**The honest residue is everything outside CP437 that is not the sparkline.** Outside: the caret `▸`, the follow marker `▶`, the pulse mark `●`, the elision `…`, the continuation `›`, the downward continuation `↳`, the rename arrow `←` (which IBM's graphic table does place at 0x1B, and which is unusable anyway because a console consumes that byte as an escape introducer), the scrollbar's step buttons `▲` and `▼`, and B21's note icon `✎` and note bar `▎`, for which `»` and `▌` are recorded as the CP437 stand-ins, with `└` for `↳`, against the day a ladder for this residue exists. Inside: `█`, `▄`, the heat strip's `■` at 0xFE, the header separator `·`, the rule `─`, the sparkline track `_` and the scrollbar track `│`. So the loss does not fall along the line anyone would guess — a reader on that console keeps the heat strip, the thumb and the track, and loses the sparkline's *shape*, the caret marking which file the diff is inside, the pulse, and every marker that says a label was cut. **Nothing detects or reports it.** Two elements were chosen on this list rather than in spite of it: [#196](https://github.com/breferrari/vigia/issues/196) picked `■` over the identical-looking `▪` U+25AA, and [#175](https://github.com/breferrari/vigia/issues/175) moved the scrollbar track inside by centring it. The step buttons were added knowing every arrow candidate is outside, and what settled it is one column over: the track they sit on was already outside, so the pair adds no new class of loss. **That is why this stays open rather than closing: a rule that happens to be free once is not a ladder, and the next element to face this will not have a neighbour already conceded.**

## 11. Behaviour

§3 says how well `vigia` does things. Every number in it is defensible and every one has a test. Nothing above says **what happens when you press a key, or when nothing has changed** — and that gap is why the product reads as a screenshot with budgets attached.

Two parts: what the shell already does, recorded because it was decided in code first, and what is still undecided.

> [!WARNING]
> **Behaviour decided in code without a line here is a defect**
>
> The README says this file is the source of truth, written before the code. That was **not true** for the whole interaction surface on 2026-07-30: the keymap and the treatment of untracked files were both settled in implementation and appear nowhere above. §11.1 repays that, and the rule it leaves behind is the same shape as §3's: **an invariant without a failing test is a wish, and a behaviour without a spec line is an accident.** Neither is caught by `take-next`'s pre-flight, which compares invariant tokens rather than behaviour.

### 11.1 What the shell does today

Where this disagrees with the code, the code is the bug.

**What the diff contains.** The default is the working tree against the index: what the agent in the other pane just wrote, and the smallest thing that is useful. `a` adds the index against `HEAD` beside it as a second run (§11.2 B17). Which way that toggle *starts* is still open, as [#50](https://github.com/breferrari/vigia/issues/50). Untracked files are included and diff as all-additions, because creating files is among the most common things an agent does and a tool blind to them would miss its own use case. Rename tracking is on by default: showing a move as an unrelated delete plus add misdescribes what happened. Its streaming cost is open in §10. *Ruled 2026-07-30, session.*

**The working-tree side is normalised the way git's clean filter would normalise it**, and the diff is taken against that rather than against the bytes on disk. Git does the same, so on a checkout with `core.autocrlf=true` the CRLF on disk becomes the LF the blob holds before anything is compared. Skipping it made every line of every such file differ from its stored form: a 21-line edit drawn as **+905 −885** on the installed default of one of three tier-1 targets ([#65](https://github.com/breferrari/vigia/issues/65)). *Ruled 2026-08-01, session, from the reader's report.*

**The rules that filter applies are re-read once a frame, not once a process.** `.gitattributes` and `core.autocrlf` are things the agent in the other pane is free to write, so resolving them at startup would draw a stale answer indefinitely, which is I5 failing silently over a window I3 measures in days. `Frame::advance` drops the filter and the next working-tree read rebuilds it, so staleness is bounded to one frame and a frame that reuses every diff rebuilds nothing. `crates/vigia-core/tests/normalise.rs` gates it through `Frame::advance` rather than through two bare `Worktree::diff` calls, because nothing in the latter marks a frame boundary.

**`core.safecrlf` is not consulted, because it guards writing.** It makes `git add` refuse a file whose conversion would not round-trip; `git diff` ignores it. `vigia` never writes, and inheriting it failed the frame over any file with mixed line endings, on that frame and every frame after, because the file stays mixed.

**External filter drivers are not run, and that is §6 rather than an omission.** `gitattributes` can point the clean filter at an external program, and running those means a process per file per frame, which is what §6 rules out when it takes an in-process diff over a `git diff` subprocess per tick. `eol`, `working-tree-encoding` and `ident` are pure Rust and do apply. The cost is recorded: under LFS the worktree holds content while the blob holds a pointer, so an LFS-tracked text file diffs as a rewrite ([#69](https://github.com/breferrari/vigia/issues/69)). What decides a file is **binary** is not settled here: the engine sniffs for NUL bytes, which is git's fallback and not its rule, so a path the attributes declare `binary` is diffed as text ([#68](https://github.com/breferrari/vigia/issues/68)).

**A file whose only difference is its line endings reports no change, and stays listed.** Dropping it from the list needs its content during `Frame::advance`, a read per changed file on the path I4 governs, which that invariant forbids; and a header count disagreeing with the body under it is the contradiction B3's empty state exists to remove. Both halves are what git does: `git status` lists such a file and `git diff` reports nothing for it.

**An empty pane says which comparison it is empty *for*, and where the work went.** B3's line reads `no unstaged changes` in those words because the comparison is index-relative ([#40](https://github.com/breferrari/vigia/issues/40)). It carries the other run's count when there is one, so `no unstaged changes · 3 staged` tells a clean tree from a fully staged one. Without it an agent that stages its own work empties the pane and the line is true of both. With both runs drawn and nothing in either, it reads `no staged or unstaged changes`. It costs one walk of the other comparison, on the one frame that computes no diff, and it is the cheaper walk because the staged one touches no file.

**The body is three regions, with a masthead above them where a reader has asked for one** ([#158](https://github.com/breferrari/vigia/issues/158), [#204](https://github.com/breferrari/vigia/issues/204)): the masthead, a pinned file list, a rule, and the scrolling diff. **The clamp order is that the band gives way before the list does.** The list is a map of the diff and yields to the diff; the band is a fact about the worktree and yields to both. A pane that could afford a band by shrinking the list draws its whole cap of list and no band, because §5.3's *richness is the reward of space* means extra space rather than space taken from the map. That cap is a share of the pane ([#160](https://github.com/breferrari/vigia/issues/160)), coupled in one direction only: the list may deepen into rows the band was going to be offered, never the reverse. Its step is one row of list per four rows of pane, which is what keeps a taller pane from losing a band it had. *Ruled 2026-08-17, session.*

**The band is drawn only where the diff keeps a whole hunk, and that floor is derived rather than chosen.** `git diff -U3` at its smallest is a hunk header, three lines of context, one changed line, three more and the file's heading: nine rows, so the floor is ten. Below eight columns of drawable width it is not drawn either, because a band narrower than the samples it holds would drop columns, which is the shape §5.1 refuses for the heat strip. **Both floors live in the split rather than in the drawer**, so a narrow pane cannot reserve rows for a region the drawer then declines to draw.

**A sample weighs the bytes a write moved, not the fact that it happened.** `Track::bump` counting files written put exactly one sample in a worktree where one file is saved repeatedly, which makes the window its own peak, and heights are scaled against that peak: every active column drew at full height, so the element said *when* and could never say *how much*. **The size is taken by the shell and not by the store**, one `symlink_metadata` per changed path per wake, because `vigia-core` has no working directory and because putting the syscall at the call site keeps its cost inside the frame the budgets gate. That syscall is one the status walk has already paid for, and taking it from there instead is [#233](https://github.com/breferrari/vigia/issues/233). *Ruled 2026-08-18, session, from a live pane ([#232](https://github.com/breferrari/vigia/issues/232)).*

**The band is drawn the way a system monitor draws one.** Three things follow. **One value per sub-column**: a 2x4 cell carries two, older on the left, which is why such graphs read as a line where a stretched value reads as a block. **An axis**: a signal that is bursty and zero most of the time forces one mark on the bottom row, so a quiet stretch draws a floor rather than nothing. **A scale that is not the maximum**: the denominator sits above the ordinary value, and anything past it saturates. *Ruled 2026-08-18, session, after the reader asked for §2's reference class to be studied rather than recalled.*

**And the scale is not the mean either.** A mean is not a robust way to find the ordinary write: agent work is heavy tailed, and a test run rewriting thousands of bytes sits in the same window as the 180-byte edits around it, so the outlier this rule exists to let saturate was setting the denominator from inside it. **A value more than ten times the median of the non-empty values is left out of the mean.** It lives in `vigia-core` beside the store rather than in either drawer, because the band and the sparkline divide by different quantities and may not differ about the rule. *Ruled 2026-08-22, session, from a live pane ([#256](https://github.com/breferrari/vigia/issues/256)).*

**A level's width says when a write happened, not how much, and a drawn column covers a fixed span of the window.** Otherwise rounding ends a level: a large write leaves no axis, a floor-weight one a single mark, and a steady worktree a comb. The cut is three times the kernel's constant and the unit a 256th of a byte, bands `[12, 18]` and `[256, 4096]`. *Ruled 2026-08-29, session ([#348](https://github.com/breferrari/vigia/issues/348)).*

**An empty column draws the axis; an empty window still draws nothing.** #158 ruled that an empty column drew nothing, because a full track of `_` *"reads as a dashed rule across the pane"*. That is what a graph's axis is, and without one every filled column floats with nothing to stand on, which is what a reader saw and reported as blocks. So the ruling is narrowed rather than reversed: a quiet stretch inside a live window is a floor, and a window holding nothing at all is still nothing, which is the case #158 came from, since every session opens on a worktree that may already be dirty with no tick behind it. It does not distinguish *not started* from *quiet for two minutes*, deliberately: both are an empty window, and this is a ruling about what an empty window draws rather than about how it got there. *Ruled 2026-08-18, session.*

**The window ages while it has something to age, and stops when it does not.** `History::roll` was reached only from the tick path, so a quiet worktree left the last burst pinned where it was. That is worse than stale: the window's axis is time, so a frozen window keeps its newest sample at the right edge and a burst from ninety seconds ago draws as *just now*, with `Recency` frozen beside it so a file that went quiet keeps its pulse. A monitor whose thesis is *correct with zero interaction* was then incorrect with zero interaction, which is I5. *Ruled 2026-08-22, reader, asked for from use ([#243](https://github.com/breferrari/vigia/issues/243)).*

**It is an instance of I1's licence rather than an exception to it.** The reason is the one `RULINGS.md` records for the first clock: every other timer the spec refuses runs while nothing is happening. This one runs only while a burst is still decaying, and the window empties `HISTORY_WINDOW` after the last write, so when nothing is happening the wait is untimed again by construction. What the licence gains is that the thing arming a clock may be a change in the worktree rather than only a reader's gesture; that it may outlive what armed it by a bounded time was already true, since `SCROLL_LINGER` keeps the direction arrows lit for 220ms.

**The period is `HISTORY_SAMPLE`, one second, and it is derived rather than picked.** That is the store's own quantum, so it is the finest interval at which any drawn cell can change and anything faster redraws identical pixels. A coarser period derived from the drawn cell is declined on the measurement: an ageing wake costs **165µs** in release at the path cap against I9's 16ms, so a width-derived period would cap 1% of one frame budget, and a cap is a feature restriction carrying a refusal's bar. Ageing costs a paint rather than a tick, which is what makes that number small: it is not a filesystem event, so it does not walk status, where an ordinary tick measures **529µs** on the same fixture. At most `HISTORY_SAMPLES` wakes follow any burst, so ageing one to nothing costs about **19.8ms of CPU spread over two minutes**.

**The height is recounted when a moved file settles, not at the next event.** While the agent writes, the tick after each file settles recounts it; when the agent goes quiet no tick comes, and the total stayed where it was until the next event or the reader's scroll, which is the jump #412 was reported for. The frame reports when the last height it kept waiting settles, `Shell::patience` folds that in beside the ageing clock, and the loop advances and paints once on it: one wake per burst, at the margin's end after the last print that moved, and nothing armed while no print is inside the margin, which is I1's licence. It costs a tick, not a paint, since the walk is what asks each waiting file again: **529µs** on the ageing fixture against I9's 16ms, plus the reads #412 priced on the settled tick. The deadline is the last print's rather than the first's, so a sweep whose prints spread over a hundred milliseconds is one walk, not a cascade; and a walk that fails disarms it, since the loop folds a spent deadline to a zero wait and would otherwise advance, fail and fold it again, flat out. *Ruled 2026-09-04, session, as an instance of I1's licence ([#425](https://github.com/breferrari/vigia/issues/425)).*

**The sparklines age with the band by construction**, which is [#234](https://github.com/breferrari/vigia/issues/234)'s coherence requirement met by the mechanism rather than by two elements being kept in step: one store, one roll, and the pulse moves with them. Gating the clock on the masthead being up is refused for the same reason: the sparklines and the pulse are drawn whether or not the masthead is, so a clock running only with the band up would leave the two disagreeing about what time it is.

**The pulse's life is a grid remainder, and that is the ruling rather than a side effect.** `Recency::Pulse` means a path was named by the newest burst *and* has ink in the newest `PULSE_SAMPLES` samples, so the mark expires at a sample boundary rather than surviving until something else is written. Its life is `[HISTORY_SAMPLE, PULSE_SAMPLES x HISTORY_SAMPLE]`, closed at both ends. **A duration of its own is refused**: that would mean a second clock per track running on wall time beside an element running on the sample grid, so the two would disagree about how long ago *now* was, which is the one thing [#234](https://github.com/breferrari/vigia/issues/234) forbids. A mark that means *there is ink in the newest cells* is bounded by them. **The frame a burst causes always keeps its pulse**, held by construction: a turn of the loop takes one instant and both the tick and the roll read it, so a boundary cannot fall between a write and the paint it triggered. *Ruled 2026-08-18, session; amended 2026-08-25, reader, from a live pane ([#313](https://github.com/breferrari/vigia/issues/313)).*

**`m` shows the masthead and hides it again, and it starts hidden.** Ruled 2026-08-17 from use: *"I see it is not always needed"*, which is the honest read of an element that costs four rows of the thing this tool exists to show. **The default stood at on for one day and is off since [#204](https://github.com/breferrari/vigia/issues/204)**, reversed the same way and by the same reader: the four rows come out of the diff on every pane that can afford the band at all, and an element with that price should be asked for rather than dismissed. What the first ruling was right about is that an element nobody discovers may as well not exist, and that is now paid in the README's key table, which named neither the band nor `m` on the day the toggle shipped. It is not paid in the hint bar, for the reason at the end of this paragraph. Either way it is a keystroke rather than a setting, which is §11.2 B6 keeping this tool configured by gesture. **Nothing leaves the pane with the band**: the branch is the header's since #158 and is drawn on every frame whatever `m` is doing, which is also what keeps the every-frame `.git/HEAD` read a read of something the frame draws. **A keypress is licensed to move content where a notice is not**, and the rule below already draws that line: the split refuses to move for a *transient* thing so that a flicker cannot jog a reader's diff, and an instruction is not a flicker. Unlike `f` it does not jump, because re-engaging follow is a move (a reader asking to follow is asking to see what changed) and asking for the masthead back is asking for the masthead back. It is deliberately **not** in the hint bar, and that is settled rather than open since #80 cut the bar to three items: `m` is named on the sheet below, which is where every gesture is written down now.

**`?` draws the gestures sheet over the pane, and `?` advances it until it takes it away.** Ruled as §11.2 B12 and shipped by [#206](https://github.com/breferrari/vigia/issues/206); the ruling and its rejected branch stay in B12 and what the shell does is here. A centred, bordered table of every gesture the pane binds, composited over cells the regions have already drawn, with a close control in its own title bar. **It moves nothing**, which is the property it was chosen for: no rect is smaller for it, no region yields a row, and closing it needs no relayout, so a reader who opens it and closes it is looking at exactly the screen they left. `crates/vigia/tests/sheet.rs::the_sheet_moves_no_content` is that claim as a gate, comparing every cell outside the sheet's own rect with the sheet up and with it down.

**It is not a mode, and that is what keeps it out of B4's refusal.** No key changes meaning while it is up: `q` still quits, `j` still scrolls the diff behind it, a digit still jumps. **`?` itself keeps exactly one meaning, *the sheet*, and B13 is what that costs**: on a pane the whole table does not fit, pressing it again is the next page and the last page is what closes it; on every pane whose sheet is one page it is the toggle it has always been. **The close control is its own action rather than the key's**: `?` means *the sheet* and advances, the control means *close* and closes from any page, and a pointer has no `?` to fall back on. **`Esc` closes it**, and it has a ladder rather than a second meaning: the sheet while one is up, a drag while one is under way, the program when neither is. `crates/vigia/tests/sheet.rs::escape_puts_the_sheet_away_before_it_puts_the_program_away` holds the sheet's rung against the program's in one gate, since a key that dismisses and departs needs its order fixed. *Ruled 2026-09-03, reader, restating what [#341](https://github.com/breferrari/vigia/pull/341) shipped on 2026-08-26 ([#391](https://github.com/breferrari/vigia/issues/391)).* A click on the control closes the sheet and anything else landing on it does nothing at all, since falling through would let a click seek a scrollbar the reader cannot see and a wheel scroll a diff the sheet is covering. **That covers the press as well as the action.** The loop asks `Regions` for geometry in two places that never go through `action_for`: `step_at` arms a hold, so a press on a covered step button armed a repeat that scrolled the region underneath, and `grab_at` is worse, since a grab hands the gesture to `drag_action`, which ignores the column by design, so the next motion relocates a region the sheet is covering. Both are guarded **inside the two methods** rather than at their call sites, so every caller is correct by construction, which is [#166](https://github.com/breferrari/vigia/issues/166)'s one-expression rule applied twice more. *Ruled 2026-08-17, session; the press half 2026-08-25 ([#298](https://github.com/breferrari/vigia/issues/298)).*

**It is opaque, and the first version was not** ([#211](https://github.com/breferrari/vigia/issues/211), reported from use within an hour of the release that shipped it). Every cell the sheet covers is **reset** before it is styled, so the sheet is a hole punched in the diff rather than a tint over it. `ratatui`'s `Cell::set_style` merges into the style already in the cell, and the chrome's own style carries no background, so the first version kept the `added_row` and `removed_row` washes underneath and drew as green and red bands with a table on top. The gate injects a theme that washes its rows rather than borrowing the shipped palette, because `Theme::default` sets no row background and a gate written against it would have been green while the reported screen was striped. **Closing it restores every cell exactly**, symbol and style, which is the other half of *it moves nothing* and is gated as such.

**The close control takes two of B10's three rungs**: the chrome's weight at rest and `bar_hover` under the pointer. It shipped in one weight, which left a reader guessing whether the glyph was a control at all (#211). A pointer resting anywhere else on the sheet marks **nothing**, since the sheet swallows what lands on it and a mark on something underneath would say otherwise.

**Two and not the step buttons' three, ruled 2026-08-25** ([#298](https://github.com/breferrari/vigia/issues/298)). This section said three and the drawer drew three, on a comparison nothing could ever make true, and it was found by asking what puts a cell into `Chrome::pressed` rather than by reading either. **The reason is what the third rung is for.** `bar_active` describes a gesture *under way* on an element still on screen, which is why a step button needs it: pressing *up* at the top of a diff moves no row, so the lit cell is the only thing that can answer. The close control **dismisses on the press**, so the sheet is gone before the next paint and no frame can draw it both. Building the rung means firing on `Up` instead, which costs dismissal latency on the sheet's only pointer escape and adds a press-here-release-elsewhere case to rule on, for a weight visible for milliseconds on an element that then vanishes. Declined on that rather than on cost, which is nil either way. **The general ladder is untouched**: *"a click is always brighter than a hover"* below is about the bar, which keeps all three. `crates/vigia/tests/sheet.rs::nothing_can_press_the_close_control` is the gate, and it says in its own words that it is **defence rather than behaviour**, since it cannot be made to go red, because what it asserts is that nothing produces a state.

**It is retained state rather than a one-frame draw**, because the pane wakes on filesystem events and an agent's write redraws the frame underneath it. A sheet that lived for one frame would be dismissed at random by somebody else's build, which is the constraint B12 named as likeliest to be missed and which `a_write_under_the_sheet_does_not_dismiss_it` holds.

**It degrades on two axes and trades between them on one rung, and both floors live in the layout rather than in the painter.** The ladder is four rungs in order, and the order is the contract: the roomy rung ([#285](https://github.com/breferrari/vigia/issues/285)), then every row in one column, then the two-column rung ([#220](https://github.com/breferrari/vigia/issues/220)) that spends width to buy height, then the **paged** rung ([#286](https://github.com/breferrari/vigia/issues/286)), which draws as many rows as the body has and puts the rest on the next page. Width picks the spelling for the whole table, wide or tight, because a table whose rows each chose their own width is not a table and a truncated verb has no identifying half to keep. **The height axis no longer drops anything**, which is B13: it splits. **Below the floor `?` still toggles and nothing is drawn**, exactly as `m` behaves on a pane that cannot carry the band, and no gesture is swallowed by a sheet nobody can see. The floors are `Body`'s rather than the drawer's for [#158](https://github.com/breferrari/vigia/issues/158)'s reason, paid for once already.

**What still drops is width, and there the drop order is unchanged.** A pane too narrow for the whole table at the tight spelling gives up the mouse group, and then keyboard rows in the drop order, leaving `f`, `m` and `?` last: the unguessable outlives the reflexive, which is the hint bar's own rule one surface over, and `q` goes first because the hint bar spells `q quit` on every frame. Measured over every width from 20 to 144 against every height from 6 to 38: **38 columns and up reach the whole table**, 35 to 37, 32 to 34 and 30 to 31 reach successively smaller sets, and below 30 no sheet is drawn. **The boundaries do not move when a row joins the table or leaves it**, because no row here has ever moved a width, and they are re-derived from a swept pane rather than incremented. Their sizes are not restated: a count beside a sentence saying a gate holds it goes stale on the next gesture, and this one had. Forty is the width the promise is stated at, because forty is I6's. `crates/vigia/tests/sheet.rs::every_gesture_is_reachable_at_forty_columns_and_up` is that promise as a gate, walking `?` from the first page to the close on every pane in the sweep, and `the_display_order_is_the_readers_and_the_narrow_floor_keeps_the_unguessable` pins the three narrow sets by name rather than by count.

**The page counter rides the title bar, and it is what makes the omission stop being silent.** ` a-b of 25 ` between the title and its rule, drawn only when the page is not the whole table, so no screen that fits everything today gains a character. It costs no content row, which is the property B12 chose an overlay for and which a say-so taking a row would have spent on the gestures it was apologising for. The ordinals are positions **within what this pane can reach**, not within the twenty: a width-dropped set is not contiguous in display order, since `q` goes first and `q` is at the bottom of the table, so a last page reading `9-12 of 20` says *this pane reaches twelve of the twenty* and the reader's arithmetic is the say-so. True positions with gaps would read as a rendering fault rather than as a count. The total is `KEYBOARD.len() + MOUSE.len()` rather than a literal, because [#288](https://github.com/breferrari/vigia/issues/288) added a sixth **and seventh** mouse row and a counter reading *of 18* on a table of twenty is a lie no gate over the drawn output would catch. It has been right through four added rows on that alone.

**Every rung charges the counter's widest spelling whether or not it draws one, and that is what turned a guard into a rung.** The floor is the title plus ` 18-20 of 21 ` plus a border, a space and the two-of-gap at each end: **thirty columns**. The charge is the counter's widest *spelling*, so a table growing from seventeen rows to twenty leaves it exactly where it was. What the charge buys is that the counter **fits**: the title bar's rule run is `width - title - counter - 5` through a saturating subtraction, so on a rung too narrow for it the rule goes silently to zero and the ordinals run into the close control. It is **not** what keeps the box the same size between pages, which is what this section said until a mutation checked it: `sheet_fields` measures over the whole row set and every page of a pane shares that set, so the width was page-independent already. It was seventeen columns and no rung reached it. The deepest dropping rungs are raised to it, and a pane under thirty draws no sheet at all rather than five gestures of seventeen with nothing saying so. That is the trade B13 states out loud rather than discovering. `crates/vigia/tests/sheet.rs::the_floor_is_a_rung_now_and_the_narrowest_sheets_are_the_sizes_the_ruling_states` holds the three numbers: 30 narrowest anywhere, 38 narrowest at I6's forty and up, 71 narrowest two-column.

**The roomy rung, at the head of the ladder: the same one column with its sections headed and air around them.** The keys cells stand four columns in, the verbs eight after the keys field, the headings two columns in so they stand back from their own rows, and a blank row sits above and below every section. **The headings are plain text rather than rules**, the one departure from every other rung and a consequence of the air: a rule under a blank row is a second separator doing the first one's job. The sections are `moving` (`j k`, `Space`, `d u`), `files` (`g`, `n p`, the digits, `J K`), `view` (`f`, `m`, `r`, `s`, `a`, `w`), `mouse` (the whole mouse table) and `leaving` (`?`, `q`), in that order, and **`leaving` sits at the bottom**: quitting is not what a reader reads first. The four keyboard runs tile the table exactly once and in order, asserted in a `const` block beside them rather than by a test, because bad bounds are an index panic on the frame path and a build that will not compile beats a suite that goes red. The mouse group sits fourth and stays last wherever the groups are stacked, because a rung with no headings cannot put two unlabelled keyboard rows after a labelled mouse group. **It takes the wide spelling always**, which is derivable rather than chosen: air is surplus, and this rung is the wide one-column sheet plus six columns of gap and six of inset. **Being first is what makes it additive**: it needs strictly more of both axes than the full one-column rung, so a pane that takes it would have drawn every gesture anyway and a pane that does not is untouched. Its figures are held by `tests/sheet.rs`'s roomy-rung gates rather than restated here, because a number here goes stale on the next gesture. *Ruled 2026-08-24, reader, from his own mock ([#285](https://github.com/breferrari/vigia/issues/285)).*

**Mock A drew it seventy-six columns wide and the shipped rung is sixty-eight, which is this file's own rule applied a second time.** The mock leaves twelve blank columns after its verb field against four before its keys, and that asymmetry is the box the reader drew rather than a table they designed. §11.1 already corrected B12's mockup in exactly this direction, *the widths are the shipped drawer's, not the ruling's estimate*: the fields are derived from the content of the rows a rung draws, and the trailing inset matches the leading one as it does at every other rung. What the mock rules is the **air**, and every one of its numbers for that is kept.

**Display order and drop order are two orders, and they were one until #285.** `KEYBOARD` is what a reader reads and `DROP_ORDER` is what the height ladder gives up, and the second is a ranking rather than a direction through the first. They were the same sentence by construction before, because the ladder dropped a prefix of the one array, so *the rows a reader meets first* and *the rows the ladder gives up first* could not disagree. They are not the same claim: a reader meets `j k` first and the ladder gives up `q` first. Keeping them conflated is what made the sections unbuildable, and it is worth stating as a trap rather than as history, because the failure is silent: reorder the one array for a new section and the keep-set is silently re-ranked, so the pane that loses a gesture is one of the two or three shortest on the whole ladder and nothing else on screen changes. With the reader's order in place, dropping from the top would have kept `q`, which the hint bar names on every frame, and dropped `f` and `m`, which this section names as the unguessable. The drop sequence itself is unchanged from before the reorder. `crates/vigia/src/render.rs`'s `sheet_tables` module holds both ends on the tables and `the_display_order_is_the_readers_and_the_narrow_floor_keeps_the_unguessable` holds them on a screen, which are two claims: a drawer free to iterate the table backwards satisfies every assertion over the constants.

**One column while one column fits, and two where the pane is short and wide** ([#220](https://github.com/breferrari/vigia/issues/220)). The failing pane is any shorter than twenty-four rows: the one reported was 120 by 20, where the sheet drew eleven gestures of sixteen and dropped the entire mouse group in silence, with sixty of a hundred and twenty columns going to nothing. **The two-column shape is a split on the group boundary rather than two columns of key-and-verb pairs**, which is the one two-column arrangement that does not read as two unrelated tables, because the sheet already drew a `mouse` heading at exactly that seam: they were two labelled groups before they were two columns, and both carry a label now, on one rule. The size follows from charging each column its own widest cells rather than the widest of either, and it is held by `crates/vigia/tests/sheet.rs::the_two_column_rung_is_the_size_the_ruling_states` rather than restated here, because every gesture added moves the height. *Ruled 2026-08-24, session.*

**The rung sits below the full one-column rung and above every dropping rung, which is what makes it additive.** A pane on which one column already fits never reaches it, so nothing that draws every row today changes. It picks its own spelling rather than the pane-wide one, because the pane-wide level was chosen against a one-column sheet, and that is what lets a pane of eighty take the tight two-column rung instead of falling past it into dropping the mouse group entirely. **It arrives at 73 columns**: `margin_of` returns 2 from 44 to 78, so a pane of 73 leaves 71 columns of room and the tight two-column rung is exactly 71 wide. `crates/vigia/tests/sheet.rs::the_two_column_rung_arrives_at_the_width_the_ruling_states` walks 70 to 84 a column at a time so that number cannot drift. The claim that growing a pane in either axis never takes a gesture away is `::the_widening_ladder_is_monotone_and_never_leaves_the_body`, which walks every width from 40 to 144 against every height from 6 to 38. Those bounds are the claim's rather than decoration: 40 is I6's floor and 144 is above every width the rung arrives at, so a pane outside them is untested rather than covered. **It snaps** in both directions, per §5.3's *snap, never ease*. The pane that is short **and** narrow has no column trading: the height axis pages rather than dropping, so the only content a pane loses is what its width cannot spell, and the counter says how much that is. *Ruled 2026-08-24, session; the arrival width corrected 2026-08-25 ([#286](https://github.com/breferrari/vigia/issues/286)).*

**The two regions are a layout ruling, not a navigation one.** B4 was written as *"one continuous scroll, list as map"*, which answered *navigable?* and settled *is it a region at all?* underneath it. `assets/preview.svg` draws the other answer and has since before the question was asked: `src/engine/watch.rs` appears **twice**, once in a block of summary rows and once as the diff heading, with a rule between them, which one stream never does. §5.1's rule that a published artifact answering an open question **is** the answer applies to layout exactly as it applied to `f`. **The rule between them stays bare** (§11.2 B11), on what a heading *is* rather than on where the reader has scrolled: it is a `Painter::file_row` carrying the glance elements through the drawer both regions share, so folding it into a border line would strip those elements. *Ruled 2026-08-01, session ([#66](https://github.com/breferrari/vigia/issues/66)).*

**The footer gets a rule over it, and both rules run edge to edge.** Every other boundary on this screen is drawn, and the bottom bar had none, so chrome sat directly under content with nothing saying so. It is the same `─` the list uses, on a reserved row. **Full bleed is the half a reader sees**: §5.3 rules that furniture runs to both edges, and a rule stopping short reads as a box someone forgot to close, so both marks are drawn from the pane's rect rather than an inset one. **It yields on a short pane** like the band and the list before it, since a rule that cost the diff its last row would be chrome announcing a region rather than separating one. `crates/vigia/tests/legibility.rs::both_rules_reach_both_edges_of_the_pane` gates the pair, including the two-line footer where a mark placed a fixed row up would land inside the bar. *Ruled 2026-08-18, reader-reported.*

**What the split buys is the differentiator staying on screen.** Three of the four glance elements ride a `Row::File` heading, so in one stream they are visible only while that heading is, and scrolling two hundred lines into a file takes every file's glance signal off the screen at once. §2 buys *readable at a glance*, and a glance surface that survives only at scroll position zero is absent whenever anyone is reading.

**The list stays not navigable**, which is the half of B4 that stands. No selection, no focus, no second mode: `▸` marks the file the diff is inside and is not a cursor, and no key changes meaning depending on where anything is. The region is a **map**, which is what "list as map" wanted and what a stream of headings could not supply.

**That row's path is drawn bold, and the weight is the caret's second channel rather than a second mark.** Every other durable distinction in this region is carried by weight, and the one row a reader most needs to find carried a glyph alone. `Painter::list` resolves the glyph and the weight from **one** predicate, so they name the same row or neither is drawn, which ties the weight to `affords_caret`: below seventeen columns the caret is dropped, and a bold row with nothing pointing at it would be a weight nobody can attribute. It says which file the diff is *already* in and no key moves it. It shares `BOLD` with the recency ladder's pulse rung, and the two stay separable because each carries a glyph of its own, `●` against `▸`, which is also what survives `NO_COLOR`. Both regions draw through one `Painter::file_row` and the stream's call site passes `false` outright, so a heading for the very file the caret marks stays plain. *Ruled 2026-08-16, session ([#193](https://github.com/breferrari/vigia/issues/193)).*

**The list's height is the changed-file count, capped at a quarter of the pane and never below six, plus the rule.** Three changed files draws three rows, which is the picture exactly; a formatter touching two hundred draws the cap and scrolls. On the 24-row pane this tool is built for the cap is six and leaves fourteen rows of diff; a 50-row pane draws twelve. The clamp order is one row per changed file, then the cap, then whatever leaves the diff `MIN_BODY`. **The share is the rule and six was its instance** ([#160](https://github.com/breferrari/vigia/issues/160)): six was recorded as an absolute and justified by arithmetic about one pane, but six is a quarter of twenty-four, so the number was a proportion stated against a single height, and a 50-row pane keeping it drew void where the map could be. What reads as a glance is the region's share of the screen rather than its row count: at a quarter the map never dominates and the diff keeps three quarters at every height.

**A rung is worth one row of list per four rows of pane, and the step bound is load bearing rather than a rounding.** The band is paid out of what the list leaves, so a cap that gained two rows for one row of pane would take a band off a pane that had just grown, which is the "a bigger container holds less" failure the margin ladder exists to avoid. Stepping by one keeps the rows left after the list non-decreasing. The row a pane gains at a rung boundary goes to the map; the other three go to the diff.

**The cap is read from the pane, never from the body**, the same ruling the inset ladder and the caret's floor already make one axis over. The body is the pane less its header and a footer whose height depends on the changed-file count, so a cap read off the body would deepen the list because a seventh file appeared. The height is a function of **pane geometry, follow state and changed-file count**, which is exactly the set `Footer::plan` takes, and none of those is transient: the region cannot jog a reader's diff the way a notice or a passing failure would. It does move when the footer does, since `f` on a forty-column pane takes a second footer line, and that is a reader's own keypress changing the shape of the screen.

**The list is ordered the way the stream is**, which is `Frame::files()`, which is status order. That is what makes it a map rather than a second opinion: the caret's place in the list and the thumb's place on the diff's scrollbar describe the same position. Ordering by diff size was rejected on I4, since it needs every changed file's diff. Ordering by recency from `History` is genuinely free and was rejected for a different reason: it decouples the list from the stream, so the caret stops corresponding to the scroll position and the map stops being one.

**A list row draws exactly what a heading in the stream draws**, through the same `Painter::file_row` and the same degradation ladder. This is the second deliberate departure from `assets/preview.svg`, beside the header's worktree name: the picture splits the elements across the two regions, giving the summary rows no kind letter and the diff heading no counters. That split stops being defensible the moment the list scrolls, because a file scrolled out of the region would lose its counters altogether.

**A region's file rows draw their glance elements in columns** ([#77](https://github.com/breferrari/vigia/issues/77)). An element drawn out of a budget that had already lost the elements outside it takes its position from their widths on that row, and the counts cell is the widest variable thing there; three sparklines that do not share a left edge fail to read as one small-multiples chart, which is the reading a list exists to give. So the ladder runs **once for a region** and every row draws into the slots it produced. Its order is counts, then the pulse, then heat, then sparkline. **A row that has no such fact keeps the column rather than closing it**, which is what makes the alignment universal rather than occasional: under right-packing each absence let that row's remaining elements slide into the space and pulled it out of line with its neighbours. The sparkline's absence is now a **track** rather than a blank; the heat strip's is still a blank, and the paragraph below says why that difference is a ruling rather than an inconsistency. **The counts cell is two columns and not one field**, `+N` right-anchored in its own and `-M` in its own, one space apart, which is what the picture draws. A single field aligns whichever end it is anchored to and leaves the other ragged, so an eye running down three files' additions gets the same non-comparison this ruling exists to remove. **Each half is drawn in its own diff colour, and a half with nothing to say is drawn in the row's dim grey**: `+42` green, `-7` red, `-0` grey ([#157](https://github.com/breferrari/vigia/issues/157)). That is §5.3's rule rather than the picture's: green and red are lent out only where they restate the same fact, and a zero restates none, so a worktree an agent is only adding to would otherwise carry red on every row and answer nothing. **Presence is shared and ink is per half**, which is the one place the two rules pull apart: the pair is drawn or dropped together, and a renderer that greyed a whole cell because one half was zero would be applying the wrong one.

**The slots come from the pane and never from the rows.** Sizing the counts field to the widest count among the rows a region is about to draw holds *within* a window and moves *between* windows: scrolling until a file with `+1500 -1500` enters it widens the field by six columns and slides every heat strip and sparkline on every row. Intermittent movement is worse than a layout that is simply wrong, because there is nothing on screen to argue with. So every slot is a constant or a rung of the pane's width. Measuring over every changed file instead would also be stable and is forbidden for [#49](https://github.com/breferrari/vigia/issues/49)'s reason: it needs every changed file's diff, which puts the frame back in proportion to the size of the diff against I4.

**Each region plans its own slots, and from forty-three columns up the two answers are the same.** They are entitled to differ and did: the list inset by the caret, which was two columns, so its status sigil sat two columns right of the same sigil on a diff heading and every element downstream inherited the offset ([#173](https://github.com/breferrari/vigia/issues/173)). **The caret is one column standing in the pane's own margin**, so the list charges the row only what the margin cannot lend it: nothing at or above forty-three, and one column below it where the ladder has no floor left to lend from. The two regions still plan separately, because `Painter::file_row` must stay one drawer that knows nothing about which region called it. Neither reads a row, so a heading scrolling past cannot move the pinned region above it.

**The residual below forty-three is one column and it is a decision, not a tolerance.** Extending the margin ladder down so the caret always has a blank to stand in was refused on [#119](https://github.com/breferrari/vigia/issues/119)'s own reason: that floor exists to protect I6's forty-column pane, and paying it here would spend a column of code at exactly forty. Dropping the caret below forty-three buys alignment at every width and costs the narrow pane the one mark saying which file the diff is inside, trading information for tidiness at the width that can least afford it. Keeping the old two columns made the gap between caret and sigil appear at forty-three, vanish, and reappear at seventy-nine as the pane widened. So the caret narrows, takes the margin where there is one, and bills the row a single column where there is not.

**The caret is the one glyph licensed to stand on the pane's own edge**, a stated exception to the inset ladder rather than a hole in it. Taking *"flush against the pane's left edge"* literally is what stops the gap between caret and sigil growing with the pane: the marker sits at column zero at every width, and what follows it is whatever margin the ladder bought. §5.3 already rules that the picture binds the element set and each element's promises rather than glyph-for-glyph fidelity. `crates/vigia/tests/legibility.rs::the_pane_insets_its_text_at_every_rung` carries the exception inside the assertion rather than around it: the caret is stripped and everything after it is still measured against the margin, so a list row that lost its inset *and* drew a caret still fails.

**The threshold that drops the caret is the row's own floor, asked as a question rather than kept as a constant.** What the caret costs a row is a function of the width, so a fixed sum would be wrong above the ladder's floor and wrong below it in the other direction. `affords_caret` asks whether the row still clears `ROW_FLOOR` after the bar, the inset and the caret's own gutter, reading the same expression the drawing plans against. It works out to seventeen columns, far below the forty I6 is named for. `crates/vigia/tests/legibility.rs::the_caret_threshold_is_the_row_floor_it_claims` asserts the comparison rather than the pixels, in both directions.

**The body opens with one blank row under the header, and it is coextensive with the list.** The header states a fact about the worktree as a whole and the list is a map of it, which are different classes, and the boundary *below* the list already spends a whole rule saying so; this one had neither ([#174](https://github.com/breferrari/vigia/issues/174)). A blank rather than a rule, because the ask was separation and not a second boundary mark, and because one glyph doing two boundaries of visibly different weight says less than nothing does. A body with no map has nothing to separate the header from, so the row goes back to the diff. The changed-file count, the notice and follow mode cannot move it. **When the band is drawn that blank *is* the band's leading air**, so the masthead screen keeps the four rows it always kept and nothing on it moves: `GRAPH_AIR` is the blank below the band alone, and the band's fit test drops by the same row, so no pane height gains or loses a band. The cost falls on the masthead-off screen, which is the default: one diff row of roughly fifteen on a 24-row pane. `crates/vigia/tests/legibility.rs::the_body_opens_with_one_blank_row_under_the_header` holds the rule and `::the_lead_row_is_the_mastheads_air_when_a_band_is_drawn` holds the claim the design rests on.

**Every slot is reserved whether or not anything can fill it**, including the sparkline in a region where no file has a history yet, which at launch is every file. Reserving only what some drawn row could fill moves every column on the tick the first file is written, which is precisely the moment a reader is looking at the screen. The price was a row mostly blank until the first write, and [#78](https://github.com/breferrari/vigia/issues/78) refunds it: the reserved sparkline slot now carries a track instead of a blank, so the slot a reader could not see the point of is the one that says *no churn in the window*. Reserving the column is what made saying so free.

**A region is planned against its own width less a scrollbar column, drawn or not.** Beside a rail, a region's width and the pane's are different numbers, and a seventy-column rail planned against a two-hundred column pane would lay a row out for a screen it does not have ([#252](https://github.com/breferrari/vigia/issues/252)). What stays the pane's is the *inset's rung*. A bar appears when `scrollable` finds the region cannot show all it holds, so its presence is a fact about the **contents**: a seventh changed file, or a diff one row taller than the screen, would otherwise narrow the region by two columns and re-plan every row in it, sliding the elements sideways at some widths and taking the counts cell off every row at others. Reserving it always is what stops that, and it survived the first fix only because a scrollbar does not look like content. **What it costs is the sparkline between 40 and 41 columns**, on top of the 36 to 39 the counts cell took, so the sparkline needs 42: at exactly the width I6 is named for, a pane shows the heat strip and the counts and no sparkline. The alternative is not *a sparkline at forty* but *a sparkline at forty until a seventh file changes*, and an intermittent view is worse than a smaller one because there is nothing on screen to argue with. **A row's band runs under the scrollbar's own column, and the bar draws over it.** `BAR_WIDTH` is `reserved(1)`, a bar column and a blank one in front of it, and a wash stopping before either leaves a notch of pane background running the height of the diff. *Reported from a real pane.* The reserve itself is about glyph adjacency and is unchanged: it exists so a full-block thumb never sits flush against a count and reads as `-6#`, and a blank cell whose background matches the band is still a blank cell. **`Painter::bar_cell` assigns rather than merges**, so the band keeps the background and the bar owns the symbol, the foreground and the modifier. Merging is wrong in a way only configuration reaches: `Cell::set_style` inserts `add_modifier` gated on nothing, and `VIGIA_THEME` accepts a trailing modifier word on every key `Theme::KEYS` names, so `removed_row = on #45222a reverse` would put `REVERSED` on the thumb and swap the two colours every contrast gate exists to prove. Assigning makes the guarantee structural instead of resting on every palette declining to author a field. **The track moves with the band**, because `bar_track` at `#57606a` falls to 1.88:1 on an added row against a 2.0:1 floor: `#656c76` on dark and `#7d8590` on light, the latter being `spark_track`'s own value there so that palette invents nothing. `heat_track` is deliberately unmoved, since the heat strip never draws on a washed row. Five gates hold it, and the last three cover what the first two structurally could not see: `render.rs::a_wash_runs_under_the_scrollbar_column`, `render.rs::every_row_of_the_bar_carries_its_own_rows_background` over every row at both bar shapes, `render.rs::a_row_washs_modifier_never_reaches_the_scrollbar`, `palette.rs::a_bar_track_is_visible_on_every_row_it_crosses`, and `palette.rs::every_bar_style_says_what_bar_cell_reads` on all three palettes including `ansi`. *Ruled 2026-08-17, reader-reported; finished 2026-08-18 ([#214](https://github.com/breferrari/vigia/issues/214), [#239](https://github.com/breferrari/vigia/issues/239)).*

**The pane stands back from its own edge, on a ladder of its own: one cell a side from 44 columns, two from 80, and nothing at all below 43.** `assets/preview.svg` draws its furniture to the window edge and its glyphs one to three cells inside it, and the shell drew everything from column 0, which by §5.1's law made it an undocumented departure from the picture rather than a choice. The floor is I6's rather than a rounding, since the sparkline has been bought and sold twice over two columns at exactly forty. **The margin is a ladder of the *total*, split between the two sides, and that is a ruling rather than arithmetic.** A per-side ladder steps both sides on the same column, spending two for the one a widening pane just gained, so the content width goes *down* where it should go up: taking both sides at once grew the footer to two rows at 44 and at 80, spending a body row on a **wider** pane, and walked the header's worktree name from marked back to whole as the pane *narrowed* across 80. So the total climbs by one per rung, split with the odd column going left, which leaves the pane square at every width except 43 and 79. The left goes first because a reader registers it as the edge of the page. *Ruled 2026-08-10, session ([#119](https://github.com/breferrari/vigia/issues/119)).*

**The inset is charged to a region on its left alone**, and that is what makes it affordable. A glance row already stops two columns short of the pane's right edge for the bar, drawn or not, so the columns a right-hand margin would want are standing there and `planning_width` spends them once. A row loses its rung's width in path and never twice it, and at 80 the pane's two margins come out equal. This holds only while no rung's **right half** exceeds the bar's reserve, and `the_inset_never_outgrows_the_scrollbars_reserve` is what fails if one ever does, because a wider half would reinstate the trailing reserve the rule below refuses.

**The diff's content rows are the one class this does not describe.** A hunk header, a note and a content line keep the *region's* right edge rather than the pane's, which is older than the margin and is why they move by two columns when a diff outgrows its pane and takes a scrollbar. The margin does not compound with that: a content row stops at whichever of the region's own edge and the pane-less-margin is already further in, so wherever a bar is drawn it lands exactly where the heading above it lands. Charging both put a content line two columns left of its own heading on precisely the screens where the diff was long, which is the contents deciding the layout. `a_diff_outgrowing_its_pane_does_not_move_the_content_rows_edge` gates the agreement. **So a residual survives, and it is stated rather than left to be rediscovered**: the movement is the scrollbar's reserve less the trailing margin, two columns below forty-four, one from forty-four to seventy-nine, and none from eighty up. Forty-three is not in the improved band, because its rung spends its single column on the left and its trailing margin is zero.

**`r` puts the pinned list beside the diff as a left rail, from a hundred and thirty-four columns up.** Below 134 it changes nothing drawn and eats no gesture, exactly as `m` behaves on a pane that cannot carry the band, and the request is **kept** rather than cleared, so a reader who narrows a railed pane and widens it again gets their rail back instead of the question. `Chrome::rail` is what was asked for and `Body::rail` is what the pane could give, which is `Chrome::masthead` and `Body::graph` one region over. *Layout ruled 2026-08-23 ([#252](https://github.com/breferrari/vigia/issues/252)); the gesture is §11.2 B14, ruled 2026-08-24 ([#295](https://github.com/breferrari/vigia/issues/295)), and until then the rail arrived on its own.*

**The arrival width is derived and there is only one of it, at the block rung.** Both regions read the layout table, so splitting a pane costs each half the width the whole had, and a split costs **no rung** only where both halves and the undivided pane one column below sit on the same plateau. The settled ladder's plateau ends at a pane of 133; the only other plateau is the table's top rung, which would need a pane of 328. So the rail is offered from **134**, the first width at which the stacked list would have left the settled ladder and spent its new columns on a twenty-four slice heat strip. Offered rather than arrives, since B14: the derivation decides where the gesture can be honoured and is untouched by the gesture existing. **What the split costs is the diff's content column, and that is the feature rather than a defect *for a reader who asked*** — which is the qualifier B14 exists for, and the reason the rail stopped arriving on its own. At 133 the diff plans against 129 columns and at 134 against 60. A rail at any width narrows the diff, because there is nowhere else for its columns to come from, and the choice was between narrowing it here and halving the heat strip in both regions at a later width. The two columns are within a few of each other at 134, 70 against 64, and the diff is the wider from 141 up.

**The rail is 70 columns until the pane reaches 213, and a third of it after that.** The floor is composed from what it is a floor of: the scrollbar's reserve, the pane's leading inset, the kind letter every file row opens with, twice `MIN_PATH_WIDTH` of path, and the settled glance cluster the picture draws. Twice the floor rather than the floor, because at exactly twelve columns a path elides to its bare tail and a rail whose paths have lost the directory they are in has given up half of what it is for. The share is the smaller half of the pane on purpose: below 213 every column the pane gains goes to the code, and above it the rail earns width the way §5.3 rules richness is earned.

**The derivation is the block rung's, which is a limit rather than a caveat.** `Columns::plan` takes the glyph rung, a dense cell draws two buckets per column, and the same layout table is reached at different widths: on a terminal carrying braille or octants the stacked ladder climbs at a pane of **119** and is past the settled rung by 133, so crossing into the rail costs twenty-four heat slices for twelve in both regions. No arrival width is loss-free at every rung, and that is arithmetic rather than a choice, because the braille plateau that would allow one is empty. [#284](https://github.com/breferrari/vigia/issues/284) is the row for an arrival that knows its rung.

**The rail draws the pictured glance complement below a 402-column pane, and climbs at it.** The table's share clamp needs 130 planning columns for the next rung up, which the rail's third of the pane reaches at exactly 402. It is stated as a number because the sentence it replaced, *"does not climb at any pane anyone runs"*, is one no sweep can fail. Below it, twelve slices and twelve buckets is exactly what `assets/preview.svg` draws, so §5.1's picture binds the rail as well as the strip; at it the rail has earned more. `tests/rail.rs::the_rail_grows_with_the_pane_and_keeps_the_pictured_complement` sweeps past the boundary and pins it in both directions.

**Beside a rail the list's height cap does not apply.** [#160](https://github.com/breferrari/vigia/issues/160) made the cap a share of the pane because the list's rows come out of the diff's; in this layout they do not, so the region takes every row under the band and a forty-row pane draws thirty-six changed files where the stacked layout draws ten. Each visible row still costs one `Frame::diff` and no more, which is the I4 claim `tests/reads.rs` owns, and the deeper region was measured against I9 rather than assumed: a frame on a 200x40 pane drawing 36 pinned rows is **0.71ms p50 and 0.79ms p99 against the 16ms budget**.

**`s` pins the diff to the file the caret is on, and the walk stops there.** When an agent is working inside one file the continuous diff makes a reader hold two positions at once, where they are in the file and where they are in the changeset, and the pin removes the second. Scrolling clamps at that file's two ends instead of carrying on into the file below, the scrollbar measures the file, and `n`, `p`, a digit, a click on a listed file and a follow are how the file changes. Off by default at every width and height. It is `f`'s sibling one step over: follow decides *which* file the pane goes to on its own, and this decides how much of the rest of the tree the reader's own scrolling will reach once it is there. *§11.2 B16, ruled 2026-08-25, reader, from the pane ([#297](https://github.com/breferrari/vigia/issues/297)).* **It is not a mode**, which keeps it out of B4's refusal the way B12's sheet and B14's rail are. No key changes meaning while it is on: `j` and `k` scroll a row, `Space` pages, the digits jump, over one file's worth of rows. **`g` and `G` are the case that has to be argued rather than asserted**: both have always meant *the ends of what you can scroll to*, and the pin decides the ends of what, so the meaning is one over a smaller subject rather than two meanings. `G` reaching a real last **row** is affordable here and nowhere else, because the pinned file has been diffed by definition, where finding the last row of the whole diff means adding up every file's height, which is the read I4 forbids and why `G` unpinned is the last file's *heading*.

**Which file is pinned is the position's, so nothing new decides it**, and every gesture that moved the viewport between files still moves it. **Follow is among them, deliberately**: `f` and an automatic follow are explicit requests to be moved, where the pin is about what a reader's own scrolling reaches, so pinning is not a manual scroll and does not disengage follow.

**The pin has no readout of its own, and that is a ruling rather than an omission.** Follow earned `follow ▶` on the argument that its state is otherwise invisible, since a pane that is following and one that is not draw the same screen until something changes. A pin is not that kind of state: the diff's scrollbar is scaled to one file rather than to the changeset so its thumb is visibly larger, the heading on screen is the only one, and scrolling to the file's end stops there. **The reader who cannot see it is the one on a pane too short for a bar**, and that is the case to reopen on rather than a reason to spend a footer rung now. The footer's `N/M` stays the changeset's, because that is the reader's place in the tree and the pin does not move it.

**The heading of the pinned file draws as the block's first row and is not sticky.** It carries the pulse, the heat strip, the sparkline and the counts, so it is kept rather than dropped as redundant; making it stand at the top whatever the scroll would cost the diff a permanent row, and the caret and the bold path say which file the pane is pinned to once the heading has scrolled past. **The last row of a pinned file is content**, which is the rule for the bottom of the diff applied to a smaller subject: the blank that closes a file's block separates it from the file below, and a pinned frame draws no file below. `crates/vigia/tests/single.rs` is the gate file.

**What it costs the frame path is negative, which is the unusual direction.** I4's single exception is the diff's **height**, counted for every changed file once per tick and the only thing in the frame path not bounded by the window. A pinned frame skips it: what the reader can reach is the pinned file, whose span the walk has already recorded, so the total is read off the screen rather than counted. `crates/vigia/tests/reads.rs::a_pinned_frame_counts_no_height_at_all` asserts the unpinned frame counts something first, because a zero on a fixture with nothing to count proves nothing. **The drag on that bar reads the same quantity**, for the reason a row-exact bar exists at all: a bar drawn from one total and dragged against another agrees at both ends of the track and nowhere in between.

**Toggling it settles rather than restoring, and the ruling says so out loud.** From a screen already inside one file, pinning and unpinning is identity. From a screen straddling two it cannot be: the pin rests the pinned file's last row on the bottom, which is a pager's answer and the one a reader was already looking at most of, and that rewrites the position. What is promised is that every pair after the first is identity, so the gesture is a toggle rather than a ratchet walking a reader up the file one press at a time.

**The band is the one thing both regions pay for, which is an exception to the clamp order rather than an oversight.** The rule is that the band gives way to both and is paid out of what is left, which the stacked layout keeps by sizing the list before the band is considered. Beside a rail it cannot: the band spans the pane above both columns, so its three rows are unavailable to the map as well as to the diff. The cost is one step, at the height the band arrives. The diff has always taken exactly that step at exactly that moment and `GRAPH_KEEP` bounds it; what is new is that the map takes it too. `tests/rail.rs::the_rail_is_monotone_in_pane_height` asserts both halves.

**The horizontal rule is dissolved and no vertical one replaces it.** B11 ruled the rule between the regions stays bare, and `Body::split` makes the rule and the list coextensive, so there is no boundary here for a horizontal rule to sit on. A vertical rule was not added: the rail's scrollbar reserve and the diff's leading inset already leave the boundary blank, and a rule carrying no fact is chrome announcing a region, which is B11's argument one layout over.

**Three rulings the vertical layout never had to make.** The **wash** follows the region and not the screen, which §5.3 carries as a law. The **margin** keeps its rung from the pane and is charged to each region's leading edge, so the pane stands back from its own two edges and the interior boundary gets the same inset. And the **caret** is afforded from the region rather than the pane, because the question it asks is whether *the row* still names its file after the marker has taken its column, and a 210-column pane says nothing about a 70-column rail. It still stands on the pane's own leading column, which in this layout is the rail's.

**The counts cell is two fixed halves of five columns**, `+9999` and `-9999`, with magnitude giving way to a shorter form past that rather than to more digits: `+10k`, `+999k`, `+1M`, `+4G`. Five is the narrowest width at which that abbreviation is **total**: a narrower rung drew `+0k` for a 250-line change, because two characters have no truthful form for it and the search fell through to the thousands unit. It cost the sparkline between 36 and 39 columns to fix, which is the honest trade against a number that says none when it means two hundred and fifty, and it is the rule the status bar's frame and memory cells already follow with `>1s` and `>1GiB`. **The halves do not narrow**, the only thing on the row that does not, and they go together or not at all, because `+42` with no `-7` beside it reads as a total rather than as half a pair.

**A rename's label is a rung, not a token to be cut.** A row draws `new ← old` whole or it draws the new path alone; it never elides the pair. Every other label loses its *head* when it does not fit, because a path's tail is what identifies the file, and that premise is false of a pair: cutting the head of `new ← old` leaves a tail belonging to `old`, so the row names the file the rename came **from** rather than the one it is about, and nothing on screen says it happened.

**The layouts are written out as a table rather than allocated element by element**, and that is what makes narrowing monotone. Allocating greedily in priority order oscillates for a *shared* layout: each element takes the widest rung it can afford and starves whatever comes after, so a row could lose its sparkline at one width and get it back two columns later. Each row of the table gives up exactly one thing against the row above it and gains nothing, so the ladder is monotone by construction rather than by argument. **The drop order, narrowing, is the sparkline's resolution, then the strip's, then the sparkline, then the strip, then the pulse, and the counts last**, because they are the row's content rather than a signal drawn beside it. `crates/vigia/tests/legibility.rs::the_glance_columns_collapse_in_one_order` asserts the monotonicity as a rule and pins the walk with the width each state begins at, because a rule alone cannot see a boundary that moved.

**The table answers two questions.** Below the widest layout that shipped, the question is *what survives* a narrowing pane, and the twelve-column path floor decides it. Above it the question is *what a wide pane is worth spending*, and there "does it fit" is the wrong test, because a fixed-sum table takes a rung the instant it fits: the widest heat rung fits inside **69** columns, narrower than the 109-column render `assets/preview.svg` is measured from, so a rung on the fit test alone would have made the published picture false while every gate stayed green. **So a rung above the settled ladder is taken only when the glance elements fit inside two columns in five of the row.** That puts the 24-slice strip at **134** and a 48-slice strip at **194**, which are the two widths [#161](https://github.com/breferrari/vigia/issues/161) asked for from a rule derived from neither. The clamp is floored at the settled ladder's widest layout, so **no boundary that shipped can move** whatever the share is set to. `crates/vigia/tests/legibility.rs::the_widest_strip_waits_until_the_path_keeps_the_row` derives the boundary from the layout's own slots rather than reading it off a failure.

**The two elements alternate down the table**, the sparkline's resolution and then the strip's, all the way ([#234](https://github.com/breferrari/vigia/issues/234)): twenty-four source buckets halving to twelve and six. The bound that once made twelve the largest division available was the churn band's fixed period, and when that was retired the bound went with it rather than being replaced, which left a conclusion outliving its stated basis. What replaced it is the **window**, which every rung now covers. **A rung removed from the top of a monotone ladder can only be free, and a rung removed from anywhere else cannot be.** The ladder's old top step dropped the pulse **label**, which §5.1 has since retired everywhere, so the table is six steps rather than seven. Every boundary below is unchanged, because a layout's width is the sum of its own slots and none of the surviving six changed, and the walk `the_glance_columns_collapse_in_one_order` pins is identical. That check is what the removal rests on rather than the arithmetic.

**Every width in the paragraphs above is the block rung's**, which is a qualification rather than a correction: they were measured when there was only one rung and are still exactly what a terminal drawing eighth-blocks does. At a dense rung the same table is reached earlier, because a slot's cost is `spark_cells` of its bucket count rather than the count itself, so the sentence about forty columns showing no sparkline is true of blocks and false of braille. The *ladder* is unchanged; only the price of one of its slots moves.

**The band draws at the block rung whatever the pane detects, and the sparkline keeps the ladder.** Scattered dots are glyph **texture** and point at a rung; waves becoming spikes are the signal's **shape** and point at the denominator. A report of the second is not evidence about the first. That denominator is [#256](https://github.com/breferrari/vigia/issues/256), which reached the same conclusion from the code three days earlier. So the rung returns and `VIGIA_GLYPHS` reaches the band again. **The ruling is the reader's and it is not conditional on a measurement**: removing a reader-facing rung is a product decision, it was taken without being asked for, and a reconstruction-error table is not a licence to keep it. What a measurement decides is the **shape** the rung returns in, never whether it returns.

**What the measurements bound is where each element's rung is worth anything.** Across widths 40 to 124 on a wave, blocks draw 16 of a possible 17 distinct column heights and a dense rung draws 7 of its 7, saturated because seven is all a 2x4 cell has over two rows. What the second sub-column buys in exchange is nothing a reader can see at ordinary widths: **98% of dense cells draw two identical halves at 80 and 109 columns**, because the band asks for `width * density` slots against a 120-sample window and therefore repeats above width 60. Below 60 it repeats nothing, and at 40 the twin rate is 0% on a bursty trace, so the horizontal gain is real exactly where the pane is narrow. The sparkline is the opposite case: its rung is capped at the window's own 24 buckets, so **0 of 12 pairs are identical** and the second sub-column always carries a distinct value. Whether a level still needs a drawn axis, now that a quiet stretch is a low level rather than an absent one, would return a further rung and is unanswered. **Spending the cell's fourth dot row instead is closed by arithmetic rather than declined by taste**: four levels over two rows is eight against the block ramp's sixteen, so it does not close the gap, and the row it would take is the axis [#78](https://github.com/breferrari/vigia/issues/78) requires. At two rows a 2 by 4 glyph *halves* its vertical resolution, and [#198](https://github.com/breferrari/vigia/issues/198) already sums every stored sample onto the width it has, so there is no unshown horizontal detail for a denser glyph to reveal; the band joins the ladder only if it ever grows past two rows. `Glyphs::BAND` is where the ruling lives, so the band cannot half-follow it, and `the_band_draws_at_the_block_rung_whatever_the_pane_detects` and `the_bands_heights_are_the_block_rungs_and_not_a_dense_cells` are the two halves of the gate: which graph, and at what resolution.

**There is no trailing reserve beyond the scrollbar column.** The picture leaves about a sixth of the row blank on its right, and that is an artifact of a fixed canvas at a width where nothing degrades rather than a promise; spending it at forty columns is what I6 forbids. The two columns a row stops short of the pane's edge are the bar's, paid whether or not a bar is drawn. The pane's inset is a *leading* margin, and the reason it costs a glance row one column per rung instead of two is precisely that this ruling stands and the trailing columns stay the bar's.

**A visible list row costs one `Frame::diff` and no more**, which is what keeps the region inside I4 rather than beside it. The bound is the region's own height, never the changed-file count, so the cost follows the window exactly as the body's does, gated in `crates/vigia/tests/reads.rs` beside a rail as well as under a stacked list. **What that row costs depends on which side of the settle margin the file is on.** Settled, it is a `stat` and a cache hit reading **zero bytes**, which is I2a doing its job and the state a monitor sits in for almost all of its life. Inside the margin it is a real read, because `Frame::diff` cannot prove a file written in the last two seconds unchanged and re-reads it by design, so a six-row region on a tree being actively written costs six reads a frame rather than six `stat`s.

**The two regions hand entries to each other rather than asking twice.** The file an agent has just written is the one the margin is certain to cover, it is always the file the diff is inside, and it is always in the window while the list follows, so asking the frame for it a second time read and diffed it again on every frame this tool exists for: **258,790 bytes where 36,970 will do**, over twenty files of five hundred lines. `View::collect`'s walk records the entries it builds and `take_list` draws from those, which is the same one-pass rule that section already followed for the diff. `a_screen_a_single_file_fills_reads_that_single_file` gates it as a relation, that the region computes one fewer diff than it asks for, so it survives a change to the region's height.

**The record is taken whether or not the heading fits.** A walk that built its entry on the row it drew the heading on would leave a file out of the record whenever the viewport sat *inside* it, and the list would ask the frame for it again. The entry is now built for every file the walk reaches on a pane that has a list, and drawn for the ones whose heading fits. On a pane too short for a list there is no `take_list` to serve and the undrawn one is not built, which `a_pane_with_no_list_builds_no_entry_it_cannot_draw` gates through `View::recorded` — a counter that exists because nothing else can see the difference, since building an entry reads nothing and no `FrameStats` figure moves for it. It costs one `entry_of` for at most one extra file per walk against a `Frame::diff` that is a whole-file read inside the margin, so the file being written saves a read and a settled tree trades a syscall for a walk over lines already in memory. *[#257](https://github.com/breferrari/vigia/issues/257).*

**The list follows the diff, and `J`/`K` move it without moving anything else.** It slides on its own to keep the caret visible, so the region is correct untouched the way I5 requires. Shift is the modifier because `Ctrl-J` is LF and `Ctrl-C`/`Ctrl-D` already quit, Alt is intercepted by terminal emulators and by macOS Option, and `G` has already taught a reader that case is load bearing here. A plain letter also reaches terminals that never report a modified arrow. **`J` takes the window over, and anything that moves the diff hands it back**, which is the list's own version of follow mode: a manual scroll takes the *diff* away from following and gives the *list* back to it, in the same line of the same function. Both halves are load bearing. Without the takeover `J` is inert; without the handback a reader who browsed once has a map that never agrees with the diff again. **The caret marks the current file whenever the window still shows it**, and is simply absent once a browsed window has moved off it: it says *the diff is in this file*, which stays true while a reader browses, so hiding it would withhold a fact the reader can act on.

**Scrolling the list does not disengage follow mode**, and that is a ruling rather than an omission. Follow is a claim about the **diff** viewport, and moving a window over a map expresses no intent about what the diff should show. Browsing the changed set while the diff goes on following what an agent is writing is the monitor behaviour, and the two would fight if one disengaged the other. `Action::is_manual_scroll` is an exhaustive match precisely so that a new action has to answer this rather than inheriting a default.

**Both regions carry a scrollbar, and both are exact.** The list's thumb spans the visible window over the changed-file count, both of which are free. The diff's spans the screen's rows over the diff's **total** rows and sits at the rows above it, which is what every other scrollbar means.

**A bar tall enough for one carries a step button at each end, and one click is one step.** The buttons come out of the track, so the ladder is a floor rather than a preference: `STEP_FLOOR` is two buttons plus the shortest track that can still express more than one position, which is four rows, written as that sum rather than as `4` so the threshold cannot keep an old total while every gate over the drawn output stays green. Below it the column is byte for byte what it drew before there were buttons, which matters because `MIN_BODY` is 2 and a diff region can legitimately be two rows tall. The floor is per region rather than per pane, decided from the region's own height, which is what lets one drawer serve a six-row list and a thirty-row diff without either being a special case. *Ruled 2026-08-15, session ([#166](https://github.com/breferrari/vigia/issues/166)).* **Holding a step button repeats it, and that is a clock this program is allowed to own.** The mechanism has to be built rather than asked for: **no mouse protocol reports a button that is still down.** `crossterm` delivers `Down`, `Up`, `Drag` and `Moved`, and a drag needs motion, so "the button is held" arrives as nothing at all until the pointer moves or the button is released. Repeat is therefore a timer, and what makes one admissible is a distinction I1 did not draw for itself: **its budget is *0 wakeups while idle*, measured over a sixty-second idle window, and a held mouse button is not idle.** Every other timer this spec refuses is a clock that would run while nothing is happening, which is the state that measure protects. This one exists only between a press on a step button and its release, is bounded by the reader's own finger, and cannot outlive it. `Held::wait` is where that stops being an intention: with nothing held it returns `None` and the loop blocks on an **untimed** receive, and `nothing_held_means_no_timer_at_all` is what fails if that changes. What I1's row gains is the qualifier its first sentence was missing: *never a fixed timer* means never one that runs unbidden, not never one a reader is holding down. *Ruled 2026-08-15, session.*

**I1 carries that as a rule, not as a licence for this control.** Naming the instance leaves the next one to be re-litigated even where the argument is identical, and one is already visible: a press held on the **track** rather than on a button is the page-repeat every desktop scrollbar has. It is a clock bounded by a gesture and it is not a step button. `Held` repeats whatever action it is armed with and `Action::repeated` is an exhaustive match precisely so a later held control inherits the mechanism, so a spec licensing one control while the code offered a facility would be the two describing different programs. I1 states the three conditions and this is an application of them.

**500ms before the first repeat, then 50ms, and the numbers are taken rather than chosen.** Qt's `QScrollBar` presses a control with `initialDelay = 500` and repeats at `50`; GTK exposes the same pair, the latter defaulting to 50ms. Two toolkits, one shape, so a reader arriving from any desktop scrollbar finds the cadence already in their hands. The delay is what keeps a single click a single step. **The rate does not accelerate**, which is a ruling and not an omission: a step button is for placing the viewport precisely, acceleration makes precise placing harder by overshooting, and a reader who wants travel has the wheel, `j`/`k`, `d`/`u`, `n`/`p`, the digits, `g`, `G` and the thumb.

**A late repeat folds into one action rather than a backlog, and that is a correctness claim.** `Action::repeated` multiplies a relative step by the number of whole intervals that have actually elapsed, so a tick arriving four intervals late applies `Scroll(5)` through one `apply` and one paint instead of five of each. The rate is then a fact about time rather than about paint speed: a slow pane scrolls the same rows per second as a fast one with coarser granularity, and can never keep moving after the finger lifts. The deadline advances by the steps it took rather than to *now plus one interval*, so a tick handled late cannot push the next one later and walk the rate downwards under load. **The mechanism is general, not scrollbar-shaped**: every action states how it composes with itself, and the ones that return themselves are rulings, since a page held down is the reader's own key repeat and `Top`, `Bottom` and `File` name a destination that does not accumulate. An action added later stops that match compiling and asks.

**A hold ends five ways.** A release of any button. Any key press, because a hand that has reached the keyboard is not holding a mouse and `q` must not be answered by a program still stepping. A **pointer move**, since `MouseEventKind::Moved` is motion with no button down and is therefore positive evidence of a release, which is what catches an `Up` that never arrived. A drag off the button, where a twitch inside the same cell keeps it. And **the window losing focus**, which is owed to I1's second condition rather than to symmetry: without it the repeat goes on stepping and repainting a pane nobody is looking at, on a clock. Resuming on re-entry is what a desktop scrollbar does and is deliberately not done, because it needs a suspended state `input.rs` has nowhere to put. **A drag onto a button is still inert**: the reader has grabbed the thumb and pulled past the end of the track, and both stepping and clamping would need to know the drag *began* on a button.

**A gesture in progress is lit, and it is one reading in three places.** A step button held down, a thumb being dragged, and the arrows while the keys scroll all take `Theme::bar_active`, brighter than the mark's resting style rather than a different hue, because the element has not changed meaning, only state. It matters most where nothing else can answer: pressing *up* at the top of a diff moves no row, and without the lit cell the control is indistinguishable from a decoration. It costs no row, no rect and no wake, since the frames it changes are frames the gesture was already painting. **The arrows answering the keyboard is the one lit thing nobody is touching**, and it earns its place because the arrows are the element whose whole job is *which way*: `j` lights the down arrow, `k` the up one, and magnitude is not direction, so a half page lights what a single row lights. **On one bar**: the two regions move different things and answer different keys, so the mark carries the region as well as the direction, with `j`/`k`/`d`/`u`/`Space`/`g`/`G` and the file steps the diff's, `J`/`K` the list's, and a jump or a drag neither.

**That last one expires and the other two do not**, which is its honest cost. A release ends a hold; a key burst simply stops and sends nothing, so without an expiry the last arrow of a burst would stay lit on an idle tree, which is a claim about the past. `SCROLL_LINGER` is 220ms, long enough to bridge the gap between two key repeats and short enough that a reader who stopped does not see one. It is the one number here that is a feel judgement rather than a measurement, and it is stated as one. The clock is bounded by the burst that armed it and fires once, so it meets I1's three conditions like the repeat does, and `input::patience` is where every clock is asked together so that *is there a timer at all* has one answer and one gate.

**Hover gets no expiry because it does not need one, and I1 does not refuse it either.** A linger armed by a motion event would meet I1's three conditions exactly as `SCROLL_LINGER` does: it could not start on its own, it would fire once, and the idle path would stay untimed by construction. Reaching for the invariant here would be the cite-without-checking that B10 was reversed for. What refuses it is what it would **do**: an expiry puts the mark out while a reader rests on a row, and a reader resting on a row is the one case hover exists for. **Stated as one rule because B10's decline was read as a rule against pointer-derived marks in general**, under which the lit step button should not have existed. It should: it was never what B10 refused. `input::hover_after` is the rule with nothing added.

**A drag keeps the bar it started on, wherever the pointer goes.** `action_for` asks what is under the pointer, which is the right question for a press and the wrong one once a hand is already moving, and a one-column target is not something a hand stays inside. So a press on a track takes hold of that region and every motion after it resolves against that region alone, with the row **clamped**: pulling above the track holds the first window and below it holds the last, which is what every scrollbar does and what a reader dragging past the end is asking for. A press on a step *button* grabs nothing, because that gesture is already a step. *Ruled 2026-08-16, reader-reported.* **A button is chrome, in the bar's own dim style rather than the thumb's.** Shape is what tells one from the track it shares a weight with, so the thumb stays the only lit thing on the column. The glyphs are `▲` and `▼`, which are outside CP437, and they stay on the ground that **every** candidate arrow is (`▴ ▾ ↑ ↓` alike, and CP437's own two triangles sit at control-code positions) while a direction is the one thing a shape has to say here. The loss on such a console is two cells on a column that otherwise survives whole. §10's Windows bullet carries the list and [#159](https://github.com/breferrari/vigia/issues/159) owns the ladder; this ruling deliberately does not invent one inside the scrollbar.

**The diff's bar is exact.** A bar approximating the whole from the current file's height vanishes on a short file, balloons on a long one, and never reaches the bottom, because the trailing files are rarely the height of the one being read. I4 forbids diffing every changed file for a total, so the total comes from the heights the walk already has. The argument was right that *diffing* every file is unaffordable and wrong that a total needs it. A height is hunk boundaries and line counts; a `FileDiff` is those plus an owned `String` per drawn line. Counting instead of building took the reference fixture from **442.71ms to 8.76ms**, against `git diff --numstat`'s 46ms for the same work, and §3's I4 carries the narrowing that admits the walk. *Reported from use within the hour.*

**`m`, `r` and `?` were bound and not in that table until 2026-08-25**, and each is described in its own paragraph below, so this was an omission rather than a disagreement. Recorded rather than fixed silently, because a keymap table that omits three of its keys is the shape a reader trusts and should not have to check.

**The half page is `d` and `u`, and it keeps no overlap row where a whole page does.** They are `less`'s own bindings and the follow-mode paragraph below already claims `less +F` semantics, so the precedent is internal as well as cultural. A page steps `height - 1` so one row survives the seam and a reader does not lose their place; a half page already leaves half the screen standing, so taking a row off it would pay twice for one anchor and leave `d` and `u` out of step with each other. Both directions floor, which makes the pair an exact inverse on an odd body as well as an even one. **`Ctrl-D` and `Ctrl-U` are refused rather than overlooked**: `Ctrl-D` is one of four ways out, and rebinding a way out to a scroll is the surprise this map has avoided everywhere else. `D` and `U` are unbound for the reason `F` is, one row above a pair where case is what tells the two apart.

**The half page is not hinted, because at eighty columns the footer is exactly full.** With follow engaged, a position and both readouts, the row is 40 columns of hints, 2, 19 of readouts, 2 and 13 of state, which is the 76 that eighty columns leave after the inset, to the column. A fifth hint is paid for out of the readouts: the frame time would first arrive at 81 columns instead of 69 and the pair at 89 instead of 77, and `render__the_status_bar_carries_what_a_frame_cost.snap`, whose job is to show this layout is *good* at one width rather than merely legal at every width, would have lost both cells. Refusing it costs little, since `Space`, `PgDn` and `PgUp` have never been hinted either, and the bar's four hints are the way out, the state whose absence is invisible, and the two vi-dialect keys. `crates/vigia/tests/legibility.rs::a_wider_hint_bar_cannot_quietly_push_the_readouts_out` pins both boundaries so the next hint added has to argue for what it spends. **What stays open is the ruling underneath**: whether a bonus rung is exempt from the drop order that puts advice above instrumentation at every width, or whether being unowed makes it the one thing that yields to a readout ([#147](https://github.com/breferrari/vigia/issues/147)).

**The file is a granularity, and the map had every other one.** Rows are `j`/`k`, screens are `Space` and `d`, the two ends are `g` and `G`, and not one of them is the unit the pinned list draws, the header counts and the reader thinks in: reaching the next file meant holding `j` through the rest of this one. `n` and `p` step one changed file, and so do `→` and `←` (§11.2 **B15**): vertical keys move inside the diff and horizontal keys move between files, so the four arrows are one set rather than half of one. `1` to `6` put the diff at the Nth row the list is drawing. **All of them land on the file's heading**, which is the resolution a click on a listed file uses, and none costs a diff: a heading is row zero, so nothing here asks how tall anything is and I4 never sees it. **A follow jump no longer shares that landing**: these keys name a *file*, which is the unit the list draws and the header counts, where I5 promises the *change*. The debt is cleared by every gesture `Action::is_manual_scroll` calls one, so a landing armed by follow can never be inherited by one of these. **B4 is untouched**: all three move the *diff*, exactly as a click does, and nothing is remembered.

**`p` from inside a file goes to the previous file, never to the top of the current one**, and at either end of the changed set the step moves nothing at all. The pager reflex of "this section first" is refused because it would make one key mean two things depending on where the viewport happened to be, and because `g` already reaches a top. Clamping the file index rather than refusing the step is refused for a neighbouring reason: it would give `n` at the last file a *backwards* jump and `p` at the first a forwards one, a key undoing what its own letter says. **Follow mode is still disengaged at both ends**, where nothing moved, because on this map follow yields to a reader's intent rather than to whether the arithmetic landed somewhere new.

**The digits address the window, not the changed set.** `3` means the third row the list is drawing, so after browsing with `J` it names a different file than it did before: what you can see is what you can name. Two bounds make that true. A digit past the **drawn rows** is the ordinary case and is one only a keystroke can reach, because a pointer is bounded by the region and a keyboard is not. The **file count** bound looks redundant and is not: what it guards is the screen being **out of date**, since the row count is what the last frame drew, so between a paint and the keystroke that follows it the changed set can get shorter — `git reset --hard`, a branch switch, or the agent reverting its own work — and `6` would still pass the window bound. **Which bound does the work was settled by mutation rather than by argument**: deleting the file-count bound left every other gate in this file's suite green, and `crates/vigia/tests/list.rs::a_digit_after_the_diff_shrank_names_no_file` is what now holds it. Both bounds refuse silently, with no bell and no error. `0` and `7` to `9` are not bound at all, which is a different thing deliberately: an unbound key is no action, where a bound one naming a row that is not drawn is a jump that lands nowhere and spends the reader's follow mode doing it.

**They stop at six because six is the deepest list *every* pane draws**, so `3` means the same thing at every height, where a key live only above some pane height would be the intermittent affordance this section refuses one region over for the caret's own column. The rows a taller pane adds are addressed by `J`/`K`, `n`/`p` and by clicking, which is bounded by the region rather than by the grammar and therefore reaches every drawn row at every height. `crates/vigia/tests/list.rs::clicking_a_listed_file_sends_the_diff_to_it` runs at 24 rows and at 50 for that reason, and `crates/vigia/tests/input.rs::the_digits_cover_the_settled_cap_and_stop_there` is the other half. **None of the three is hinted, and the reason is [#121](https://github.com/breferrari/vigia/issues/121)'s.** The eighty-column footer is exactly full, so a fifth hint is paid for out of the frame-time and memory cells whichever hint it is, and `Space`, `PgDn`, `PgUp`, `d` and `u` are an established unhinted family. The argument that a drawn numbered list *is* the affordance does not hold here, because **the list draws no numbers**: `rows__a_real_repository_draws.snap` draws a caret column and then the kind letter, with no rank on any row. So the digits are the first binding here with no drawn affordance at all, which the thumb, the list and every hinted key each have in their own way. Whether the list should draw the rank it is addressable by is ruled below; [#147](https://github.com/breferrari/vigia/issues/147) owns the rung question underneath.

**The list does not draw the rank the digits address.** The region is a map, and a rank makes it a menu. B4 keeps the list not navigable because selection implies focus, focus implies a mode, and modes are reviewer-class; the caret is a fact about *state*, that the diff is in this file, where a rank is a fact about the *keymap*, that pressing this goes there. It would be the first thing in the region that is neither content nor location but instruction, drawn on every row permanently, and numbered rows are the file-manager idiom, where a file manager is a surface you operate. `btop`, which §2 names as the class this tool is in, numbers nothing. **A full footer is a reason not to have a fifth hint, not a reason to move the hint somewhere cheaper**: §5.3 puts advice in the footer and [#121](https://github.com/breferrari/vigia/issues/121) measured that bar exactly full at eighty columns, so drawing the digit onto a content row relocates advice into a region this spec does not meter, and every later binding that cannot afford a hint would acquire the same claim. **And a rank is read**, in the leftmost cell, first in the eye's path and last in what it says about the worktree, which is the §5 glance law that retired the pulse's label ([#99](https://github.com/breferrari/vigia/issues/99)). The digits are the fourth way to a file after `j`/`k`, `n`/`p` and a click, so a reader who never finds them loses a shortcut rather than a capability. The honest cost is that `README.md` is the only place they are met, exactly as for the pager keys. `crates/vigia/tests/legibility.rs::the_caret_column_draws_a_mark_and_never_a_rank` is what fails if the gutter ever gains one. *Ruled 2026-08-14, session ([#149](https://github.com/breferrari/vigia/issues/149)).*

**The case for drawing it is not discoverability, and it is the one to reopen on.** The digits address the **drawn window**, so which of them are live is a function of pane height and changed-file count, and nothing on screen says so. A rank would carry that fact and keep it current, where a hint could not: it would have to read `1-6 files` and be wrong on every pane drawing fewer than six rows. It loses on how benign the failure is that it prevents, since a digit naming no drawn row refuses silently and moves nothing, and because a measured zero-column cost is not sufficient: §5.3 prices **ink** at zero on the ground that the frames happen anyway, and does not price **attention** at zero, where the glance surface is exactly the place attention is the budget. **Drawing the rank and the caret together at widths that afford a third column is refused rather than left lying around as a compromise**, because it would make the region's left edge width-dependent and hand a reader an affordance present on some panes and absent on others. **What reopens it is [#72](https://github.com/breferrari/vigia/issues/72)'s week of real use**, if readers do not find the digits or reach for a number and get nothing. This ruling has no use-evidence in either direction and the binding was one day old when it was made. Two other triggers were written here and have since resolved without reopening it: a list deeper than six arrived with [#160](https://github.com/breferrari/vigia/issues/160), and a heading in the border line for an address to ride was closed off by §11.2 B11.

**The caret travels the window; the window moves the least it can.** It is held while the current file is inside it and pushed by exactly the overshoot when the file leaves, so scrolling from the start walks the caret down the rows and only then does the list move under it. **Two fixed positions were ruled first and both were wrong**, in opposite directions and for one reason: a constant row is not following a file, it is dragging the window on every step. Ending the window on the current file showed the six files *before* the six the diff was drawing; starting the window on it pinned the caret to the first row, which reads as the list scrolling while the marker never moves. Minimal movement subsumes both: at the top the caret is on the first row because the file is first, and at the end the pull-back rests the last file on the bottom row. *Both reported from use.*

**A click on a listed file puts the diff at it.** It is the gesture a reader tries without being told, next to a region that draws the names of the things it is a map of. It is **not** selection and B4 stands: nothing is remembered, no row becomes special, no mode appears, and the event after it means what it would have meant, which is the same argument that already licensed dragging a scrollbar.

**The pointer is acknowledged when it arrives as well as when it acts: what it is over is marked, on three surfaces and nowhere else.** They are **a step button, a scrollbar, and a listed file**. **Nothing in the diff body**, where a drag says where it is going as it goes, and which is the one region `Regions::hover_at` answers `None` for at every row. It is not a cost question: motion already reaches this loop and already draws, so **the mark itself** adds no wake, no paint and no frame, only an `Option` of a target and a style on cells that were being redrawn anyway. *§11.2 B10, ruled 2026-08-16, reversing the previous day's decline ([#123](https://github.com/breferrari/vigia/issues/123)).*

**What the build added, which the ruling never priced, is the focus step's own traffic.** Asking for `?1004h` makes `FocusGained` and `FocusLost` arrive on Unix and macOS where they previously never did, and `run` draws once per drained batch whether or not a wake in it produced an action, so each costs a wake and a frame. `FocusLost` earns it, since clearing the mark is a visible change. **`FocusGained` does not**: it retires nothing, produces no action, and repaints a byte-identical screen. It is bounded by how often a reader tabs back, it is an external event rather than a clock so `Shell::patience` never consults it and the idle receive stays untimed, and Windows has been paying the same repaint since before this branch, because its console delivers `FOCUS_EVENT` records whether or not anyone asked. Recorded rather than fixed: the repaint-per-batch is [#154](https://github.com/breferrari/vigia/issues/154)'s.

**A click is always brighter than a hover, and that rule decides which elements may carry a mark at all.** A gesture has to outrank a pointer merely resting somewhere, or *you are doing this* stops being distinguishable from *you could*. On the bar that is three weights: `Theme::bar_track` at rest, `Theme::bar_hover` under a pointer, `Theme::bar_active` under a press or a drag. The **ordering** is the load-bearing half rather than the middle rung, because the pressed mark exists for the case where nothing else can answer, since pressing *up* at the top of a diff moves no row, and a hover that won there would take that answer away in the one case it exists for. `crates/vigia/tests/render.rs::a_gesture_is_always_brighter_than_a_pointer_at_rest` asserts it as a rule across every surface rather than at the one element that forced it.

**The thumb and the track are one target.** A press anywhere on a track seeks, so the surface a click acts on is the whole column, and the thumb answers because it is what would move. It shipped unmarked on the reasoning that it rests at `Theme::bar` and drags at `Theme::bar_active` with no rung between, and **that reasoning was sound and its conclusion was not**: *there is no rung* is a reason to add one, not to decline, which is the shape B10 itself was reversed for. `Theme::bar_hover` is that rung. **A listed file takes `Theme::path_hover`**, which underlines, and that is what §5.3's amendment is about: intensity belongs to recency for anything durable, and a mark that follows the pointer is not durable. It holds `Theme::bar_hover`'s own colour rather than a fourth weight *above* the whole ladder, which would make the pane's stalest fact its loudest one. One colour for the pointer everywhere it lands, and the underline is what holds on `ansi`, where the foreground equals `Theme::path_cold`'s exactly. **Clearing is a ladder, and naming its rungs is the ruling rather than a caveat on it.** Motion inside the pane clears exactly, because `?1003h` reports at **cell** granularity, so leaving one row arrives as entering the next. **It is available wherever the mouse is**, which is not quite everywhere: a reading of tmux's source says a non-active pane may not have motion requested for it at all under the default `mouse` setting, which is unverified and filed as [#188](https://github.com/breferrari/vigia/issues/188). **Leaving the window is what needs asking for**, and the asking is one step: `TAKEOVER` is `RawMode`, `AlternateScreen`, `MouseCapture`, `FocusChange`, `Cursor`, and `terminal.rs::the_takeover_takes_every_step_there_is` is what fails if the fourth is ever taken out, which the two gates beside it cannot see. Every terminal **checked** implements the mode, and the Windows console delivers the records without being asked; the word is *checked* because "How colour degrades" below rules such a list to be evidence about terminals someone checked rather than a claim about the ones nobody has. `RULINGS.md`'s B10 section names the six. **The rung missing even where the terminal has it is tmux's**, whose `focus-events` defaults to off: a terminal's own split has the rung and tmux without that setting does not, and a reader cannot tell from the screen which case they are in. **A fourth rung keeps the residual honest: any repaint that moves the bars retires the mark.** A mark is a claim about the screen it was resolved against, so when a tick changes the geometry every cell it named may belong to something else, and without it a pointer parked on the list's down button becomes the diff's up button lit on a control nobody pointed at. `input::hover_repainted` is that rule, and it deliberately does not try to tell one button from another, because the version that did was a tautology. It runs **between the layout and the paint that uses it**, since correcting the field after drawing fixes the state and not the screen, and on an idle tree there is no next paint to correct.

**A hover mark is the quietest thing that is still visible in its region.** That is what pays for the residual the ladder leaves: the pointer leaves the pane with the window still focused, on a tree nobody is writing to, and the last target stays lit until the pointer comes back. Accepted rather than fixed, because a stale mark at that weight costs a glance nothing and never competes with the caret, which means *the diff is in this file*.

**It is view state and never an action, which is what keeps B4 intact.** The mark is resolved from `Regions` in the loop and drawn, exactly as a pressed step button is; it is not a keymap entry, so no focus appears and every binding means what it would have meant. `crates/vigia/tests/input.rs::pointer_motion_over_a_laid_out_screen_is_still_no_action` holds that line: motion alone is still no act, which is what separates it from the drag B20 rules on.

**A drawn thumb is a published affordance, so both are draggable**, and a press anywhere on a track jumps to it. The scrollbar column is tested before the region containing it, or every drag would read as a wheel. **A track maps onto travel, not onto the whole**: the list's travel is its file count less its own height, the diff's is its total rows less a screenful. Mapping onto the whole leaves the last screenful's worth of track dead, since every fraction past the bound clamps to the same window, and the pointer reaches the bottom with the view still short of the end.

**Scroll position is `(file, offset within that file)`, never a row index.** A frame that changes something above the viewport therefore does not teleport the view. That is a correctness property rather than an implementation detail: with a row index, an agent writing to a file earlier in the list would yank the reader's position on every keystroke it makes.

**A position past the end of the diff resolves to the last screenful, not the last row.** The two are not the same place, and taking the second for the first draws one line of content over a blank screen while the header goes on truthfully saying how many files changed, which is one thing on screen contradicting the other two. A pager rests the final row at the *bottom* of the viewport and so does this. Resolving it is `View::collect`'s alone, because `App::view` stores the resolved position back on every frame, so there is one rule in one place rather than a clamp in the scroll path and another behind it. It is reachable two ways and **only one of them is scrolling**: the other is the diff shrinking under a position that was reasonable when it was taken, which is `git reset --hard`, a branch switch, or an agent reverting its own work. The walk back reads only the files the screen is about to draw, so I4 is untouched.

**It is deliberately not what `G` does**: `End` goes to the last *file* from its top. The cost argument for that expired when I4 was narrowed, since adding up every file's height is what `Frame::height` does once a tick, so a row-exact `End` is now affordable. The behaviour stands on the reason it should always have rested on: `g` and `G` are the two ends of the *file list*, the pair the header counts and the pinned region draws, and a `G` that landed mid-file would make the two keys mean different units.

**Follow mode, which is I5.** `less +F` semantics, and the toggle the README mockup already published: follow is **on at startup**, **any manual scroll disengages it**, and **`f` re-engages it and jumps straight to the newest change** rather than waiting for the next one. The footer shows `follow ▶` while it is engaged. Two boundaries are load bearing, because each is a way for the mode to be quietly wrong rather than visibly broken. A **terminal resize does not disengage**: it moves no viewport and expresses no intent, and a monitor beside an agent is resized constantly. And **`G` disengages rather than re-engaging**, because "jump to the last changed file" and "resume following" are different intents that would otherwise be the same key.

**The newest change is the file whose write landed last in the settled batch**, and the batch is the coalesced tick. A monitor cannot find that file by looking: `stat`-ing every changed file is the cost [#19](https://github.com/breferrari/vigia/issues/19) records as breaching I9 at scale, and I4 forbids reading files the frame does not draw. It does not have to look, because the filesystem event already carries the path, so following costs no read, no `stat` and no diff. When the named path is not in the diff — an index write, or an edit reverted before the tick landed — the view stays where it is, because there is no newest *change* to follow. **Follow lands on the change rather than on the heading, where those are not the same place.** A file whose diff is one screenful keeps I5's promise by accident of size, because the heading and the change are the same place; a file carrying a 76-line deletion under three one-line tweaks does not, and the element built to show a reader what an agent just did showed them a filename and some unchanged context instead. **The rule is one sentence: follow keeps the heading on the top row while the first changed line of the file's busiest hunk is already drawn from there, and puts that hunk's header on the top row when it is not.** The heading carries the path, the counts, the sigil and the heat strip, so it is spent only where it buys the change, and a reader with a taller pane is moved off it less often. *Ruled 2026-08-22, reader, from a live pane ([#257](https://github.com/breferrari/vigia/issues/257)).*

**The busiest hunk rather than the first**, which is the obvious reading and cannot reach this case at all: a block is a heading and then a header plus lines per hunk, so the first hunk's header is always row one and landing on it moves the pane by a row. **And a hunk rather than the heat strip's busiest slice**, which is the same intent in the wrong unit: a bucket names a working-tree line where a viewport needs a row, and the thing a row falls inside is a hunk. Ties keep the earlier hunk, and a file with nothing to land on keeps its heading.

**The test is the first changed *line* twice over, and testing the header instead is a real edge rather than a rounding of it.** A hunk opens with up to three unchanged lines, so a pane one row short of them draws the `@@` and none of what it changed, which is the reported symptom with the gate reporting it handled. A landing therefore needs the change to be **not drawn from the heading and drawn from the landing**, and the second half is what settles `Body::split`'s floor: a one-row diff region cannot show a changed line from anywhere, and one bare `@@` is strictly less than the heading it would replace.

**A landing fills the pane, where a jump does not.** A viewport reached by scrolling backs up rather than resting a short tail over blank rows, and one reached by a *jump* does not, because a jump is a claim about which file belongs on the top row. A landing's claim is weaker: that the change is **visible**, which any row it is drawn from satisfies. So it backs up, the change moves down the pane rather than off it, and the rows below are the diff's rather than blanks. Only a landing that moved the viewport, though; one that kept the heading is an ordinary jump.

**What this is not is the *newest* hunk, and that is the case to reopen on.** What a reader asks is *what did it just do*, and the diff alone cannot say: the newest hunk is the one that differs from the previous tick's diff, which is a comparison with staleness rules of its own. Busiest is never worse than the heading it replaces and is right in the shape reported. The case that would reopen it is the accumulating one, a rewrite from ten minutes ago outvoting the tweak that just landed, and the answer there is the comparison rather than a third heuristic.

**A landing belongs to the file it was armed for, and to no other.** It names a row *inside a file* while the viewport holds an index, and the changed set is renumbered by every advance: a file committed, an edit reverted, a branch switched. Ticks coalesce and only the paint is shared, so an advance can land between the follow that armed a landing and the frame that would resolve it, including on a tick that names no path at all, which a `.git/index` write is. So the request is applied only while the position still names the path the tick named, and a refusal **settles** it rather than holding it.

**It costs nothing, and the signature is what keeps that true.** `App::follow` takes `&Frame`, so following cannot diff, cannot read and cannot `stat`, which also means it cannot find the row: the loop advances, follows and only then draws, so at the moment of the jump the frame holds the previous tick's diff for the one file that just changed. The jump names the file and the walk that draws it resolves the row, from a diff it has already fetched, once. `tests/follow.rs::following_a_file_costs_no_diff_and_no_read` and `::landing_on_a_change_costs_no_extra_diff` are the gates. **How the chrome fits**, which is I6. One rule, and the layout follows from it: **a thing made of items breaks, a thing made of characters marks its edge, and content is neither.**

The **hint bar is a list**, so when the footer cannot hold both halves on one line it takes a **second line** rather than shortening anything. The state moves to the upper of the two and the hints keep the bottom row, so narrowing a pane never moves the hints out from under a reader's eye. It grows only while at least two body rows survive, and only when there is a state worth moving. A notice, which replaces the hints, inherits that whole line when there is one but **never causes it**: a notice is transient, and a footer that grew for one would jog the reader's diff. Below the width where even a full line holds the bar, it drops **whole hints** and never part of one: `q quit` first, then `? keys`, leaving `f follow` last.

**The bar is three items**: `q quit · f follow · ? keys`, twenty-three columns at its widest where the four-item bar was thirty-eight. What makes it defensible rather than merely shorter is B12: the keymap is on a sheet, so a bar naming four gestures of sixteen was giving a reader an arbitrary quarter of a table they can open in full. **So the bar is what it is for**: the way out, the state a reader can lose invisibly, and the door to everything else. `? keys` sits above `q quit`, because a reader who cannot find the keymap cannot find anything else, and below `f follow`, because a sheet nobody opened costs nothing while a follow mode nobody can see costs the screen. **The arrows are deliberately unadvertised**, named on the sheet and nowhere on the bar: `f follow` earns the last rung by being the one nobody would guess, and an arrow key is the one everybody guesses. *Ruled 2026-08-17, reader, from use ([#80](https://github.com/breferrari/vigia/issues/80)).*

**There is no bonus rung, and that is what the shorter bar bought.** The footer's height is decided by the widest bar a reader is owed, and every rung here is owed, so `HINT_BASELINE` is rung zero and no hint can buy a body row by existing. `JK files` is why the constant exists: it made the widest bar exactly forty columns, so the footer began taking a second line at the width I6 is named for, and every reader lost a body row to advice including the ones who never pressed `J`. **The state is two columns from the hints rather than one**: every other group on the row is two columns from the next, and at one column the state read as a fourth hint.

**Advice outlives instrumentation**, which is the rung the two status readouts join. `0.8ms frame` and the memory cell sit left of the state as one **diagnostics** group, dropping the memory cell first and the frame cell second, so both are gone before a single hint is. That is not the ladder rule repeated: the hints are how a reader *operates* the tool and the state is what the *tree* is doing, while these two describe **`vigia` itself**, which is the least of the three things a narrow pane owes anyone. Memory before frame time, because the frame cell reports a budget a reader can act on.

**Neither readout can change how many rows the footer takes**, and that is a rule rather than a consequence. `Footer::plan` decides its height from the state ladder alone, and the diagnostics take only what is left after the hints have their widest fitting rung. Two things would otherwise jog a reader's diff down a row and back for no reason they could see: the frame cell **does not exist on the first paint**, because no frame has completed to have a p99 of, and the memory cell does not exist on a platform with no cheap read.

**The footer's right-hand side carries three colours, and they are the picture's.** `assets/preview.svg` draws `0.8ms` and `24MiB` in its cyan, the word `frame` beside them in the same grey as the hints, and the follow marker in green. The shipped footer drew all of it in one grey, so the two numbers a reader *checks* and the marker saying the mode is on looked like the words a reader *reads*. §5.1's rule that a published artifact answering a question is the answer applies to colour exactly as it applied to layout. The position `N/M` keeps its grey: the picture gives no colour for it, and it is a place rather than a measurement. Both styles are **reused rather than named anew**, which keeps this a reading of the picture rather than a palette decision: the cyan is the one every other structural mark uses and the green is the diff's own added colour. Drawn as a **second pass over the cells** rather than as separate placements, which is load bearing: each readout is part of a token a ladder picks whole, so placing each colour separately would take the choice of what to draw away from the ladders and oblige the footer's width arithmetic to know about colour. Tinting afterwards cannot move a column.

**The pass must terminate and must not reach past the diagnostics**, and both are rulings rather than implementation notes because both were got wrong. A walk that asks whether a cell *opens* a measurement and whether it *carries* one has to consume the opening cell whatever it says: `>` answers yes and no, so on `>1s` the two questions spun against each other and the pane froze mid-frame. And the marker is found within the state's own columns, never the whole row, because a notice is an error string carrying a path and `▶` is a legal filename character.

**Both cells are a constant width whatever they say.** `0.8ms frame`, ` 12ms frame` and `999ms frame` are all eleven columns, with the number right-aligned inside them, so a value changing between frames never shuffles what is beside it. Past the field, magnitude gives way to a sigil rather than to precision: `>1s` for a frame and `>1GiB` for memory, because the exact value at those magnitudes tells a reader nothing the sigil does not, and a number that grew a column would move the footer under their eye.

**The header never grows**, and that is said of both sides rather than of one token. A worktree name is not a list and has nowhere to break, so it marks its edge like every other single token; the clause it leads *is* a thing made of items, and it breaks by dropping a whole rung rather than by taking a line. A second line could not guarantee a fit either way, and it would spend a body row on a maybe.

**The header is laid out by subject, the way the footer is.** Two facts about the **tree** on the left, the worktree name and then how much of that tree has changed, and the one fact about **`vigia` itself** on the right, which is whether the watch is still live. That is the footer's three-subject rule applied to the row at the other end of the screen. The count reads `changed` rather than `files` for a reason that only appears once it has moved: `vigia · 3 files` would be a **worse** claim than the one it replaced, since the repository has more than three files in it. Next to the name of a tree, a bare noun describes that tree; `changed` is what makes the number a fact *about* it, and it is one rule where there were two, because `changed` is a participle with no plural to inflect.

**The ladder keeps its order and changes only which side each rung is dropped from.** Widest first: `{worktree} · {N} changed` with the mode word, then the worktree name with the mode word, then the worktree name alone. That is the ladder rather than the whole list of screens, because the two sides degrade independently: a narrowing pane walks through **six** states, both facts and the word, the name and the word, a marked fragment of the name and the word, the word alone, the name alone, and a marked fragment alone.

**The left-hand side leads with the worktree, not the program**, which is the first of two deliberate departures from `assets/preview.svg`, the other being §5.1's element split. A title bar spends six of forty columns telling the reader which program they started, which is the one thing they already know; what they do not know from looking is *which tree*, the question that decides whether two panes side by side mean anything. And it is the worktree's own name **even when the path it was given does not contain one**: `vigia .` hands `gix` a workdir of `.`, which has no final component, so the header drew `.`. The path is resolved for **display** before its last component is taken, display only, because resolving it where the watch compares event paths would introduce `\\?\C:\` on Windows and `/private/var` on macOS ([#30](https://github.com/breferrari/vigia/issues/30)).

**The mode word sits on the right, alone.** The picture agrees with the shell on this row, so the deliberate departures stay at two.
| Mode | What it means |
|---|---|
| `watching` | the watch is live, so the screen follows the tree |
| `not watching` | the watch never armed, or it ended, so this is a still picture |

**Two words, and I1 is the reason rather than minimalism.** §5.1 read `watching` as implying at least a settling state and an idle one. It implies neither, because both are *durations* and this shell wakes only when something changes: `Watcher::next_tick` blocks until a burst has settled, so the shell is never awake **during** settling, and "idle" needs a wake that says nothing happened, which is the timer I1 forbids. Either word could come into existence and then never leave. **The word starts at `watching`, before the watch is armed**, because arming happens after first paint so the watch does not observe the shell's own setup reads; a third word for those microseconds would flicker on every launch to describe a state that always resolves the same way within one wake, and a genuine arming failure arrives as its own wake and corrects the word. **`not watching`, not `stalled` and not `still`**: it is the mockup's word negated, so a reader who has learned one has learned both, where `stalled` reads as temporary when this is not and `still` means both "motionless" and "continuing".

**The mode is state, so the reason for it is not.** A watch that ends puts `not watching` on the header **and** its error on the footer as a notice. The header carries what is durable, that this diff has stopped being live, and the notice carries which failure did it, which is not. **A dead watch is drawn loud while a live one stays quiet**: `watching` takes the header's dim grey, `not watching` takes the footer's alert. A state nobody can catch at a glance has not been reported, and §5 makes colour half the differentiator.

**The footer has three voices, and neither its colour nor its motion is invented.** *Ruled 2026-09-04, reader*, reported from the pane: every message on it was `alert` red, a clipboard receipt included, so the line said the same of a success and a failure. What a message **is** cannot be recovered from its text, and one call site produces two of them, so the voice travels from the producer.

| Voice | What it is | Colour | How the colour travels | Takes |
|---|---|---|---|---|
| Said | An act of the reader's, answering | `chrome` | left to right, like something being written | 550ms |
| Arrived | Unasked-for, nothing wrong | `note` | the whole line at once | 750ms |
| Alert | Something went wrong | `alert` | from both ends, closing | 450ms |

Three colours the palette already had: `note` is what this program spends on something that is not diff content, and an announcement is that.

**The transition is a crossfade, and the glyphs never move.** A status bar is static and its text is the only thing on it that changes, so what arrives is a *change of that text*, not an entrance. Revealing characters progressively was tried and reported from the pane: it leaves the line unreadable for as long as it runs, which is the one thing a message must never be. So the letters are there from the first frame and only the colour travels, eased at both ends, over a duration a reader can watch. Speed carries the urgency, as it does on a phone: the warning is quickest because it has to be read now, the announcement slowest because nobody asked for it.

**Where the depth leaves both ends the same colour there is no transition at all**, and the message simply appears. That is the same answer a phone gives to reduced motion, and it is why the motion is not built on the glyph channel to survive: a transition nobody can see is better skipped than replaced by one that makes the text harder to read.

**A message replaces the one before it without cutting it off.** The outgoing message runs its departure first and the new one begins when the line is free, so the change is always one thing fading into another. `NOTICE_LINGER` is 4.5 seconds and is the **whole** of a message's time on the line: the departure comes out of it rather than after it, so the slowest voice is 750ms in, three seconds settled, and 750ms out.

**A newer published version is one footer notice, once, and nothing else.** *Ruled 2026-09-04, reader* ([#401](https://github.com/breferrari/vigia/issues/401)). One request at startup, on a thread, so first paint never waits on it, and one `NOTICE_LINGER` notice naming the version when crates.io answers with a higher one. Already current, offline, refused, slow, unparseable, and an architecture the TLS provider will not compile on are one outcome between them: **silence**, because a network problem is not the reader's problem and a monitor that nags is a monitor that gets closed. It arms no clock of its own, which is what keeps I1 whole: the check answers once and cannot repeat, and the deadline the notice sets is the one every notice already sets. `VIGIA_UPDATE=off` declines it, and a value this does not understand is refused before the terminal is taken rather than quietly ignored.

**The mode word outranks everything else wherever it fits at all**, which is why it holds the side placed first: the count summarises a body that is on screen and can be recovered by counting it, and whether the pane is still live is recoverable from nowhere. That matters most at exactly the widths where the body has nothing in it to count. **It is not, however, the last thing standing on the row.** The two sides have independent budgets: the word is all-or-nothing at its own width, while the name marks its edge at any width above zero. So on a live watch the name has the row alone from 5 to 7 columns, the word takes it alone from 8, a marked fragment of the name rejoins it at 10, and both are drawn whole from 14; with `not watching`, four columns wider, those are 5 to 11, 12, 14 and 18. **Those numbers are gated by `crates/vigia/tests/legibility.rs::the_header_degrades_at_the_widths_the_spec_records`**, which is a rule rather than a courtesy: they were wrong here first, and a measurement quoted in prose and nowhere else drifts from the thing it measured, silently, because no document fails.

**A file whose language this process has not met yet arrives plain and colours a moment later.** The reader sees the text immediately, at the pane's ordinary few milliseconds, and the colour follows when the grammar has compiled off the frame: a cold screenful measures 124ms under Rust and 695ms under Markdown. **What it replaces is not colour but a freeze**, since the loop is single-threaded and the pane stopped answering while the grammar compiled. This is I7's opening rule generalised rather than a new one: I7 already draws the first frame of a process without colour on the grounds that a compile belongs behind a screen that has content on it, and the same reasoning now applies to the frame that meets a *grammar* rather than only to the one that starts a process. **Only the hunks under that grammar are plain**, never the pane, and it happens once per grammar per session. **And the case a reader is actually watching should not flicker at all**, which is why the three languages the repository leads with are compiled at launch from the index: a pane is very often opened on a clean tree *before* the agent writes, so a warm over the changed set has nothing to warm, and what a repository is mostly made of is the best available guess at what will be written next. *Ruled 2026-08-21, session ([#129](https://github.com/breferrari/vigia/issues/129)).* **The count is nothing at all when it is zero**, the same way a position is nothing when there is no diff to be positioned within: `0 changed` spends columns restating what the empty state says below in words. **And there is no fourth fact.** The header carries the worktree, the changed-file count and the mode word, and it does not carry a repository-wide `+`/`-` total, which is a ruling rather than an omission ([#49](https://github.com/breferrari/vigia/issues/49)): a total needs every changed file's diff, which puts first paint back in proportion to the size of the diff and is exactly what I4 forbids, and computing it behind the frame to dodge that needs a wake no filesystem event caused, which is I1's.

**The mode word is never cut.** It is drawn whole or dropped, which is stricter than the marking rule the rest of the header follows: `wat›` is a state a reader cannot read, and unlike a path it has no half that identifies it. What delivers that is `put_right`, which draws its token whole or not at all, rather than a ladder of the word's own.

**The empty state**, which is B3. This is the screen the tool sits on most of the time, and the first thing anyone sees when they open it beside an agent that has not written yet, where a blank pane and a hang look identical. Four facts, two of which the header already carries, so the body spends one line rather than four.

The line reads `no unstaged changes`, and since B17 it names the other run when that run has work: `no unstaged changes · 3 staged`, which is what tells a clean tree from a fully staged one. With both runs drawn and nothing in either it names both: `no staged or unstaged changes`. **It does not read `working tree clean`**: that phrase is git's, and git means index-against-HEAD as well as tree-against-index, so a worktree with every change staged draws zero files and would be told it is clean while `git status` says the opposite. `no unstaged changes` is exactly what zero files means here, untracked files included, since an untracked file is unstaged too.

**The branch is orientation, not the comparison**, and it lives on the header rather than this line ([#158](https://github.com/breferrari/vigia/issues/158)). Nothing about it changes what is diffed, and it is named anyway because two agents on two worktrees of one repository are otherwise identical on screen, which is the multi-worktree case §4 defers rather than rejects. A detached HEAD names no branch and the line drops it rather than inventing one: `HEAD@abc123` would put a commit id in a monitor that shows no commits. It costs one `.git/HEAD` read, taken only on frames that draw no diff, so I4 holds because the thing read is the thing drawn and the frame that draws it is the cheapest there is.

**A token that had to lose characters says so, in the direction it lost them.** `…` on the **left** means the beginning is gone, and only a file path uses it, because the end of a path is what names the file. `›` on the **right** means it continues past the edge: the worktree name, a notice, a hunk header, a note, the empty-state line. A hunk header silently cut to `@@ -258,7 +25` reads as a different line number, which is the failure this closes.

**A blank row closes every file's block but the last.** The stream has one boundary per changed file and drew none of them, while the boundary between the two **regions** one level up gets a rule of its own. **Trailing rather than leading, and that is what keeps the map's promises**: every jump here resolves to `Position { file, row: 0 }`, so row zero of a file has to be its heading, and a leading blank would put one above every heading a reader jumped to. **And not after the last file, which is the exception rather than the tidy rule**, because the rule about resting on the last **screenful** makes the bottom of the diff content, gated by `crates/vigia/tests/scroll.rs::the_bottom_of_the_diff_is_content_rather_than_blank`. **A blank row and not a rule**, because B11 has ruled the rule between the regions stays bare, so a second rule inside the stream would mean something different on the same screen and §5.3's furniture law would run it full-bleed. Space is the quietest thing that is still a boundary. *Ruled 2026-08-15, session ([#165](https://github.com/breferrari/vigia/issues/165)).* **The blank is counted, which is the half that had no gate.** `view::rows_of` and `view::span_of` are the counting twins the row-exact scrollbar is scaled against, and the blank belongs to neither: whether a file is followed by one is a fact about its **position**, where both are handed a file. `view::gap_rows` is that fact written once, and a caller holding a position asks for a **block** rather than adding the term.

**A clipped diff line is marked, and is not a truncated label.** Content cannot wrap by default, because a wrapped line moves every line below it and the shape of the screen stops meaning anything. Nor can it elide, because unlike a label no part of it is the identifying part. So an unwrapped line is clipped and marked `›`, and I6's *truncated-to-useless labels* is read as being about labels rather than about content.

**A line wraps as far as it needs, and the only ceiling is the pane.** A reader who presses `w` means *show me the line*, so a mode that shows part of it is the defect this ruling was opened on, one rung smaller. **It reaches content rows and nothing else**: a file heading, a hunk header, a note and the empty-state line are labels, they keep their own marks in both modes. *§11.2 B19, ruled 2026-08-26, reader, from the pane ([#272](https://github.com/breferrari/vigia/issues/272)).*

**A continuation row blanks its gutter and draws `↳` in its sigil column, in the row's own diff ink.** The blank line number is `bat --style=numbers`' own signal and is the cheap half, since a real line always has a number. It is not enough on its own, because `gutter_width` drops the gutter **entirely** below `MIN_TEXT_WIDTH`'s floor, which is precisely the narrow pane this gesture exists for, so at forty columns a continuation carrying a repeated sigil and no number would read as a line of its own. **The continuation is indented to its own line's indent, capped at half the content width**, which is Neovim's `'breakindent'` and is [#164](https://github.com/breferrari/vigia/issues/164) one rung down rather than a decoration: that ruling made a content row's origin uniform down the block, and an unindented continuation breaks the block shape of exactly the nested code this tool is pointed at. The cap is what stops a deeply indented line buying a second row with nothing on it. **The wash and the left bar cover both rows**, since a band that stopped at the first would make a wrapped removal read as ending early.

**`w` wraps and unwraps, and it starts off.** A keystroke rather than a setting, which is B6 keeping this tool configured by gesture, and off on launch for [#204](https://github.com/breferrari/vigia/issues/204)'s reason: every neighbour that wraps is given the whole terminal and this one is built for half of it, so the mode with a price is the one asked for. **What it does not move is what the scrollbar counts**, which is B19's own ruling rather than an omission: the bar counts the diff's rows and not the terminal's. **The trim at the bottom is a display offset and moves nothing stored**, which is what keeps the end of a wrapped diff a place a reader can scroll out of. It costs one narrow thing: where a wrapped last screenful spans two files the first row drawn can belong to the file after the one the position names, so the caret in the list marks the reader's position rather than the topmost drawn row.

**A press washes its row, a drag every row it crosses and no more than its region's, and the button coming up sends them.** Whole rows, because the copy is whole lines, and a wash over part of a row would promise a substring the send does not carry. **Never the drawn row**, which elides where I6 is aimed and clips where a line runs past the pane: the copy is resolved against the row model rather than read out of the cells, so it carries a clipped line's tail, a wrapped line as one line, a heading's path whole and a hunk header's `@@`. By path and not index, since a tick rebuilds the list mid-batch. **The payload is the frame's rather than the gesture's**: what goes is what the last painted frame washed, so the release's own coordinates do not extend the span, and a write mid-drag does not clear the wash, since the span is re-resolved against every frame. **The wash lasts exactly as long as the gesture**, so nothing is remembered once the button is up. While the button is down `Esc` cancels the gesture and sends nothing, which is its rung under the sheet's and over quitting. A span with no text in it sends nothing: an empty OSC 52 write clears what the reader had. The escape goes to the backend rather than a cell, since it draws nothing. The footer says **sent**, not copied, because OSC 52 has no reply, and a failed write is reported there rather than ending the pane. It clears on a one-shot deadline `Shell::patience` folds beside the other three, and sits over a lasting warning rather than replacing it. *§11.2 B20.*


**The branch is drawn on every frame.** B3 gave it to the empty state because nothing else on the pane named it, and it answers *which line of work*, which is the one thing here a reader cannot reconstruct from the body: the list says what changed and the diff says how, and neither says against what. **And `branch_for`'s guard is gone, which is the rule surviving its instance.** It read *never touch a file the frame does not draw*, and its instance was that only the empty state names a branch. Drawing the branch always makes that premise false: the read is now one the frame **is** going to draw, which is what the rule permits. `crates/vigia/tests/reads.rs` asserts the other direction, that every frame reads it. *Ruled 2026-08-17, session ([#158](https://github.com/breferrari/vigia/issues/158)).* **A clear column stands between the sigil and the line, and it does not ladder.** It is the fifth deliberate departure from `assets/preview.svg` this document records: the mockup places the line number end-anchored, the sigil beside it and every content origin a further cell in. **It does not degrade where every other spacing decision here does**, because the sigil column **is the diff signal** at any depth or on any palette that cannot wash the row, which §5.1's tinted-row cell states and `crates/vigia/tests/colour.rs` gates, so a column that keeps that signal legible is part of the signal rather than decoration beside it, and I6's *every cell is contested* does not reach it. **And it is uniform rather than conditional on the line**, which is the part worth stating because the cheaper rule is so nearly right: the gap earns its column only where a line has no leading whitespace of its own, but drawing it only for unindented lines would make a content row's origin a function of its *contents*, which is the intermittent layout this section has already refused twice. **What it costs, measured**: one column of every content row, landing hardest at the forty I6 is named for, where the reference fixture goes from **one** clipped line to **three** while the eighty-column pane clips nothing either way. The hunk header, the file heading and both regions' chrome are untouched. *Ruled 2026-08-15, session, towards the picture ([#164](https://github.com/breferrari/vigia/issues/164)).*

**How a diff line is coloured**, which is what I2b pays for. Content is syntax highlighted, and the mockup had already ruled how: added, removed and context lines all carry the same classes, the sigil is green or red, and the line number stays faint. Only content is highlighted; a file heading, a hunk header and a note are chrome. *Ruled 2026-07-30, session, following the picture literally per §5.1.*

Three things follow, and each is a constraint rather than a preference.

**The engine emits meanings, not colours.** `vigia-core` maps a syntax scope onto one of nine classes and stops. Which colour a class gets is the shell's. A core that emitted truecolour would have settled the palette question in the one place §6 says has no terminal in it, and pre-empted the 256-colour degradation path before anyone wrote it.

**The diff signal degrades at sixteen colours, to the sigil column *and* the left bar.** What separates an added line from a context line in the mockup is the row tint and the left bar of §5.1. Sixteen foreground-only colours cannot draw the **tint**; they can draw the **bar** ([#218](https://github.com/breferrari/vigia/issues/218)), because it is a background on a blank column of margin with no text over it.

**A file type nothing recognises is not an error.** The syntax is resolved by §6's five steps, and anything unresolved draws exactly as it did before there was highlighting at all. A monitor that refused a file because it could not colour it would have inverted its own job.

**How recency is drawn**, which is I10 and which §5.1 asked for as two separate things. It is **one ladder with three rungs**, read from one store through one lookup, and each rung is an intensity on the file's own heading:

| Rung | What it means | How it draws |
|---|---|---|
| **pulse** | named by the most recent tick **and** holding ink in the newest samples | brightest |
| **live** | has a sample inside the 120-second window | plain |
| **cold** | nothing in the window, so nothing is tracked for it | faintest |

**The top rung is not a duration.** §5.1 reads the mockup's persisting mark as a decay, and a decay measured against a wall clock has to be *seen* decaying, which once meant a redraw nothing schedules. The window ages on a clock now and I1's licence reaches it, so what carries the ruling is the grid rather than the invariant: the mark's life is the sample boundary, as the pulse paragraph above states.

**Cold is not a fourth rule.** A path with nothing left in the window is dropped from the store entirely, per I10, so *cold* and *untracked* are the same state. That is also what the **first** frame of a session looks like: a worktree that was already dirty draws every row cold, because a monitor has no way to know what happened before it was looking, and inventing a recency for it would light up rows nothing has touched. **Three is a property of the store, not of the palette, and this file said otherwise for a phase.** §5.1 and `theme.rs` both promised that the *real* gradient arrives with [#11](https://github.com/breferrari/vigia/issues/11)'s truecolour, on the reasoning that sixteen foreground-only colours have only bold, plain and dim to spend. The arithmetic is right and the conclusion does not follow. What #11 widens is how many distinct colours a rung may be drawn *in*; what decides how many rungs there **are** is `Recency`, and it has three variants because the store can answer exactly three questions about a path: is it in the newest tick, is it anywhere in the window, or is it not tracked at all. A fourth rung would have to mean *how far through the window*, which nothing currently computes and which the row above makes expensive to add honestly: the window is real time, the sampling is event-driven, and a fraction of it read on a quiet tree is a number that ages without being redrawn. So #11 replaced bold, plain and dim with three chosen luminances, and stopped there. Widening the ladder is an I10 change with a budget attached, not a theme.

The general shape, and it is the second time this file has recorded it: **a limit blamed on the rendering layer was a limit of the data behind it.** §5.2 caught the mirror image, an expensive-looking property that turned out to be a by-product already computed. Before assigning a limitation to the thing that draws, check what the thing that supplies can actually distinguish.

**The sparkline never draws a partial bucket or a squeezed strip**, and until 2026-08-20 that was because it was read as a thing made of items and **broke**: it dropped whole buckets, oldest first. **It is a projection now** ([#234](https://github.com/breferrari/vigia/issues/234)), so a narrower rung sums adjacent source buckets and draws the whole window at a lower resolution, which is the clause below stated for a second element rather than a new rule.

**The reason the old ruling was reversed rather than outvoted.** The clause below was written on 2026-08-16, and the worktree churn band landed the same day; both postdate the sparkline's ruling, which was made when nothing else on screen drew the same window. A sparkline's items are slices of one **window**, in order, and the set of them is the claim, so a strip showing the newest half of a window beside a band drawing all of it is the same misdescription the clause below refuses one axis over. Measured before it was believed, over forty seeded series in three work patterns: dropping the oldest half costs **shape as well as span**, taking a twelve-bucket strip from 5.75 distinct drawn heights to 5.25 on a steady worktree, and what carries the shape is the number of drawn columns rather than the period each covers. So the count became a rung and every rung covers the window. `crates/vigia/tests/legibility.rs::the_sparkline_reprojects_rather_than_dropping_buckets` is the gate, over a window written at both ends and quiet between them, which is the one shape where truncation and re-projection differ.

**And the bound the retired ceiling left is the window rather than a period.** #161 ruled twelve a ceiling because a drawn bucket had to stay coarser than a churn-band column; [#232](https://github.com/breferrari/vigia/issues/232) retired the band's fixed period and the bound with it. What replaced it is that both elements read one store over one window and a reader has both on screen, so what has to agree is the **window they cover**: the band covers all of it at every width, and so does the sparkline at every rung. `crates/vigia/tests/masthead.rs::the_band_is_never_coarser_than_a_drawn_sparkline_bucket` is what compares them, where the retired gate compared two constants.

**One consequence is a denominator rather than a width, and it is the half that is easy to get wrong.** A drawn bucket summing `n` source ones has to be measured against what `n` source buckets are worth, and that is **not** the finest figure multiplied: `scale_of` averages the non-empty values and grouping merges empties into their neighbours, so multiplying is exact on a busy worktree and wrong by up to `n` on a quiet one. Measured on a sparse fixture the estimate moved a cell by as much as **four rungs of the eight-level ramp**, so `vigia_core::History` computes one figure per grouping in the walk it already makes, and `vigia_core::SPARK_GROUPS` is the ladder it computes them for.

**The heat strip is a fourth kind of thing, and the rule needed a third clause to say so.** *A thing made of items breaks, a thing made of characters marks its edge, and content is neither* covers a list, a token and a line. A heat strip is made of items and is **not a list**: its items are slices of one file, in order, and the set of them *is* the claim. Dropping the last six would draw the first half of a file as though it were the whole of it, and a reader would conclude the tail is untouched. Less detail is honest; a prefix presented as a whole is not.

So **a projection re-projects rather than dropping items**: a narrower rung sums adjacent slices and classifies the sums, which at halves is exact. Twenty-four slices, then twelve, then six, then none. **The source resolution and the drawn count stopped being one number on 2026-08-18** ([#161](https://github.com/breferrari/vigia/issues/161)): `heat_at` groups `HEAT_BUCKETS / width`, so the source is the ceiling on this ladder, and doubling it is what lets a pane wide enough to deserve it draw a finer strip. **Twelve is a rung now rather than a constant**, which keeps §5.1's ruling instead of overturning it: what `assets/preview.svg` answers is how many slices a pane draws **at the picture's own width**, its comment records that width as 109 columns, and `crates/vigia/tests/legibility.rs::the_pictured_width_still_draws_twelve_slices` is what turned that from a sentence into a gate. **What bounds the ladder from here is the projection and not the layout**: below a source of 48 a file shorter than the strip draws a solid change as dashes, because consecutive lines land on non-adjacent slices, so the 48-slice rung waits on [#230](https://github.com/breferrari/vigia/issues/230) rather than on a width. `crates/vigia/tests/legibility.rs` gates it with a file changed at both ends and quiet in the middle, which is the one shape where truncation and re-projection differ, and it reads **cell colours** rather than symbols because every slice draws the same block.

**And the two strips scale against different things, deliberately.** A sparkline's height is measured against `scale_of`'s figure over every bucket **on screen**, because the question a reader asks down a file list is which file is busiest, and a row scaled against itself draws every file at full height the moment it is the busiest thing it has ever been. A heat slice's intensity is measured against the busiest slice **of its own file**, because the question is where in *this* file the work is, and the neighbouring rows have nothing to do with it. One is a comparison down the list, the other across a row. Its heights are scaled against that one figure **on screen** rather than against each row's own maximum, because scaling per row draws every file at full height the moment it is the busiest thing it has ever been, which answers a question nobody asked while destroying the one comparison a file list is for.

**A sparkline bucket with no writes draws a track, and a file with no churn is the all-empty case.** Drawing no strip at all buys nothing: the reserved-slot ruling earlier in this section takes the slot from the pane whether or not a row can fill it, so the row is spent either way and "nothing" costs exactly what "a track" costs. Replaced 2026-08-03 ([#78](https://github.com/breferrari/vigia/issues/78)). §5.1 carries the ruling and why the track is `_` rather than the ramp's floor.

**The heat strip's empty case is not the same case, and its opposite ruling stands.** `heat_at` draws nothing for a file with no line diff at all, because a strip of pure track there would say *"this file is in the diff and I cannot tell you where"*. That is an **epistemic gap**: the row asserts the file changed, and the strip cannot place it. A sparkline's empty state is a **fact** the store actually holds, that nothing has been written since the watch opened, so the two elements draw opposite conclusions from the same-looking input and both are honest. The distinction is what keeps #78 from being an argument for changing the strip too.

**And no glance element may take a heading below twelve columns of path.** The counters, the pulse, the strip and the sparkline are all placed from the right, against a floor the path keeps; which of them survives a given width is the layout table's business rather than a per-row allocation, and the order is the one recorded above. A row reduced to `M …` would have stopped naming its own file, which is the truncated-to-useless shape I6 forbids, arrived at by decoration rather than by narrowing.

**CLI.** One optional positional path, defaulting to the working directory. **One flag, `--version` (and `-V`), which prints `vigia <version>` and exits successfully**, and every other argument beginning with `-` is refused with one line naming that fact rather than being taken as a path, so `vigia --colour=never` is told what the surface is instead of being told `--colour=never` is not a repository. **A second argument is refused too**, which this line said implicitly and nothing enforced until [#12](https://github.com/breferrari/vigia/issues/12): the classifier saw only the first argument, so `vigia . --colour=never` watched `.` and dropped the flag in silence, which is a worse answer than the refusal a flag gets alone because the tool starts and draws and so appears to have accepted it. Arity is part of the surface, so the classifier takes the whole argument list rather than one of it. That is not `--help` implemented; B6 leaves the question of whether it should be, and rules everything else about this line, including why the version query is not the thing it forbids. The version is `CARGO_PKG_VERSION`, so the string cannot drift from the manifest the release was cut from, and the classification lives in the library rather than in `main.rs` because §7 makes the test suite the proof and a test cannot import a `main.rs`.

**Configuration is two files and one environment variable**, which is B6 ruled 2026-07-31, amended the same day, and amended again 2026-08-25 by [#306](https://github.com/breferrari/vigia/issues/306). The CLI gains nothing either way. The files are a **palette** and a set of **view defaults**, and they are separate for a reason stated below that is mechanical rather than tidy.

**A palette is a preference, so it lives in a file.** `~/.config/vigia/theme` is read when nothing overrides it, resolved from `HOME` or `USERPROFILE`, which is **one** rule rather than one per platform: no XDG matrix, no `%APPDATA%` special case, no discovery crate. `VIGIA_THEME` still names a built-in or points at a file, and still wins, because a variable is how you say "not this time" without editing anything.

**A colour depth is not a preference, it is a property of the terminal you are in right now.** One machine, one user, one afternoon: this pane is truecolour, that one is an `ssh` into something ancient, the third is CI. A file gives all three the same answer and is wrong for two of them. So `VIGIA_COLOR` stays a variable, which is the same reasoning that makes `NO_COLOR` one.

**A font is the same kind of fact as a colour depth, so `VIGIA_GLYPHS` is a second variable and not a second setting.** Added 2026-08-17 ([#159](https://github.com/breferrari/vigia/issues/159)). It takes `block`, `braille`, `octant` or `auto`, and it overrides a detection that reads the terminal's identity exactly as the one above does. **B6's count is unchanged by it, for B6's own reason**: that ruling counts one environment variable of *configuration*, which is `VIGIA_THEME`, and a variable saying what the terminal in front of you can draw configures nothing. The test is the one the paragraph above states, and a font passes it the same way a depth does: a file would give three panes on one machine the same answer and be wrong for two of them. **Refused rather than ignored** when the value is not one of the four, on `VIGIA_COLOR`'s rule that a reader who set a variable and got no effect cannot guess that it was silently discarded.

The amendment costs less than B6 assumed because **the format and the parser already existed**: `VIGIA_THEME` has always been able to point at a theme file. What was added is a place to look, not a surface. And it removes a step rather than adding one, since a preference set once now survives a new shell.

**The view toggles are a preference too, so they live in a file as well: `~/.config/vigia/config`.** Added 2026-08-25 ([#306](https://github.com/breferrari/vigia/issues/306)). Five keys, `masthead`, `rail`, `single`, `staged` and `wrap` (the fourth added with §11.2 B17 and the fifth with B19), each `on` or `off`, in the theme file's own grammar: one key per line, `#` comments, a byte order mark stripped, an unknown key **refused** rather than dropped, and every error naming its 1-based line. Absent is not an error; unreadable is. It is read where the palette is, before the terminal is taken, so a file that does not parse is said on a screen the reader can still see.

**A second file rather than three more keys in the first, and the reason is a defect rather than a preference.** `VIGIA_THEME` is resolved before the theme file is opened and a built-in name wins outright, so `VIGIA_THEME=dark` never reads that file at all. View keys inside it would be discarded, silently, by a reader naming a palette for one session — on a gesture with nothing to do with the settings it would lose. What the two files share is everything that costs something: one format, one discovery rule, one error path. What they do not share is a subject.

**`follow` is not a key, and that is I5 rather than an oversight.** *Correct with zero interaction* is a promise about the program, and a file able to turn follow off would make it a promise about one reader's configuration. `f` is how a session says otherwise, which is a session's choice about a session. The three keys that are there have in common that every combination of them is a legitimate pane.

**And no variable joins them**, so B6's count of one is unchanged. A variable is how you say *not this time* without editing anything, which is what `VIGIA_THEME` is for; here that sentence is already spoken by `m`, `r` and `s`, one press each, named on the gestures sheet. A variable would be a second spelling of something the pane says better.

**`rail on` below 134 columns sets the request and draws nothing**, which is §11.2 B14 unchanged: the request survives a pane too narrow to honour it, so a reader who configured a rail and opened a narrow pane gets one the moment it widens. `Chrome::rail` is what the file sets and `Body::rail` is what the pane can give.

**And the monitor writes nothing of its own.** Today that is nothing at all: not into the worktree, not into a state directory, not into `.git`. §11.2 B21 opens one exception, ruled and not yet built: what the reader typed goes to the state directory on the reader's gesture, and nothing else is ever written. Its build extends the gate below to a snapshot of that directory, still asserting zero writes across the same drive, with a sibling asserting that one gesture writes exactly one file. **Reading a second file does not touch that**, which is worth saying because B7 rests on it: the claim is about writes, and both files are opened read-only, once, before the screen is taken.

B7 ruled 2026-08-05, and it is stated here because it was load-bearing in two places before it was a rule in any: §6 makes the settle margin a table lookup rather than a measurement on the grounds that measuring would need a probe write, and §10's settle-margin bullet rests the whole 2-second constant on *"a monitor never writes, so it only ever sees the gaps its user's tools happened to leave"*. Both arguments were true because `vigia` happens to open no file for writing, which is nobody's decision. A cache, a lock file or a crash dump added in good faith would have made two recorded rulings quietly wrong, and nothing would have said so.

**It is a rule about the filesystem, and deliberately not about what the process emits.** Bytes going to the terminal this program draws into are a different surface with different costs, and reading this rule as covering them would foreclose questions it has no business deciding: [#120](https://github.com/breferrari/vigia/issues/120) asks about OSC 8 links on paths and a yank key over OSC 52, both pure emission, and it is right to treat those as outside this line rather than settled by it. Where the two meet is that neither may become a *reason* to write: a clipboard fallback needing a temp file, or a link needing a resolved path cached to disk, is this rule's business again. **Both were ruled 2026-08-15 and both were declined, as §11.2 B8** — which is where a reader following this pointer should go, and neither decline rests on this rule, exactly as this paragraph required.

**The mechanism a reader revisiting B7 needs, because it is the part that is not obvious.** A log inside the worktree is not untidy, it is a **self-sustaining wake loop**: the write is a filesystem event, the event is a tick, the tick is a frame, and the frame writes again, at frame rate, for as long as the process lives. `vigia-core`'s event filter decides how visible that is, and of the four places a write can land it hides three. A path *outside* the worktree fails `strip_prefix` and is dropped. A path inside it and **gitignored** is dropped by the exclude rules. A path inside `.git` is dropped unless its file name is `index`, which is the one file there that changes a diff. A path inside the worktree and **not** ignored is accepted. So the guard a writing monitor would need is not a convention about where the file goes; it is the worktree root resolved before the file is opened, and a refusal — which is a behaviour, not a detail, and is one of the five B7 counts.

**Where an instrument goes instead, since declining one is not the same as having none.** The harness, which is where every other measurement of this product already lives: the soak is `vigia::run` with the terminal removed (§7), and `VIGIA_BUDGET_SLACK` is the standing precedent for a variable the tests read and the binary does not, so a measurement switch can cost the product surface nothing. What the *reader* gets is the footer's own readouts, which is the other half of the same split and is §5.1's business rather than this paragraph's.

Gated by `crates/vigia/tests/writes.rs`, over every entry under a fixture root with `.git` included and the root itself stamped, across a first paint, six reader actions, a second tick and the grammar warmer **joined** rather than detached, because a write that lands after the comparison is a gate that passed by racing. One thing a reading could have got wrong was checked rather than assumed: `gix`'s status walk is never asked to write the index — `write_index` is called nowhere in `crates/` — and the gate confirms it empirically, so a monitor that reads a working tree many times a second leaves it byte for byte as it found it. Both directions are tested, per §7: a sibling gate writes a file and asserts the comparison **reports** it, because a comparator that cannot say "something moved" has not been tested.

### How colour degrades

`SPEC.md` §5 makes shape and colour the whole differentiator, so a palette that assumed 24-bit colour would be a product that silently stops working on the terminals that do not have it. §10 named that and left it open. This is the answer, and it is **two axes rather than a fallback chain**.

**The palette decides what may be drawn. The depth decides how finely it can be expressed.** Both have to allow an element before it appears, and they genuinely disagree: `ansi` refuses a row wash at *every* depth, because a wash has to assume a background and that palette's entire contract is that it assumes none, while `dark` draws one wherever the depth can express it.

Three palettes ship. **The default is decided by the terminal's own answer since [#325](https://github.com/breferrari/vigia/issues/325)** (§11.2 B18): at startup, before the event reader exists, the shell asks OSC 11 and waits at most 150ms, and a background that answers picks `dark` or `light`. **`ansi` is the fallback**, unchanged from what shipped before there was a choice: every colour in it is one of the sixteen *names*, so it resolves to whatever the reader's own terminal scheme says and `vigia` matches the pane beside it instead of fighting it. It is the only palette that is correct on a background nothing has detected, which since #325 means a terminal that stayed silent: over ssh, under a multiplexer that swallows the query, on Windows where none is sent. This paragraph said the round-trip was one "this shell does not make" and that clause is what #325 retired; the reasoning it carried was always about the silent case, and there it holds. `dark` is `assets/preview.svg` read out of the file rather than approximated. `light` is the same design re-picked at light-background luminance, with every ramp reversed, because on white it is the dark end that has contrast to spend.

The depth ladder, and what each rung loses:

| Rung | Foreground | Background |
|---|---|---|
| truecolour | 24-bit, as authored | as authored |
| 256 | quantised to the xterm palette | **dropped** |
| 16 | nearest of the sixteen names | dropped |
| none | dropped | dropped |

**A background needs 24-bit and a foreground does not**, and that asymmetry is the one thing here worth arguing with. §5.1 already records that a quantised background is a solid block rather than a tint: the darkest available green behind a line of code is a slab, and a slab destroys the syntax colours sitting on it. Worse than no tint. So the row wash needs the top rung while the text goes all the way down to sixteen, and below it the diff signal narrows back to the sigil column exactly as §11.1 recorded before #11.

**That boundary sat at 256 for a phase and it took a screen to move.** The cube has six levels per axis and its darkest two are 0 and 95, so a *subtle* colour has nowhere to land: `#1b3d29` quantises to `#005f00` and `#45222a` to `#5f0000`, saturated primaries at roughly two and a half times the authored luminance. Over a hunk that reads as a strong tint and the report would have been "the colour looks wrong". Over a **newly added file, where every row is an addition**, it is a screenful of flat green, and §5's whole claim is that colour carries signal. Reported 2026-08-03 with two photographs of it. The argument was already written here as the reason Windows detects 24-bit rather than 256; what was missing was applying it to the rung itself.

**The grey ramp is not the escape**, and it is worth naming because it is the obvious next idea. It is far nearer in distance than the cube, and it is where the quantiser would send a desaturated wash if its chroma gate did not stop it. But `#1b3d29` and `#45222a` average to the *same* grey, so an added row and a removed row would be one colour, which is the one thing §5 says may never happen at any rung that has colour at all. There is no honest wash below 24-bit. A reader whose terminal draws more than detection can prove says so with `VIGIA_COLOR`, and inside `tmux` that also needs the multiplexer to pass 24-bit through rather than approximate it.

Detection is a precedence chain, first answer wins: `VIGIA_COLOR`, then `NO_COLOR`, then `TERM=dumb`, then `COLORTERM` claiming 24-bit, then **`TERM_PROGRAM`**, then **Windows with `WT_SESSION`**, then `TERM` promising 24-bit, then `TERM` containing `256color`, then **Windows**, then sixteen.

**A terminal that names itself sits above `TERM`, and that ordering was learned rather than designed.** Git Bash and MSYS export `TERM=xterm-256color`, so a chain that read `TERM` first sent the most common shell for this repo to 256, where a subtle colour has nowhere to land: the xterm cube's darkest axis levels are 0 and 95 with nothing between, so a row wash of `#1b3d29` quantises to `#005f00`, a saturated primary rather than a tint. A terminal that names itself is better evidence than a variable describing a terminfo entry.

**That ruling was written for `WT_SESSION` and it generalises, which is what `TERM_PROGRAM` is doing here.** A chain with two positive signals on a Unix has both of them fail in the arrangement §1 describes as the whole point of the tool. `COLORTERM` is the only convention for claiming 24-bit and **nothing propagates it**: `ssh` forwards `TERM` alone, and a multiplexer replaces `TERM` with an entry of its own. `tmux` at its default `default-terminal screen` is the ordinary case, and `screen` contains neither `256color` nor anything else the chain read, so a reader running an agent in one pane and `vigia` in the pane beside it landed on sixteen. Sixteen drops backgrounds by the rule above it, so `dark` coloured every foreground and washed no row, and from the outside that is a palette being ignored rather than a rung being wrong. Reported from a real macOS pane 2026-08-03, where the giveaway was the `@@` header: at sixteen `#58a6ff` resolves to `LightCyan`, and it was cyan.

`TERM_PROGRAM` survives all of it, because it names the process that owns the screen rather than the entry the innermost layer chose to advertise. **`Apple_Terminal` is the one entry in that table that is not truecolour**, and it is why the table answers with a rung rather than a yes: Terminal.app has never drawn 24-bit, it rounds the sequences to its own palette, and claiming truecolour there is the over-claim this ladder's floor exists to avoid. An under-claim only looks flatter than it had to.

**`TERM` reads two more promises than it did, both terminfo's own vocabulary.** The `-direct` suffix is what the database calls direct colour, and a handful of terminals ship an entry naming themselves (`xterm-kitty`, `xterm-ghostty`, `alacritty`, `wezterm`, `foot`, `contour`, `rio`), none of which spells `256color` and none of which has ever had a 16-colour era. A terminal that merely *usually* has truecolour is not in that list: it belongs behind `COLORTERM` or `VIGIA_COLOR`, because the list is evidence about terminals someone checked rather than a claim about the ones nobody has.

**Windows detects truecolour, and 256 was not a safe default but a different wrong one.** What it was protecting against is consoles older than Windows 10 1703, which has not been a supported target for years. A reader on something genuinely older says so with `VIGIA_COLOR`, which is what the override is for.

**`TERM` only ever promotes.** On a Unix it is the last signal rather than the whole one; on Windows it describes a world where sixteen was the floor, so reading it as a demotion would take colours away from consoles that have them. An entry that promises neither rung yields nothing and leaves the floor where it is. The floor is sixteen because it is the one answer that is never actively wrong.

**Modifiers survive every rung, including none.** `NO_COLOR` asks for no *colour*, and bold is not colour. On a monochrome terminal it is the only distinction left.

**Quantising happens once, at startup.** The palette is walked a single time and the result stored, so the frame path draws with values that already mean what this terminal can show and I9 never sees any of it.

**What a wider palette does not buy is a wider ramp.** Mapping a 24-bit colour onto sixteen entries cannot keep nine syntax classes distinct: `#ffa657` and `#e3b341` are both yellow, and that is arithmetic rather than a choice. `ansi` is the answer for a sixteen-colour terminal and hand-picks all nine. What may **never** collapse at any rung that has colour at all is the diff signal, because §5 spends it on colour, and that has its own gate.

**A theme that does not parse is reported before the screen is taken**, which is the rule B5 already states for a path that is not a repository and holds here for the same reason: an error painted inside a TUI that then hands the terminal back is an error nobody sees. An unknown key is **refused rather than ignored**, with the line it was found on, because a silently dropped key is a theme that does nothing and "it was discarded" is the one explanation a reader cannot arrive at by looking at their screen.

**A path that is not a repository exits before the screen is taken.** That is the first half of B5: `Worktree::discover` and the opening walk both run ahead of `Session::enter`, so the failure reaches a terminal the reader can still read. An error painted inside a TUI that then hands the terminal back is an error nobody sees.


**The first signal from outside leaves the way the quit key does: the terminal goes back, nothing is printed, and the exit status is 0.** Nothing failed, so there is nothing to report, and a message printed after the terminal has come back would arrive on a shell prompt the sender was not looking at. **The first ask deliberately does not re-raise**, so a parent's `wait` reports *exited 0* rather than *killed by SIGTERM*, because from this program's point of view it was asked to stop and it stopped. If a script ever needs to tell "quit" from "killed" on the first ask, this is the line that changes. That is a choice about what leaving politely means rather than a concession to a dependency: `signal-hook`'s `low_level::emulate_default_handler` would re-raise, it is in a crate §6 already names, and the unique-crate count on all three tier-1 targets is unchanged by using it.


**The second signal takes the default disposition, so it kills the process and restores nothing.** It is the half that keeps the first half safe. Arming a handler takes away the guarantee the sender had before it: an unarmed `vigia` died on one `kill`, where an armed one turns that `kill` into a wake for a loop, and a loop wedged for any reason would swallow every further one. That process is unkillable short of `SIGKILL`, and reaching for `SIGKILL` produces exactly the wrecked terminal this invariant exists to prevent, so the graceful path has to have a floor under it. The consequence is stated rather than buried: **on the second ask the terminal is not restored**, `wait` reports killed by that signal, and the I8 row names it as a by-choice exclusion. *Ruled 2026-08-08, session ([#24](https://github.com/breferrari/vigia/issues/24)).*

Hover's own scope is narrower than the licence and is stated in §11.1 rather than derived from it, so widening the licence does not quietly widen the feature.


**The losing branch first, because it is the one that will be raised again.** On an idle monitor the pointer is more often parked than aimed: a reader typing in the agent's pane leaves the mouse wherever it was, and a lit row then means *the mouse happens to be here*. It is unevidenced in both directions and stays labelled so — §2 says interaction is rare or never and says nothing about where a resting pointer sits, while every mouse defect §11.1 records from use describes somebody **aiming**. The case for is that acknowledgment before action is most of what "snappy" means with a pointer, and that it costs an `Option` and a style.


**The gate that held the decline is the gate that survives it.** `crates/vigia/tests/input.rs::pointer_motion_over_a_laid_out_screen_is_still_no_action` stays green through the reversal because **hover is view state and never an action** (§11.1), so the assertion written to catch hover being built now keeps it out of the keymap. `crates/vigia/src/terminal.rs::every_command_is_the_escape_sequence_it_is_named_for` asserts the mouse bundle byte for byte, `?1003h` included, so the sunk cost above stops being true loudly rather than quietly. **The gate #123 asked for is still not written**: it wanted zero paints for motion over a non-target, and the honest count is one paint per motion batch until [#154](https://github.com/breferrari/vigia/issues/154) lands.


**B11 — a speaking rule: the diff's heading embedded in the border line between the regions.** *Ruled 2026-08-15, session: no, and on what the heading *is* rather than on when it is there.* ([#124](https://github.com/breferrari/vigia/issues/124).) The proposal is the terminal's oldest space-saver, `─ src/engine/watch.rs ● ────`, costed as a relocation that gains one body row. **A heading here is not a line of text.** It is a `Painter::file_row` drawing the kind letter, the path, the pulse, the heat strip, the sparkline and the counts through the one drawer §11.1 rules for both regions. Folding that into a border line has two branches and each spends something already ruled: **drop the glance elements**, and the pinned occurrence stops being what a list row is; or **keep them**, and the rule is a full glance row with dashes at the ends, which is not a rule. Neither branch is a relocation.


**The row it would reclaim is real, and more often than the decline first said.** `App::jump_to` lands every jump on the file's heading, and follow is on before anything is touched (I5), so the row is there at startup, after every jump and on a followed tick, and absent only after a relative scroll. [#257](https://github.com/breferrari/vigia/issues/257) narrows the followed-tick clause: on a tall diff being actively written, follow lands inside a file whose busiest change is not drawn from its heading. **On a monitor being watched rather than read the saving is available most of the time**, which is the strongest form of the case for adopting. In the frames between, the row under the rule is content, so a rule that spoke would be pinning a heading no longer otherwise on screen: a sticky heading, which is new state rather than a moved row.


**And B4 already answered stickiness the other way, by construction.** *The heading scrolls away, so you lose track of which file you are in* is why the pinned list exists at all. What makes that airtight is `Body::split`, which sets `rule: list > 0`: **the rule and the list are coextensive**, so there is no state anywhere with a rule and no list to answer the question the rule would be answering. **What this ruling does not rest on is counting carriers.** An earlier argument that the caret and the footer's `N/M` already carry the current file proves too much: §11.1 rules restatement *in* where it makes a map rather than a second opinion, and the three carry three different facts — a path, a row, an ordinal.


**What reopens it is not #125.** That proposal turns the list into a left rail, which is the same two regions rearranged and says outright *"Not the borders — #124 owns the chrome question."* A left rail has no horizontal rule at all, so #125 does not reopen B11, it **dissolves** it. What would reopen this is [#72](https://github.com/breferrari/vigia/issues/72) measuring the quantity the ruling turns on — how much of a real session is spent at a file boundary against scrolled inside one — and a reopening has to answer the structural objection first.


**Declining costs the picture nothing.** `assets/preview.svg` draws the rule and the heading as two separate rows, so the artifact and the shell already agree. `crates/vigia/tests/render.rs::the_rule_separates_the_regions_and_spans_the_pane` is what fails if the rule ever speaks: it asserts the rule row equals the rule glyph repeated across the pane at 40, 64 and 120 columns, so a title in the line reddens it on the first character.

**B12 — where the keymap lives once it outgrows the hint bar: a gestures sheet drawn over the pane.** *Ruled 2026-08-17, session: yes, on a ground that is structural rather than spatial. Shipped the same day. See §11.1.* ([#167](https://github.com/breferrari/vigia/issues/167); the build is [#206](https://github.com/breferrari/vigia/issues/206).) `?` toggles a centred, bordered sheet of the keymap, composited over cells that are already drawn.


*It buys space* is the weaker half of the case. The stronger half is that **an overlay is the only form of a cheatsheet that cannot move content**, and §11.1 has already ruled that a transient thing may not: the footer refuses to grow for a notice so that a file vanishing between being named and being read cannot jog a reader's diff. Every answer that lives in the footer runs at that rule from the other side, because more items is more width, more width brings the second footer line at more pane widths, and the second line takes a row off the diff. That route is not merely tight but **full**: [#121](https://github.com/breferrari/vigia/issues/121) measured the eighty-column footer at 40 columns of hints, 2, 19 of readouts, 2 and 13 of state, which is exactly the 76 that eighty leaves after the inset.


**The key is `?`, and the reference class is unanimous.** `btop`, `bottom`, `rtop`, `htop` and `less` all open help on `?` or F1, and `?` is unbound here, so nothing is overloaded. **`h` is refused**: it is a vi *motion* everywhere else and this pane has no horizontal scroll to give it.


**The sheet is not a mode, which is what reconciles it with B4.** No key changes meaning while it is up: `q` still quits, `j` still scrolls the diff behind it, a digit still jumps. B4 refused selection and focus because keys meaning different things depending on where focus sits is the defect. Here that is impossible by construction, so this is a third thing the pane can be **drawing** and not a third thing it can **be**.


**What it costs is that it covers the content this tool exists to show.** The answer is not that the cost is small but that it is **held by the reader**: a sheet is asked for and dismissed in the same second, where chrome that takes rows takes them from everybody on every frame.


**Centred rather than full pane**, so the header, the footer and the edges of the diff stay visible and a reader can see the tool is still alive behind it. A full-pane sheet hides the state a monitor exists for.


**It is retained state rather than a one-frame draw, and this is the constraint most likely to be missed.** The pane wakes on filesystem events, so an agent's write redraws the frame underneath the sheet, and a sheet that lived for one frame would be dismissed at random by somebody else's build. It follows `m`'s mechanism: a private `App` field, a `Chrome` field the drawers read, an `Action` the keymap resolves to. **It snaps** in both directions, which is §5.3's *snap, never ease* and not a preference: an animation needs a clock, and a clock needs the timer I1 forbids.


**It degrades on two axes, and both floors live in the layout rather than in the painter.** Width picks the spelling for the whole table. Height drops the mouse group before the keyboard group, then keyboard rows in their own drop order, leaving `f`, `m` and `?` last. **That order is a constant** ([#285](https://github.com/breferrari/vigia/issues/285)) rather than the table's own, because *from the top down* would have kept `q` and dropped `f` and `m`: the unguessable outlives the reflexive, which is why `f follow` is the hint bar's last rung standing. The floors belong to the body's split for the reason [#158](https://github.com/breferrari/vigia/issues/158) paid for once, where a width floor lived only in the drawer and a narrow pane reserved four rows for a region the painter then declined to draw. **Below its floor `?` still toggles and nothing is drawn**, which is what `m` does on a pane that cannot carry the band: a key whose effect is sometimes invisible is better than one that is sometimes not a key.


**I1 is untouched.** A reader pressing `?` is not idle, so I1's *0 wakeups while idle* does not reach this in either direction, and §5.3 prices ink at zero. `crates/vigia/tests/budgets.rs::a_frame_under_the_sheet_holds_the_frame_budget` times a frame with the sheet up on the pane the two-column rung arrives on, asserting the rung is the one it is named for so it cannot quietly become a second copy of the gate above it. `a_frame_under_the_roomy_sheet_holds_the_frame_budget` sits beside it since [#285](https://github.com/breferrari/vigia/issues/285), because the widest rung and the largest one stopped being the same rung: the roomy rung is what a full-screen terminal takes where the two-column rung is what a short one falls to, and it is the larger cell count.

**B13 — how a pane too small for the whole table reaches the rest of it: the sheet pages.** *Ruled 2026-08-24, session: `?` advances, and the last page closes it. Shipped the same day. Measured on `main` at 0.25.0 over every width from 20 to 140 against every height from 3 to 40, a 40 column pane reached **11 of 16** gestures at every height and a pane of 8 rows reached 4. A help sheet that silently omits help is a worse failure than a tight one, because the reader cannot tell it happened.


**`?` keeps exactly one meaning, and that is the whole of why paging wins.** Every route to a *scrolling* sheet breaks B12's reconciliation with B4: `j`/`k` scroll the diff, `Space`, `d` and `u` page it, and taking one back is the mode B12 refused. The one route that takes no key is the wheel, and a mouse-only answer does not reach a keyboard reader on exactly the narrow pane where they are likeliest to be inside `tmux` or over `ssh` with no mouse reporting ([#188](https://github.com/breferrari/vigia/issues/188)). A scrolling sheet would also need its own bar, which is furniture inside furniture. **Paging costs one key that was already the sheet's**, and on every pane whose sheet is one page it is the toggle it has always been.

Alone it does not meet the gate, because the gestures stay out of reach. As the page counter in the title bar it is the honest half and costs no content row — a say-so taking a row would spend it on the gestures it was apologising for.

A sheet that cannot say how much of the table it is hiding is the state this ruling exists to end, so declining to draw one is the same answer `m` gives on a pane that cannot carry the band.

**B14 — whether the left rail arrives on its own or is asked for.** *Ruled 2026-08-24, session: it is asked for, on `r`, and the default is the strip above the diff at every width. Shipped the same day. See §11.1.* ([#295](https://github.com/breferrari/vigia/issues/295).) [#252](https://github.com/breferrari/vigia/issues/252) shipped the rail arriving at 134 columns on its own, and what that meant for a reader is one number: at 133 the diff plans against 129 columns and at 134 against 60. Widening a pane past a threshold nobody chose more than halved the thing this tool exists to show. **The derivation of 134 is not reversed and is not touched** — both regions read one glance ladder, so splitting a pane costs each half what the whole had. What it decides now is where the gesture can be honoured.


**It is not a mode**, which keeps it out of B4's refusal the way B12's sheet is: no key changes meaning while the rail is up, and the list is still not navigable, merely somewhere else. B6 keeps it a keystroke rather than a flag. Below 134 it changes nothing drawn and eats no gesture, and the request survives a pane too narrow to honour it, so narrowing and widening again returns the rail rather than the question.


**The branch not taken: leave it automatic and add an opt-out.** Rejected because it inverts the cost. The reader who has not thought about it is the one whose diff goes from 129 columns to 60, and the discovery path is the same gestures sheet either way. If the sheet is how a reader learns the gesture whichever direction it points, the default should be the one that changes nothing.


**`r` is a fourth gesture a reader cannot guess at, beside `f`, `m` and `?`, and `SHEET_KEEP` keeps three**, so one of the four has to go first. `r` is given up at rank eight of `DROP_ORDER`. **The reason first written for that was false and is corrected here**: the rank that would drop it needs a width below thirty, and below thirty no sheet is drawn, so the reorder is **unreachable on every pane that draws**. What it is is a defensive ordering — `sheet_tables` asserts the keep-set is `f`, `m` and `?`, the untouched order would have dropped `f`, and if a future rung ever reaches that depth `r` is the right one to lose, because it is the only one of the four that needs 134 columns.


**B15 — whether the left and right arrows move between changed files.** *Ruled 2026-08-24, session: yes, as aliases of `n` and `p`. Shipped the same day. See §11.1.* ([#296](https://github.com/breferrari/vigia/issues/296).) The capability already existed and this is a naming fix: `Action::File` already moved the caret, and a reader who reached for an arrow got `Shift+↑`'s list scroll instead. Vertical keys move inside the diff, horizontal keys move between files. One action, one arm, so the two directions cannot drift.


**What it spends, since the arrow pair is scarce.** The one feature that would want these keys back is a horizontal pan, which §11.1 declined as *"a key and a mode this spec does not name"*. B19's wrap toggle needs no arrows, so nothing open is blocked. If a pan is ever ruled in it takes `h` and `l`, or it takes these back; that is a sentence here rather than a reservation nobody can see.


**The sheet names them at the wide spelling only, and that is arithmetic.** The tight keyboard keys field is eleven columns and the arrowed cell is thirteen, so carrying the arrows there would cost panes of 35 and 36 their twelve gestures. Two columns of pane losing gestures to an *alias* is the wrong trade, and dropping aliases at the tight spelling is what `q  Esc  Ctrl+C  Ctrl+D` already does.


**B16 — whether the diff can be pinned to one file, and what every other key means while it is.** *Ruled 2026-08-25, session: it can, on `s`, off by default, and every key keeps its meaning over a smaller subject. Shipped the same day. See §11.1.* ([#297](https://github.com/breferrari/vigia/issues/297).) Asked for from the pane: an agent works inside one file for minutes at a time, and a continuous diff makes the reader hold two positions at once — where they are in the file and where they are in the changeset. Pinning removes the second. It is `f`'s sibling one step over: follow decides which file the pane goes to, this decides how much of the rest of the tree the reader's own scrolling will reach once it is there.


**It is not a mode.** No key changes meaning while it is on, and the list is still not navigable: it is the same map, addressing a diff that has been narrowed. Four questions had to be ruled and the answer to all four is one sentence, *one subject, narrowed*.


**`g` and `G` are the first and last row of this file.** The alternative — keeping the changeset and jumping out of the pinned file — would make two keys mean something different while the pin is up, the exact thing this ruling claims not to do. **`G` reaching a real last row rather than a heading is affordable here and nowhere else**, and that asymmetry is worth stating because it looks like an inconsistency: unpinned, finding the diff's last row means adding up every file's height, which is the read I4 forbids; pinned, the subject has been diffed by definition and the row is free.


**Follow still moves between files.** `f` and an automatic follow are explicit requests to be moved, where the pin is about what a reader's own scrolling reaches, so pinning is not a manual scroll and does not disengage follow. The pairing is the gesture's best case rather than an edge of it.


**The heading of the pinned file draws, as the block's first row.** It carries the pulse, the heat strip, the sparkline and the counts, so dropping it as redundant would take the glance elements off exactly the screen built to watch one file. **The branch not taken is a sticky heading**, refused rather than declined: it costs the diff a permanent row, it is a second answer to a question the caret and the bold path already answer, and it is a larger claim than a gesture that only narrows what the walk reaches. If a heading scrolling away turns out to be what a reader misses, it reopens as its own ruling rather than as an amendment to this one.


**The scrollbar measures this file, and so does a drag on it.** Both read the pinned file's span and neither counts the changed set. A bar drawn from one total and dragged against another agrees at both ends of the track and nowhere in between, so a gate asserting the ends would pass against it: that is a recorded lesson from the row-exact bar, and the gate walks the middle.


**What it costs the frame path is negative, which is why no budget argument was needed.** I4's single exception is the diff's height, counted for every changed file once per tick and the only thing in the frame path not bounded by the window. A pinned frame skips it: the total is the pinned file's span, which the walk recorded on its way past. The gate asserts the unpinned frame counted something first, because a zero over a fixture with nothing to count is not evidence.


**Toggling settles rather than restores.** From a screen already inside one file, a pin and an unpin is identity. From a screen straddling two it cannot be: the pin rests the pinned file's last row on the bottom, which is a pager's answer and the one the reader was already looking at most of. **The resting is the walk's own back-up for a short screen, and the pin licenses it as a term in the guard rather than as a flag it writes.** Left to whatever placed the position, it held for a reader who had scrolled there and not for one who had dragged the bar; written as a flag, it leaked past the pin and moved a reader who had jumped onto a short tail and toggled twice. A term has neither failure. What is promised is that every pair after the first is identity, so the gesture is a toggle rather than a ratchet.


**Two gestures the pane answered and the sheet did not name, ruled 2026-08-25, session** ([#288](https://github.com/breferrari/vigia/issues/288)). `README.md`'s Mouse table taught the **hover mark** and `MOUSE` did not carry it; the sheet's own **close control** was named in neither, which is worse, because `✕` is a clickable control this element draws and the only way to learn it was one was to rest a pointer on it. Both are rows of `MOUSE` now.


**A configuration file carrying the pin as a default is asked for on the same issue and is not ruled here.** It is a B6 question and gets its own issue ([#306](https://github.com/breferrari/vigia/issues/306)), its own ruling and its own change.


**B17 — nothing shows staged files, so an agent that stages its own work empties the pane.** *Ruled 2026-08-25, reader: `a` draws the staged run beside the unstaged one, as two labelled runs with the staged rows marked, off by default. Shipped the same day. See §11.1 and §5.3.* ([#313](https://github.com/breferrari/vigia/issues/313).) Reported from the pane. §11.1's opening contract excluded staged content *by construction*, so a worktree with everything staged had no changes by this tool's definition and plenty for `git`, and B3's empty state said `no unstaged changes` — true of a clean tree and of a fully staged one alike.


**A union rather than a swap, and that is the reader's ruling rather than the derived one.** Swapping which comparison is drawn is one walk, one diff and no new channel, and it was what this was planned as; it was rejected because neither view alone answers *what has the agent done since the last commit*, which is the question a monitor beside an agent exists for. Both runs are drawn, unstaged first, and **a path changed on both sides appears in each** — they are two diffs of two different pairs of bytes, and one `MM` row would show a third thing belonging to neither.


**`a`, for *all***. `i` for *index* was the proposal while the toggle was expected to swap, and it adds.


**And it walks on the keypress, which is the one thing on this map that does.** The other view toggles rearrange rows the frame already holds; this one changes what the frame *contains*, and `Frame::advance` otherwise runs only on a tick. Found in a live pane before it shipped: the reader pressed `a`, the header read `0 staged` over a worktree holding two staged files, and the pane drew what it drew before — until something happened to be written, which on a tree an agent has finished with may be never. I1 is untouched, because this is work on a wake the reader caused rather than a clock.


**What it costs, measured before it was allowed to decide anything.** The second walk is `HEAD^{tree}` against the index: it reads no file, allocates one change per path and nothing per line, at **430µs against 2.15ms** for the index-worktree walk beside it on a 200-file fixture. A staged diff is two object ids compared, so it spends no syscall and its cached answer needs no fingerprint and no settle margin — two ids unchanged names the bytes outright.


**It repaid a watch defect that predates it.** The `.git` arm admitted `index` and nothing else, which was the whole answer while there was one comparison. `git reset --soft` writes `refs/heads/<branch>` and **not** `index`, so the staged run would have drawn a comparison against a commit that was no longer `HEAD`, indefinitely, with nothing saying so. `HEAD`, `refs/heads/**` and `packed-refs` are watched now; `refs/remotes`, `refs/tags`, the reflogs and the object database still wake nothing, so a `git fetch` costs no frame. The same gap already staled the empty state's branch name after `git switch -c`.


**The runs are named in the list and marked on every row, and the two halves are not redundant.** The map names the runs, because a heading is worth a row there; every row carries its own gutter mark, because the stream is a continuous scroll and a heading a reader has scrolled past says nothing. A separator in the *stream* was in the plan and is refused: every row there is a row in the height arithmetic `span_of`, `block_of`, `gap_rows` and `Frame::height` share, which the diff's scrollbar, the scroll clamp and I4's counting bound are all computed from, so a label row there is a change to the scroll model bought to repeat what the mark already says.


**B18 — what a monitor-class pane may draw in 2026.** *Ruled 2026-08-25, reader: the vocabulary expands to everything the research priced, ruled at the checkpoint rather than by rows.
